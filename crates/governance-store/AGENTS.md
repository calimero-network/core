# calimero-governance-store - Local Group-Governance Apply Pipeline

Signature/nonce-checked apply of signed group and namespace governance ops into per-group RocksDB state, plus the acked-broadcast machinery that publishes them to peers.

## Package Identity

- **Crate**: `calimero-governance-store`
- **Entry**: `src/lib.rs`
- **Key deps**: `calimero-context-client` (`SignedGroupOp`/`SignedNamespaceOp`/`GroupOp` wire types + `AckRouter`), `calimero-store` (typed RocksDB column families), `calimero-op` / `calimero-op-adapter` (unified causal-log `Op`/`OpPayload`, decoded from applied ops), `calimero-dag` (`CausalDelta`), `calimero-node-primitives` (`NodeClient`, gossip sizing constants)

Extracted from `crates/context/src/group_store` in #2307 (closes epic #2300); `calimero-context` still re-exports this crate's public surface through compat shims so external call sites did not need to change imports.

## Mental Model: Apply Pipeline and Broadcast

**Two apply entry points, one shared mutation core.** A group op reaches local state through either `apply_local_signed_group_op[_at_cut]` (direct group-DAG apply - local replay, tests) or `NamespaceGovernance::apply_signed_op` (the gossipsub-receive path, which unwraps an encrypted `NamespaceOp::Group` first). Both funnel into `apply_group_op_mutations`, which builds a `GroupApplyCtx` and calls `ops::group::dispatch`. `dispatch` is a flat match over every `GroupOp` variant, each handled by its own `ops/group/<variant>.rs` file - this is why the module list above is so long: the file-per-variant split keeps each apply handler's authorization + mutation logic independently reviewable and testable, instead of one giant match arm.

**Apply order per op**: validate size bounds (`op.validate()`, `MAX_PARENT_OP_HASHES`) -> verify Ed25519 signature -> check the per-signer nonce window (dedup/replay guard, short-circuits with `Ok(())` on a stale nonce) -> run the mutation (`apply_group_op_mutations`) -> record the nonce -> idempotent op-log append keyed by content hash (a second dedup gate covers the case where `apply_group_op_mutations` re-ran on a DAG replay after a crash between the nonce-window write and the op-log append) -> advance `dag_heads`/`sequence` -> flush any `OpEvent`s queued during apply. Every handler MUST be idempotent on re-apply (e.g. `MemberAdded` is an upsert, never an insert-or-error) because this replay-then-dedup sequencing re-runs the mutation before checking whether the op was already logged.

**Authorization is resolved at the op's causal cut, not live state.** `AtCutAuthorizer` (`authorizer.rs`) is the seam: this crate defines the trait and calls it from `GroupApplyCtx`'s admin/capability gates, but the real implementation (backed by the unified projection folded up to the op's `parent_op_hashes`) lives in `crates/context`, which depends on this crate - so the dependency is inverted through the trait. `None` from any `AtCutAuthorizer` method means "not yet decidable here" (the projection hasn't folded that far), and every method contracts to return `None` on an empty cut. `LiveFallbackAuthorizer`/`LIVE_FALLBACK_AUTHORIZER` is the default no-op implementation used by plain `apply_local_signed_group_op` (tests, replay) where no projection context is wired up. When the cut genuinely can't be resolved, the apply returns `ApplyError::AuthorityUndecidable` rather than guessing from live rows - guessing would make the verdict depend on this replica's fold progress and could silently diverge two peers forever; `AuthorityUndecidable` instead stalls (head not advanced, nonce not burned) until the missing ancestry arrives and the op is retried.

**Post-apply, state hashes are compared, never enforced.** `MemberRemoved`/`MemberLeft` carry `expected_group_state_hash` / `expected_context_state_hashes` that the signer precomputed before applying locally. `verify_post_apply_state_hashes` recomputes the receiver's own post-apply hashes and logs a structured warn on mismatch - it never rolls back the apply (the signed op is already valid) or errors. A mismatch signals cross-DAG divergence to be healed by reconcile-via-anchor sync, not a failure of this op.

**Broadcast is acked but not blocking.** `GroupGovernancePublisher::sign_apply_and_publish[_removal|_rotation]` signs, applies locally, encrypts as `NamespaceOp::Group`, and calls `publish_and_await_ack_namespace` (`governance_broadcast.rs`), which publishes on the `ns/<namespace_id>` gossipsub topic and waits (per-op-kind timeout: cheap/member-change/heavy) for `min_acks` distinct `SignedAck`s from namespace members. The local apply already committed before publish is attempted - a timeout or zero-ack result (`PublishReadiness::Degraded`/`Solo`) is not a failure signal, just "no one confirmed yet, sync will catch peers up eventually." Only `Publish` (gossipsub itself rejected the message) and `NoAckReceived`-with-`min_acks>0`-and-zero-mesh-peers are hard errors.

**The unified causal log rides along, not behind.** `unified_op_decode::decode_*` builds a `calimero_op::Op` from the just-applied `SignedNamespaceOp`/`GroupOp` and persists it to the op-store on the SAME `Store` handle as the gov-DAG write, in this crate (not in `calimero-context`, which can't see the projection but does consume these decode functions) - so the op-store can never lag the governance DAG it mirrors.

## Invariants and Gotchas

- **`ACCOUNT_ROOT_LOCK` and `NODE_DEVICE_MINT_LOCK` no longer nest, and it should stay that way.** Only `provision_account_root` and `try_import_account_root` take the root lock, and neither is reachable from a path holding the mint lock: provisioning happens in `merod init`, and import requires the node stopped. `ensure_enrolled` takes `NODE_DEVICE_MINT_LOCK` and calls `require_account_root`, which is a pure read and takes nothing. This used to be an ordering rule — `ensure_enrolled` reached the root lock through the lazy-minting `ensure_account_root`, so mint-then-root was fixed and reversing it was an ABBA deadlock. Splitting the mint out of the read removed the nesting entirely. Do not reintroduce it: nothing holding the mint lock should call a function that acquires the root lock.
- **A forced account-root import must release the replaced root's device rows.** A `NodeDeviceIdentity` row is a singleton — one device per node, serving every namespace — and `stored_identity_still_serves` refuses to replace a *linked* row naming a different account - so rows left behind after a forced import make `ensure_enrolled` refuse under the newly imported root, advising a revocation that needs the discarded key. Only rows whose account re-derives from the replaced root are dropped: a paired row names another node's root account and dropping it would strand a device that still opens scope keys.
- **Serialize per group, not globally.** `apply_local_signed_group_op` is documented as requiring callers to serialize access per `group_id` (the node relies on the single-threaded actix `ContextManager` actor for this). Concurrent calls for the *same* group from multiple threads are not safe and can mint duplicate sequence numbers; different groups are independent.
- **`parent_op_hashes` are not validated against current `dag_heads`.** An op may cite ancestors further back in the DAG - this is fine because authorization is checked against the op's own causal cut (via `AtCutAuthorizer`), not against `dag_heads`, and `DagStore` topologically orders independently.
- **Every `GroupOp`/`RootOp` handler must be idempotent on re-apply.** The replay-then-dedup ordering in `apply_local_signed_group_op_at_cut` re-runs the mutation before the op-log dedup check fires; a handler that errors on "already applied" (instead of upserting) leaves the nonce window unpersisted and the node stuck retrying forever.
- **`OpEvent`s are dropped, not re-emitted, on a deduped replay.** If the op-log already contains the op's content hash, `pending_events` from the re-run mutation are discarded rather than re-notified - firing them again on every ordinary duplicate (re-gossip, DAG replay) would be worse than the rare one-time-signal loss on a crash landing exactly between op-log append and event flush.
- **`AtCutAuthorizer` methods must return `None` for an empty cut.** A genesis op has no causal context to resolve against; an implementation that returns `Some` there could falsely reject an op a live admin legitimately signed.
- **`ensure_rotation_is_publishable` runs before any mutation, not after.** A `MANAGE_MEMBERS`-capability (non-admin) removal from a group encrypted under its own key would mint a rotation peers reject (rotation requires admin), leaving this node's peers permanently unable to decrypt its future ops. The publisher fails closed by refusing the removal outright, before the local apply happens - bailing afterward would leave the removal committed but never published.
- **`AbsorbRepository` buffers verbatim bytes, never deserializes.** A future-schema (newer binary version) straggler entity is stored as opaque bytes keyed by the *sender's* schema/`bytecode_id`, not interpreted by the receiving (older) binary - protects against corrupting or rejecting bytes the receiver's schema can't parse yet.
- **`calimero-projection` is a dev-dependency for fold-equivalence cross-checking** (the unified projection's membership fold against this crate's live `MembershipRepository` resolver over the same op sequences) - `serial_test` is also dev-only, needed because the `op_events` tests observe a process-global broadcast bus that would cross-talk under parallel test execution.
- **A relayed join is gated on the op INSIDE the seal, never the envelope.** `NamespaceOp::RootRelaySealed` carries the joiner's whole `SignedNamespaceOp`, sealed under the namespace key, with the envelope signed by the relaying admitter. `apply_signed_op` verifies the envelope (who carried it) and `open_relayed_join` verifies the inner signature (who joined) — and the apply arm hands `apply_root_op`/`root_op_side_effects` the **inner** op, so `join_op_proves_ownership` compares the joiner's key against the joiner's credential. Passing the envelope there instead refuses every relayed join with "signer does not hold a credential for member". `open_relayed_join` is the single place the inner checks live (namespace match, bounds, signature, non-zero nonce, join-only); the receive path and the key-delivery retry both call it, so a replayed relay is authenticated exactly as an arriving one. Replay is guarded on the inner op in TWO places, because the envelope's content hash cannot serve as one: the op log answers for a join that also arrived in the clear (it is stored under its own hash), and the per-signer nonce window answers for one that only ever arrived relayed. Dropping either half lets a member re-seal an old join and resurrect a removed member.
- **Never read a group's own keyring to find the key that covers it — go through `key_covering_group`.** One predicate decides which key covers a group, `CapabilitiesRepository::is_open_chain_to_namespace`: every ancestor `Open` up to the namespace ⇒ the **namespace** key; anything else (a `Restricted` subgroup, an `Open` one behind a `Restricted` ancestor, and the root itself, which the predicate answers `false` for against itself) ⇒ the group's own key. The writers have always agreed on this — `execute`'s state-delta path, `GroupGovernancePublisher`, `pending_rotation` — and `key_covering_group` is the one helper readers share with them. The trap is that a group's own keyring is never *empty*: `create_group` mints a key row for every subgroup at birth whatever its visibility, because a later `SubgroupVisibilitySet -> Restricted` establishes no key of its own and an apply handler could not mint one consistently across peers, so that row is what the flip turns into the real key. On an Open chain it is a key **nothing is encrypted under**, which makes serving it strictly worse than serving nothing: the recipient records "key present" and then decrypts nothing, with no error on either side. That is why the join responder refuses an Open-chain request instead of answering it, and why `groups_member_but_keyless` skips Open-chain groups — the namespace key they need is not one a subgroup-only member may ask for.
- **A join whose invitation targets a subgroup travels sealed, as `NamespaceOp::RootSealedForGroup`, and a cleartext one is refused at apply.** It is the one root op a joiner can seal for itself: a subgroup-targeted invitation's bundle delivers that group's key and `join_group` stores it before publishing, so the joiner holds it — it never holds the namespace key, which is why `RootSealed` cannot carry this op and `root_op_is_sealable` still answers `false` for `MemberJoined` / `MemberJoinedAt`. The refusal lives in `apply_signed_op` rather than in `root_op_is_sealable` because that function is `const` and sees only the op, which cannot tell whether the invitation's `group_id` IS the namespace root; a namespace-root joiner holds no key and must still publish in the clear. The `group_id` in the envelope is cleartext on purpose — the receiver needs it to know which keyring resolves `key_id` — and the encrypting group comes from `key_covering_group`, so an Open chain seals under the namespace rather than under a row nothing encrypts to. **Authorization is subgroup-scoped:** the readers are that subgroup's admins and any admitted TEE node, and that set suffices because every invariant a join touches is already written by ops sealed to it — deny-list and re-entry rows come from `MemberRemoved` / `MemberLeft` (`GroupOp`s), and `count_admins` is per-group. Adding a reader is not needed and a dual seal was rejected. When adding a reader of a sealed root op, resolve the keyring from the op's own `group_id`: looking every shape up in the namespace keyring parks a subgroup join forever even on a peer that holds its key, which is the bug that arm was written to avoid. **And the envelope carries a join and nothing else, checked on every path that opens it** (`ensure_subgroup_sealed_carries_a_join`). Without that restriction the variant is a general-purpose envelope for any root op that opens with a *subgroup* key, which is a privilege widening rather than a looser type: `RootOp::KeyDelivery` stores the delivered key unbound to any signed op, so carried here it let a plain `Member` of one Restricted subgroup write a key of its own choosing into a co-member's keyring for an unrelated group. Reachable only via `RootSealed` it needed the namespace key. That escalation is now independently blocked by the trusted-anchor gate on delivery (next bullet), but this restriction is not redundant: it is a property of the carrier, which must not become a general-purpose envelope for root ops, while the gate is a property of one op. The same guard pins the envelope's `group_id` to one of the two values `key_covering_group` can emit for that invitation — the target, or the namespace root covering an Open chain — because the sealing group decides which peers authorize the join and so is not the joiner's to choose freely; it is checked against those two values rather than re-derived, since re-deriving reads local visibility rows and two peers mid-flip would disagree about admissibility.
- **A `KeyDelivery` is applied only when its signer is a trusted anchor of the group it delivers for** (`MembershipRepository::anchor_device_keys`, checked in `root_op_side_effects`). The op's own handler is a deliberate no-op, so the side effect *is* the op, and it used to run for any signer at all. The envelope apply is called with `expected_key_id: None` and that is the truth rather than a shortcut — a `KeyDelivery` names no `key_id`, so no hash can check the bytes it carries — which makes every delivery the *unverifiable* case. The direct-pull path had already ruled on those: `key_servers_allowed` accepts an unverifiable key from a trusted anchor and from nobody else, refusing outright when no anchor is known. This path applied that rule to nobody; `check_sender` only pins `envelope.sender` to `op.signer`, which a self-signed op satisfies by construction, so provenance stood in for authority. Any namespace-key holder could then name any group in the namespace and have a key of its own choosing adopted — minting the wrap needs no secret beyond the victim's PUBLIC identity key — and it did not merely sit unused: `store_key` writes at epoch 0 and `key_rank` breaks epoch-0 ties on local `insertion_seq`, so it outranked the real key and became the one the victim encrypted under, then propagated as that group's covering key to later joiners. **Three properties to preserve when touching this.** First, the anchor set is the group's own *or*, while the group's own governance has not folded, the **namespace's** (`key_delivery_anchors`). A delivery legitimately races ahead of the `GroupCreated` that writes the group's meta, parent edge and member rows — `add_group_members` produces exactly that, and it is the same stranded case the cross-namespace pin allows for — so the group's anchor set is empty and refusing on an empty set would refuse the deliveries the op exists for. The fallback is not a guess (the op arrived on this namespace's topic, sealed under its key) and it is not a hole (a plain member is not a namespace anchor either, which is what the paired refusal test pins, since an attacker always picks the group id and would otherwise just name an unfolded one). Once `GroupCreated` folds, the group's own anchors decide again, which keeps the boundary #3858 drew for a Restricted subgroup. Second, a refusal is a *skipped effect*, never a DAG failure: the delivery is best-effort (an error would orphan every later op) and `recover_missing_group_keys` is its durable retry enforcing the same rule. And the lookup has **three** outcomes, not two: authorized, refused, and "could not tell". A store error is neither propagated (this arm's errors never are — a failed apply orphans every op after it, and unlike `apply_key_rotation`, which must propagate because a dropped rotation leaves a node unable to read later ops, delivery has the pull behind it) nor folded into the refusal, because "not an anchor" is a verdict about the signer and an I/O failure is no verdict at all; logging one as the other sends an operator hunting a permissions problem that does not exist. The anchor set deliberately includes `ReadOnlyTee` as well as `Admin`, because an admitted TEE node legitimately holds and hands out keys; `device_link` publishes a delivery for the namespace root and is unaffected, since that op is sealed under a key the new device does not hold (it is a causal record, and the device pulls the key instead). Compare `apply_key_rotation`, which gates on `is_admin` at the op's cut *and* binds content to `new_key_id`: same file, same job, both halves present. See #3871.
- **`PLACEHOLDER_ADMIN_IDENTITY` (`[0u8; 32]`) is a safe sentinel, not an `Option` dodge.** It decodes to a torsion point outside the Ed25519 prime-order subgroup, so no real keypair's public key can ever equal it - the genesis established-check can rely on the cheap `[u8; 32]` comparison without risking collision with a legitimate admin key.
