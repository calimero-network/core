# calimero-app-host - the host core of `calimero:app`

## Package Identity

- **Crate**: `calimero-app-host` (`publish = false`, prototype); engine-neutral, no wasmtime
- **Entry**: `src/lib.rs`; `core.rs` (`HostCore`, `RunLimit`), `entry.rs` (`entry_bytes`), `action.rs` (`ActionHost`, `HttpHost`, `subcall_key`), `blobs.rs` (`BlobHost`, `blob_refs`, `BLOB_REF_TAG`), `search.rs` (`SearchHost`, `SearchQuery`), `files.rs` (`Files` provider traits, limits, soft-error strings, `NoFiles`, `MemoryFiles` under `testing`), `core/file_ops.rs` (the `files_*`, `writer_*`, `reader_*` host calls), `fuel.rs` (the host-work fuel table, `MAX_SEARCHES_PER_RUN`), `engine.rs` (`Engine`, `Prepared`), `abi.rs`, `overlay.rs`, `state.rs` (`StateView`, `stored_key`), `time.rs`, `types.rs`
- **Docs**: [Application execution](https://calimero-network.github.io/core/protocol/execution/) ([Storage](https://calimero-network.github.io/core/protocol/execution/#storage), [Time and randomness](https://calimero-network.github.io/core/protocol/execution/#time-and-randomness)), [The env API](https://calimero-network.github.io/core/build/host-functions/)

## What This Crate Does

`HostCore` is the only code that reads or writes app state, applies policy, or serves time and randomness. An `Engine` maps the WIT world one-to-one onto `HostCore` methods (`storage_*`, `range_open/next/close`, `rebuild_*`, context, `emit`, `xcall_send`, `blobs_*`, `files_*`, `writer_*`, `reader_*`, `action_*`, `wall_ms`, `monotonic_ns`, `random_fill`, `log`) and returns `HostCore::finish(..)` as the `Outcome`.

## Contract

- `HostCore` is `Send + 'static` (a wasmtime `Store`'s data): `HostCore::new(app_id, Arc<dyn StateView>, applied_index, Invocation, Arc<dyn Directory>)` owns or shares its inputs and returns `Err(InvalidInvocation)` for a `Timer` without `TimerCtx` or a `TimerCtx` on any other kind.
- Every refusal is `Err(HostDenied)`; the engine turns it into `Trap(HostDenied)`.
- State writes (`put`, `delete`, `add`), `emit` and `unique_id`: call, timer, init, xcall delivery only. Reads: everything but actions. `rebuild.*` is refused in this milestone.
- Actions: `start_action` in calls and timers queues an `ActionStart` (key `a.<term>.<seq>.<n>` from the run's unique ids, at most `MAX_STARTED_ACTIONS`) on `Outcome::actions`, emptied unless `Ok`. In `kind = action` with `HostCore::with_action(Arc<dyn ActionHost>)`: `action_key`, `action_view`, `action_call` (at most `MAX_ACTION_SUBCALLS` per run; each call's key `subcall_key(action key, method, args, occurrence)`, the occurrence counting identical (method, args hash) calls in the run); elsewhere `HostDenied`. Storage stays off in actions. `http_send` in actions, calls, timers and deliveries (`HostDenied` in views, `init`, migrations), at most `MAX_HTTP_REQUESTS` and `MAX_HTTP_BODY_BYTES`, through `HostCore::with_http(Arc<dyn HttpHost>)` (default `NoHttp`: refused); a logged run records each exchange (`HttpExchange::record`, bodies cut to `MAX_RECORDED_BODY_BYTES` with their lengths) on `Outcome::http`, kept whatever the status. `Budget::action()`: `ACTION_WALL_CLOCK` (10 s). `MethodKind::Action` (`"action"`) and `MethodAbi::action_only` (`allowAction`) come from the ABI.
- xcall: `xcall_send` in calls, timers, `init` and deliveries (`HostDenied` elsewhere) queues an `Xcall` on the outcome (`Outcome::xcalls`, emptied unless `Ok`); soft errors `XCALL_TOO_MANY` (over `MAX_XCALLS`, 100) and `XCALL_BAD_TARGET` (an empty or over-`MAX_XCALL_NAME_BYTES` app or method, a `__` method); app, method and args count toward `MAX_RUN_BYTES`. `MethodAbi::allow_apps` / `allows_app` read `allowApps` (`"*"` = any app).
- Synchronous xcalls (`xcall.rs`): `HostCore::with_xcall_host(Arc<dyn XcallHost>)` (default none: every one is the WIT error `XCALL_SYNC_UNAVAILABLE`). `xcall_call` in calls, timers and actions, `xcall_view` in those and views (`HostDenied` elsewhere: a delivered xcall, `init`, a migration make none, so chains are one hop). Soft errors: a malformed target (`XCALL_BAD_TARGET`), the app itself (`XCALL_SYNC_SELF`), more than `MAX_SYNC_XCALLS` (16) per run (`XCALL_SYNC_TOO_MANY`), args over `MAX_SYNC_XCALL_ARGS_BYTES`, an answer over `MAX_SYNC_XCALL_RESULT_BYTES`, and the host's own failure. A call's key is `sync_xcall_key(host.key(), app, method, args, occurrence)` (`xc:` + hex SHA-256, length-prefixed parts; the occurrence counts identical (app, method, args hash) calls in the run), so a re-run of the caller replays the target's answer. `xcall_batch(&[XcallRequest])` (WIT `xcall.batch`): the same per-request checks and soft errors, in place; `HostDenied` for a batch where views are refused, or with a call where calls are; each request that passes counts, and a batch that would pass `MAX_SYNC_XCALLS` answers `XCALL_SYNC_TOO_MANY` for all of them and counts none; calls keyed in list order with the same occurrence counter, so a batch is keyed as the same xcalls one after another; the passing ones go to `XcallHost::batch(&[SyncXcall])` together (default: one after another; the node's runs them at once), answers bounded as `call`'s; an empty batch answers nothing.
- Blobs: `HostCore::with_blobs(Arc<dyn BlobHost>)` gives a run the node's record of the app's blobs (default `NoBlobs`: none). `blobs_info` and `blobs_grant` in every kind but actions and migrations (`HostDenied`); `info` of an unknown or malformed id is `None`; `grant` refuses an unknown blob and a TTL outside 1..=`MAX_GRANT_TTL_SECS` (86,400) and expires at `wall_ms() + ttl`. `storage_put` refuses (`HostDenied("unknown blob")`) a value holding a `BlobRef` (CBOR tag `BLOB_REF_TAG` = 0xCA1B around 32 bytes, found by `blob_refs`) to a blob `info` does not know; the node counts the references at apply.
- Host fuel (`fuel.rs`), always on: the engine takes `FUEL_HOST_CALL` (1,000) as each host call starts; the core adds the rest to what the run owes, the bytes it was handed first, before any check (so a refused or denied call pays for them; a denial is still `HostDenied`), then the work: `FUEL_STATE_ACCESS` (1,000 more) per storage access, range open and range batch, `FUEL_PER_RANGE_ENTRY` (200) per entry, `FUEL_PER_BYTE` (1) per byte handed or moved, and for a search that runs `FUEL_SEARCH_QUERY` (4,000 more) + `FUEL_PER_SEARCH_MATCH`·total + `FUEL_PER_SEARCH_HIT`·hits + `FUEL_PER_SEARCH_BYTE`·hit bytes (the `crates/search/bench` fit; 1 fuel ≈ 1 ns). A cursor's, reader's or writer's drop owes `FUEL_HOST_CALL` itself (drops are not wrapped). The engine takes it with `take_host_fuel()` as each call returns. A write refused with a run limit (the soft `RunLimit`, WIT `put-checked`, `delete-checked`, `add-checked`) pays for its bytes too. Regressions: `a_read_owes_what_the_fuel_table_says`, `refused_and_denied_calls_owe_for_the_bytes_they_were_handed`, `writes_refused_with_a_run_limit_owe_for_the_bytes_they_were_handed`.
- Search (spec section 7): `HostCore::with_search(Arc<dyn SearchHost>)` (default `NoSearch`: every table answers that it declares no search fields). `search_query` in views only (`HostDenied` elsewhere); a limit outside 1..=`MAX_SEARCH_LIMIT` (100) or a query over `MAX_SEARCH_QUERY_BYTES` (256) is the WIT result's error, as is the host's own refusal and a search past `MAX_SEARCHES_PER_RUN` (32, `SEARCH_TOO_MANY`). The count is per request, a `SearchBudget` shared by clones: `with_search_budget` gives a run its request's (the node passes a sync `xcall_view` target its caller's, and a view forwarded to a peer takes the rest as `searchesLeft`), `search_budget()` hands it on; the default is a fresh one. Regression: `searches_are_capped_per_run_and_owe_fuel`. `Abi::search` is `state.search` (table to fields; empty tables left out; a non-string field is `BadAbi`).
- Files: `HostCore::with_files(Arc<dyn Files>)` sets the provider (default `NoFiles`: nothing exists, `create` is `"files are not enabled"`). `files_create`, `writer_write` and `writer_finish` are logged-write kinds and compute runs only (else `HostDenied`); `files_info` works in every kind but migrate, and `files_open` and `reader_read` in a compute run only (anywhere else `files_open` is `HostDenied`): a sealed file's contents are readable only inside a compute run. Limits: `MAX_OPEN_FILES` (16 readers and writers), `MAX_FILE_BYTES` (2 GiB plaintext per file, soft `"file too large"`; a logged run is held to `MAX_RUN_FILE_BYTES` in all, so the cap matters only to a compute run), `MAX_RUN_FILE_BYTES` (64 MiB per run, because the node holds a logged run's new ciphertext in memory until its entry is proposed; soft `"run wrote too much"`; a refused write is not counted), `MAX_READ_CHUNK` (1 MiB; `max` is clamped to `1..=MAX_READ_CHUNK`, so an empty list always means end of file, and a provider answer longer than `max` is truncated with the rest kept for the next read), `MAX_NEW_FILES` (1,000, soft `"too many new files"`). Files are sealed blobs and there is no delete: retention is the blobs' (the node collects a file no state refers to). `blobs_info` answers for a file the provider holds or the run finished (empty `mime`), `blobs_grant` refuses one (`HostDenied`), and `storage_put` accepts a `BlobRef` to one. Every soft error is a fixed `pub const` string. `finish` puts `Outcome::new_files` on the outcome only for status `Ok`; a writer dropped unfinished leaves no file. An unknown handle is `HostDenied`, and so is running out of handle ids (they are never reused). A provider error string is passed through as an opaque soft error, except a read that fails with `ReadError::Corrupt` (an altered or truncated file, found at any point including the end of the stream), which is `HostDenied(FILE_CORRUPT)` so the guest cannot ignore it. `Files::open` and `create`, and a writer's `write` and `finish`, fail with `FileError`: `Failed` is a soft string, `Unavailable` (the node cannot serve the bytes now) is, in a logged run, a `HostDenied` that `finish` turns into `Trap(Unavailable)` so the node does not log the run and retries it. A write refused for either cap, a failed provider `write` or a failed `finish` leaves the writer failed, so `finish` never seals a truncated file and the writer answers `"file write failed"` (`FILE_FAILED`), never `"file already finished"`.
- Publishing: `compute_publish(id)` is a logged-write kind only (`HostDenied` in a view, an action and a migration; the compute world does not import it).
  The provider's `Files::publish` answers a `PublishedFile { source, id, size, bytes }` for an output of one of the app's done runs, else the soft `NOT_A_RUN_OUTPUT` (the default, so a provider that knows no runs refuses).
  Publishing a source twice in a run answers the same id and records one; at most `MAX_PUBLISHED_PER_RUN` (16) per run, then `"too many new files"`; at most `MAX_PUBLISHED_BYTES` (64 MiB) of plaintext, judged from `Files::info` before the bytes are read, then `"run published too much"`.
  `Outcome::published` carries them only for status `Ok`, and `storage_put` accepts a `BlobRef` to a blob the run published.
  `MemoryFiles::mark_output(id)` makes a stored file publishable.
  `files_uploader(id)` (the WIT `runs.uploader`) asks `Files::uploader`, which answers the account that uploaded the sealed file, else none; every kind but a migration, never a compute run.
  `MemoryFiles::insert_by(bytes, uploader)` stores a file as uploaded.
  `BlobHost::published(id)` marks a published blob, and `blobs_grant` of one is `HostDenied` outside a logged write, so the log records who shared it.
- Compute runs: an `Action` invocation with `Invocation.compute = Some(ComputeCtx { run_id, owner, inputs })` is a compute run (only an action may carry one: `InvalidInvocation::RunOutsideAction`); an action without it is a plain action. `inputs` are blob ids. A run has no state, `emit`, `xcall`, `unique_id`, `start_action`, network (`http_send`) or action host (`HostDenied`); `files_open` and `files_info` accept only ids in `inputs` (else `HostDenied`), and there is no delete, so it only reads its inputs. `create`/`write`/`finish` work with `MAX_COMPUTE_FILE_BYTES` (2 GiB) in place of `MAX_RUN_FILE_BYTES`, and each file is still at most `MAX_FILE_BYTES`. A run's outputs are sealed blobs on `Outcome::new_files`; they are retained only if the run's result method stores their ids as `BlobRef`s, where `storage_put` accepts an id the node holds for that entry and refuses any other. Clocks are `entry_ts_ms` and randomness ChaCha20 from `seed`. `compute_run_id`, `compute_inputs` and `compute_progress(percent, step)` back the WIT `job` interface; progress goes to the `Progress` callback set with `with_progress` (percent capped at 100, step cut at `MAX_PROGRESS_STEP_BYTES` = 128 on a character boundary, outside a compute run `HostDenied`, never logged). `finish` turns a result, or an app error whose code and message together are, over `MAX_COMPUTE_RESULT_BYTES` (64 KiB) into `Trap(HostDenied, "result too large")`. A compute run sees a constant context: `org` none, `org_role`/`org_role_strict` none, `orgs_of` empty, `in_team` false, `applied_index` 0, `app_owner` = `ComputeCtx.owner` (fixed at the start); the directory is never consulted. Every provider failure in a compute run (`Failed` or `Unavailable` from open, read, create, write, finish) ends the run `Trap(Unavailable, FILE_UNAVAILABLE)`, never a soft error (a corrupt file stays `HostDenied(FILE_CORRUPT)`); `FileError::Unavailable` in a logged run is `Unavailable` too, no longer `Timeout`. `reader_read` fills to `min(max, remaining)` by looping over the provider, so chunking depends only on the file and `max`; a provider failure met after some bytes is answered by the next read. `Usage.peak_memory` is set by the engine.
- Starting runs: `compute_start(method, args, inputs)` and `compute_cancel(run)` are logged writes only (call, timer, init, xcall delivery; a compute run, a view and migrate get `HostDenied`).
  `with_compute(abi, runs)` gives the core the running bundle's ABI and a `Runs` provider (the app's active runs, asked once per invocation); the defaults have no compute method and no active run.
  `with_compute_component(false)` (the node passes whether the running release ships one) makes `start` answer `NO_COMPUTE_COMPONENT` before anything else; the default is a component.
  `start` answers the remaining soft errors, in this order: `NOT_A_COMPUTE_METHOD`, `RUN_ARGS_TOO_LARGE` (`MAX_COMPUTE_ARGS_BYTES`, 64 KiB), `RUN_TOO_MANY_INPUTS` (`MAX_RUN_INPUTS`, 64), `RUN_DUPLICATE_INPUT` (an id named twice), `RUN_INPUT_MISSING` (an input must be one of the app's sealed files, which `Files::info` knows: not a plain blob, not an unknown id, and not a file this run finished, which the app does not hold yet), `RUN_INPUTS_TOO_LARGE` (declared plaintext over `MAX_RUN_INPUT_BYTES`, 2 GiB), then an active or already started run with the same (method, SHA-256 of args, inputs in order) answers its id and records nothing, then `RUN_TOO_MANY_STARTS` (`MAX_STARTS_PER_RUN`, 16) and `RUN_TOO_MANY_ACTIVE` (`MAX_ACTIVE_RUNS`, 64, active plus this run's starts); a new run's id is `unique_id()`.
  `cancel` needs an active run (`NO_ACTIVE_RUN`; a run started in the same invocation is not active) and is recorded once.
  `Outcome::compute_starts` (`StartedRun`: run, method, args, inputs with size and SHA-256, the ABI's `ComputeCaps`) and `compute_cancels` are kept only for status `Ok`.
- ABI: `"kind": "compute"` with `"compute": { fuel, memoryMib, wallSecs, result }` is `MethodKind::Compute(ComputeCaps)`; `computeResult` is `MethodAbi::compute_result`. `from_json` refuses (`BadAbi`) caps outside `1..=MAX_COMPUTE_FUEL` (10^12), 4,096 MiB, 900 s, a missing fuel or result, a `result` that is not a `computeResult` method of the same ABI (not checked for a compute component's ABI, `"world": "calimero:app/compute@0.5.7"`, which lists compute methods only and refuses any other kind), and `compute` on another kind; `Budget::compute(&caps)` is the run's budget.
- `MemoryFiles` (feature `testing`) is an in-memory provider: ids are the hex SHA-256 of the content, the ciphertext is the content (one segment per file), and `apply(new_files)` plays the node applying an entry.
- Deadline: `HostCore::with_deadline(Instant)` (the embedder's: the node passes `now + budget.wall_clock`, the same instant it hands its waiting hosts). Every host call that may block (`http_send`, `xcall_call`, `xcall_view`, `xcall_batch`, `action_view`, `action_call`, through `blocking`) is refused `HostDenied(WALL_CLOCK_EXCEEDED)` once the deadline has passed and answers the same when it returns past it; `finish` then answers `Trap(Timeout, WALL_CLOCK_EXCEEDED)` whatever status the engine reports, the outcome an overrun in the guest's own code gets, and keeps no diff, events or exchange of it. No deadline set: hosts wait as long as they do. `WALL_CLOCK_EXCEEDED` lives here (the engine re-exports it). Test: `a_host_call_past_the_runs_deadline_ends_it_timed_out`.
- At most `MAX_WRITES` (10,000) writes per run; a refused write is not counted.
- Run limits are soft: `storage_put`, `storage_delete` and `storage_add` answer `Result<Result<(), RunLimit>, HostDenied>`, the inner `RunLimit { limit: RunLimitKind::{Writes, Bytes}, max, attempted }` for the write past `MAX_WRITES` (`attempted` its number) or `MAX_RUN_BYTES` (`attempted` the run's bytes with it), nothing of it kept or counted; the engine answers it to WIT `put-checked`/`delete-checked`/`add-checked` (0.5.7) as `limit-exceeded`, and to the older trapping `put`/`delete`/`add` as the trap they always got (`RunLimit::denied`: `TOO_MANY_WRITES`, `ENTRY_TOO_LARGE`). `emit`, `xcall_send` and `start_action` past `MAX_RUN_BYTES` answer their soft string, `RunLimit`'s `Display` (`entry too large: the run would write <n> bytes, over 1048576`). The answer depends only on the run's own calls, so it is the same on every node. Policy refusals (a view writing, a key over 1 KiB, an unknown blob) stay `HostDenied`.
- `entry_bytes(EntryOf, EntryIds, &Outcome)` (`entry.rs`) is the length of the JSON log entry `calimero-node` writes for a call, tick or `init` (pinned by the node's `the_host_cores_entry_size_is_the_logs`), with `MAX_ENTRY_BYTES`; the SDK's harness refuses a run over it as the node does. It leaves out a delivery's source fields and the marks of files, published outputs and compute starts.
- Keys are at most `MAX_KEY_BYTES` (1 KiB, before the generation prefix): `storage_get/put/delete/add` and `range_open` bounds over it are `HostDenied`. Values have no separate cap: `MAX_RUN_BYTES` (1 MiB) bounds what one run writes, counted at each host call (key + value of every `put` and `add`, the key of every `delete`, each overwrite again, and the name, data and audience strings (every account, the team or org id) of every event); the call that would pass it is refused (the soft `RunLimit` above) before the bytes are kept (the canonical ABI's lift of one argument, bounded by guest memory, is transient), so the overlay and the events never hold more. The executor still checks the encoded entry against 1 MiB.
- `unique_id()` is `"<id_term>.<id_seq>.<n>"`: `Invocation.id_term` is the leader's Raft term while it runs the call, `id_seq` the leader's per-term execution counter (assigned by the executor, incremented for every execution including re-runs, never repeated within a term), `n` counts from 0 per run. The log index is not used: it is assigned only at proposal, so two runs on the same base could share it.
- `Abi::from_json` requires `abiVersion` in `SUPPORTED_ABI_VERSIONS` (`[1]`; missing is `MissingAbiVersion`, unsupported is `UnsupportedAbiVersion`), ignores unknown keys at the top level and per method, and refuses a known key with a wrongly shaped value (`BadAbi`).
- Keys are stored as `stored_key(GENERATION, key)`; `Write.key` in the diff carries the prefix, keys returned to the guest do not.
- `storage_add` reads the current value host-side; it must be a shortest-form CBOR integer (absent = 0); the sum is stored in the same encoding.
- A cursor reads the state as of `range_open`: the committed state plus the run's writes made before it opened. The overlay stamps every write with a run sequence number and keeps each key's versions (bounded by `MAX_WRITES`); a cursor uses, per key, the newest version at or before its opening sequence, else the `StateView`. `storage_get` and the diff use the newest version. A scan that moves records ahead of itself therefore never meets them again.
- Ranges are lazy and hold no iterator between batches: every `range_next` re-ranges the `StateView` (forward from `last ‖ 0x00`, reverse up to `last`) and the overlay from the last returned key, reading one committed entry ahead (at most `max + 1` entries held); a batch is capped at `MAX_RANGE_BATCH` entries and, past its first entry, `MAX_RANGE_BATCH_BYTES` (4 MiB) of keys and values, so a shorter batch is not the end (only an empty one is). Regressions: `a_range_batch_stops_at_its_byte_cap_and_the_next_carries_on`, `an_entry_past_the_byte_cap_comes_back_alone`.
- `emit` returns the WIT `result<_, string>` inside `Ok`; a policy refusal is the outer `HostDenied`. Soft errors, as fixed `pub const` strings, leave no event recorded:
  - `EMIT_TOO_MANY` ("too many events"): more than `MAX_EVENTS` (1,000) per run.
  - `EMIT_NAME_TOO_LONG` ("event name too long"): name over `MAX_EVENT_NAME_BYTES` (100).
  - `EMIT_DATA_TOO_LARGE` ("event data too large"): data over `MAX_EVENT_DATA_BYTES` (16 KiB).
  - `EMIT_BAD_AUDIENCE` ("malformed audience"): an empty `accounts` list or account id, or an empty team or org id.
  - `EMIT_UNKNOWN_TEAM` ("unknown team"): `Directory::team_exists` is false.
  - `EMIT_FOREIGN_ORG` ("audience names another org"): `org-members`/`org-admins` naming an org other than the app's own.
  - `EMIT_TOO_MANY_ACCOUNTS` ("too many audience accounts"): an `accounts` audience naming more than `MAX_AUDIENCE_ACCOUNTS` (1,000) accounts.
- The executor, not this crate, refuses a log entry over 1 MiB. That check covers the diff and the events together, so a run within every event limit can still be refused as "entry too large".
- Logged invocations draw randomness from ChaCha20 seeded with `Invocation.seed` and see `entry_ts_ms` on both clocks; views and plain actions use the node's CSPRNG; plain actions see the real clock rounded to the second (a compute run is seeded and fixed, see above).
- Any status but `Ok` empties the diff and events; the result and logs stay.
- `Outcome::logs` are the app's own lines and may hold user data, so `HostCore` keeps none unless its embedder asks with `with_logs(true)` (default off: `log` drops each line at once): a development node (`Config::app_logs`, `--dev`) and `meroctl local compute run` ask, a production node and a job node never do. Regression: `a_host_keeps_no_log_lines_unless_its_embedder_asks`. `Outcome`'s `Debug` prints only their count (`an_outcomes_debug_counts_its_log_lines_and_never_prints_them`), and the node stores none of them.
