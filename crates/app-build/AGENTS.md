# calimero-app-build - Rust guest to `calimero:app` component

## Package Identity

- **Crate**: `calimero-app-build` (`publish = false`, prototype; `meroctl`, which ships with each release, runs it); a library (the `mero-app-build` binary is gone; `meroctl` is its command line); the standard library's `File::lock` for the build lock
- **Used by**: `meroctl app build`, `meroctl app codegen`, `meroctl app abi diff`, `meroctl app uses` and `meroctl app pack DIR` (`crates/meroctl/src/make.rs`); an app's `build.rs` (`uses::generate`)
- **Entry**: `src/lib.rs`
- **Docs**: [Packaging & signing](https://calimero-network.github.io/core/build/packaging-signing/)

## What This Crate Does

`build_components(crate_dir, target_dir)` builds the app component and, when its ABI has compute methods, the compute component, and when it has sandbox methods, the sandbox component (`build_sandbox_component`: `--cfg calimero_compute --cfg calimero_sandbox`, into `<target>/sandbox`; `meroctl app build --sandbox-out`, `app pack --sandbox`; cached as `<name>-<key>.sandbox.wasm`) (`build_compute_component`: the same crate under `CARGO_ENCODED_RUSTFLAGS` plus `--cfg calimero_compute`, into `<target>/compute`, so the two builds never invalidate each other); `meroctl app build [<crate>] [--out <file>] [--compute-out <file>] [--target-dir <dir>]` writes both (the crate defaults to `.`, `--out` to `<crate>/app.component.wasm`) (the compute one beside `--out` as `compute.component.wasm` by default). `build_component(crate_dir, target_dir)` runs `cargo build --release --target wasm32-wasip2`, lifts the `calimero:abi` custom section from the nested core module to the component's top level, and returns the component, its ABI JSON and its top-level imports. `build_component` holds an exclusive file lock (`<target>/.calimero-app-build.lock`) for the build, so threads and processes sharing a target dir (nextest) build one at a time; test: `tests/concurrent_build.rs`. `abi_of` and `imports_of` read a component's top level only.

`build_components_cached(crate_dir, also_hash, cache_dir)` reuses `cache_dir/<name>-<cache_key>.wasm` (the app component) and `<name>-<cache_key>.compute.wasm` (the compute one, written first and present only when the app has compute methods), and returns both as `CachedApp`.
`build_component_cached` returns the app component of the same entry.
A miss builds under an exclusive cross-process file lock (`std::fs::File::lock`, `cache_dir/target/<name>.build.lock`, one per crate) into one cargo target dir for every crate, `cache_dir/target/shared` (`build_component`'s own lock makes builds of different crates take turns; their shared dependencies compile once), recomputes the key and re-checks the cache once it holds the lock, so concurrent processes (nextest runs each test in its own) build once and the rest reuse the result. The key walk skips a file that vanishes while it walks. Test: `tests/concurrent_cache.rs` (6 processes on a cold cache, one `cargo build`).

`build_in_repo_cache(crate_dir)` is that cache at the repository's `target/app-components`, hashing the SDK, its macros, `calimero-app-sdk` and the WIT, answered as a `BuiltApp` (`Built::from_component` reads the ABI and imports back from the cached bytes). Every test that builds a guest goes through it (the node's, the engine's, the SDK's, meroctl's `compute_run`), so a guest compiles once per tree whichever test binary asks first; CI keeps `target/app-components` in its test-app cache.

`meroctl app codegen --abi <abi.json|.wasm|.mpk|manifest.json> --lang ts|python|swift|kotlin|openapi [-o <dir>] [--name <n>] [--service <s>] [--package <p>] [--kotlin-serialization-plugin] [--no-openapi]` writes the app's `openapi.json` (unless `--no-openapi`) and a typed client (`client.ts` over mero-js, `client.py` over calimero-client-py, `<Name>Client.swift` / `.kt`). The library runs the same in process: `codegen::Codegen::new(abi, lang, out)` and `run()`, which returns the paths written (`src/codegen.rs`). The client's name is `--name`, else the service, else the bundle's package, else the file's stem; a stem that names no app (`abi`, `app`, `component`, `compute`, `manifest`) falls back to the package name of the nearest `Cargo.toml` above the file, and with none the run fails asking for `--name`. `meroctl app abi diff <old> <new> [--json] [--service <s>]` prints what changed and exits 1 on a breaking change; `meroctl app abi show <file>` prints one ABI. The CLI side of both is `src/abi_tools.rs` over `calimero-app-abi`, which `meroctl` calls; tests: `crates/meroctl/tests/app_abi_tools.rs`. `meroctl --version` prints the release. `examples/codegen.rs` is the same command line without meroctl's build, for the SDKs' vendored app clients (`scripts/app-codegen.sh`).

`uses` (`src/uses.rs`): the apps a crate's release `uses`. `declared` reads `[package.metadata.calimero.uses]` (`package`, `range`, `mode` = `create`|`attach`, `methods`), `read_lock` reads `calimero.lock` (`[[uses]] name, package, version, range, mode, abi`, the format `meroctl app pack`'s `uses_of` reads), `vendor(dir, name, version, abi)` writes `calimero/abi/<name>.json` (pretty JSON) and the reference's lock entry (`abi` = `sha256:` of the file), and `check` refuses a reference declared but not locked, a lock entry not declared, a package, range or mode that differs, a vendored ABI whose hash is not the lock's, and a listed method the ABI lacks. Whether the version is inside the range is `meroctl`'s (`app uses update|check`, `app pack`): this crate has no semver. `generate()` is for an app's `build.rs`: it checks the crate (`CARGO_MANIFEST_DIR`) and writes `$OUT_DIR/uses.rs`, the module `calimero_app_abi::codegen::rust::uses_module` generates (a typed client per reference), with `rerun-if-changed` on `Cargo.toml`, the lock and `calimero/abi`. It lives here, not in `calimero-sdk-macros`, because the example apps already depend on this crate (dev-dependency for `build_component`), so a build-dependency adds nothing to their lockfiles, and a `build.rs` reruns on the files it reads where a proc macro would not. `meroctl app uses update|check` is its command line (`crates/meroctl/src/make/uses.rs`). Tests: `src/uses.rs`; the examples: `apps/planner`, `apps/booking`.

## Rules

- Section lifting is raw byte surgery on section boundaries (no re-encode of contents); keep it that way.
- Table `partition` refusal is not here; it is a compile error in the `#[table]` derive.
- `tests/guests/echo` is a standalone crate (own `[workspace]`), not a member of the core workspace.

## Verify

`cargo test -p calimero-app-build`

Docs teach `meroctl app build|codegen|abi`; an app's CI that only runs `codegen` downloads the release's prebuilt `meroctl_<target>.tar.gz` (Linux x86_64/aarch64 and macOS aarch64, in `SHA256SUMS`). Core's own scripts and CI jobs call `meroctl app build` (from `target/release`, or `cargo install --locked --path crates/meroctl`). The crate stays `publish = false`, as does `calimero-app-abi`.
