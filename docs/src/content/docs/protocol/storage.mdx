Everything a node persists is in its data directory (`--data-dir`, by default
`{home}/{node}/data`):

```text
<data-dir>/
├── store/          one RocksDB database for every group on this node
├── snapshots/      sealed snapshot files, one current per group
├── components/     compiled components, each with a MAC under a key from K_c
├── cluster-key     K_c, AES-256-GCM under HMAC-SHA256(K_r, "calimero.cluster-key.wrap.v1")
├── signing-key     the receipt key, under HMAC-SHA256(K_r, "calimero.signing-key.wrap.v1")
└── log.redb.migrated   (only if the node was upgraded from the redb store)
```

The database is opened with tuned column and table options
(`calimero-log`'s `tuning`): compression, bloom filters, one bounded block
cache (128 MiB). Log appends, votes and blobs are synced writes; RocksDB shares
one WAL sync between the groups writing at once, and groups never queue behind
one another.

## Columns

| Column | Key | Value |
| --- | --- | --- |
| `log` | `group (u64 BE) ‖ index (u64 BE)` | A Raft entry |
| `meta` | `group ‖ name` | `vote`, `committed`, `purged`, `applied` (last applied log id and membership), `generation`, `snapshot` (the current snapshot's metadata and file); and, under the node's own group (`u64::MAX`, `NODE_ROWS`), `format` (the [store format](#format-versions)) and `rollback` (`{ node, entry: { generation, mark }, epoch }`, [the rollback counter](/protocol/encryption/#rollback-protection)) |
| `state` | `group ‖ generation (u32 BE) ‖ machine key` | The state machine's rows |
| `blobs` | `name` | Bundles, uploaded releases and app blobs, by `hex(SHA-256)` |

## Sealing

Every value is sealed with AES-256-GCM under the cluster key K_c
([Encryption](/protocol/encryption/)), with a random 96-bit nonce stored in
front, and bound as associated data to its column tag,
its group and its key: `"cl" ‖ tag ‖ group ‖ key`. A state row's associated
data names its machine key but not its generation, so installing a snapshot can
move sealed rows to the next generation without opening them. A value copied
to another row, group or column fails to open.

Two further keys are derived from K_c (`HMAC-SHA256(K_c, label)`):

- `calimero.log.hidden-keys.v1` keys the HMAC that hides row keys;
- `calimero.log.snapshot.v1` seals snapshot frames.

### Hidden rows

A machine can hide a key (`StateTx::put_hidden`). The row is then stored at
`tag ‖ HMAC(group ‖ tag ‖ key)` (33 bytes), and the value, before sealing, is
`u32 BE key length ‖ key ‖ value`. The disk then shows neither which keys an app
uses nor how they sort; reading a hidden key needs K_c.

## An app group's rows

An app group's machine key space (`crates/node/src/app.rs`, `rows`). Hidden
rows (the key on disk is an HMAC) are those whose names or ids would say
something about the app:

| Row | Hidden | Holds |
| --- | --- | --- |
| `c` + the app's key | yes | The component's storage: what its runs write (`storage.put`, `add`, `delete`) |
| `j` + `caller\|key` | yes | Idempotency records: the answer replayed for a repeated key, and its expiry |
| `q ‖ class ‖ n` | no | The idempotency keys in the order they were recorded, per class (client keys, node keys) |
| `h` | no | The `Head`: bundle, executor, initialized and init error, last applied index, event-ring bounds, and the component's host records (timers, id terms, compute component, active and finished runs and pipeline runs, the step cache's keys, `lastWriteMs`, the time of its last write, left out until the first) |
| `e ‖ n (u64 BE)` | no | Event `n` of the event ring (the last 10 000), with its audience |
| `b` + blob id | yes | The app's record of each blob and sealed file (size, mime, idle time, a file's seal and wrapped key) |
| `o ‖ seq`, `d ‖ n` | yes | The xcall outbox and its dead letters |
| `a` + action id | yes | Pending actions |
| `u` + run id | yes | Compute run records |
| `p`, `y`, `v`, `x` | yes | Pipeline runs, their step items, step-run proofs, and the step cache |

An SDK 0.12 app's rows (`k`, `i`, `r`) are kept as they were and read by no
run: that runtime is gone.

Only the `Head` is kept in memory; runs read the app's keys through the group's
state (`KvView`), so an app's state is never loaded whole.

The **system group** keeps its state in memory and writes one checkpoint row
(`\0calimero.log.checkpoint`) with each snapshot.

## Snapshot files

A snapshot is `snapshots/<…>.snap`: a first line naming its format
(`CALIMERO-SNAPSHOT-1`, [Format versions](#format-versions)), then
frames of up to about 1 MiB of rows each, each frame sealed with associated
data naming the group, the snapshot id, the frame's position and whether it is
the last. It is written from a consistent RocksDB view, so a large state is
streamed rather than held in memory. A follower receiving one writes it to a
file first, then installs it as the next generation in batches of about 4 MiB
and switches generations in one batch ([Replication](/protocol/replication/#state-restarts-and-snapshots)).

## Backups

A backup is a copy of a group's current snapshot file under
`{backup-dir}/{app}/{index:020}.{group}.{snapshot}.snap`, with its sealed
manifest beside it (`….snap.manifest`, backup format 1; a lone snapshot file is
format 0) ([The operator](/protocol/operator/#backups)). `backup::find` checks a
backup against its manifest; `backup::latest` opens the newest one with K_c and
returns its index and rows. A restore writes a backup's rows into a new group
(`Group::replace_state`): each row is opened and sealed again for that group,
and a hidden key is hidden again under it.

## Recovery files

The recovery disk (`--recovery-dir`, [merod](/operate/merod/#node-flags)) holds
a second set of backups, sealed to the public key of whoever upgrades each app
rather than to K_c, so they open after every mero-kms is gone
([Recover after every key service is gone](/operate/runbooks/#recover-after-every-key-service-is-gone)).
Each holder has a directory, named for its key with `:` made `-`: `operator/`,
`org-<id>/` or `account-<id>/` (`recovery_disk::holder_dir`). In it, every
`RECOVERY_EVERY` (5 minutes), each node writes:

| File | Holds |
| --- | --- |
| `app-<app>.<index>.<writtenAt>.rbak` | one app's state at that log index: its directory record and file key, then its rows as `calimero_log::PortableRow`s (a hidden row by the key it hides, so a group under another K_c hides it again) |
| `holder.<index>.<writtenAt>.rbak` | an organization's or account's slice of the system state (`system::HolderSlice`: the org, its people's accounts and passkeys, its apps, the bundles and releases they run) |
| `system.<index>.<writtenAt>.rbak` | the operator's: the whole system state |
| `code-<hash>.rbak` | one bundle or release `.mpk` an app runs, written once |
| `seg-<hash>` | one segment of a sealed file an app lists, copied as stored (already ciphertext under the file's own key); deleted `SEGMENT_KEEP` (7 days) after no held app lists it |

Index and time are zero-padded to 20 digits, so names sort oldest first; the
newest `KEEP` (3) per subject stay, and a subject unchanged since its last file
is not written again.

An `.rbak` file (`calimero_client::recovery`, format 1) is:

1. `calimero.recovery-backup.v1\n` (`MAGIC`);
2. the header's length (u32, big-endian), then the header, JSON (camelCase,
   unknown fields refused, at most `MAX_HEADER_BYTES`, 1 MiB): `format`,
   `kind` (`app`, `holder`, `system`, `code`), `holder`, `cluster`, `app`,
   `org`, `hash`, `group`, `index`, `writtenAt`, the `merod` and mero-tee
   `release` that wrote it, `node`, `recipient` (the holder's X25519 public
   key), `enc` and `wrappedKey` (the body's data key, sealed with HPKE,
   RFC 9180, base mode: DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-256-GCM;
   info `calimero.recovery-backup.v1`, associated data
   `calimero.recovery-backup.key.v1`), `size` and `sha256` of the plaintext,
   `bodyBytes` and `bodySha256` of the ciphertext, `signingKey` (the node's
   receipt key) and `attestation`;
3. 64 bytes: the receipt key's Ed25519 signature over
   `calimero.recovery-backup.v1\0` followed by the header bytes;
4. the body: the plaintext sealed under that data key as a sealed file is
   (64 KiB AES-256-GCM STREAM chunks, [Sealing](#sealing)).

The `attestation` is the writing node's `purpose=receipts` quote over the nonce
`SHA-256("calimero.recovery-backup.attest.v1\0" || u32 length || cluster ||
u64 node)` and the receipt-key binding (`receipt-key.v3`: the key, the
governance, the cluster and the node id). A reader checks the signature, that
the attestation names the header's cluster and node and binds the signing
key, and the quote under its own policy, before it opens a key; a node takes
no recovery file whose attestation its peer policy refuses
(`400 UNATTESTED_RECOVERY_FILE`). The holder opens the data key on its own
device (`meroctl ops recovery-keygen` and `ops recover` for the operator,
mero-js's and calimero-client-py's `recovery` modules for an organization or
account) and sends only that key; no node holds a holder's private key.

## Format versions

Each container of what a node keeps names the format it was written in, so a
node tells "an older format, which needs its reader" from "damaged", and
refuses what a later release wrote instead of misreading it:

| Container | Where the version is | This release | Unmarked (written before markers) |
| --- | --- | --- | --- |
| The store (every row of every column) | node row `format` in `meta` (sealed, `calimero_log::STORE_FORMAT`) | 1 | format 0: every release up to 1.0.0-rc.15, the same rows as format 1 |
| Snapshot and backup files | the first line, `CALIMERO-SNAPSHOT-<n>` (`calimero_log::SNAPSHOT_FORMAT`) | 1 | none: every file so far says 1 |
| A component app's log entries (with the outcomes and file marks they carry) | `{"v":<n>,` as the start of the entry (`component::ENTRY_FORMAT`) | 1 | format 1: no entry so far carries a marker |
| Sealed files and their segments | the domain strings the chunk AAD and the file id are bound to (`calimero.file.v1`, `calimero.file.segments.v1`) | v1 | none |
| Recovery files (`.rbak`) | the first line, `calimero.recovery-backup.v1`, and the header's `format` (`calimero_client::recovery::FORMAT`) | 1 | none |

The store's format is settled when the engine opens it, before any group
starts: a store marked newer than this release reads is refused (`the store is
in format N, which a later release wrote`), and the node does not start; an
older one is brought forward one registered step at a time, the marker written
after each step, so a crash part way resumes where it stopped; an empty store
takes the current format. A snapshot or backup of a later format is refused
by its first line, and an app entry of a later format applies as a no-op that
names its format on every replica of this release (the release that raises the
entry format writes it only once every replica of the group reads it).

Changing a row, a snapshot's framing or an entry's meaning raises the matching
number in the same change and keeps a reader (a migration step, or the old
shape's decoder) for what is already written; a change with no reader is a
hard cutover, declared in `CHANGELOG.md` and in mdma's release compatibility
table before it ships. The
`format` row shows under the node's own rows (group `18446744073709551615`) in
`merod inspect` with the key.

## Migration from the previous format

A data directory holding the previous single redb file (`log.redb`) is migrated
when the engine opens it: entries, votes, commit and purge marks, blobs, and
each machine's old whole-state snapshot, which the app machine imports into its
rows (the app's keys, events, idempotency records with their expiry ring). The old
file is kept, renamed `log.redb.migrated`.

1.0.0-rc.20 is a hard cutover on top of this: a data directory or log that
holds an app outside an organization is not read, so clusters are recreated
on that release and nothing written before it is replayed (`CHANGELOG.md`).

## Inspecting a stopped node

`merod inspect [--storage-key-file F]` summarizes the store's layout and sealed
sizes; with the key, it also opens each group's metadata (vote, applied index,
membership). It opens the store for writing, so stop the node first.
