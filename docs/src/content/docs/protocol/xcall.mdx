A run may send messages to other apps (`env::xcall(app, method, &args)`). The
message is a **follow-up**: it runs after the sending entry commits. The guest
API is in [Cross-app calls](/build/guides/cross-context/); this page is how the
cluster runs them (`crates/node/src/component/xcall.rs`).

```rust
// Sender (apps/fixture-kv): queue a message; it leaves once this entry commits.
pub fn relay(&mut self, app: String, key: String, value: String) -> app::Result<()> {
    env::xcall(&app, "setFromApp", &SetArgs { key: &key, value: &value })?;
    Ok(())
}

// Sender: told when the platform gives up on a message.
#[app::allow(system)]
pub fn on_xcall_failed(&mut self, app: String, method: String, reason: String) -> app::Result<()> {
    self.xcall_failures.insert(&method, &format!("{app}|{reason}"))?;
    Ok(())
}
```

The target method names who may call it, `#[app::allow(app = "<source>")]` or
`#[app::allow(app = "*")]`, and sees the sender as `Caller::App(<source>)`.

## Outbox

A run's messages go to its outcome. When the entry ends `Ok`, they are
appended, in order, to the source app's outbox, kept as hidden rows of the
source app's group. A failed run sends nothing. The outbox holds at most
`MAX_OUTBOX` (10,000) messages; one past it goes to the dead letters at once.

## Delivery

The source's leader delivers the head of its outbox one message at a time, so
messages leave each source in order. The target runs the method as an xcall
delivery, with `Caller::App(<source>)`.

## Authorization

The node that runs the target checks:

1. **Entry point.** The target method's ABI must allow the source:
   `#[app::allow(app = "<source>")]` or `allow(app = "*")` (`allowApps`).
2. **Boundary.** The two apps are in the same organization. Every app is in
   one, so an account's own apps reach each other when they share an
   organization, and apps of two different organizations never do.
3. **Provenance.** The target sees the caller as `Caller::App(<source>)`, set by
   the node; no argument can claim it. Only where the person the source's run serves
   granted it does the call run as that person instead
   ([As the person](#as-the-person)).

## As the person

An app calls another as itself: the target sees `Caller::App(<source>)` and never
learns whom the source's run was serving. A person can let an app do more: call
some methods of another app as them, so the target applies its own rules for that
person, as if they had called it directly. A calendar that already keeps each
person's events works unchanged under a scheduling plugin.

- **The release says what it would call.** Each reference in the source's signed
  `uses` lists the methods of that package it calls as the person (`methods`, at
  most 64). The release's card shows them, and an upgrade's consent page flags a
  reference whose methods change.
- **The person grants it.** `PUT /apps/{source}/delegations/{target}` with the
  person's passkey over exactly the target and those methods (`<source> /
  __delegate / { target, methods }`). They must reach both apps, which are in one
  organization. `DELETE` takes it back without a passkey; `GET
  /apps/{source}/delegations` lists what they granted. Deleting either app ends it.
  The grant is the account holder's own: a session opened on an app's frontend is
  refused the route (`403`), and the source's frontend asks on the
  [consent page](/protocol/consent-page/) instead (`delegate { app, target }`),
  which names both apps and every method before the passkey.
- **The node decides, call by call.** When the source's run was started by the
  person (their account or an API key of theirs), its message, synchronous call or
  view of a granted method runs on the target with the person as the caller and
  `env::via()` (WIT `context.via`, `calimero:app` 0.5.2) naming the source. A
  message is judged when it is delivered, so a grant taken back meanwhile stops it.
  Anything else (no grant, another method, a person who no longer reaches the
  target, a timer or an action, a run another app called) runs as the source app.
- **The target's checks apply to the person.** A method that needs the person's
  passkey confirmation is refused (`ConfirmRequired`); a plugin never confirms for
  them. A target that wants less for a call through an app reads `env::via()`.

Grants exist only once every node runs 1.0.0-rc.31 (`Feature::Delegation`), and a
message's outbox row names its person from the logged cluster version that brings
it, so every replica keeps the row alike.

## Synchronous calls and views

`env::xcall_call(app, method, &args)` runs the target's method as one call in
its own log, as `Caller::App(<source>)`, before the sending run continues, and
answers its result; `env::xcall_view` runs a view on the target's latest
committed state. Both are futures, awaited in an `async fn` app method (or a
generated client's methods, which are the same futures, typed). Both pass the
same checks, and the target must be a component app other than the sender.
They are not atomic: the target's call commits whatever the sender does next,
so a target method should be safe to have run (a captcha's `verify` spends the
challenge either way). A re-run of the sending call replays the target's
answer: the target's idempotency key is derived from the sender's, the target,
the method, the arguments and how many identical calls came before in the run.
A read-only member's run may make a synchronous view, never a synchronous
call. A delivered xcall makes no synchronous call.

**Concurrency.** The SDK runs an `async fn` method with a small executor of its
own: it polls the method until every future it awaits waits on an xcall, then
sends those xcalls to the node in one `xcall.batch` (WIT `calimero:app@0.5.5`)
and polls again with the answers. Futures awaited one after another make one
batch each; futures awaited together (`app::join!(a, b)`, `app::join_all(v)`)
are in one batch, which the node runs at once:

```rust
let cal = uses::calendar()?;
let (events, count) = app::join!(cal.my_events(), cal.event_count());
```

The sending run holds its own app's proposal lock while it waits, so a batch
holds it for the slowest request rather than the sum of them. Requests to the
same target take turns on the target's lock, as two callers' would. Each
request of a batch is checked, counted and keyed exactly as the same call or
view made on its own, in list order: the occurrence counter runs across the
run's batches, so a batch of two identical calls gets two keys and a re-run
makes the same batches with the same keys. A batch is answered in order, a
refused request in its place.

| Limit | Value |
| --- | --- |
| Synchronous xcalls one run makes, batched or not (`MAX_SYNC_XCALLS`); a batch that would pass it is refused whole | 16 |
| Arguments of one (`MAX_SYNC_XCALL_ARGS_BYTES`) | 512 KiB |
| Answer handed back for one (`MAX_SYNC_XCALL_RESULT_BYTES`) | 1 MiB |
| How long a run waits (`SYNC_XCALL_WAIT`): for one call, or for a whole batch (one deadline) | 3 s |

A request still running at the deadline is told it timed out; a call may still
commit in its target, and the sender's retry replays it. A component built
before 0.5.4 makes its xcalls one at a time with `xcall.call` and
`xcall.view`, which nodes keep serving.

## Deduplication

The target keeps, per source app, the highest sequence number it applied; a
message at or below it is answered as delivered without running. A leader
change on either side never runs a message twice. A target keeps watermarks
for at most `MAX_WATERMARKS` (10,000) sources; past that the lowest is dropped.

## Retries and dead letters

A timeout or an unreachable target is retried with backoff (at most 30 s
between attempts) for up to an hour from the send (`XCALL_WINDOW_MS`). Then, or
at once for a deleted target, one outside the organization, or one that is not
a component (an app the node no longer runs), the message goes to the source's
dead letters (the newest 1,000), and the source's `onXcallFailed` runs if its
ABI has one that allows the system. Anything the target answered, an app error
or a trap included, is a final answer; so is a refusal because the target's
developer is over its fuel cap for the day.

## Limits

| Limit | Value |
| --- | --- |
| Messages one run sends | 100 |
| Messages one outbox holds (`MAX_OUTBOX`) | 10,000 |
| Retry window (`XCALL_WINDOW_MS`) | 1 hour from the send |
| Dead letters kept (`MAX_DEAD_LETTERS`) | 1,000 |
| Sources one target keeps a watermark for (`MAX_WATERMARKS`) | 10,000 |

An empty or overlong app id or method, or a reserved (`__`) method, is refused
at the send.
