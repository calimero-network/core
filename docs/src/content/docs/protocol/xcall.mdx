A run can ask for more runs after it commits: an **event handler**
(`app::emit!((event, "handler"))`, or `"tee:handler"` for one that runs as the
app's TEE authority) and a **cross-app call** (`env::xcall(context, method, params)`). Both are **follow-ups**. The guest API is in
[Events](/build/guides/events/) and [Cross-context calls](/build/guides/cross-context/);
this page is how the cluster runs them.

## Queued in the log, run by the leader

A follow-up is part of the run's outcome, so it is committed with the entry
that asked for it. When the entry applies — on every replica — each follow-up
is queued in the app's state (`AppState::pending`) with a sequence number, the
index of the entry that asked for it, and its **depth**.

The leader drives the queue (`Node::drive`, woken whenever an entry may have
queued work, and on every reconcile pass):

- An **event handler** runs as a call of the same app, caller
  `App { app: itself }`, with the event's data as input and
  `Trigger::FollowUp { seq }`. Its entry consumes the follow-up when it applies.
- A **cross-app call** is a call to the target app, wherever its leader is,
  caller `App { app: origin }`, with the idempotency key `xcall:{origin}:{seq}`
  and `Trigger::XCall`. After the target answers, the origin's leader commits
  `AppCmd::Done { seqs }`.

Because "run it" and "it was run" are the same entry (handlers) or an
idempotent call followed by a `Done` entry (xcalls), a new leader picks up
exactly what is still pending: it neither skips a follow-up nor runs one twice.
A replayed driver pass that finds the follow-up already consumed does nothing.

Handlers and xcalls run **once**, on the leader — not once per replica.

## Authorization

Three checks hold, enforced by the node that runs the target:

1. **Entry point.** An event may run only a method the bundle's ABI marks
   `#[app::handler]` (a `tee:` handler is the app's own TEE run). An xcall may
   reach only a method the target's ABI marks `#[app::xcall]`; anything else is
   refused (`xcall denied: … is not an #[app::xcall] entry point`).
2. **Boundary.** The two apps must belong to the same organization, or, outside
   any organization, have the same owner.
3. **Provenance.** The target sees the caller as the calling app and reads
   `env::xcall_origin()`, the origin's context id, set by the node — a client
   cannot forge it. An entry point declared `from_same_app` admits only an
   origin running the same bundle.

A refused follow-up is still a run: it is recorded with its error, and the
follow-up is consumed. An xcall to an app the cluster does not know is dropped
and marked done; one whose target cannot be reached right now waits for the
next driver pass.

## Bounds

- **Depth.** A person's call is depth 0; each handler or xcall it causes is one
  deeper. A run at `MAX_FOLLOWUP_DEPTH` (3) still runs but queues nothing more,
  so a cascade cannot run forever.
- **Per run.** The runtime caps a run's xcalls (8), their function name (100
  bytes) and parameters (16 KiB), and its events (100) ([Limits](/protocol/limits/#execution-limits)).
- **Per pass.** The leader takes at most 64 pending follow-ups per pass.

## Outcomes are runs, not return values

An xcall is fire-and-forget. The origin's run has already committed when the
target runs, and the target's answer is not handed back to it. If the origin
needs to learn the outcome, the target can emit an event or call back with an
xcall of its own.

## Component apps (`calimero:app`)

A component app (spec `app-runtime-v0.14` D13, D25, D29) sends with
`env::xcall(app, method, &args)` (WIT `xcall.send`), in calls, timers, `init`
and deliveries, at most 100 per run. It is an outbox, not a follow-up:

- **Outbox.** An `Ok` entry's xcalls are appended to the source app's outbox,
  host rows outside its keyspace (D39), each with a sequence number. A failed
  run sends nothing. At most 10,000 wait; one past that is dead-lettered.
- **In order, at least once.** The source's leader delivers the outbox head,
  one message at a time: the target runs the method as `kind = xcall-deliver`
  with `Caller::App(source)`, and the source's leader then logs
  `componentXcallDone`. A new leader resumes from the head.
- **Exactly once at the target** (D25). The target keeps, per source app, the
  highest sequence number it applied (a watermark in its host records). A
  message at or below it answers as delivered without running.
- **Who may be reached.** Only an app in the source's organization, or another
  personal app of the same owner, and only a method whose ABI allows the source:
  `#[app::allow(app = "<app id>")]`, or `allow(app = "*")` for any app the node
  delivers from. Anything else is refused (`Forbidden`) by the node before the
  app runs.
- **Retries and dead letters** (D29). A timeout or an unreachable target is
  retried with backoff (200 ms doubling, at most 30 s) for up to an hour from
  the send. Then, or at once for a missing target, one outside the organization,
  or a wasmer app, the message goes to the source's dead letters (the newest
  1,000), and the source's `onXcallFailed { app, method, reason }` runs if its
  ABI has one with `allow(system)`. Anything the target answered (an app error,
  a trap, a refusal) is final.
- `GET /apps/{app}/xcalls` (the owner or an org admin): `{ pending,
  deadLetters: [{ seq, app, method, reason, atMs }] }`.

A wasmer app's xcall into a component, and a component's into a wasmer app,
are refused.

## Timers

`#[app::tee(every = "…")]` methods are driven by the same loop. The leader
fires each one once per period (tick = now ÷ period), as the app's TEE
authority, and the entry records the tick it fired for, so a new leader does
not fire the same tick again ([Who a run acts as](/protocol/authorship/#the-tee-authority)).
