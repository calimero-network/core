Some decisions belong to the account holder alone: which mero-tee releases may
hold their data, which code may read it, which addresses it may be sent to
([Deployment governance](/protocol/governance/)). Each is approved with a fresh,
user-verified passkey assertion that the node logs as consent. Apps still need
to prompt for them: a new version is out, a feature needs an outbound host. The
**consent page** is how an app does that without ever being the page that asks
for the passkey.

## Why the app's own page cannot ask

A passkey assertion is blind. The authenticator shows the person a site name
and a fingerprint prompt, never what the challenge commits to. Whatever page
starts the ceremony decides what the person believes they approve.

An app's frontend is the publisher's code, served from the bundle and possibly
closed source. If it could run an approval ceremony, it could show "update to
1.2.1" and have the passkey sign an upgrade to something else, or show "allow
analytics" and approve every prefix the manifest declares. So a session opened
on an app's origin is bound to its package and refused every approval route
([Accounts, passkeys & sessions](/protocol/identities/#which-credential-may-do-what)).
That stays true. Instead, the app asks the **node** to ask the person.

1. **Request.** The app calls `POST /consent/requests` inside the sealed
   channel with any session of the account, a package-bound one included:

   ```json
   { "kind": "upgrade", "subject": { "app": "<appId>", "toVersion": "2.0.0" },
     "returnTo": "https://<label>.<apps-domain>/2.0.0/settings" }
   { "kind": "release", "scope": "account" | { "org": "<orgId>" },
     "subject": { "version": "1.4.0" }, "returnTo": "…" }
   { "kind": "outbound", "scope": "account" | { "org": "<orgId>" },
     "subject": { "package": "<package>?", "prefixes": ["https://api.example/"]? },
     "returnTo": "…" }
   ```

   Unknown fields are refused. The node checks the caller could make this
   approval at all (the governance holder, upgrade authority, organization
   membership, a package-bound session only about its own package and apps),
   resolves the subject from its own state and the releases' verified `.mpk`
   files, and freezes what the page will show. It answers
   `{ "requestId", "url", "expiresAt" }`. The request lives in that node's
   memory, bound to the account, for 10 minutes (`CONSENT_REQUEST_TTL`), and
   can be decided once.
2. **Page.** The app sends the person to `url`, `GET /consent/{id}` on the
   node's own public URL. The page is static HTML compiled into `merod`: no
   app code, an inline script and stylesheet allowed by their hashes only,
   `default-src 'none'`, `connect-src 'self'`, `frame-ancestors 'none'`,
   `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control:
   no-store`. It reads `GET /consent/{id}/model` and shows it.
3. **Passkey.** *Approve* posts `POST /consent/{id}/approve`. The node runs the
   very route a signed-in client would run (`/apps/{app}/upgrade`,
   `/auth/releases` or `/orgs/{org}/releases`, `/auth/outbound` or
   `/orgs/{org}/outbound`) with the arguments frozen in the request, so the
   `412 CONFIRM_REQUIRED` challenge commits to exactly what the page showed.
   The page asks the authenticator for a user-verified assertion and posts it
   back as `confirm`. The node checks that the passkey is one of the request's
   account, checks its authority again, writes the approval with the
   assertion as consent, and marks the request approved. *Decline* posts
   `/consent/{id}/decline`; nothing is approved.
4. **Back.** The page navigates to
   `returnTo?request_id=<id>&result=approved|declined`. If that redirect is
   lost, the app asks `GET /consent/{id}/result` (sealed, the same account;
   any node answers, asking the node that holds the request):
   `{ "requestId", "kind", "status": "pending|approved|declined", "decidedAt" }`.

### Where the app may be sent back

`returnTo` is never arbitrary: a node that redirects anywhere would lend its
trusted page to phishing. For a package-bound session it must be the
package's served frontend origin (`{label}.{apps-domain}`) or an origin the
package's newest signed manifest names (`links.frontend`, `frontendAliases`);
for an unbound session, one of the cluster's configured `--origins`. It must
be `https` (`http` only for `localhost`), without credentials or a fragment,
and at most 2 KiB. Otherwise `400 RETURN_TO_NOT_ALLOWED`.

## What the page shows

Every page leads with a headline, then two plain sentences: what holds **until**
the person approves, and what changes **once** they do. For example: "Until you
approve, nodes running mero-tee 1.4.0 receive none of the data of your own
apps: the nodes that hold it refuse to send them any." Then who is approving
(the account), for whom (the account's own apps, an organization, or one app),
which app asked and where it returns to, and when the request expires.
Warnings the person should not miss come next, in their own boxes.

| Kind | Shown, from node-side data only |
| --- | --- |
| **Release** | The version; whether it is already approved and what is approved now; which of the cluster's nodes attest it; this node's profile if it runs it; the release's signed measurements per profile and their digest (on mock attestation it says there are none); links to the signed release and its Sigstore-signed `published-mrtds.json`, with how to verify them independently; the deadline, if any |
| **Upgrade** | The app, current and target version, the publisher's key and author, and a **capability sheet** computed from the two signed manifests and the ABIs their WASM embeds: outbound prefixes added and removed; frontend origin and aliases, with every **new sign-in origin** highlighted (a page there could act in the app as the person); interfaces used and exported; public methods added, removed or changed (view or write, xcall entry point, event handler, destructive); events; timers; whether a migration runs and between which state versions, or why the upgrade would be refused; SDK and build information; the `.mpk`, WASM and manifest hashes |
| **Outbound** | The package and its publisher, the release whose declarations are listed, the prefixes being approved, which of them are new, which are already approved |

The model is what the app can neither write nor alter: it is frozen when the
request is made, from the node's state and the releases' verified manifests.
App-controlled strings in it (a package's display name, URLs) are rendered as
text only.

## What the consent binds

| Kind | The passkey signs `confirm_challenge(subject, method, args, nonce)` with `args` = |
| --- | --- |
| Release | `{ version, policyDigest }`: `policyDigest` is SHA-256 of the release's Sigstore-verified measurements as the node reads them when it writes the approval, so a release re-published under the same tag with other measurements is another approval. A node that cannot fetch them refuses (`503`); on mock attestation, where no node checks measurements, the digest is over none (`{ "profiles": {}, "version" }`) |
| Upgrade | `{ bundle, migrate, manifest }`: the target WASM's hash and the target release's signed-manifest hash (`VerifiedBundle::manifest_hash`: SHA-256 of the canonical manifest, every artifact digest included; `null` only for a raw development bundle, which has no manifest) |
| Outbound | `{ package, prefixes, replace }`, with the prefixes listed on the page, never `"manifest"` |

Before asking for the passkey and again before writing, the page checks that
what it showed still holds: the app still runs the bundle it ran, the target
version is still the same `.mpk`, the package's newest release (whose
declarations it listed) is still the same. Otherwise `409 CONSENT_STALE`, and
the app asks again so the person sees the new facts.

The routes bind the same arguments whoever calls them: `POST /apps/{app}/upgrade`,
`POST /auth/releases` and `/orgs/{org}/releases` compute the manifest hash and
the measurements digest themselves, and the challenge they hand out commits to
them. A target or release that changes between the `412` and the assertion no
longer matches the challenge, and the approval is refused. Withdrawing a
release lets nothing in and binds `{ version }` alone.

## Limits

| Limit | Value |
| --- | --- |
| A request's life (`CONSENT_REQUEST_TTL`) | 10 minutes |
| A decided request's result stays readable (`CONSENT_RESULT_TTL`) | 10 minutes after the decision |
| Requests one node holds (`MAX_CONSENT_REQUESTS`) | 1,000, then `429` |
| Undecided requests per account per node (`MAX_OPEN_REQUESTS_PER_ACCOUNT`) | 8, then `429` |
| `returnTo` (`MAX_RETURN_TO_BYTES`) | 2 KiB |
| Prefixes in one outbound request (`MAX_REQUESTED_PREFIXES`) | 64 |
| Request and page bodies (`MAX_CONSENT_BODY_BYTES`) | 64 KiB |

## What it does not protect

- **The page travels under TLS, not the sealed channel.** A browser cannot open
  a sealed session without a client library, so the page, its model and the
  approve and decline posts are plain HTTPS to the node. Whoever terminates TLS
  in front of the node can read what is being approved and could serve another
  page in its place. It cannot change what is approved (the arguments were fixed
  inside the sealed channel when the app asked, and the passkey signs a
  challenge over them), and cannot approve without the person's passkey.
  Terminate TLS inside the TD to close this.
- **The relying party.** The passkey must be usable on the node's origin: the
  cluster's `--rp-id` must be a registrable suffix of the node's host. The node
  accepts consent-page assertions from its own nodes' origins and the cluster's
  `--origins`, never from an app's origin.
- **Requests live in one node's memory.** A restart forgets them; the app asks
  again. The page is on the node that issued the request (its `url`).
