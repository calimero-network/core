Some decisions belong to the account holder alone: which mero-tee releases may
hold their data, which code may read it, which addresses it may be sent to
([Deployment governance](/protocol/governance/)). Each is approved with a fresh,
user-verified passkey assertion that the node logs as consent. Apps still need
to prompt for them: a new version is out, a feature needs an outbound host. The
**consent page** is how an app does that without ever being the page that asks
for the passkey.

## Why the app's own page cannot ask

A passkey assertion is blind. The authenticator shows the person a site name
and a fingerprint prompt, never what the challenge commits to. Whatever page
starts the ceremony decides what the person believes they approve.

An app's frontend is the publisher's code, served from the bundle and possibly
closed source. If it could run an approval ceremony, it could show "update to
1.2.1" and have the passkey sign an upgrade to something else, or show "allow
analytics" and approve every prefix the manifest declares. So a session opened
on an app's origin is bound to its package and refused every approval route
([Accounts, passkeys & sessions](/protocol/identities/#which-credential-may-do-what)).
That stays true. Instead, the app asks the **node** to ask the person.
Which routes a package-bound session is refused, and the consent kind that
replaces each, are side by side in [Sessions & authority](/protocol/sessions-and-authority/).

1. **Request.** The app calls `POST /consent/requests` inside the sealed
   channel with any session of the account, a package-bound one included:

   ```json
   { "kind": "upgrade", "subject": { "app": "<appId>", "toVersion": "2.0.0" },
     "returnTo": "https://<label>.<apps-domain>/2.0.0/settings" }
   { "kind": "release", "scope": "account" | { "org": "<orgId>" },
     "subject": { "version": "1.4.0", "withdraw": false }, "returnTo": "…" }
   { "kind": "outbound", "scope": "account" | { "org": "<orgId>" },
     "subject": { "package": "<package>?", "prefixes": ["https://api.example/"]? },
     "returnTo": "…" }
   { "kind": "createOrg", "subject": { "name": "Acme" }, "returnTo": "…" }
   { "kind": "createInvite",
     "subject": { "org": "<orgId>", "role": "member", "teams": ["<teamId>"]?,
                  "ttlSecs": 604800?, "uses": 1?, "allApps": false? },
     "returnTo": "…" }
   { "kind": "acceptInvite", "subject": { "token": "inv_…" }, "returnTo": "…" }
   { "kind": "leaveOrg", "subject": { "org": "<orgId>" }, "returnTo": "…" }
   { "kind": "removeMember", "subject": { "org": "<orgId>", "account": "<accountId>" },
     "returnTo": "…" }
   { "kind": "setMemberRole",
     "subject": { "org": "<orgId>", "account": "<accountId>", "role": "admin" },
     "returnTo": "…" }
   { "kind": "setMemberTeams",
     "subject": { "org": "<orgId>", "account": "<accountId>",
                  "teams": [{ "team": "<teamId>", "role": "member"?, "capabilities": 3? }] },
     "returnTo": "…" }
   { "kind": "removeMemberTeams",
     "subject": { "org": "<orgId>", "account": "<accountId>", "teams": ["<teamId>"] },
     "returnTo": "…" }
   { "kind": "revokeInvite", "subject": { "org": "<orgId>", "inviteKey": "<key>" },
     "returnTo": "…" }
   { "kind": "renameOrg", "subject": { "org": "<orgId>", "name": "Acme Labs" },
     "returnTo": "…" }
   { "kind": "deleteOrg", "subject": { "org": "<orgId>" }, "returnTo": "…" }
   { "kind": "setCapabilities",
     "subject": { "org": "<orgId>", "account": "<accountId>"?, "team": "<teamId>"?,
                  "capabilities": 3 },
     "returnTo": "…" }
   { "kind": "setAllApps",
     "subject": { "org": "<orgId>", "account": "<accountId>", "allApps": true },
     "returnTo": "…" }
   ```

   The organization kinds (`createOrg` onwards) are how an app's frontend
   manages organizations at all: a package-bound session is refused every
   organization route (`POST /orgs`, members, teams, invites, redemption,
   capabilities, renaming, deleting; `403`) except its own package's channels
   ([Package-bound sessions](/protocol/identities/#package-bound-sessions)),
   so an app that creates
   workspaces, invites people, moderates them or changes a workspace's
   settings asks here
   ([Organizations and invites](#organizations-and-invites)).

   A release request approves by default; `"withdraw": true` asks to withdraw
   the release's approval instead (a console's *Withdraw*). Unknown fields are
   refused. The node checks the caller could make this
   approval at all, with the route's own rules, before any page exists: the
   governance holder; for an organization's release, `APPROVE_RELEASES`
   there (`403`); for an upgrade, whoever the package names
   (`SystemState::may_upgrade`: a package that declares `upgrades:
   publisher` is its publisher organization's, `409` while no organization
   has bound its key, and an owner-upgraded app is never moved to a
   publisher release, `403`), and a release deadline that stops the
   upgrade (`409 RELEASE_DEADLINE`); organization membership; a
   package-bound session only about its own package and apps. `/approve`
   asks again, before the passkey, so a capability revoked while the page
   is open is refused there. It
   resolves the subject from its own state and the releases' verified `.mpk`
   files, and freezes what the page will show. It answers
   `{ "requestId", "url", "expiresAt", "code" }`; `code` is the request's
   [confirmation code](#the-confirmation-code), which the app or console shows
   before it sends the person to `url`. The request lives in that node's
   memory, bound to the account, for 10 minutes (`CONSENT_REQUEST_TTL`), and
   can be decided once.
2. **Page.** The app sends the person to `url`, `GET /consent/{id}` on the
   node's own public URL. The page is static HTML compiled into `merod`: no
   app code, an inline script and stylesheet allowed by their hashes only,
   `default-src 'none'`, `connect-src 'self'`, `frame-ancestors 'none'`,
   `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control:
   no-store`. It reads `GET /consent/{id}/model` and shows it.
3. **Passkey.** *Approve* posts `POST /consent/{id}/approve`. The node runs the
   very route a signed-in client would run (`/apps/{app}/upgrade`,
   `/orgs/{org}/releases`, `/orgs/{org}/outbound`; `"scope": "account"` is the
   account's [personal organization](/protocol/organizations/#personal-organizations),
   since an account approves nothing of its own) with the arguments frozen in the request, so the
   `412 CONFIRM_REQUIRED` challenge commits to exactly what the page showed.
   The page asks the authenticator for a user-verified assertion and posts it
   back as `confirm`. The node checks that the passkey is one of the request's
   account, checks its authority again, writes the approval with the
   assertion as consent, and marks the request approved. *Decline* posts
   `/consent/{id}/decline`; nothing is approved.
4. **Back.** The page navigates to
   `returnTo?request_id=<id>&result=approved|declined`. If that redirect is
   lost, the app asks `GET /consent/{id}/result` (sealed, the same account;
   any node answers, asking the node that holds the request):
   `{ "requestId", "kind", "status": "pending|approved|declined", "decidedAt" }`,
   plus `outcome` once an organization request whose route answers something
   is approved (below).

`POST /orgs` and `POST /invites/{token}/redeem` take no passkey from a
person on the cluster's own page; through the consent page they do, so the
person, not the app that sent them, creates the organization or joins it.
Both step-ups are over the account (`account:<id> / __create_org / { name }`,
`account:<id> / __accept_invite / { inviteKey }`) and are not logged: the
log records exactly the `CreateOrg` and `RedeemInvite` the routes write.
`createInvite` runs `POST /orgs/{org}/invites` itself, whose consent
(`org:<org> / __create_invite`) is logged as always.

The node asks the rules first, before any page exists: an organization's
name (`400`), the inviter's membership (`404`), an invite above their own
role or an owner invite (`403`), `allApps` below admin (`403`), a `ttlSecs`
of 1 second to 90 days and at most 64 teams (`400`), and for
`acceptInvite` an invite that exists, is unexpired and has uses left
(`404`). The log judges the rest (`INVITE_MEMBERS`, teams the inviter sees)
when the approval is written.

What the approval made reaches only the account and app that asked, through
the sealed `/result`, as `outcome`: `{ "orgId" }` for `createOrg` (with
`teamId`, see below),
`{ "token" }` for `createInvite` (the page's own answer, which travels in the
clear, never carries it), `{ "org" }` for `acceptInvite`, `{ "orgId", "name" }`
for `renameOrg` and `{ "apps" }` (the apps deleted) for `deleteOrg`; the other
kinds' routes answer nothing, and neither does `outcome`. The request is
held in memory and never logged, so an invite token in an `acceptInvite`
request, or minted by a `createInvite` one, leaves with it.

A `createOrg` asked from an app's frontend (a session bound to its package)
makes the organization with that app's own team in it, in the same approval
and the same log entry (`CreateOrg { app_team }`): the team `ScopeApps` would
make for the package (open, the creator its lead, its members able to make
channels below it), so the frontend runs its channels there at once. The page
says so (`appTeam { package, name }` in the model), the step-up states it
(`{ name, appTeam }`), and `outcome` carries the team's `teamId`. On a cluster
whose version is below 1.0.0-rc.22 (`Feature::OrgAppTeam`), or for a package
not installed, the organization is made bare, as before.

#### Moderation and settings

The other organization kinds run the API's own route as the person, with the
route's own logged consent, so the log entry is exactly the API's and no
feature gate is new:

| Kind | Route it runs | Who may ask (judged at request time, again at apply) |
| --- | --- | --- |
| `leaveOrg` | `DELETE /orgs/{org}/members/{self}` | any member but the owner (`409`: ownership moves first) |
| `removeMember` | `DELETE /orgs/{org}/members/{account}` | an admin; never the owner (`403`), never oneself (`400`, that is `leaveOrg`) |
| `setMemberRole` | `POST /orgs/{org}/members` | an admin; the owner for ownership (`403`); a current member only (`404`), and a change (`409`) |
| `setMemberTeams` | `POST /orgs/{org}/members/{account}/teams` | each row as `SetTeamMember` judges it: a team's lead, or `MANAGE_MEMBERS` there below lead (`403`); 1 to 64 teams (`400`) |
| `removeMemberTeams` | `DELETE /orgs/{org}/members/{account}/teams` | the member themself, or whoever manages each team (`403`) |
| `revokeInvite` | `DELETE /orgs/{org}/invites/{key}` | whoever sees the invite (`SystemState::sees_invite`; else `404`) |
| `renameOrg` | `POST /orgs/{org}/name` | the owner or an admin (`403`); a name that fits (`400`) |
| `deleteOrg` | `DELETE /orgs/{org}` | the owner (`403`); not while it owns a deployment (`409`) |
| `setCapabilities` | `POST /orgs/{org}/capabilities` | with `team`: its managers or `MANAGE_MEMBERS` there; without: an admin (`403`); a team the asker sees, a member with a row there (`404`) |
| `setAllApps` | `POST /orgs/{org}/all-apps` | an admin (`403`); a member (`404`), and a change (`409`) |

Outside the organization every kind answers `404`, and ids longer than
`MAX_SUBJECT_ID_BYTES` (128) are `400`. The page names people by the name
the approver sees them by (their self-set name in the organization, else
their account's name; "you" for the approver) and teams by their names, and
says what each change takes: the teams and apps a member who leaves or is
removed loses, the capabilities gained and lost, and for `deleteOrg` the
counts of members, teams, invites and apps under `attention` (`deletes`).
Handing ownership over is flagged `transfersOwnership`, and granting
`MANAGE_MEMBERS`, `MANAGE_APPLICATION` or `APPROVE_RELEASES`
`grantsManagement`. Where a fact the page showed could change while it is
open (a member's role, the organization's name, what a deletion takes, the
capabilities held, the all-apps grant), `/approve` answers
`409 CONSENT_STALE` if it did.

### Where the app may be sent back

`returnTo` is never arbitrary: a node that redirects anywhere would lend its
trusted page to phishing. For a package-bound session it must be one of
the package's origins (`api::app_origin`: its served frontend origin
`{label}.{apps-domain}`, a served custom domain, or a registered origin) or an
origin the package's newest signed manifest names (`links.frontend`,
`frontendAliases`);
for an unbound session, one of the cluster's configured `--origins`. It must
be `https` (`http` only for `localhost`), without credentials or a fragment,
and at most 2 KiB. Otherwise `400 RETURN_TO_NOT_ALLOWED`.

## What the page shows

The page is written for the person who approves, not for an engineer. The
main view is short; everything else is one click away under *Details*. From
top to bottom:

1. **Header.** The Calimero logo and "Check your address bar shows *host*",
   the page's own host, always in view.
2. **Who is asking.** The app and its publisher in plain words ("Team notes
   by Acme Inc.": the signed manifest's `metadata.name` and `author`), and the
   account approving ("Signed in as …").
3. **The headline**, the model's `title`: "Update Team notes to version
   1.5.0", "Allow a new secure server version (2.3.131) to hold Acme's data",
   "Stop server version 2.3.128 from receiving Acme's data", "Allow Team notes
   to send data to api.openai.com"; below it one sentence of what happens,
   the model's `after`.
4. **What needs care**, only when there is some: `attention`, the things not
   to miss, as "Needs your attention". For an upgrade each entry is present
   only when it applies: sends data to new addresses (hosts only), adds a new
   sign-in address, lets anyone use methods without signing in (methods added
   or newly public), declares its stored data at another state version
   although an update runs no migration, removes features (methods removed),
   another publisher key; with none, "No new permissions." A withdrawal of the
   last approved release is flagged too. A check below that calls for care (a
   new publisher key, a test cluster) is repeated here as "Check before you
   approve".
5. **The confirmation code**, large: the app or console that sent the person
   here shows the same one.
6. **Approve with passkey** (*Withdraw approval* for a withdrawal) and
   **Decline**, with the status line and the expiry below.
7. **Details**, collapsed:
   - **What happens**: the model's `points`, two to five plain sentences
     (what approving allows, that nothing changes until they approve, what a
     withdrawal stops and that nothing is deleted).
   - **How you know this is legit**: checks a person can make. The page is
     served by their node at *host*, not by the app; the passkey will ask to
     sign in to `rpId`, and any other site means cancel; for an upgrade or
     outbound request, published and signed by the publisher (the
     organization its key is bound to on the cluster, when there is one), with whether the
     key is the one the running version (or every release of the package) was
     signed with; for a release, built by Calimero's public release process and
     its signature verified by the node, or, on mock attestation, "Test
     cluster: no hardware checks". When the node is configured with an
     [independent verifier](#the-independent-verifier), every kind gets a
     line "Check this server's hardware and software on *verifier host* ↗",
     a link that opens in a new tab, with the host shown as text and the ask
     to check that the page opens there (on mock attestation it says there is
     nothing to verify instead of linking).
   - **Why you approve here, not in the app**: the node serves the page, so
     an app can ask but cannot change what is shown or approve for the person.
   - **Technical details**: everything below, long values cut to one line
     with the full value as their title and selectable, and every empty list
     left out.

| Kind | Technical details, from node-side data only |
| --- | --- |
| **Release** | The version; whether it is already approved and what is approved now; which of the cluster's nodes attest it; this node's profile if it runs it; the release's signed measurements per profile and their digest (on mock attestation it says there are none); links to the signed release and its Sigstore-signed `published-mrtds.json`, with how to verify them independently; the deadline, if any |
| **Release withdrawal** | The version; whether it is approved now (if not, that withdrawing changes nothing) and what else is; whether it is the only approved release, which the node refuses to withdraw; which of the cluster's nodes attest it; this node's profile if it runs it. No measurements: a withdrawal lets nothing in, so it never waits on fetching them. The page says what changes: the nodes that hold the data send nodes on that release no more Raft entries or snapshots, and no app is placed or moved onto them; and what does not: nothing is deleted or moved, a replica already there keeps what it holds until the operator moves it, and one that leads an app keeps leading it until leadership moves |
| **Upgrade** | The app, current and target version, the publisher's key and author, and a **capability sheet** computed from the two signed manifests and the `calimero:abi` section each component embeds: outbound prefixes added and removed; frontend origin and aliases, with every **new sign-in origin** listed (a page there could act in the app as the person); interfaces used and exported; methods added, removed or changed (kind, passkey confirmation, public and its rate, accepted from the system, other apps or only the app's actions, parameters and result); events; timers; the state version each side declares (an update is code only: no migration runs); SDK and build information; the `.mpk`, WASM and manifest hashes |
| **Outbound** | The package and its publisher key, the release whose declarations are listed, the prefixes being approved, which of them are new, which are already approved |
| **New organization** | The name; that the person becomes its owner |
| **New invite** | The organization, the role, the teams by name, how many may join and until when, `allApps`, and that the app receives the link |
| **Joining** | The organization, the role, the teams by name, the person's current role there if any (they keep the higher), `allApps` |
| **Moderation and settings** (`leaveOrg` … `setAllApps`) | The organization and the people by the name the approver sees them by; the teams and apps a member who leaves or is removed loses; the role, teams or capabilities before and after; for `deleteOrg` the counts of members, teams, invites and apps it takes (`attention`: `deletes`, `transfersOwnership`, `grantsManagement`) |

Each kind's model also keeps the engineer's wording: `headline`, `before`
(what holds until the person approves), `after` (what changes once they do)
and `notes`, shown under *Technical details*.

### The model's plain-language fields

| Field | Kinds | What it is |
| --- | --- | --- |
| `title` | all | The headline in plain words |
| `points` | all | Two to five plain sentences: what approving means |
| `attention` | all | `[{ "flag", "text", "items" }]`, what not to miss; `items` are hosts, origins or method names. Flags: `sendsData`, `newSignIn`, `newPublic`, `stateVersion`, `removesFeatures`, `newPublisherKey` (upgrade), `lastApproved` (withdrawal), `transfersOwnership` (`setMemberRole` to owner), `grantsManagement` (granting `MANAGE_MEMBERS`, `MANAGE_APPLICATION` or `APPROVE_RELEASES`), `deletes` (`deleteOrg`). Empty: no new permissions |
| `app` | upgrade, outbound | `{ "name", "package" }`: the manifest's display name and the package id |
| `publisher` | upgrade, outbound | `{ "name", "signer", "keyChanged", "org" }`: the manifest's author (`null` when it names none), the verified signing key (`did:key`), whether it differs from the running version's, and the organization the key is bound to on this cluster (`{ "id", "name" }`, from `BindPublisher`; `null` while unbound). The page names that organization as the publisher when there is one |
| `release.deadline` | release | `{ "after", "afterSecs", "passed" }` when the operator set an end-of-new-work deadline for the version (`SetReleaseDeadline`, `GET /releases`), else `null`; `points` then say it in plain words ("After Nov 15, 2026 (UTC), new apps, installs and updates for Acme's apps pause until this version (or a newer one) is approved") |
| `requestedBy` | all | `{ "package", "name", "publisher", "returnOrigin" }`: the asking package (a package-bound session's, else `null`), its newest release's display name and author |
| `rpId` | all | The relying party ID the passkey prompt will name |
| `code` | all | The [confirmation code](#the-confirmation-code) |
| `verifier` | all | `{ "url", "host", "release", "mock" }` when the node has `--attestation-verifier-url`, else `null`: the link to the [independent verifier](#the-independent-verifier) for this node (its `--public-url`) and its own mero-tee release, the verifier's host to show beside it, and whether the node runs mock attestation (then the page does not link) |

The author and display name are what the publisher wrote in the signed
manifest; the node verifies the signature and the key, not that the name is
true. The page says which key signed.

### The independent verifier

Everything the page says about the node comes from the node. A tampered node
could serve a page that says anything, including a green "verified": a check
run on this page, by this page's script, proves nothing. So the page does not
check the node's attestation itself; it links to a verifier that does, on its
own origin. Calimero runs one at `https://verify.calimero.network`, and the
operator names it with `merod --attestation-verifier-url`
([merod](/operate/merod/#node-flags)). The link has the shape mdma uses for
each node:

```
{verifier}/mero-tee?node_url=<the node's public URL, no trailing slash>&release_tag=mero-tee-v<release>
```

The verifier fetches the node's quote over a fresh nonce and checks it against
the signed measurements of that mero-tee release. Since the page is the node's,
it could also link to a fake verifier; that is why it shows the verifier's host
as text next to the link and asks the person to check that the page opens
there, as it asks them to check its own address. The link opens in a new tab
(`target="_blank"`, `rel="noopener noreferrer"`); it is plain navigation, so
the page's content security policy is unchanged. On mock attestation there is
no quote to verify, and the page says so instead of linking.

### The confirmation code

A short code that ties the page to the request the person's own app or
console made, so a link to another request (on the same node) shows a
different code. The create answer and the model both carry it as `code`; a
client can also compute it:

1. Take `SHA-256` of the request id's UTF-8 bytes.
2. Read the first 4 bytes as a big-endian unsigned 32-bit integer and keep
   its top 30 bits.
3. Write them as six 5-bit groups, most significant first, each as a
   character of Crockford's base32 alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`.
4. Put a `-` after the third: `XXX-XXX`.

For example, `1.AAAAAAAAAAAAAAAAAAAAAA` is `R02-9P2` and
`2.q7Xb3kR0fLzM8nW1yVt5cA` is `54E-429`
(`consent_page::confirmation_code`). The code is not a secret and proves
nothing on its own: the passkey's challenge is what binds the approval.

The model is what the app can neither write nor alter: it is frozen when the
request is made, from the node's state and the releases' verified manifests.
App-controlled strings in it (a package's display name, URLs) are rendered as
text only.

## What the consent binds

| Kind | The passkey signs `confirm_challenge(subject, method, args, nonce)` with `args` = |
| --- | --- |
| Release | `{ version, policyDigest }`: `policyDigest` is SHA-256 of the release's Sigstore-verified measurements as the node reads them when it writes the approval, so a release re-published under the same tag with other measurements is another approval. A node that cannot fetch them refuses (`503`); on mock attestation, where no node checks measurements, the digest is over none (`{ "profiles": {}, "version" }`) |
| Upgrade | `{ bundle, migrate, manifest }`: the target WASM's hash and the target release's signed-manifest hash (`VerifiedBundle::manifest_hash`: SHA-256 of the canonical manifest, every artifact digest included; `null` only for a raw development bundle, which has no manifest) |
| Outbound | `{ package, prefixes, replace }`, with the prefixes listed on the page, never `"manifest"` |
| `createOrg` | `account:<a> / __create_org / { name }`, with `appTeam` (the package) when the asking app's team comes with it (not logged; the log records `CreateOrg` as `POST /orgs` writes it, with `app_team`) |
| `createInvite` | `org:<org> / __create_invite / system::invite_args` (logged, as the route's) |
| `acceptInvite` | `account:<a> / __accept_invite / { inviteKey }` (not logged; the log records `RedeemInvite`) |
| `leaveOrg`, `removeMember` | `org:<org> / __remove_member / { account }` (oneself for `leaveOrg`) |
| `setMemberRole` | `org:<org> / __set_org_role / { account, role }` |
| `setMemberTeams` | `org:<org> / __set_team_members / { account, teams }` |
| `removeMemberTeams` | `org:<org> / __remove_team_members / { account, teams }` |
| `revokeInvite` | `org:<org> / __revoke_invite / { inviteKey }` |
| `renameOrg` | `org:<org> / __rename_org / { name }` |
| `deleteOrg` | `org:<org> / __delete_org / { org }` |
| `setCapabilities` | a member's: `org:<org> / __set_capabilities / { team, account, capabilities }`; a default: `__set_default_capabilities / { capabilities }` or `{ team, capabilities }` |
| `setAllApps` | `org:<org> / __set_all_apps / { account, allApps }` |

Before asking for the passkey and again before writing, the page checks that
what it showed still holds: the app still runs the bundle it ran, the target
version is still the same `.mpk`, the package's newest release (whose
declarations it listed) is still the same. Otherwise `409 CONSENT_STALE`, and
the app asks again so the person sees the new facts.

The routes bind the same arguments whoever calls them: `POST /apps/{app}/upgrade`,
`POST /orgs/{org}/releases` computes the manifest hash and
the measurements digest themselves, and the challenge they hand out commits to
them. A target or release that changes between the `412` and the assertion no
longer matches the challenge, and the approval is refused. Withdrawing a
release lets nothing in and binds `{ version }` alone, through the page
(`"withdraw": true`) as through the route; the node fetches no measurements
for it, so revoking a bad release never waits on the network. The last
approved release cannot be withdrawn: `/approve` answers `400 REJECTED`
("the last approved release cannot be withdrawn") after the passkey, and the
request stays pending. A withdrawal the person confirms is reported like any
consent: `result=approved` (they approved the withdrawal).

## Limits

| Limit | Value |
| --- | --- |
| A request's life (`CONSENT_REQUEST_TTL`) | 10 minutes |
| A decided request's result stays readable (`CONSENT_RESULT_TTL`) | 10 minutes after the decision |
| Requests one node holds (`MAX_CONSENT_REQUESTS`) | 1,000, then `429` |
| Undecided requests per account per node | 1: a new request replaces the older one, whose page and `/result` then answer `404` |
| `returnTo` (`MAX_RETURN_TO_BYTES`) | 2 KiB |
| Prefixes in one outbound request (`MAX_REQUESTED_PREFIXES`) | 64 |
| Request and page bodies (`MAX_CONSENT_BODY_BYTES`) | 64 KiB |

## What it does not protect

- **The page travels under TLS, not the sealed channel.** A browser cannot open
  a sealed session without a client library, so the page, its model and the
  approve and decline posts are plain HTTPS to the node. Whoever terminates TLS
  in front of the node can read what is being approved and could serve another
  page in its place. It cannot change what is approved (the arguments were fixed
  inside the sealed channel when the app asked, and the passkey signs a
  challenge over them), and cannot approve without the person's passkey.
  Terminate TLS inside the TD to close this. Calimero Cloud does: the node's
  TLS key is made inside the TD and certified only against its attestation,
  and mdma watches Certificate Transparency for any other certificate on its
  names.
- **What a forged page could still do.** Serving a page on the node's own
  host, it could show one request's words and ask the passkey for another
  request of the same account. Two rules leave it nothing to swap in: an
  account has one undecided request per node (a new one replaces the older,
  whose page and `/result` answer `404`), and an app checks, after the
  redirect, that `/result` reports its own request decided (the SDKs' consent
  helpers do). Answers carry `Strict-Transport-Security`, so a browser that
  has seen the page over TLS never loads it over plain HTTP.
- **The relying party.** The passkey must be usable on the node's origin: the
  cluster's `--rp-id` must be a registrable suffix of the node's host. The node
  accepts consent-page assertions from its own nodes' origins and the cluster's
  `--origins`, never from an app's origin.
- **Requests live in one node's memory.** A restart forgets them; the app asks
  again. The page is on the node that issued the request (its `url`).
