The **operator** runs the machines: it starts nodes, gives them a network and
disks, and keeps the cluster healthy. It is not trusted with app data. The
**Ops API** (`/ops/*`) gives it what operating requires and nothing that opens
an app. mdma's `OpsClient` and `meroctl --ops-token TOKEN ops …` use it.

## The credential

The operator holds a bearer token. A node is given either the token
(`--ops-token`) or only its SHA-256 (`--ops-token-sha256`), so a machine's
metadata or configuration need not hold anything usable. The token is compared
in constant time, inside the sealed channel like every other request. A node
given neither has the Ops API disabled. The operator's actions that the system
log records carry the actor `operator`, which no account id can be.

## What it can do

| Route | What |
| --- | --- |
| `GET /ops/status` | This node, the system group's Raft status, the Raft status of the app groups hosted here (by app id), the node list, the governance, and counts of apps and accounts |
| `GET /ops/metrics` | Prometheus text: nodes, apps, accounts, organizations, packages, bundle bytes; groups hosted and led here; open streams; system applied index, leadership, voters, learners; each hosted group's applied index; the build release |
| `GET /ops/placement` | Each app's group and replica node ids; each node's zone, attested release and app count |
| `GET /ops/apps` | What each app runs and which releases may hold it (below) |
| `GET /ops/orgs` | Each organization's id and the releases approved to hold its apps |
| `POST /ops/nodes` | Register a node; the system leader then adds it as a learner ([Replication](/protocol/replication/#joining-nodes)) |
| `POST /ops/apps/{app}/replicas` | Move an app to a new replica set, onto approved releases only ([Replica moves](/protocol/replication/#replica-moves)) |
| `GET` / `POST /ops/quotas` | Read or set the per-account quotas |
| `POST /ops/backup` | Write sealed snapshots of the app groups this node leads (below) |

And, only where the deployment's [governance](/protocol/governance/) gives
the operator that decision:

| Route | Decision |
| --- | --- |
| `POST /ops/releases { version, approved }` | Release approvals, for every app |
| `POST /ops/apps/{app}/upgrade`, `POST /ops/orgs/{org}/upgrade` | App upgrades, to a release it installed or one the app's owner may see |
| `POST /ops/packages`, `/ops/packages/install`, `GET /ops/packages`, `DELETE /ops/packages/{p}[/{v}]` | Installing the releases it upgrades to (it lists and removes only what it installed) |
| `POST /ops/outbound { package, prefixes, replace }` | Outbound approvals, for every app |

Elsewhere, the operator configures the node: the outbound policy (which hosts
any app may reach, and the secrets requests may carry), the registry releases
are installed from, the domain app frontends are served under, and the
measurement policy for peers.

## What runs where

`GET /ops/apps` is how the operator follows a rollout: per app, its id, group
and **scope** (`{ kind: "org", org }`, or `{ kind: "account" }` for an
account's own app, never the account), the **bundle digest** it runs, its publisher (the package's pinned signer,
with the package), who holds
app upgrades, its **last upgrade** (`from` and `to` digests, when, whether it
succeeded, and the **actor kind**: `owner`, `member` or `operator`), the
mero-tee releases approved to hold its data, and each replica's node, release,
and whether that release is approved for the app. `GET /ops/orgs` gives each
organization's approved releases. Both are paged (`?after=ID&limit=N`, at most
`MAX_REPORT_PAGE`, 100, per page; `next` continues).

What it leaves out is deliberate:

- **Package names and versions only for releases the operator installed.**
  Which package an app runs can say what an organization does (a package
  uploaded for one customer is named after it), so the report names a release
  only where `sees_release` lets the operator see it anyway: the releases it
  installed itself (`/ops/packages`, its catalog). For any other app,
  `package` is `null` and only the bundle's digest (`hex(SHA-256)` of its WASM)
  appears: enough to group apps that run the same code and to see an upgrade
  happen, nothing that names it.
- **The actor's kind, not the actor.** An upgrade's account, its error text
  (which the app's code can write) and its upgrade run are left out.
- Approved releases and governance are not secrets: every replica attests the
  governance, and the approved releases decide which nodes the operator can
  place an app on.

## What it cannot do

There is no Ops route that runs a view, reads state, streams events, lists an
account's apps, downloads a blob or a bundle, or returns a credential. Status,
metrics and the reports above give counts, ids, digests, releases and Raft positions; app names, organization
names, people's names and app state never appear. The operator cannot sign in
as anyone: sessions are minted only after a passkey ceremony, under a key held
in the system state.

The operator does control availability. It can stop, freeze or restart nodes,
withhold the network, or refuse to register nodes. An app stays available
while a majority of its replicas run.

## Backups

With `--backup-dir`, every node writes, every 60 seconds (and on
`POST /ops/backup`), a copy of the current snapshot file of each app group it
leads, first asking for a fresh snapshot if the last one is older than what it
has applied. A backup is the log's own snapshot file, sealed frame by frame
under the cluster's storage key, stored as
`{dir}/{app}/{index:020}.{group}.{snapshot}.snap`. Only a node holding the
cluster's K_r can open one (`backup::latest`). The directory stands in for
object storage.

Restoring a snapshot into a running cluster is not done yet.

## Offline inspection

`merod inspect` reads a stopped node's store: without the storage key, the
layout and sealed sizes only; with it, each group's metadata (vote, applied
index, membership).
