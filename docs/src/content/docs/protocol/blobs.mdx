A **blob** is immutable, content-addressed bytes kept outside every log: an
attachment, an image, a model. Log entries are capped at 1 MiB and should stay
small, so anything large goes to the **blob store** and the log carries only
its id. The same store holds bundles and uploaded `.mpk` releases. Apps are
`calimero:app` components, and the node keeps their blobs as described here
(spec `app-runtime-v0.14`, the blob requirement).

## The store

Each node keeps blobs in its own RocksDB `blobs` column, sealed under the
cluster's storage key like everything else ([Storage schema](/protocol/storage/)).
A blob's id is `hex(SHA-256(bytes))`; the API also accepts the base58 form.

- **Writes reach a majority.** Storing a blob writes it locally and pushes it to
  every other node (`internal/blob`); the write succeeds once a majority of the
  cluster's nodes hold it.
- **A node that missed one fetches it.** A node asked for a blob it does not
  hold — it was down when the blob was stored — fetches it from a peer
  (`internal/blob/get`), checks the hash, and keeps it.

A blob larger than `MAX_BLOB_BYTES` (47 MiB, what still reaches every node
inside the sealed envelope) is refused `413 TOO_LARGE` up front; one past the
sealed cap (64 MiB) is refused by the envelope. Larger content is a sealed
[file](#files-of-component-apps), which is stored in segments.

## Which blobs are an app's

Bytes in the store belong to no one. The node records each of an app's blobs
(`size`, the uploader's `Content-Type`, a reference count) as host-owned hidden
rows of the app's group (`rows::CBLOB`), outside the keyspace the app writes.
The records replicate with the app and are ordered with its calls.

- **Typed references.** State refers to a blob through a `BlobRef`, which the
  SDK stores as CBOR tag 51,739 (`0xCA1B`) around the blob's 32-byte SHA-256
  and sends in JSON as the 64-hex-digit id. A run that stores a reference to a
  blob the app does not hold traps `HostDenied`.
- **Host-tracked retention.** Every replica counts references from the diffs it
  applies and the values they replace. A blob nothing refers to is held for one
  hour after its upload or after its last reference went (`BLOB_IDLE_MS`), so a
  client uploads first and attaches it with a later call. After that the app
  forgets it, judged against entry timestamps so every replica forgets it in
  the same entry; the leader then collects the bytes (below) and logs
  `componentBlobsCollected`.
- **No bytes in runs.** The WIT `blobs` interface has `info` (size, SHA-256,
  content type; none for a blob the app does not hold) and `grant(id, ttl)`.
  Calls, views, timers, `init` and xcall deliveries may use them; actions may
  not. Content a run must read is a sealed file, below.

## Getting a blob in

`POST /apps/{app}/blobs` (raw bytes) by a signed-in caller who reaches the app
and may write it — not a read-only API key and not a read-only team member.
The blob is stored with the request's `Content-Type` (printable ASCII, at most
127 bytes; `application/octet-stream` when none), which downloads answer with.
The node pins the id on the app's leader, stores the bytes on a majority, then
commits `componentBlob { id, size, mime, tsMs }` to the app's log. Any `sealed`
parameter is refused `400 USE_FILES_API`: sealed files have their own routes.
An app holds at most 100,000 blobs (`429 QUOTA_EXCEEDED` past it).

## Reading, grants and listing

- `GET /apps/{app}/blobs/{id}` downloads a blob the app holds, by anyone who
  reaches the app, with its recorded content type, except a published compute
  output (a grant is needed). A blob the app does not hold is `404`, whether or
  not the bytes exist. A download asks the app's leader whether the app still
  holds it; with no leader answering, `503`.
- **Grants.** `blobs.grant(id, ttl)` returns `<expiresMs>.<mac>`, an HMAC under
  a key derived from the cluster key over the app, the blob and the expiry (the
  run's clock plus 1 s to 24 h). `GET /apps/{app}/blobs/{id}?grant=<grant>`
  downloads with no session on any node until it expires; a bad or expired
  grant answers `404`.
- `GET /apps/{app}/blobs` and `/blobs/{id}/info` list the app's plain blobs and
  their sizes (files are listed only to those who may handle them, below).
- Inside the sealed channel, a download is sealed frame by frame like any
  response.

## Deleting

`DELETE /apps/{app}/blobs/{id}`, by the app's owner (while a member of its
organization) or an organization admin, commits `componentBlobForget`: the app
no longer has the blob, and the API answers `404` for it. Then the node
collects the bytes (`Node::collect_blob`): it deletes them on every node
unless

- another app still holds the same content — asked of each app's **leader**,
  because a lagging replica could miss a record committed a moment ago, and an
  app whose leader does not answer counts as holding it;
- an upload of the same id is between storing its bytes and committing its
  record: every path that stores bytes first pins the id on the app's leader
  until its record commits or fails (a peer's pin is a lease that expires after
  60 s), and every deletion asks whether the id is held or pinned; or
- the content is a bundle or a release `.mpk`.

A leader change between a pin and its commit is not covered: the pin stays on
the old leader.

## Files of component apps

A component app's runs can also make sealed files: a file is written in a call, tick or `init`, and its contents are read only inside a compute run.
A file is a sealed blob.
It shares the blob id namespace and the `BlobRef` type, and `blobs.info` answers for it with an empty content type.
It cannot be downloaded or granted, and no blob upload can claim its id.
A call, view, timer or `init` may create a file and ask for its size and hash, and `files.open` is refused there.
So a sealed file's contents can be read only inside a compute run of the app release the organization approved, and leave only as a compute output published through a logged call.
The node seals a file in the TD as 64 KiB AES-256-GCM chunks under a random data key, and wraps that key under a key derived from the cluster key for this app.
The blob id is the SHA-256 of the ciphertext, so a replica can check what a peer sends.
The app's blob record for the file holds the plaintext size and SHA-256 and the wrapped key, in the hidden rows the guest cannot reach.
The log entry carries these marks and never the ciphertext.

A client uploads a file with `POST /apps/{app}/files` (the raw bytes, up to one part of 16 MiB) or, for a larger file, through an upload session.
The answer is `{ id, blobId, size, sha256, index }` for the plaintext.
A node that does not lead the app passes the request to the leader.
The leader seals the file as a run's files are sealed, stores it on a majority of the app's voters, and then commits the blob record as a command of the node's own, which no `/intents` call can name.
Only the app's owner and the members (not guests) of its organization may upload and list files, even where the app is public.

An upload session lives in the leader's memory, belongs to the account that began it, and takes the file one part per segment.
`POST /apps/{app}/files/uploads { size }` answers `{ uploadId, partBytes, parts, expiresAt }` (`expiresAt` in Unix seconds).
`PUT /apps/{app}/files/uploads/{uploadId}/parts/{k}` takes part `k` as raw bytes, exactly `partBytes` but for the last, and answers `{ next }` once the part is sealed and stored; its segment is pushed to a majority of the voters in the background, at most four segments ahead (past that the answer waits for a slot, up to 20 seconds, then is `503 FILES_UNAVAILABLE` and the resent part replays its answer).
Parts go in order: a part ahead of `next` is `409 PART_OUT_OF_ORDER` naming `next`, a resent part answers its first answer, and a resent part with other bytes is `409 PART_CONFLICT`.
`GET .../uploads/{uploadId}` answers `{ uploadId, size, partBytes, parts, next, expiresAt }`, for a client that resumes.
`POST .../uploads/{uploadId}/complete` waits up to 20 seconds for every segment to reach a majority (else `503 FILES_UNAVAILABLE`, and a retry resumes), charges the quota, commits the mark and answers like the single request; before every part is in it is `409 UPLOAD_INCOMPLETE` naming `next`.
It commits under the key `node:upload-{uploadId}`, so a retried `complete` answers the same file, even after a leader change.
`DELETE .../uploads/{uploadId}` aborts the session and deletes what it stored.
A session that is unknown, belongs to another account, has run out (no part for 15 minutes, or six hours old) or whose leader changed answers `404 UPLOAD_UNKNOWN`, and the client begins again.
An app holds at most 4 sessions, a node 32, and a leader's open sessions declare at most 16 GiB together (`429 TOO_MANY_UPLOADS`).
Nothing is charged before `complete`; a `complete` past the quota is `429 QUOTA_EXCEEDED` and deletes the bytes.
`GET /apps/{app}/files` lists the files (`{ files: [{ id, blobId, size, sha256 }] }`) and `GET /apps/{app}/files/{id}` answers one, to the app's owner and its organization's members; `/apps/{app}/blobs` lists plain blobs only and answers `409 NOT_SUPPORTED` for a file id.
The reason is that a file's SHA-256 is the plaintext's, and would let anyone confirm a guessed document.
`GET /apps/{app}/blobs` lists the files after the blobs, and `GET /apps/{app}/blobs/{id}/info` answers a file's size and SHA-256, to those people only.

The committed entry also records the account that uploaded the file, taken from the authenticated session or API key of the upload, never from a field of the request; a node that forwards the upload to the leader names it, and the leader refuses a name that is no account id.
The app reads it with `runs.uploader` (`files::uploader` in the Rust SDK), which answers none for a file a call or a run made and for an unknown id.
Every upload is sealed under a key of its own, so the same bytes uploaded twice are two files with two ids and two uploaders; the entry of an id the app already holds is refused, so a later upload never replaces the first uploader.
A compute run does not see it.
Everyone else gets the list without files, and `404` for a file's info, as for an id the app does not hold.
Neither answer ever carries the key or any content.
An uploaded file is held like any file: for an hour unless the app stores a `BlobRef` to it.

There is no delete.
`files.finish` returns the blob id, and the app keeps the file by storing it as a `BlobRef`, exactly as for an uploaded blob.
The entry that makes the file also applies the state write that stores the reference, so the file is never collectable in between.
A file nothing refers to is held for an hour from its entry, and one whose last reference went is forgotten the same way a blob is.
Every replica forgets the record in the same entry, and the bytes are then collected from the nodes that hold them.

The ciphertext lives on the app's replicas, not on every node.
Before the leader proposes the entry, the new files are stored on it and pushed to the app's other replicas.
The call proceeds only once a majority of the app's voters hold every new file; otherwise it fails with a retryable `503`, nothing is logged, and its idempotency key is not spent.
A node holds at most 256 MiB of new files' ciphertext across all runs until their entries are proposed; a call that cannot get its share fails with a retryable `503`, is not logged, and does not spend its idempotency key.
A file is stored as segments of 256 sealed chunks (16 MiB of plaintext), each under its own hash, and the file's id is the hash of that list; a replica that misses a segment fetches it from the other replicas when a run opens the file.
If no replica can serve it, a call, tick or `init` is aborted with a retryable `503` and not logged, while a view is told the bytes are not available.
A run reads a file by decrypting it as it goes, and the end of the stream checks the plaintext size and SHA-256 against the mark.
A file that was altered or cut short fails the run with a trap, so no app can ignore it.
Each file has its own random key, so no other app can mark the same ciphertext.

The plaintext bytes of an organization's files count against `maxFileBytesPerOrg` (default 50 GB).
A file counts from the moment it is charged until retention collects it.
The charge is taken before any bytes move, so an upload or a call that would pass the quota fails with `429 QUOTA_EXCEEDED`, nothing is logged and the stored bytes are removed.
When the leader collects the bytes of files the app forgot, the same entry that logs the collection tells the node how many plaintext bytes it released.
Deleting an app or an organization frees its files in the same system command.
A node that stops hosting a deleted app drops the bytes of its files.
The count and the app's log are not one atomic step.
When a record's commit fails, the leader checks whether it was logged and settles the count either way.
A crash between the two can still leave an over-count.
Below cluster version 1.0.0-rc.32, transferring an app from a personal organization to someone outside it, which moved it to their personal organization, was refused if its files would pass that organization's quota; from that version an app is transferred only within its organization.
`GET /auth/usage` shows an account's file bytes per payer.

## Publishing a compute output

A sealed file never leaves the cluster, with one exception: an app's logged write can publish the output of one of its finished compute runs with `runs.publish` (`compute::publish` in the Rust SDK).
The node answers a plain blob of the app, named by the SHA-256 of the plaintext.
From then on `blobs.info` answers it, and `blobs.grant` gives a time-limited link, for example to an outside auditor.
Until an app publishes, the same download answers `409`.

A published blob downloads only through a grant, for every caller including the owner: the plain `GET /apps/{app}/blobs/{id}` answers `404`.
`blobs.grant` of it works only in logged writes (calls, timers, init, xcall deliveries), never in a view, so the log records who shared it.
The owner or an org admin can revoke every grant made so far with `POST /apps/{app}/blobs/{id}/revoke`, after which a new grant holds.
The blob record counts the revokes and a grant names the count it was made under, so every replica refuses a revoked grant, and a new leader does too.
The app also keeps a floor above the count of every published blob it forgot, and a blob made again starts there, so a revoked grant stays refused when the same output is published again.
`DELETE /apps/{app}/blobs/{id}` takes a published blob down: the app forgets it, its bytes are collected and its charge is released.

The platform enforces one rule: the id must be an output of a `done` run of this app.
An uploaded file, a file a call made, another app's output, a failed or cancelled run's output and an unknown id answer the soft error `NOT_A_RUN_OUTPUT`.
Each app decides who may publish, in the method that calls it.
The rule is in the log, not in the leader.
The leader decrypts the output, stores the plaintext on a majority of the app's voters as it does a new file, and only then proposes the entry.
The entry carries the source, the plain blob's id and its size, never the bytes.
Every replica applies the entry only if the source is a file the app's records mark as a done run's output, and the id and size are that file's plaintext hash and size.
Otherwise it answers `NOT_A_RUN_OUTPUT` and changes nothing, so a leader cannot publish anything else.

The plaintext counts against the organization's file quota from the entry until retention collects it.
Retention: the plain blob is held while a `BlobRef` in state names it, and for an hour after.
Publishing an output the app already holds as a plain blob stores and charges nothing again.
A run publishes at most 16 outputs, each at most 47 MiB (the plain blob it becomes; a larger output answers `file too large`) and 64 MiB together.
Past that `publish` answers the soft error `run published too much` and records nothing.

## Limits

| Limit | Value |
| --- | --- |
| A plain blob (`MAX_BLOB_BYTES`) | 47 MiB (`413 TOO_LARGE`) |
| A sealed request (and so one upload request) | 64 MiB |
| Blobs one app holds (`MAX_COMPONENT_BLOBS`) | 100,000 (`429 QUOTA_EXCEEDED` past it) |
| A blob's content type | 127 bytes, printable ASCII |
| A blob held with no reference (`BLOB_IDLE_MS`) | 1 hour |
| A sealed file held with no reference | 1 hour |
| Plaintext bytes of an organization's files | `maxFileBytesPerOrg`, 50 GB (`429 QUOTA_EXCEEDED` past it) |
| New-file ciphertext all runs of a node hold before their entries | 256 MiB |
| A grant | 1 s to 24 h |

## In `calimero-node`

Where the node implements this chapter, by the names in its code: paths are under `crates/node/src`
unless another crate is named. The design and its reasons are above; a module's own detail is in its
`//!` doc, and the node's mental model is [`crates/node/AGENTS.md`](https://github.com/calimero-network/core/blob/master/crates/node/AGENTS.md).

### Bundles are blobs, not log entries

`POST /bundles` stores the WASM in every node's sealed blob store (`internal/blob`, majority
required), then the system log records only `{hash, size}`.
A node missing a blob fetches it from a peer (`internal/blob/get`) on first use.
Log entries are capped at `calimero_log::MAX_ENTRY_BYTES` (1 MiB): openraft gives each append one
heartbeat.
A call whose arguments pass `MAX_ARGS_BYTES` (below that cap) is refused where it arrives (`413
ARGS_TOO_LARGE`), never proposed.

### Blob routes and deletion

Code: `POST/GET /apps/{app}/blobs[/{id}]`; how an app holds one: below.

Bytes live in the cluster's blob store (`hex(SHA-256)`, a majority before the answer, a missing one
fetched from a peer).
A download asks the app's leader whether the app still holds the blob (`blob_held_strong`, through
`Node::ask_leader`, which asks the replicas again through an election for up to
`LEADER_ANSWER_WAIT`; 503 when no leader answers by then).
`DELETE /apps/{app}/blobs/{id}` (owner or org admin) forgets it, then `Node::collect_blob` deletes
the bytes on every node (`internal/blob/delete`) unless another app still holds the same content
(asked of each app's leader; an app whose leader does not answer counts as holding it) or it is a
bundle or a release `.mpk`.
Every path that stores bytes before their record commits pins the ids on the app's leader first, and
holds the pin until the record commits or fails (`node/blob_guards.rs`): `logged_entry` (a publish,
a call's files, a run's outputs; it runs on the leader) and the plain upload (`Node::pin_on_leader`:
locally on the leader, else through `internal/blob/pin`, a lease that expires after `LEASE_TTL` if
the receiving node never releases it).
Every deletion of bytes (`collect_blob`, which the owner's delete, the queued collection and
discarded files call, and a peer's `internal/blob/delete`) asks `Node::blob_in_use`: held or pinned,
as each app's leader answers, unknown counting as in use.
A put of an id (`BlobGuards::put`) also stops a deletion of that id that was between its checks and
its delete, here and on every peer.
A leader change between the pin and the commit is not covered: the pin stays on the old leader.
A blob past `MAX_BLOB_BYTES` (47 MiB) is refused `413 TOO_LARGE` by the node, one past the sealed
cap (64 MiB) by the envelope, in the clear; the client reports both as `TOO_LARGE`.

### Blobs a component holds

(`component/blobs.rs`.)

The cluster's store and routes (`store_blob`, a majority, `fetch_blob`, `collect_blob`,
`blob_held_strong`), but the app holds a blob through a host record (`BlobRecord { size, mime, refs,
idleSinceMs }`, hidden rows `rows::CBLOB`, in memory as `BlobTable`), not a mark in its keyspace.
Upload (`POST /apps/{app}/blobs`, `Content-Type` kept as the mime, at most `MAX_BLOB_MIME_BYTES`)
commits `componentBlob`; the owner's delete `componentBlobForget` (both through `CallRequest::host`,
`Node::component_blob_cmd`).
A `BlobRef` in a stored value is CBOR tag `calimero_app_host::BLOB_REF_TAG`; `apply` counts
references from each diff and the values it replaces (`ref_deltas`), so every replica agrees; a blob
with none is held `BLOB_IDLE_MS` (1 h) from its upload or its last reference, then forgotten against
entry timestamps (`expiry_now`, at most `BLOB_EXPIRY_STEP` per entry) and queued in
`ComponentHead::collect`; the leader's timer poll collects the bytes (`collect_blob`) and logs
`componentBlobsCollected`.
Runs see the records through `RunBlobs` (`HostCore::with_blobs`): `info`, and `grant` =
`<expiresMs>.<HMAC>` under `grant_key(K_c)`, which `GET /apps/{app}/blobs/{id}?grant=` takes without
a session (a bad one is `404`).
At most `MAX_COMPONENT_BLOBS` per app (`429`).

### The sealed file format

Code: `files.rs` (re-exporting `calimero_sealed::file`), `files/wrap.rs`.

A file is 64 KiB AES-256-GCM STREAM chunks (`FileSealer`, `FileOpener`) under a random data key.
The nonce is 4 zero bytes then the big-endian chunk index; the AAD is `calimero.file.v1` then a
last-chunk flag byte.
`FileOpener::finish_expecting` checks the plaintext size and SHA-256 against the mark, as GCM does
not commit to its key.
A file is stored as segments: `SegmentWriter` cuts the ciphertext stream into segments of
`SEGMENT_CHUNKS` (256) whole chunks (`SEGMENT_BYTES`, 16,781,312 stored bytes; the last segment is
the rest), and `SegmentReader` joins them, checking each against the list.
A segment's hash is the SHA-256 of its bytes and the file id is `file_id`: SHA-256 of
`"calimero.file.segments.v1\0" || u32 count || h0 ||... || hn-1`, so an id never equals a plain
blob's content hash.
A mark (`FileMark`) and a record (`FileSeal`) list the segments (`segments`, required, hex, at least
one); `FileMark::segment_hashes` is the one check that the list is well formed and hashes to the
mark's id.
`wrap_key` wraps the data key as salt || nonce || AES-256-GCM under a subkey of `backup::file_key`
(per app, from K_c, not the TEE key), with the app id as AAD.
`wrap_for_job` re-wraps a secret to a job node: ephemeral X25519, then HKDF over both public keys,
the kind (file key or noise seed), the length-prefixed app and run ids, attempt and index.
The job node opens it through `SealedTransport::derive`, which never returns the raw DH output and
labels its HKDF (`calimero_sealed::derive_shared`, shared with the wrap side).
`noise_seed` and `run_token` derive a run's seed and capability from the file key.

**Exporting a file** (`api/exports.rs`): `POST /apps/{app}/files/{id}/export { recipient }` (64 hex,
an X25519 public key) and `GET /apps/{app}/files/{id}/segments/{k}` take the `/files` gate
(`files_gate`: `api::may_handle_files`, fresh system read, even where an `anyone` grant admits
others) and judge the file on the app's leader (`Node::file_record_strong`: `internal/blob/held`
with `record`, which answers the size and `FileSeal`), else `404`; a segment past the last is `404
NO_SUCH_SEGMENT`, and one is read from this node's store or a replica (`segment_from`).
The export answer is `{ app, id, size, sha256, segments, ephemeral, wrapped }`; `wrapped` is `nonce
|| AES-256-GCM` of the data key (unwrapped from the `FileSeal` with the app file key, then zeroized)
under `HKDF(X25519(ephemeral secret, recipient))`, salt `calimero.export-wrap.v1`, info `ephemeral
public || recipient public || u32 length-prefixed app id || u32 length-prefixed hex file id`
(`calimero_sealed::wrap::wrap_export`, over `derive_shared`, which refuses a low-order key: `400
BAD_RECIPIENT`, as does a recipient that is not 64 hex).
The construction lives in `calimero-sealed` (`wrap.rs`, with the AES-GCM helpers `wrap_for_job`
shares, and `file.rs`, the file STREAM format) so `calimero_client::Client::export_file_to` opens it
with `unwrap_export`, checks the segment list against the file id, each segment against its hash,
and the size and plaintext SHA-256 with `finish_expecting`, and succeeds only when all match.
An account may export `MAX_EXPORTS_PER_MINUTE` (30) times a minute per node (`ExportLimits`, an
in-memory token bucket over at most `MAX_TRACKED_ACCOUNTS` accounts): `429 TOO_MANY_EXPORTS`.

### Sealed files of a component

Code: `node/component/files.rs`.

A file is a sealed blob.
It shares the blob id namespace and the `BlobRef` type; there is no delete, and retention is a blob's.
A run's `files` provider (`NodeFiles`) is built per run from the app id, the file key
(`backup::file_key`, not the TEE key) and the app's blob records.
A sealed file's record carries a `FileSeal` (`BlobRecord::file`: the plaintext hash and the wrapped
key) in the hidden `rows::CBLOB` rows the guest cannot reach, so a snapshot and `restore` carry it.
A writer seals (`SegmentWriter`), stores each segment on this node the moment it is complete and
wraps the data key; the file id is the hash of its segment list (`FileSeal::segments`,
`FileMark::segments`).
Each segment is stored in the `blobs` column under `seg.<hex hash>` and, in the same batch, an empty
index row `seg/<hash>` in `meta` (`Engine::put_segment`, `list_segments`), so segments are listed
without reading a byte of them; no whole-file row exists.
Segments travel raw (no base64): a push is `PUT /internal/segment/{hash}`, checked on receipt
(`SHA-256(body)` is the hash, at most `SEGMENT_BYTES`), a fetch `GET /internal/segment/{hash}`,
served only to a node approved for an app hosted here whose files list it (`caller_may_hold`; `404`
for a hash no hosted app lists); there is no peer delete, a replica's unreferenced segments go with
the sweep after `SEGMENT_GRACE` (`Node::pin_segments` holds an upload's or a pending entry's out of
it).
A job transfer still sends and receives the joined segments in one request.
The outcome and the entry carry marks only (`Outcome::files`, a serde default: old entries decode
unchanged).
`apply` records them as unreferenced blobs before the diff, only for status `Ok`, so a `BlobRef` the
same entry stores is counted and a file is never collectable in between.
A file is then held while a stored `BlobRef` names it, `BLOB_IDLE_MS` after its entry or after the
last reference went, and forgotten by `expire_blobs` in the same entry on every replica.
The leader then collects the file's id through the same `collect_blob` and `componentBlobsCollected`
as any blob, which releases its quota and deletes no file bytes: no blob path (`collect_blob`, the
blob routes) deletes a `seg.` row.
Every node deletes segments itself: `Node::sweep_segments` (every `SWEEP_EVERY`, 10 min, over the
`meta` index; `node/segments.rs`) deletes a stored segment no hosted app lists
(`BlobTable::holds_segment`, a map from segment hash to file rebuilt on `load`) and nothing pins, if
this node saw it listed at an earlier sweep (its file was forgotten) or it has been unlisted for
`SEGMENT_GRACE` (24 h) since first seen so; first-seen times are in memory, so a restart restarts
the grace, and there is no caught-up check, so segments handed to a joining node before it applies
survive the grace.
`BlobTable::upload` and `forget_blob` refuse a file id, so a blob upload or an owner delete cannot
take one.

**Publishing** (`runs.publish`): `NodeFiles::publish` answers only a sealed file whose
`FileSeal.output` is set, which `apply_compute_final` sets on a done run's outputs and nothing else
sets.
A run attempt's log is a sealed file marked `FileSeal.log` instead (see [compute
actions](/protocol/compute-actions/)), so it is never published.
It opens and proves the whole file, holds the plaintext against the pending budget (`plaintext`),
and answers a `PublishedFile` (a file over `MAX_BLOB_BYTES`, the plain blob it becomes, is a soft
`file too large`).
The outcome and entry carry `Outcome::published` (`PublishedMark { source, id, size }`, never bytes;
a serde default).
`run_with` adds the plaintext of each published blob the app does not hold to the run's blobs, so
`logged_entry` charges it (`new_file_bytes`, once per id) and `persist_files` pushes it to a
majority before the entry is proposed.
`apply_component_outcome` checks every mark first (`publishes_only_outputs`): the source must be an
output record, its plaintext hash must be the mark's id and its size the mark's, and at most
`MAX_PUBLISHED_PER_RUN` marks.
A failing mark makes the whole entry a no-op that answers `NOT_A_RUN_OUTPUT`, on every replica, so a
leader cannot publish an uploaded file, a file a call made, another app's output or a different
plaintext.
Any entry that applies as a no-op (a conflict or a refusal) has the bytes it stored discarded and
its charge refunded (`recorded_nothing`).
Then `BlobTable::add_published` records the plain blob (`BlobRecord::charged`,
`application/octet-stream`) before the diff, unless the app already holds that id; `expire` and
`BlobsCollected` release the charge of a file or a charged blob.
A published blob is served only through a grant (`blob_download` judges it on the leader's record,
`Node::blob_standing_strong`), and `blobs.grant` is refused for it outside a logged write.
`BlobRecord::epoch` counts the owner's revokes (`ComponentCmd::BlobRevoke`, `POST
/apps/{app}/blobs/{id}/revoke`, `__blob_revoke`); a grant above zero carries its epoch
(`grant_token`), and a download whose grant names another epoch than the record's answers `404`.
The app also keeps an epoch floor (`BlobTable::floor`, the hidden `rows::CBLOB` row `floor`):
forgetting any blob but a sealed file raises it above that blob's epoch, and a record made again
(`add_published`, `upload`) starts there, so a grant of a forgotten blob never holds for its
successor.
`load` fails on an unreadable floor or record instead of defaulting, and `revoke` refuses at
`u32::MAX` (`no revocation left`).
The owner's delete (`forget_blob`) forgets a published blob too, queuing its bytes and charge in
`collect` and `collect_files` like `expire` does; it still refuses a sealed file.
A result method sees its own run's outputs without the flag (`blob_view_with_outputs`), so it cannot
publish them; it stores the `BlobRef` and a later call publishes.
`RunBlobs::info` answers a file with its plaintext size and hash and an empty mime, as `files.info`
does; the host core refuses `blobs.grant` for it.
`GET`, `POST` and `DELETE` on `/apps/{app}/blobs` refuse a file id with `409 NOT_SUPPORTED`
(`refuse_sealed_file`, judged by the app's leader through `file_held_strong`).
`/apps/{app}/storage` counts their sealed bytes in `blobBytes` (a tag per chunk).

**Uploads** are `POST /apps/{app}/files` for a file of up to one part (`PART_BYTES`, 16 MiB;
`Client::upload_file`) and, for a larger one, upload sessions (`node/component/uploads.rs`):
`POST.../files/uploads { size }` answers `{ uploadId, partBytes, parts, expiresAt }` (Unix seconds),
`PUT.../uploads/{u}/parts/{k}` takes part `k` raw and answers `{ next }`, `GET.../uploads/{u}`
answers `next`, `POST.../uploads/{u}/complete` waits up to `COMPLETE_WAIT` (20 s) for every segment
to reach a majority (else `503 FILES_UNAVAILABLE`; a retry resumes) and answers the file,
`DELETE.../uploads/{u}` aborts.
Only the app's owner and the members of its organization (role Member or above,
`api::may_handle_files`, through `api::files_gate`) may upload, list and read files, even where the
app is public; anyone else gets `403` on every `/files` route.
`GET /apps/{app}/files` lists the files (`{ files: [{ id, blobId, size, sha256 }] }`) and `GET
/apps/{app}/files/{id}` answers one (never the key); `/apps/{app}/blobs` lists plain blobs only and
answers `409 NOT_SUPPORTED` to `info` of a file id, as to a download.
A session lives in the leader's memory (`Uploads`, one `Session` per upload: segment writer, segment
and part hashes, what is on a majority), belongs to its account (another account, an unknown id, a
leader change, `UPLOAD_IDLE` 15 minutes without a part or `UPLOAD_TTL` 6 hours all answer `404
UPLOAD_UNKNOWN`) and is ended by `Node::expire_uploads` (the timer poll) when it lapses or this node
stops leading the app.
Part `k` is sealed into segment `k` (`SegmentWriter::write_more`: a full part closes its segment
without waiting for the next) and stored here, and a background task pushes it to a majority
(`push_blobs`, no discard on failure; retried with backoff until it lands or the session ends); the
answer waits only for a slot in the window (at most `UPLOAD_WINDOW` = 4 segments stored but not yet
on a majority; the part is sealed and stored anyway, and past `PART_PUSH_WAIT` the answer is `503
FILES_UNAVAILABLE` and the resent part replays its answer); parts go in order (`409
PART_OUT_OF_ORDER` names `next`), a resent part answers its first answer and other bytes are `409
PART_CONFLICT`, a part of the wrong length `400 BAD_PART`.
Begin refuses past 4 sessions per app, 32 per node or 16 GiB declared per leader (`429
TOO_MANY_UPLOADS`, `admit`) and when the payer's file bytes plus its open sessions plus `size` pass
the quota (`429 QUOTA_EXCEEDED`); nothing is charged until `complete`, which charges once
(`State::charged`) and commits through `commit_mark` under the key `node:upload-<id>`, so a retried
`complete` replays, from the leader's record of that key (`replayed`, only for the uploader) even
when no session is left.
A `complete` before every part is in is `409 UPLOAD_INCOMPLETE`; one past the quota is `429`,
deletes the bytes and ends the session; one whose commit may yet land (`Upload::Unknown`) keeps the
session and its bytes until it ends, when a barrier tells whether the mark committed: absent, the
charge is refunded and the segments deleted (`Node::undo_unmarked`).
Ending a session (abort, idle, age, leader change) answers unknown at once, then stops its pushes
and deletes its segments here (`Node::end`); replicas' copies go with the sweep.
A follower forwards every session request one hop to the leader (`internal/upload*`, raw part
bodies, `PART_FORWARD_TIMEOUT`).
The single request (`POST /apps/{app}/files`, one part) is a session of one part run through the
same operations (`Node::upload_file`): begin, part 0, complete, retrying a `503` `complete`,
starting over when the leader changed, aborting on failure.
`StorageStats::files` carries each file's id, size and SHA-256 for these routes, and
`internal/storage` sends it to a peer.
The command carries the uploader (`uploader`, a serde default), the account the API's `principal`
derived, which the `internal/upload*` routes refuse unless it is an account id (`valid_uploader`);
`BlobTable::add_uploaded` stores it as `FileSeal::uploader`, and files made by calls and runs have
none.
`NodeFiles::uploader` answers it to `runs.uploader`; an id already held is refused (`file exists`),
so a second upload never replaces the first uploader.
A recorded answer for another file under the same key wins and the new file is undone.
`apply` records the file as an unreferenced blob stamped with the entry's `ts_ms`, as
`Node::component_blob_cmd` stamps an upload, so a client has the idle time to attach it.
If the commit fails, a `componentBarrier` entry (applies as nothing) is committed through the
leader, so the failed entry has either committed or never will.
The leader then reads the record: present, the upload succeeded; absent, its bytes and charge go; no
barrier possible, they stay.
A file is held while its blob record exists, and the quota counts it for as long.
A logged entry's new files are charged first, within `CHARGE_WAIT` (`Node::charge_files`, from the
run's thread).
A refused charge pushes nothing, answers `429` and logs nothing; a charge that lands after the wait
is refunded when its answer arrives.
`Node::discard` undoes the bytes and the charge if the entry does not commit.
The charge is released by retention: `expire_blobs` queues a forgotten file's plaintext size in
`ComponentHead::collect_files` beside its id in `collect`.
The leader's `componentBlobsCollected` entry answers `freed`, the bytes of the queued files it
really took off, and the node releases that many (`collect_component_blobs`), so a repeated entry
releases nothing.
A node that stops hosting an app that is deleted everywhere drops its sealed files' segments
(`Node::drop_deleted_files`); plain blobs stay, as they may be another app's.
A crash between the entry and the release leaves an over-count, never a loss; a queue past
`MAX_COLLECT_QUEUE` drops its oldest ids with their sizes.
Before a call, tick or `init` proposes, `Node::persist_files` pushes the new files' segments, read
back from this node's store, at most `MAX_PUSHING_BLOBS` (2) at a time and each body shared by every
target, to the app group's voters and learners (its own Raft membership, not the directory's
replicas), under one deadline below `FORWARD_TIMEOUT` and a node-wide byte budget
(`MAX_PUSH_BYTES`).
It needs a majority of the voters, this node counted; a voter with no address still counts.
It runs only after the entry bytes are built, so an entry the log replaces as too large stores
nothing.
When the majority is missing the call is `503 FILES_UNAVAILABLE` (the forward loops pass it on
unchanged and do not retry it; the client does, with its key), nothing is logged and the pushed
bytes are removed; so are the bytes of an entry that conflicts or whose proposal fails.
A run's writers hold only their partial segment in memory, which draws on a node-wide budget
(`MAX_PENDING_FILE_BYTES`, `PendingBytes`) and returns as each segment is stored; the segments of a
file no entry marks are deleted when the run ends (`NodeFiles::forget_made`).
A write it cannot hold takes nothing and aborts the logged run as `FileError::Unavailable`, so runs
together never hold more than the budget.
`open` reads the file one segment at a time: a local segment is used only if its SHA-256 is its
hash, else it is dropped and fetched from the other replicas (5 s); a segment nobody holds ends the
read as unavailable.
Any opener failure, including at the end of the stream, is `ReadError::Corrupt`, which the host core
makes a `HostDenied` trap.
Open readers hold one segment and its plaintext (`OPEN_READER_BYTES`, at most the file) against a
per-run budget (`MAX_RUN_OPEN_BYTES`) and a node-wide one (`MAX_OPEN_FILE_BYTES`; logged runs wait 1
s for it).
Only a compute run opens a file (the host core refuses `files.open` in every other kind), so a
sealed file's contents are readable only inside a compute run of the release the organization
approved.
A file that cannot be had (no replica holds it, or a budget is spent) aborts a logged run as `503
TIMEOUT`, not logged, key not spent (`FileError::Unavailable`, for `create`, `write` and `finish`)
and ends a compute run `Unavailable`.
The provider is built for every run but touches keys, budgets and bytes only when a run touches a
file.
Blocking on the runtime from a run needs a multi-thread runtime, else the run is refused.
Pushes skip members `may_send` refuses, and `fetch_blob_from` asks only the app's other replicas,
which serve a file as a blob their app holds (`holds_blob`); bundles and other blobs still use every
node.
Replica moves hand over the app's files, segment by segment, with the bundle (`hand_over_bytes`),
and again after the voters change, only what the joining nodes do not hold, for files made while the
move ran; the second hand-over is retried for 10 s and never abandons the move.
A snapshot from before carries no file-byte counts, so files stored earlier start from zero, and
their release floors at zero.
