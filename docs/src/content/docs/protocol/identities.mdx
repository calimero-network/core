A **person** is an **account**. They prove it with a WebAuthn **passkey**, and
each passkey on the account is one of their **devices**. Signing in gives them
a short **session token** that every node of the cluster verifies on its own. A
**machine** acting for an account uses an **API key**. `calimero-identity`
holds the logic (WebAuthn, tokens, challenges) with no storage of its own; the
records live in the [system group](/protocol/system-group/).

## Accounts

An account id is 32 random bytes in base64url, made when someone signs up. The
account record holds a display name, its passkeys (at most 10) and their
labels and the account's aliases for apps. An account approves nothing for
itself: every app is in an organization, and its approvals (mero-tee releases
and outbound prefixes) are that organization's. A sign-up makes no
organization: the account's own apps are in one it creates, one made with an
instance, or one it is invited to (see
[Where an instance goes](/protocol/organizations/#where-an-instance-goes) and
[Deployment governance](/protocol/governance/); below cluster version
1.0.0-rc.32 a sign-up made a
[personal organization](/protocol/organizations/#personal-organizations) in the
same entry, `CreateAccount { personalOrg }`). Who may sign up is the
cluster's [sign-up policy](/protocol/governance/#sign-up): `open` (the
default; the operator's `maxAccounts` quota bounds how many accounts a cluster
takes), `invite` or `closed`. `CreateAccount` carries the invite a person signs
up with, as the token key's signature over the new account and the time, and
`apply` judges it against the policy.

The release of the node an organization was made through is approved for it
from the start, so its apps can run where it began.

## Passkeys

`calimero-identity::webauthn` verifies registrations and assertions itself
(ES256 and EdDSA, via `ring`). Attestation statements are not checked
(passkeys register with `attestation: none`); the relying party id is `--rp-id`
and the accepted origins are `--origins`, plus a package's frontend origin for a
ceremony that comes from it. A ceremony from an origin a package's manager
registered (below) is checked against that origin alone and its own relying
party id.

| Ceremony | Routes | Result |
| --- | --- | --- |
| Sign up | `/auth/passkey/register/{begin,finish}` | A new account with this passkey, and a session |
| Sign in | `/auth/passkey/login/{begin,finish}` | A session for the passkey's account |
| Add a device | `/auth/passkeys/add/{begin,finish}` (signed in; `finish` answers `412` and is approved by a passkey the account already has) | Another passkey on the account |
| Recover (lost every passkey) | `/auth/recovery/{begin,start}` (signed out; the account's recovery code and a new passkey), then after 72 hours `/auth/recovery/finish` (the new passkey; `/auth/recovery/cancel` with an existing passkey stops it before) | The code spent and the passkey pending; at finish the passkey on the account, every earlier session and API key revoked, and a session ([Account recovery](#account-recovery)) |
| Label or remove a device | `POST` / `DELETE /auth/passkeys/{cred}` (removal approved with a passkey, `412` first) | A label; or the passkey gone and its sessions revoked (the last passkey cannot be removed) |

A ceremony's challenge lives in the memory of the node that issued it, for 5
minutes; its id names that node. It may finish on any node: that node takes
the challenge from the issuer over the attested peer channel, so it is still
used once (a load balancer may send the two requests anywhere). A node holds
at most 10 000 open sign-in and sign-up ceremonies, and apart from those 64
step-ups per account (10 000 across accounts), so a full anonymous pool never
blocks a signed-in account's step-up; past either it answers `429`.

### Passkeys are each cluster's own

Accounts and passkeys live in one cluster's system group, while clusters may
share a relying party id (every Calimero Cloud cluster uses
`calimero.network`). A browser therefore offers a passkey made on one cluster
on every other one. Two things keep that from confusing anyone:

- **The name it is made under.** A registration's `user.name` and
  `user.displayName` (sign-up, adding a device, recovery) are the person's name
  and the cluster's (`--cluster`) with its tag, `alice · eu-shared-1 · 3f2a`; a
  sign-up begun on a package's frontend (a served or registered origin, `origin`
  on `register/begin`) names the app too, `alice · kv-store (eu-shared-1 ·
  3f2a)`: the
  newest release's display name, else the package id. Each part is cut at 32
  characters (`MAX_PASSKEY_NAME_PART_CHARS`). The account's own name is the
  person's alone. The tag is the first 2 bytes of the cluster's identity key
  (from its cluster key), 4 hex characters, public in `GET /sign-up`
  (`passkeyTag`, beside `cluster`): a cluster begun again under the same name
  has another cluster key, so its passkeys are listed apart from the old
  cluster's. Each registration gets a random user handle (sign-up, adding a
  device and recovery alike): a password manager keeps one passkey per site
  and handle, so a shared handle would make a second passkey added in the same
  manager replace the first.
- **The answer to a passkey from elsewhere.** An assertion (sign-in or step-up)
  whose credential no account here has answers `401 PASSKEY_UNKNOWN_HERE`,
  "this passkey belongs to another Calimero cluster or was removed from this
  one; sign up here, or open the app from the link for the cluster your account
  is on". It names no cluster and no account: a node knows only its own
  cluster's passkeys, and the answer is the same for a passkey that was removed.

Sign-in and sign-up need the user present. A **step-up** — approving a confirm
method, an upgrade, an approval or an organization's deletion — needs the user
**verified** too (PIN or biometric): a touch alone is not consent.

## Sessions

A session token is `v2.<claims>.<Ed25519 signature>`, signed by the node that
issued it with its signing key (the key it signs receipts with, attested with
`GET /attestation?purpose=receipts`) over `"calimero.session.v2\0" ‖ claims`.
A node makes that key on its first start and keeps it in its data directory
wrapped under its storage key K_r, so a restart on the same data directory (a
crash, a rolling upgrade of the binary) keeps it.
The claims are the account, a session id, the expiry (15 minutes), the passkey
the session was opened with, for a session opened on a package's frontend that
package (and, on a registered origin, that origin), and the issuing node with its key. Signing in also returns a refresh
token (`rt_…`, 30 days): `POST /auth/refresh` on any node answers a new
token, signed by that node. A refresh token younger than an hour
(`api::REFRESH_ROTATE_AFTER`) is kept: the node judges it on the cluster's
latest system state (a read index) and writes nothing to the system log, so a
sign-out, a recovery or a passkey removal committed through any node already
ends it. An older one is exchanged in the system log for a new refresh token;
a refresh token presented again after it was exchanged revokes its session.
So every active session writes to the system log once an hour, not once per
session token.

A node verifies a token issued elsewhere without asking the issuer: it checks
the signature against the issuer's signing key as it attested it at the
address the cluster registered for that node, checks the expiry, and that the
issuer's attested release may vouch for the account: a release one of the
account's organizations approved (where
the operator holds release approvals, one it approved;
`SystemState::release_may_serve_account`). Each app access then also
requires the issuer's release to be approved for that app's data. So a node on
a release nobody approved can mint tokens, but no other node takes them. Then —
on fresh system state — the node checks that the session is not revoked and
that its passkey still belongs to the account. See
[Keys & their lifetimes](/protocol/key-rotation/) for revocation.

### Failover

Every node attests each registered peer's signing key ahead of time: at start,
once it learns the directory, and whenever a node is registered. It keeps
`node → (key, release, attested at)` in memory (`Node::warm_issuers`, at most
`MAX_CONCURRENT_ISSUER_ATTESTS` at once, each bounded by `ISSUER_ATTEST_WAIT`).
A token is verified from that entry without reaching the issuer, so a session
outlives the node that issued it: with the issuer stopped or frozen, any other
node still takes it.

- **The issuer restarted on its data directory:** same key; its sessions go on
  verifying everywhere.
- **A token under another key than the one attested** (the issuer's data
  directory was replaced): the node attests the issuer again, at most every
  `ISSUER_RETRY_SECS`. If the issuer cannot be reached, or attests another
  key, the token is refused with `401`.
- **The issuer was removed:** its entry is dropped and its tokens stop
  verifying once the removal applies.

On a `401` a client refreshes once, on any node, and sends the request again
(the Rust client and `meroctl` do it on their own).

The key is wrapped under K_r, not K_c. K_r comes only to the release whose
mero-kms holds its root, so only that release opens the key: a key attested
once under release R signs only for R, and a node on another release booted
on the same disk cannot sign as this one.

A node on a release none of the account's organizations approved neither
issues nor takes the account's sessions: it answers `421 WRONG_NODE`, and the client uses
another node.

## Devices

There are no device keys. A device is a passkey; `/auth/me` reports which one
the current session was opened with (`passkeyId`), when each was added and last
signed in with (`addedAt`, `lastSignInAt`), and removing a passkey ends that
device's sessions. `GET /auth/sessions` lists the account's sessions, the
passkey each was opened with and the package and origin it is bound to, and
`DELETE /auth/sessions/{session}` ends one ([Sessions](/operate/auth/#sessions)).
`GET /auth/activity` lists what each passkey did, the last 100 entries: the
package and origin each sign-in was bound to, and the method and subject of
each change it approved ([Activity](/operate/auth/#activity)).
These are the account holder's alone: the times come from the log entries a
sign-up, a sign-in, an added passkey and a recovery already write (each carries
its time; a refresh writes none), and no route shows them to operators,
organization admins or deployment managers. Inside an app, `env::caller()` is the account, whichever
of its devices made the call ([Who a run acts as](/protocol/authorship/)). Presence keeps one entry per device: the session's
passkey, or the API key.

## API keys

`POST /auth/apikeys { label, apps?, methods?, readOnly?, allowConfirm?, ttlSecs? }`
creates a key `cal_…` for the signed-in account, approved with a passkey (`412`
first; the consent binds the key's hash and record); only its hash is stored and
the key is shown once. A key may be scoped:

- `apps`: only these app instances (default: every app the account reaches);
- `methods`: only these methods (`*` for any);
- `readOnly`: views, events and reads only;
- `allowConfirm`: may carry the account holder's passkey assertion for a confirm
  method (it can never produce one);
- `ttlSecs`: lifetime, at most and by default one year.
- `upgrades: { app, package? }`: an [upgrade key](#upgrade-keys), which takes
  none of the fields above but `ttlSecs`.

### Follow-ups

A key is often useless until an app grants it access, and that grant is usually a confirm method: a second passkey prompt.
`then: [{ app, method, args }]` folds it into the key's one prompt.
Each entry names a confirm call method of one of the key's own `apps` (not an action, which answers before it runs; at most four, 64 KiB as JSON with the key's id written in; none on an upgrade key), judged as `POST /apps/{app}/intents` judges the caller, a read-only member of the app's team refused.
Each must name the new key: a follow-up whose arguments hold no `key:$key` is refused.
That only requires the placeholder to appear somewhere in the arguments: it does not limit which other principals or values the call names, which the person sees in the `412` and approves.
The first request makes the key's id and writes it into the arguments: every string value that is exactly `key:$key` becomes `key:<keyId>` (no substring is replaced).
The `412` details list the calls so written (`then`), and the person's passkey signs the key and them in one consent.
`__create_api_key`'s arguments gain `then`, only when it is set, so a plain key's consent reads as before; it states each call as `{ app, method, argsHash }`, because the system log reaches every node, those the app's organization never approved included.
`argsHash` is the hex SHA-256 of a random salt the node makes for that call on the first request (16 bytes, kept with the challenge) followed by the call's arguments as the node parsed them, with `key:$key` written in, every object's keys sorted by their UTF-8 bytes, in the node's compact JSON (not JCS, and not the bytes the client sent: `1e2` is written `100.0`).
Equal arguments of another key, or a guess at them, give another hash.
Those arguments are exactly `then[i].args` as the `412` echoes them; the call's entry in its app's log carries the salt (`{ followUpOf, index, salt }`), so the app's auditors check the hash against that echo.
Both requests check the account's key quota first, so the retry runs no call for a key the log would refuse; on the retry the node takes the account's turn first, so two keys made at once through one node do not both run their calls for one last place.
The retry checks its own `then` against the signed one (hashing its own arguments with the signed key id), runs each call in order as the person, and only then makes the key, in a task a dropped connection does not stop; the answer adds `then: [{ index, result, receipt }]`.
Each call's entry in its app's log names only the approval it ran under, never the assertion, the key's hash or the other calls, and runs under an idempotency key of the node's own (`node:apikey:<keyId>:<index>:<argsHash>`, a prefix `/intents` refuses from a client).
If a call fails, no key is made and the answer is `422 FOLLOW_UP_FAILED` naming it (`details: { index, app, method, error, applied, unknown }`); the calls in `applied` stay applied, naming a key id that never exists. A call whose answer was a 5xx is sent again under its own key (at most three times, so a call that did apply replays); if it still cannot say, its index is in `unknown`. A failure of the key itself after the calls carries `applied` too, and `keyWrite`: `refused` when the log refused the key, `unknown` when the write may still land (a 5xx, such as a system group that did not commit in time); a request that ended without any answer says every call and the key are `unknown`.
On an `unknown` key, list the account's keys (`GET /auth/apikeys`) and revoke the key if it is there and not wanted.
Two retries of different approvals through two different nodes at the account's last free place can still both run their calls; the one the log refuses answers its `applied` calls.
The account's activity (`GET /auth/activity`) lists the key's approval and one entry per call (`method`, `subject`: the app).
The hosted consent page does not show `__create_api_key`: a client shows the `412`'s `then` itself.
A node logs a key with follow-ups only from cluster version 1.0.0-rc.38 (`Feature::KeyFollowUps`; rc.37 was cut without it).
A node before that release ignores `then` and makes a plain key, so a client checks that the `412` lists `then` and that the answer's `then` is as long as the one it sent.

## Upgrade keys

A deploy from CI cannot answer a passkey step-up. An **upgrade key** is an API
key whose scope is one app's upgrades: `POST /auth/apikeys { label, ttlSecs?,
upgrades: { app, package? } }`, approved with the passkey of someone who [may
upgrade](/protocol/upgrades/#who-may-upgrade) the app: an owner or admin of its
organization (`CreateApiKey { owner_approves }`, judged where it applies). Its record keeps the
app, the package (by default the one the app runs) and that package's pinned
signer, and the public half of an Ed25519 key derived from the key itself
(`proof::api_key_public`: seed `SHA-256("calimero.api-key.v1\0" || key)`); the
passkey consent covers all four.

- **What it does**: `POST /apps/{app}/upgrade { version }` for its app, with no
  step-up, to a release of its package installed under the signer it names (a
  registry release is installed first, as for a session). The node signs the
  upgrade's statement (`<app> / __upgrade / { bundle, migrate, manifest }`) with
  the derived key, and the directory's `UpgradeApp` carries that signature in
  place of a passkey consent. Every replica checks it where it applies, against
  the key as the log holds it then, and spends it once; a node that saw only
  the log cannot sign one.
- **What it does not**: every other route, reads included, answers `403
  UPGRADE_KEY_ONLY`. A raw bundle, another package, another signer and another
  app are refused `403`.
- **The rules that still apply**: governance holding app upgrades for owners,
  the key's account still [may upgrade](/protocol/upgrades/#who-may-upgrade) the
  app (an admin made a member, or who left, takes the key's power with them; a
  key a member made before 1.0.0-rc.33 upgrades nothing once that release
  holds),
  an owner release is never moved to a publisher one, [release
  deadlines](/protocol/governance/#release-deadlines), and [deployer
  grants](/protocol/governance/#deployers) for a registry install.
- **Revoking** it (`DELETE /auth/apikeys/{key}`, approved with a passkey) stops it on every node at once,
  for an upgrade logged later too. It also ends with its `ttlSecs`.
- **What is logged**: the app's `lastUpgrade` names the account and the key
  (`apiKey`), in `GET /auth/apps` and `GET /orgs/{org}/apps`; the node logs
  each such upgrade with the app, the key's id and the bundle.

## Which credential may do what

How the session check and the account's authority combine for each request, with worked examples, is in
[Sessions & authority](/protocol/sessions-and-authority/).

| Action | Passkey session | Package-bound session | Unscoped API key | Scoped API key |
| --- | --- | --- | --- | --- |
| Call and read apps it reaches | ✓ | that package's apps only | ✓ | within scope |
| Install packages, create apps | ✓ | instances of its own package only | ✓ | — |
| Manage passkeys, API keys, approvals, upgrades, uninstalls | ✓ | — | — | — |
| Manage organizations, teams, members and invites; delete an app or change its access | ✓ | its own package's channels directly ([below](#package-bound-sessions)); everything else through the [consent page](/protocol/consent-page/#organizations-and-invites) only: create, rename or delete an organization; mint, accept or revoke an invite; leave; remove a member or change their role, teams, capabilities or all-apps grant; a team's or the organization's default capabilities | — | — |
| Upgrade one app to signed releases of its package, without a step-up | — | — | — | an [upgrade key](#upgrade-keys), and nothing else |
| Approve a confirm method | ✓ (with step-up) | from its own origin | only with `allowConfirm`, relaying an assertion | same |
| Ask for an approval on the node's consent page | ✓ | ✓ (returns to its own origin) | — | — |

Deleting an app, changing its access, creating organizations and issuing
invites also need a passkey session on the cluster's own origin, or, for
the organization changes the consent page takes (creating, renaming and
deleting an organization; issuing, accepting and revoking invites; leaving;
a member's removal, role, teams, capabilities and all-apps grant), the
person's passkey on the node's consent page: an API key cannot do them, nor can a
package-bound session by itself.

### Package-bound sessions

A session opened on a package's frontend is bound to that package
(`SessionClaims::app`, carried through refresh): it reaches only apps running a
release of that package, and the node refuses it credential management, API
keys, approvals, upgrades, uninstalls and uploads, and every change to
organizations, teams, members and invites (redeeming one included), and to an
app's lifetime or access, with one exception below.

**Its own package's channels.** In an organization where the package has an
[app team](/protocol/organizations/#app-teams), the session may manage the
teams below that app team (`Principal::within_team`; `Org::package_of_team`):
create a team under it, rename or move a team below it (never the app team
itself, and a move only within), add, change and remove members there, delete
a team below it whose apps are all of the package, and move the package's apps
between those teams (`POST /apps/{app}/access`). This is how a chat app runs
its channels. The authority is still the person's, judged where each command
applies as for any session; the step-ups these need (`__set_team_member`,
`__remove_team_member`, `__delete_team`, over `org:<org>`) are accepted from the
package's own origin, and only over its own package's teams. Everything else in
the organization stays refused to it.

A step-up it makes is otherwise for one of its package's apps only. An app that creates organizations,
invites people, lets them join or leave, moderates members or changes an
organization's settings asks the node's
[consent page](/protocol/consent-page/#organizations-and-invites) instead,
where the person approves each with their passkey. An app's page is
third-party code; this keeps it from acting as the whole account.

## Registered origins

A developer's own site (their domain, a hosting preview) is not an origin the
node serves, so on its own it could not run a passkey ceremony against the
cluster. A package's **manager** registers it (`/package-origins/{package}`):
where the package's signing key is bound to a publisher organization, that
organization's org-wide `MANAGE_APPLICATION` holders; otherwise the account
that installed the package's first release. Never the operator, an API key or
a package-bound session.

| Change | Route | Consent (`412` first) |
| --- | --- | --- |
| List | `GET /package-origins/{package}` | none |
| Register | `POST /package-origins/{package} { origin, rpId?, served? }` | `package:{package} / __add_origin / { origin, rpId }` (`{ origin, rpId, served: true }` for a served one) |
| Remove | `DELETE /package-origins/{package} { origin }` | `package:{package} / __remove_origin / { origin }` |

The consent is logged with the command (`AddPackageOrigin`,
`RemovePackageOrigin`) and checked where it applies, on every node: a
command without the manager's own consent over exactly that change is
refused there, whichever node proposed it. The registrations live in the
system state (`SystemState::package_origins`, `crate::origins`).

**Relying party.** WebAuthn binds a passkey to a relying-party id, which must
be the page's host or a parent domain of it. The cluster's `--rp-id` cannot be
a developer's domain, so each registered origin carries its own `rpId`: the
origin's host by default, or a parent domain of it that the manager names
(`https://app.example.com` with `example.com`). The cluster's rp-id, or a
parent of it, is refused, so the cluster's own passkeys never answer on a
developer's site. A person signing in there makes a passkey for that site;
the account it opens is an ordinary cluster account whose sessions from that
origin are always bound to the package. WebAuthn's Related Origin Requests
(one rp-id, a `/.well-known/webauthn` list of origins) was not chosen:
browsers allow the list five registrable domains, for the whole cluster; the
rp-id's host would have to serve the list, which the node does not control;
and not every browser supports it.

**Ceremonies.** `POST /auth/passkey/{register,login}/begin` take the page's
`origin` and answer its rpId (`403 ORIGIN_NOT_REGISTERED` for an origin that
is neither the cluster's, a node's own, a served frontend's nor registered).
The finish routes verify a ceremony from a registered origin against
`{ rpId, [origin] }` alone, and open a session bound to the package exactly as
a served frontend's (`SessionClaims::app`), which also names the origin
(`SessionClaims::origin`, carried through refresh; an exchange that changes
it is refused). A step-up of that session answers `412` with the origin's
rpId.

A sign-up there is a sign-up like any other: the cluster's sign-up policy
judges it (`invite` on `register/begin` and `register/finish`, `403
SIGN_UP_REFUSED`, checked again at apply), and the new passkey signs the
account it creates (`register/finish` answers `412`). That `412` names the
origin's rpId, as the new passkey belongs to it, and the confirmation is taken
from that origin only.

**Removal** ends it: from the next request every session opened on the
origin, and its refresh token, is refused `401`, judged on fresh system
state. An uninstalled package takes its origins with it.

**Limits and rules.** `https://host[:port]` exactly as a browser writes it
(lowercase, no path, no default port); `http://` only for a `localhost` name
and only on a `--dev` node. One package per origin (first come; the cluster's
own origins and served frontends are refused). 8 origins per package, 4096
per cluster. CORS on the node's API admits registered origins. The node logs,
at `info`, each registration and removal (package, origin, rp-id) and each
session opened on a registered origin (package and origin); who made the
change is in the system log's command and at `debug` only, never in the
journal an operator reads.

**Served origins (custom domains).** Registered with `served: true`, the
origin is one the cluster also serves the package's frontend on, from its
signed bundle, as at `{label}.D`: the developer points their domain at the
cluster, and a request whose `Host` is that name (on 443) gets the package's
site before any node route. Everything else is a registered origin's: its own
rp-id, package-bound sessions naming it, removal ending them and the site with
them. Its consent names `served: true`, so a consent to the plain origin never
makes it served, and one origin is held either way (change it by removing it
first). Only `https://host` with no port (`http://name.localhost:port` on a
`--dev` node); not on a node without `--apps-domain` (`400 NOT_SERVING`), not
under the apps domain or the cluster's rp-id, not a node's API host; 4 per
package and 64 per cluster; adding one needs every node on this release
(`409 CLUSTER_NOT_UPGRADED`). The operator lists them, by the package's label,
at `GET /ops/served-origins`. A custom
domain's sessions are only as safe as its DNS: whoever controls the name can
serve their own page there and use its passkeys for that package
([custom domains](/protocol/applications/#custom-domains)).

Registering an origin proves nothing about controlling it: a manager who
registers another developer's origin denies them its use on this cluster, but
never sees a token, since the sessions go to the pages on that origin. Origins
belong to a package, never to a deployment.

## Account recovery

An account acts only with its own passkeys. A person who loses every one can
no longer sign in, and nobody can act for them: not an organization admin, not
the operator, not a node. [Organization recovery](/protocol/organizations/#recovery)
hands an organization to another account and never touches the old one.
Account recovery gives the account itself a new passkey, after a delay during
which any passkey the account still has can cancel it.

<OrgRecoveryTimeline />

**The recovery code.** An account may hold one: 160 random bits, shown once as
32 Crockford base32 characters in groups of four
(`calimero_identity::new_recovery_code`). It is read back however it is typed:
case, dashes and spaces are ignored, and `O`, `I`, `L` read as `0`, `1`, `1`
(`normalize_recovery_code`; at most `MAX_RECOVERY_CODE_CHARS`, 80, are read).
The code stands for an Ed25519 key, as an invite token does: its seed is
`SHA-256("calimero.account-recovery-code.v1\0" ‖ code)`
(`proof::recovery_signing_key`). The log keeps only the public half
(`SystemState::recovery_keys`, key → account), so neither the code nor anything
that redeems it is logged.

| Step | Route | Who | Proof logged | Effect where it applies |
| --- | --- | --- | --- | --- |
| Make a code | `POST /auth/recovery` (`412` first) | The account, on an unbound passkey session | Passkey consent over `account:<a> / __set_recovery / { recoveryKey }` | `SetAccountRecoveryKey`: replaces any code the account had; the answer carries the code, once |
| Remove it | `DELETE /auth/recovery` (`412` first) | The account | Consent over `account:<a> / __remove_recovery / {}` | `RemoveAccountRecoveryKey` |
| Begin | `POST /auth/recovery/begin { code }` | Anyone, signed out | None (nothing is logged) | A passkey registration challenge for the account the code names |
| Start | `POST /auth/recovery/start { challengeId, code, registration }` | Anyone, signed out | The code key's signature over `recover_message` | `StartAccountRecovery`: the code is spent; `accountRecoveries[a] = { credential, startedAt, readyAt }`; no passkey is added and no session opens |
| Cancel | `POST /auth/recovery/cancel` (`412` first) | The account, with a passkey it already has | Consent over `account:<a> / __cancel_recovery / { credentialId }` | `CancelAccountRecovery`: the pending recovery goes; the code stays spent |
| Finish | `POST /auth/recovery/finish { accountId? }` (`412` first) | The new passkey, signed out, at or after `readyAt` | The new passkey's sign-in assertion over `session / __sign_in / sign_in_args(refresh)` | `FinishAccountRecovery`: the passkey is added; every session, refresh token and API key of the account is revoked; the new session's refresh token is recorded |

`recover_message` is
`"calimero.account-recovery-start.v1\0" ‖ key ‖ 0 ‖ account ‖ 0 ‖ credential id ‖ 0 ‖ SHA-256(credential public key JSON) ‖ 0 ‖ at`
(`proof::recover_message`). It names the passkey, so a node that saw the log
cannot put its own in its place, and it is spent once (`used_proofs`). The
finish opens a session as every sign-in does: the challenge is the new
session's statement (the refresh token's hash and key, the session and its
expiry), and the assertion is checked where it applies, under the pending
credential, with the user verified. So no node can finish a recovery, or open
its session, without the new passkey.

**Limits.** `RECOVERY_DELAY_SECS` is 72 hours, the same as for organizations,
judged at the commands' own `at` (the clock of the node that took the request,
replicated with the command), never at apply. One recovery per account at a
time: a begin or a start while one is pending is `409 RECOVERY_PENDING`. One
code per account; a code starts one recovery and is spent whether that
finishes or is cancelled. A wrong or spent code is `401` at `begin`, and a
wrong code at `start` spends the ceremony (begin again). There is no attempt
counter: a counter changes nothing against guessing 160 bits. A finish before
`readyAt` is `409 RECOVERY_NOT_READY` with `details.readyAt`; with no recovery
under way, `404`. The recovered passkey is not held to the per-account passkey
cap, since each recovery spends a code a passkey approved.

**What clients show.** `/auth/me` answers `recoveryCode` (whether one is set)
and `recoveryPending` (`{ accountId, credentialId, startedAt, readyAt }` or
`null`), so every device the account is signed in on can warn that a recovery
is under way. An organization's owner and admins see only whether each member
has a code ([Members' security](/protocol/organizations/#members-security)),
never a recovery under way.

**API keys end with it.** Whoever took the lost passkey may also have made API
keys with it, and a key works without a passkey, so a finish revokes every API
key of the account as it ends every session. The machines the person runs need
new keys once the recovery finishes. A finish an earlier release logged
(without `revoke_api_keys`) replays as that release applied it, keeping the
account's API keys, so a replica that replays it after a restart reaches the
state the others reached; from the cluster's `RequireCurrentRules` mark on,
every finish revokes them. An account recovered that way revokes its keys
itself once signed in (`DELETE /auth/apikeys/{key}`).

| Who | Can they recover the account? | What limits it |
| --- | --- | --- |
| The operator, a node, anyone reading the log | No | The log holds the code's public key and spent signatures, each over one account and one passkey; the finish needs that passkey's assertion |
| Someone who stole the code | Yes, unless the account acts within 72 hours | Every signed-in device sees `recoveryPending`; any passkey cancels |
| The person, every passkey lost | Yes | Begin and start with the code and a new passkey, wait 72 hours, finish |
| The person, code and passkeys lost | No | Nobody can |

## Backup keys

The [recovery disk](/protocol/storage/#recovery-files) seals each app's
backups to the X25519 public key of whoever upgrades the app: the operator
where it holds app upgrades, else the app's organization
(`SystemState::backup_holder`). An account's own apps are in its personal
organization, so their backups open with that organization's key
(`POST /orgs/{org}/backup-key`, see
[Organizations](/protocol/organizations/#backup-key)).

:::caution
`GET` / `POST /auth/backup-key` (passkey consent over
`account:<a> / __set_backup_key / { publicKey }`) still records a key for the
account itself, but since every app is in an organization no app's backups are
sealed to it (`apps` in its answer stays `0`). Check
`crates/node/src/api/backup_keys.rs` and `SystemState::backup_holder` before
relying on it.
:::

## Development passkeys

`meroctl login --dev-passkey FILE` keeps a software passkey in a file
(`SoftAuthenticator`, feature `testing`). It is a real WebAuthn credential, so
only a development cluster whose relying party accepts it can use it. Against
a real cluster, people use their own authenticators in a browser and give
programs API keys.

## In `calimero-node`

Where the node implements this chapter, by the names in its code: paths are under `crates/node/src`
unless another crate is named. The design and its reasons are above; a module's own detail is in its
`//!` doc, and the node's mental model is [`crates/node/AGENTS.md`](https://github.com/calimero-network/core/blob/master/crates/node/AGENTS.md).

### Passkeys are per cluster

Code: `api/passkeys.rs`; docs: protocol identities "Passkeys are each cluster's own".

Clusters share an rp-id, so a registration's `user.name`/`displayName` is `passkey_user_name`
(person · `config.cluster` · `cluster_tag`, the first 2 bytes of the cluster identity key, public in
`GET /sign-up` as `passkeyTag`; plus the app's name for a sign-up begun on a package origin), every
registration's user handle is random (a shared one makes a password manager replace the earlier
passkey), and an assertion with a credential no account has answers `401 PASSKEY_UNKNOWN_HERE`
(`unknown_here`, from `check_assertion_for`), naming no other cluster or account.

### Devices

A person is their account, and each passkey is a device: the session names the one it was opened
with (`SessionClaims::passkey`, `passkeyId` in `/auth/me`); `auth/passkeys/add` adds one.

### Passkey times and sessions

(The account holder's alone.)

`Account::passkey_times` (`types::PasskeyTimes { addedAt, lastSignInAt }`, by credential) and
`RefreshRecord::opened_at` are set at apply from the times the entries carry: `CreateAccount::at`
(added, signed in, session opened), `AddPasskey::at`, a sign-in's `CreateRefresh` record `opened_at`
(last sign-in, the latest wins), a recovery finish's record `opened_at`; `UseRefresh` keeps the old
record's `opened_at`, so a refresh is no sign-in and no extra entry is written.
Each is outside what a passkey signs (`account_args` and `sign_in_args` are unchanged, and every
field is left out when empty), so a replica on the earlier release checks the same consent and
ignores them; an earlier release's entries carry none and leave the times unknown (`null`) on every
replica.
`/auth/me` gives `addedAt` and `lastSignInAt` per passkey; `GET /auth/sessions`
(`api::account_sessions`, `MAX_SESSIONS_LISTED`) lists the caller's live sessions with
`lastActiveAt` = the last exchange (`expires_at - REFRESH_TTL`, up to about 1 h 15 min behind), and
`DELETE /auth/sessions/{session}` ends one (`RevokeSession`; `404` for any session the account does
not hold live).
Both are `holder` (unbound passkey session), as `/auth/logout-all`.

### Key follow-ups

Code: `api::auth::follow_ups`, `types::KeyFollowUp`; docs: "Follow-ups" above.

`POST /auth/apikeys { then }` takes up to `MAX_KEY_FOLLOW_UPS` confirm calls of the key's own `apps`;
`gate` and the running ABI judge each before the passkey (`takes_follow_up`: a `Call`, never an
action), and `key:$key` is written as `key:<keyId>` (exact string values only, `for_key`).
They are signed in the key's one consent: `api_key_args` states `then` only when set
(`CreateApiKey { then }`, `Feature::KeyFollowUps`), and consent and entry carry
`types::SignedFollowUp`, holding the arguments only by a hash salted per follow-up
(`KeyFollowUp::signed`: the parsed arguments with keys sorted by UTF-8 bytes in compact JSON; the
salts are in the challenge's `KeyCarry`), since the system log reaches unapproved nodes.
Read-only team members and follow-ups without `key:$key` are refused before the prompt.
Both requests check `SystemState::api_key_room` (the rule `CreateApiKey` applies); the retry takes
`Node::api_key_turn` (per account, this node), catches up on the system log, and runs `make_key` in a
spawned task (`interrupted`, `key_write_failed`: `keyWrite`).
It runs the follow-ups first through `calls::call_consented`, each under `follow_up_consent`
(`{ followUpOf, index, salt }`, never the assertion) and a `FOLLOW_UP_KEY_PREFIX` idempotency key that
`/intents` refuses from clients (a 5xx is sent again up to `MAX_FOLLOW_UP_TRIES`), then writes the
key; one that fails answers `422 FOLLOW_UP_FAILED` with the indexes `applied` and `unknown` and makes
no key.
`approval_of` adds an activity entry per follow-up.

### Activity

(The account holder's alone.)

`SystemState::activity` (by account, beside `accounts` so `account_args` is unchanged), the last
`types::ACTIVITY_KEPT` `ActivityEntry { at, passkey, kind }`, `kind` `signIn { app, origin }` (from
a session's opening record: `CreateRefresh`, `CreateAccount`, `FinishAccountRecovery`, via
`system::sign_in_of`) or `approval { method, subject }` (one hook in `SystemMachine::run`:
`system::approval_of` finds the consent `authorize` verified, by its used marker, before the command
applies, and records it after).
The time is the step-up's `proof::Consent::at`, outside what the passkey signs; 0 (a sign-in's
consent, or an earlier release's) records nothing, so a replayed old log adds nothing.
`GET /auth/activity` (`api::activity_list`) is `holder`.

### Account recovery

Code: `crates/node/src/system/recovery.rs`, `crates/node/src/api/recovery.rs`; shaped like
[organization recovery](/protocol/organizations/#recovery), same `RECOVERY_DELAY_SECS`.

An account may hold one recovery code (`calimero_identity::new_recovery_code`, Crockford base32,
`normalize_recovery_code`, `MAX_RECOVERY_CODE_CHARS`); the log keeps only its Ed25519 public key
(`proof::recovery_key`, as invites; `SystemState::recovery_keys`, key -> account).
`SetAccountRecoveryKey` (`POST /auth/recovery`, unbound passkey session, `consent_minted`
`account:<a> / __set_recovery { recoveryKey }`, the code answered once), `RemoveAccountRecoveryKey`
(`DELETE /auth/recovery`, `__remove_recovery {}`).
Signed out, `POST /auth/recovery/begin { code }` then `/start { challengeId, code, registration }`
(UV, the cluster's own origins): `StartAccountRecovery` carries the code key's signature
(`proof::sign_recover` over account, credential id, SHA-256 of its public key and `at`, checked in
`authorize` and spent), spends the code, and records `SystemState::account_recoveries[a] =
types::PendingAccountRecovery { credential, startedAt, readyAt }`; no passkey, no session.
One per account (`409 RECOVERY_PENDING`).
`CancelAccountRecovery` (`POST /auth/recovery/cancel`, a passkey the account has, `__cancel_recovery
{ credentialId }`).
`FinishAccountRecovery` (`POST /auth/recovery/finish { accountId? }`, `412`,
`Pending::RecoverFinish`): the pending passkey's assertion over `session / __sign_in / sign_in_args`
of the new refresh token (`api::NewSession`, as `CreateRefresh`), verified at apply under that
credential; at `at >= readyAt` (the node's `app_clock`, `409 RECOVERY_NOT_READY` before) it adds the
passkey (counter from the assertion), revokes every session of the account
(`SystemState::revoke_account_sessions`) and records the refresh token.
`/auth/me`: `recoveryCode`, `recoveryPending`.

### Members' security

(Owner and admins.)

`GET /orgs/{org}/members?detail=security` (`api::org_members`, `holder`,
`SystemState::is_org_admin`, filtered by `Org::sees_member`) answers per member the passkey count
capped at `PASSKEYS_COUNTED` (`"3+"`), `recoveryCode` (a `recovery_keys` entry), `lastActiveDay`
(`api::last_active`: the latest `PasskeyTimes::last_sign_in_at` or live session exchange,
`api::session_use`, as a UTC day) and `sessions` (live, unrevoked, each session once).
Nothing the holder alone sees (ids, labels, sessions, origins, activity).
`deployment_orgs` adds counts only, `memberCount` and `activeMembers30d` (`ACTIVE_WINDOW_SECS`).

### Account proofs

Code: `api/account_proof.rs`, `Node::account_proof`.

`POST /auth/account-proof { nonce, audience }` (a passkey session, `holder`: never an API key or a
package-bound session) answers `calimero_client::attest::AccountProof`, the receipt key's signature
over `"calimero.account-proof.v1\0" || JCS({ cluster, node, account, nonce, audience, issuedAt,
expiresAt })`, valid `ACCOUNT_PROOF_TTL` (5 min); limits `ACCOUNT_PROOF_NONCE`,
`MAX_ACCOUNT_PROOF_AUDIENCE`, plain text only.
`GET /ops/nodes/{id}/receipt-key` (ops token) answers the key `Node::session_issuer` holds for that
node, so the operator (mdma) checks a proof from any node.

### Aliases

`Account::aliases`, `PUT/GET/DELETE /auth/aliases/{alias}` and `GET /auth/aliases`; an alias names
only an app its account reaches.

### Registered origins

Code: `origins.rs`, `api/origins.rs`; docs: protocol identities "Registered origins".

A package's manager (`SystemState::manages_package`: the bound publisher's org-wide
`MANAGE_APPLICATION` holders, else `PackageRecord::owner`) registers a web origin of their own
(`GET|POST|DELETE /package-origins/{package}`; `AddPackageOrigin`/`RemovePackageOrigin`, passkey
consent `package:{p} / __add_origin / { origin, rpId }`, `__remove_origin / { origin }`, checked in
`authorize`).
Each carries its own rp-id (the host or a parent; never the cluster's rp-id or a parent,
`origins::covers_cluster`).
`api::app_origin` is the one lookup (served first, then registered) for ceremonies (`claimed_app`,
`rp_with`: a registered origin alone under its rp-id), CORS (`lib.rs`) and the consent page's
`returnTo`; begin routes take `origin` (`403 ORIGIN_NOT_REGISTERED`).
Sessions opened there are bound like a served frontend's and name the origin
(`SessionClaims::origin`, `RefreshRecord::origin`, kept by a sign-up's `Pending::SignUp` and stated
nowhere in the sign-in challenge, like `app`); `principal` and `refresh` refuse them once it is
removed, and `UseRefresh` refuses an exchange that changes it.
A sign-up there answers its `412` with the origin's rp-id and takes the confirmation from that
origin only; the sign-up policy judges it like any other.
`UninstallPackage` of the last release forgets them.
Limits `MAX_ORIGINS_PER_PACKAGE`, `MAX_PACKAGE_ORIGINS`; `http` only for `localhost` names on a
`--dev` node (`allow_package_uploads`).

**Served origins** ([custom domains](/protocol/applications/#custom-domains)): `served: true` on the
body, `PackageOrigin::served` and `AddPackageOrigin::served` (both left out when false), consent `{
origin, rpId, served: true }` (`origins::add_args`, the one builder for the API and `authorize`).
`app_host::layer` serves the package's site on a `Host` whose origin (`served_origin_of`:
`https://name` on 443, or `http://name.localhost:port`) is a served one (`Node::served_site`, after
`app_host_site`; never under the apps domain or on a node's API host).
Ceremonies, CORS, binding and removal are the registered origin's, unchanged (`app_origin` answers
it with its rp-id; `app_origin_package` stays apps-domain only).
The API refuses (`served_fits`) a port, no `--apps-domain` (`NOT_SERVING`), a name under the apps
domain or the cluster's rp-id, a node's API host, a held origin with the other `served`; limits
`MAX_SERVED_ORIGINS_PER_PACKAGE` (4), `MAX_SERVED_ORIGINS` (64, the certificate metadata budget);
`require_upgraded_nodes` before the consent, so no older node drops the flag.
`GET /ops/served-origins` (ops token) lists `{ origin, host, label, addedAt }`, no package names,
for mdma's certificates and resolver routes. merod terminates no TLS: Traefik in the TD does, with
certificates mdma delivers.
