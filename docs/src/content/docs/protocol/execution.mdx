An **application** is a `calimero:app` component: a WASM component, built with
`calimero-sdk`, that defines a state machine: its data types and the methods
that change them. An **execution** (a *run*) is one call of one method. On a
cluster, only the app group's **leader** runs calls; the other replicas apply
what the run produced ([Replication](/protocol/replication/)).

The node runs components on `calimero-app-engine-wasmtime` through the host core
`calimero-app-host` (`crates/node/src/node/component.rs`,
`crates/node/src/component.rs`), preparing each bundle once and caching the
compiled artifact by its hash. A WASM core module (an SDK 0.12 app, which ran on
wasmer) is refused at upload (`400 UNSUPPORTED_BUNDLE`); an app of that kind
that a data directory still holds is listed and can be deleted, and anything
else on it answers `410 UNSUPPORTED_ENGINE`.

## What an app looks like

A method is a Rust function on the app's state; `&mut self` makes a call,
`#[app::view]` a read. This is `apps/kv-store`'s `set` and `get`:

```rust
use calimero_sdk::prelude::*;

#[app::state(version = 1)]
pub struct KvStore {
    entries: UnorderedMap<String, String>,
}

#[app::event]
pub enum Event {
    Inserted { key: String, value: String },
    Updated { key: String, value: String },
}

#[app::logic]
impl KvStore {
    #[app::init]
    pub fn init() -> app::Result<Self> {
        Ok(Self::load())
    }

    pub fn set(&mut self, key: String, value: String) -> app::Result<()> {
        let event = match self.entries.insert(&key, &value)? {
            Some(_) => Event::Updated { key, value },
            None => Event::Inserted { key, value },
        };
        env::emit(event, Audience::All)?;
        Ok(())
    }

    #[app::view]
    pub fn get(&self, key: String) -> app::Result<Option<String>> {
        Ok(self.entries.get(&key)?)
    }
}
```

`meroctl app build` turns the crate into a component with its ABI embedded
(`calimero:abi`), which the node reads to tell views from calls and to find
confirm methods ([Build](/build/)). On a cluster, a call to
`set` is one run on the leader, and the map's writes are its diff.

A run reads the app's state as an ordered, immutable version (`StateView`);
its writes stay in the run. When it ends, they become the outcome's **diff**,
which every replica applies. Each run gets a fresh instance of the component
from a pool of precompiled ones, dropped when the run ends, so nothing in a
module's memory or globals carries from one caller to the next.

A run ends with one status, the same whichever engine ran it:

| Status | The caller gets | In the log |
| --- | --- | --- |
| `Ok` | the result, and the events the caller is in the audience of | the diff, events, xcalls, started actions and compute starts |
| `AppError { code, message }` (the method returned an error) | `422 APP_ERROR`, `details.{code, fields}` | logged, nothing else kept |
| Trap `OutOfFuel`, `OutOfMemory`, `StackOverflow`, `Fault` (a guest panic, an out-of-bounds access, `unreachable`, a host panic), `HostDenied` (a call the run's kind may not make) | `422 TRAP`, `details.{kind, detail}` | logged, nothing else kept |
| Trap `Timeout` (the wall clock ran out) or `Unavailable` (the node had no instance slot, memory or file bytes for it) | `503 TIMEOUT`, `details.retryAfter` | not logged |

A logged failure spends the call's idempotency key, so a retry with the key
answers the same failure. A timeout depends on the node's load, not on the call,
so it is not logged and the key stays unspent: the client retries with the same
key. Outbound requests a run made are logged whatever its status, because they
left the node ([below](#outbound-http-from-component-calls)). A trap's `detail`
is a fixed text, never data from the guest.

## What the host offers a cloud run

The `calimero:app` world (`crates/app-wit/wit/calimero-app.wit`):

| Interface | What it does on a cluster |
| --- | --- |
| `storage` | The app's replicated state: `get`, `put`, `delete`, the commutative `add`, ordered `range` |
| `context` | The caller, the app's id and owner, its organization, the caller's role and teams there (`org-role-strict` on a read index), the applied index, unique ids, and starting an [action](#actions-component-apps) |
| `events` | Emit an event to an audience (`all`, the caller, listed accounts, a team, the org's members or admins); a removed member stops receiving at once |
| `blobs`, `files` | The app's [blobs](/protocol/blobs/) and sealed files |
| `search` | The app's own full-text indexes, in views |
| `xcall` | Send a call into another app (outbox), or call or view one synchronously |
| `runs` | Start or cancel a [compute run](/protocol/compute-actions/) on a job node, the uploader of a sealed file, publish a done run's output (logged writes only) |
| `rebuild` | A migration's new key space; migrations are refused (`MigrationsNotSupported`), so no run gets it |
| `action` | Inside an action: its key, and views and calls of the app |
| `wasi:clocks`, `wasi:random` | The run's clock and randomness, served by the host ([Time and randomness](#time-and-randomness)) |
| `wasi:cli/stdout`, `stderr` | The app's log ([Logging](/build/host-functions/#logging)); `wasi:cli/environment` is empty: no variables, no arguments |
| `wasi:http` | Outbound HTTPS, from actions and as recorded requests of a call (below) |

A package may also ship a **compute component** (world `compute`: `files`,
`job` and WASI's clocks and randomness, no storage, no network), which job
nodes run outside the log ([Compute actions](/protocol/compute-actions/)).

A component imports this world and nothing else. Its WASI interfaces are
pinned to 0.2.12 and `calimero:app` is 0.5.7; an import at an older patch of
the same minor (`wasi:*@0.2.z`, `calimero:app/*@0.5.z`) links as well, so an
app built before a patch keeps installing and running. Nine WASI interfaces
that Rust's standard library on `wasm32-wasip2` imports whatever the app does
are accepted and served by stubs that refuse:
`wasi:cli/{stdin, exit, terminal-input, terminal-output, terminal-stdin,
terminal-stdout, terminal-stderr}` and `wasi:filesystem/{types, preopens}`.
Stdin is empty, no terminal is present, preopens lists no directory, every
filesystem function fails and `exit` traps `Fault`. Nothing reaches the node's
operating system. Any other import, `wasi:sockets` among them, is refused when
the bundle is uploaded or installed (`400 BAD_BUNDLE`).

## Kinds of run

`handle(kind, method, args)` is the component's one export; the kind says what
the run may do. A host call the kind does not allow traps `HostDenied`.

| Kind | Runs as | Logged | May |
| --- | --- | --- | --- |
| `init` | The app's owner | Yes | Read and write state, emit events, `xcall.send`, `unique-id`, create files, start and cancel compute runs, publish outputs |
| `call` | The caller: an account, an API key, or `public` (not signed in; `context.visitor` names a visitor through a public link) | Yes | All `init` may, plus synchronous xcalls, `start-action` and outbound HTTP |
| `timer` | `system` | Yes | All a call may |
| `xcall-deliver` | `app(source)`, or the person the sending app served, with their grant ([Cross-app calls](/protocol/xcall/)) | Yes | All `init` may, plus outbound HTTP; no synchronous xcall, so a chain of them is one hop |
| `view` | The caller | No | Read state, search, `xcall.view`; any write, event or outbound request traps |
| `action` | Whoever started it | Its calls are | No state: `action.view`, `action.call`, synchronous xcalls, outbound HTTP |

`blobs.*` work in every kind but an action; `files.info` and `runs.uploader` in
every kind; `files.open` only in a compute run, which is an `action` run on a
job node ([Compute actions](/protocol/compute-actions/)). A method's kind and
whom it admits come from the [ABI](/build/app-abi/#what-the-node-enforces), which
the node checks before it calls `handle`: a view never runs as a write, and a
`confirm` method never runs as a view.

## Storage

A component has one key space: its own keys, which the node keeps as hidden rows of
the app's group, sealed on disk. Per-caller data is rows keyed by
`env::caller()`, and writer sets are rows the app checks before it writes
(`apps/team-space`); the host keeps no space of its own inside
an app's keys. (SDK 0.12 apps had a private and a host space beside the shared
one; they are gone with that SDK.)

- **Keys** are at most 1 KiB; a longer one traps `HostDenied`. Values have no
  cap of their own: the run's bytes and the entry size bound them
  ([Limits](/protocol/limits/#execution-limits)).
- **`add(key, delta)`** changes an integer without the guest reading it: the
  value is a shortest-form CBOR integer (an absent key is 0), the sum is stored
  the same way, and the add counts as one write. A value that is not such an
  integer, or a sum that overflows, traps `HostDenied`. The log records the
  summed value.
- **A range cursor** reads the state as of when it opened: the committed state
  plus the run's writes made before then, never writes made after. `get` and the
  diff see the newest writes. So a scan that moves records ahead of itself (an
  update that changes their index key) never meets them again, where it could
  otherwise loop until it ran out of fuel.
- **The checked writes** (`put-checked`, `delete-checked`, `add-checked`) answer a
  write past the run's write count or bytes as `limit-exceeded { limit, max,
  attempted }`, write nothing for it, and let the run go on; `put`, `delete` and
  `add` trap instead, for components built before them.

## What the node checks after the run

Before a run's outcome becomes an entry, the node applies these host-side
rules:

- **Read-only team members**: a member whose row in the app's team is read-only
  reaches the app's views only: a call to any other method is refused with `403`
  before it runs, so no run burns the developer's fuel uncounted.
- **Entry size**: an entry over the log's cap is logged trapped (`HostDenied`),
  and arguments over 512 KiB are `413 ARGS_TOO_LARGE`.
- **Conflicts**: a run built on a state another entry has since moved past, or
  on a bundle an upgrade replaced, commits as a no-op and runs again.

## Outbound HTTPS

A component sends HTTPS from an action, or as recorded requests of a call
(both below), at most `MAX_HTTP_REQUESTS` (8) per run either way. Either way the request leaves only when every gate holds:

1. the operator turned outbound on and allows the host (`[outbound]` in the
   node's configuration);
2. the app's bundle is a signed release whose manifest declares a URL prefix
   covering the request;
3. that prefix was approved for the publisher by whoever the cluster's
   [governance](/protocol/governance/) gives outbound approvals;
4. never from a view, `init`, a migration, or a read-only member's call;
5. `https` on port 443 to a name that resolves only to public addresses, within
   the size limits, no redirects.

## Actions (component apps)

A `calimero:app` component calls out from an **action**: an `#[app::action]`
method that runs outside the log, on the app's leader. A call can also make recorded requests itself
(below), never a view.

- **Start**. A client calls the action's method through `/intents`, or a
  call or timer runs `env::start_action(method, &args)`. Either way an entry
  logs that it started, under a key (`a.<term>.<seq>.<n>`), and the answer is
  `{ "actionId" }`.
- **Run**. The leader runs pending actions in a bounded pool, with a 10 s
  budget and the starter as caller. An action has no storage. It reads
  with `ctx.view`, writes with `ctx.call`, and sends HTTP with `ctx.fetch`
  over `wasi:http`. Each `ctx.call` is its own log entry under a key derived
  from the action's key, the method, the arguments' hash and an occurrence
  count, so a retried action's calls replay, while two identical calls in one
  run are two writes and a retry that takes another path gets new keys rather
  than another call's stored result. A method marked
  `#[app::allow(action)]` is reachable only from the app's own actions.
- **Outbound**. A request leaves only through the same gate as
  above. The URL must sit under a prefix the signed release's manifest
  declares, whoever governance gives outbound approvals (the app's organization, or the operator) must have approved it, the operator's hosts apply, and
  an action run sends at most 8 requests (`MAX_HTTP_REQUESTS`). A credential the
  manifest binds to the host (`secrets`: one header or body field) is attached by
  the node, never placed by the app, and redacted from the response
  ([Secrets](/protocol/secrets/)). Bodies are bounded in-memory buffers, so a guest
  cannot block a node thread.
- **End**. Success, or an app error, a fault or out-of-fuel, ends the
  action at once. A timeout is retried with backoff, 5 attempts in all. The
  end is logged. A failure sends an `ActionFailed { actionId, method, reason }`
  event to the starter and runs the app's `onActionFailed` as the starter. A
  new leader resumes every action that has not ended, with the same key.

## Outbound HTTP from component calls

A component's call, timer or xcall delivery may send requests itself (up to 8 per run)
(`env::fetch`), for a check that belongs in the same request as the
write it guards, such as a captcha service verifying a Turnstile token:

- **The same gate as actions.** A URL the signed release declares under
  `outbound`, its organization (or, per governance, the operator) approved and the operator allows; a credential the
  manifest binds to the host is attached by the node and redacted from the response. Views, `init` and
  migrations cannot send (`HostDenied`), nor can a read-only member's call.
- **Once, recorded.** The leader sends it while it runs the call, before
  proposing. The call's log entry records the exchange (`Outcome::http`: the
  request as the app made it, with placeholders, and the response the gate
  returned; bodies cut to 64 KiB), whatever the call's status. Followers apply
  the diff and never fetch, and a retry with the same idempotency key replays
  the recorded answer. A run the log never commits (a leader race, a timeout)
  recorded nothing and sends again when it re-runs.
- **Bounded.** The node waits at most 1.5 s for the response, inside the
  call's 2 s budget; a timeout, a refusal or an unreachable host is an error
  the app's `fetch` returns.
- **Trust.** The leader sees the response before it is logged. Attestation
  covers the code that made the request and its TLS connection, not the remote
  server's answer: the same trust as an action's request.

`apps/fixture-captcha`'s `verifyTurnstile` is the example; the kv
fixture's `setHumanTurnstile` reaches it with a synchronous xcall, so the
token is checked and the form written in one request.

## Time and randomness

The host serves `wasi:clocks` and `wasi:random` itself, never from the node's
operating system, by the kind of run:

| Run | Wall clock | Monotonic clock | Randomness |
| --- | --- | --- | --- |
| `init`, call, timer, xcall delivery | The entry's timestamp | Fixed at the entry's timestamp | ChaCha20 seeded for the run by the leader; followers see only the diff |
| View | The timestamp of the newest entry applied where it reads | Fixed at that timestamp | The node's CSPRNG, not recorded |
| Action | The node's clock, rounded down to the second | Fixed at the action's start | The node's CSPRNG, not recorded |
| Compute run | The timestamp of the entry that started it | Fixed at that timestamp | ChaCha20 from the run's seed, so the run repeats exactly |

The monotonic clock never moves within a run, and a guest's sleep or poll is
ready at once, so no guest code can measure elapsed time: a run cannot time
other tenants' work, and a sleep never holds a node thread. A request for more
than 1 MiB of random bytes in one call traps `HostDenied`; the SDK asks in
pieces.

The leader stamps each entry with the later of its own clock and the last
applied entry's timestamp plus 1 ms, so an app's timestamps never go backwards,
even across a leader change. Idempotency expiry and timer slots read these
timestamps, never a node's local clock, so every replica judges them alike.

## Timers

An `#[app::every("…")]` method is a timer. The app's leader looks for due
ticks every 100 ms (`TIMER_POLL`). A timer's slots fall at the timestamp of the
app's `init` entry plus whole multiples of its interval, and the leader
proposes the latest due slot (`componentTick`). The tick runs as `system`;
`env::timer()` gives its `scheduled` slot and the `previous` one applied, as
decimal strings on the wire.

- **Once per slot.** A replica applies a tick only if its slot is later than
  the timer's last applied one, so a tick that two leaders propose around a
  failover runs once.
- **Failures count.** A tick that traps or returns an app error is logged with
  its status and its slot counts as applied: it is not retried, and `previous`
  stays right. A tick that times out is not logged, and the next poll proposes
  the slot again, or a later one if it is due by then.
- **No bursts.** Slots missed while no leader ran collapse into one catch-up
  tick for the latest of them. An app that must cover every slot loops over the
  gap from `previous` to `scheduled`.

## Determinism is not what converges

Only the leader runs, so the clock, randomness, outbound responses and search
answers cannot make replicas disagree. Runs are still bounded and
transactional: a call or view gets 200 000 000 fuel, 64 MiB of memory and 2 s
of wall clock, an action 10 s, and one run writes at most 10 000 keys and
1 MiB ([Limits](/protocol/limits/#execution-limits)); a trap or an app error
leaves an empty diff. Fuel pays for host work too: each storage access, range
batch, search and byte a host call moves costs fuel
([What host work costs](/protocol/limits/#what-host-work-costs)), so a run
cannot make the node read or search without bound for little fuel.

## Views and upgrades

A **view** runs the same way against a replica's applied state, with search
available, and its writes are discarded ([Reads](/protocol/reads/)). An
**upgrade** swaps the bundle; a named migration is refused
`MigrationsNotSupported` ([Upgrades](/protocol/upgrades/)).
