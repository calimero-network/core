The claim Calimero makes is narrow and checkable: **nobody operating the
cluster — Calimero included — can read an app's data or put new code in front
of it without the party the deployment named for that decision.** This page
lists what that rests on.

## What is trusted

| Trusted | For | Checked by |
| --- | --- | --- |
| Intel TDX and its attestation (DCAP collateral) | That a quote comes from a genuine TD with the measured image, and that a debug TD is not passed off as one | Every client and peer, on every new channel |
| The signed mero-tee release | That the measurements in `published-mrtds.json` are the image Calimero built and signed (Sigstore) | `Measurements::Release` in the client and peer policy |
| mero-kms | Releasing the storage key only to an attested TD, and keeping each node's rollback counter | The KMS client verifies the KMS against the signed release too, and the node reports the KMS quote it accepted, bound into its own quote (`purpose=kms`, [Attestation](/protocol/tee-attestation/#which-kms-a-node-took-its-keys-from)), so anyone verifying the node can check which KMS that was |
| The `merod` build in that image | Everything in this reference | Its measurement is part of the image |
| The person's authenticator | Their passkey | WebAuthn, with user verification for step-ups |

Not trusted: the host and hypervisor, the disks, the network and any TLS
terminator, the operator, other tenants, the app's publisher beyond its own
code, and app code beyond what its owner approved.

## Who can do what

| Party | Can | Cannot |
| --- | --- | --- |
| **Network / proxy** | See that clients talk to nodes, sizes, timing; drop or delay traffic | Read or forge requests, responses or frames; replay a request; impersonate a node without its attested key |
| **Host / hypervisor** | Stop, freeze, restart a node; read sealed disks; withhold the network; restart a node on an older copy of its disk, which then refuses to start | Read memory of a non-debug TD; open sealed values without K_c; get K_r (it comes from mero-kms, not the host) or K_c (wrapped under K_r, or delivered by a peer only to the attested TD at a registered node's address) |
| **Operator** (ops token) | Register nodes, move replicas onto approved releases, set quotas, take sealed backups, read counts and Raft status, set public release deadlines that stop new work on old images (signed with the operator key); force a start past a rollback (`--accept-rollback`, which raises the epoch every node reports); and whatever governance gives it | Read state, events, blobs or credentials; sign in as anyone; move an app's data to an unapproved image (a deadline approves nothing); block an approval; upgrade apps, approve releases or outbound destinations unless governance gives it that decision |
| **A backup holder** (whoever upgrades an app: the operator, the app's organization or its owner) | Open its own apps' recovery-disk files on its own device and bring them back on a cluster that admits it | Open another holder's files; recover onto a cluster without that cluster's operator signing the import (`/recover/holder`) |
| **A publisher** (the organization a package's signing key is bound to) | Where owners decide: approve the releases every instance of its packages runs on (`APPROVE_RELEASES` holders), and upgrade its own organization's instances of its packages (its owner and admins), each with a passkey assertion checked where it applies | Read its customers' apps; upgrade a customer's instance (that organization's owner and admins approve it), or turn a package back to `publisher` once a release declared `owner` |
| **A node on an approved release** | Everything this reference describes for the apps whose owners approved its release | — (it is the trusted computing base for those apps; that is why every peer is attested) |
| **A node on a release nobody approved** (attested, registered: an operator rolled it out) | Join the system group, hold and replicate the system state, lead it; propose system commands | Receive or read an app's data, through Raft, internal routes, blobs or presence; act as a user with a session it signed; log a decision (approval, publisher binding, upgrade, transfer, deletion, operator decision) without its maker's passkey or the operator key |
| **An app's owner** (while a member of its organization) | Upgrade it (unless its package says `publisher`), change its access, transfer or delete it | Read other apps; act for other accounts |
| **An organization's approvers** (owner and admins; members granted `APPROVE_RELEASES`, or `MANAGE_APPLICATION` org-wide) | Where governance says owner: approve the releases its apps run on while their package's key is not bound to a publisher, and the outbound prefixes its apps may reach; an account's own apps are its personal organization's | Approve for another organization; approve without a passkey assertion |
| **A member** | What the app's grants and the app's own code allow | Read the app's state except through its methods; receive events outside their audience; write if their team row is read-only |
| **An app's frontend** (third-party page) | Act as the signed-in person for that package's apps only; ask the node to show its user a consent page | Reach other apps, manage credentials or API keys, approve anything, upgrade or uninstall, or choose what the consent page shows or where it returns |
| **An API key** | What its scope allows | Manage credentials or keys; produce a passkey assertion |

## Which mechanism stops which attack

- **Reading traffic** — the sealed channel, keyed to an attested key, with
  forward secrecy per session ([Networking](/protocol/networking/)).
- **A fake or outdated node** — the quote check with a measurement policy and a
  release floor, for clients and peers alike ([Attestation](/protocol/tee-attestation/)).
- **Reading disks** — AES-256-GCM under K_c, bound to row, group and column;
  hidden row keys ([Encryption](/protocol/encryption/)).
- **A new image reaching data** — release approvals, enforced by the replicas
  that hold the data before any Raft entry or snapshot leaves
  ([Deployment governance](/protocol/governance/#release-approvals)). Release
  deadlines are the operator's, and only availability: they refuse new apps,
  installs and upgrades for a party on an old image, but approve nothing, so
  they cannot send data anywhere, and they never refuse an approval.
- **Someone posing as a package's publisher** — a binding carries the package
  key's own signature over the cluster, the organization and the key's
  binding generation, verified at apply, so it is neither forged nor replayed.
- **New code reaching data** — app upgrades held by one named party, with a
  passkey step-up for owners.
- **Exfiltration over the network** — outbound HTTPS only to hosts the operator
  allows, under prefixes the app's signed manifest declares and its approver
  approved, from writing runs only. An API key goes only where the signed
  manifest binds it, attached by the node: the app never places or reads one
  ([Secrets](/protocol/secrets/)), but a raw request can still use it for
  anything it allows under its bound paths. The app's own code is not stopped
  from sending what it reads to an approved host; an organization that needs
  that guarantee turns egress off (for itself or one instance), and then no
  request leaves for its apps whatever an approval says
  ([Egress off](/build/guides/outbound/#egress-off)). The instance's owner and
  managers see each request's host, path, status and secret names in its
  outbound audit, refusals while egress is off included, so a release that
  turns an approved host or a secret to another use shows up there; the audit
  reports, it does not stop anything.
- **A stolen session** — 15-minute tokens, refresh tokens exchanged once they
  are an hour old whose reuse after that revokes the session (a copy taken
  within the hour refreshes beside its owner until then), revocation that
  holds on every node before the next request and the next refresh. A
  browser's session is bound to its non-extractable holder key: its refresh
  token is used only with that key's signature, so a copy taken off the device
  refreshes nothing, and it lives 7 days
  ([Sessions](/protocol/identities/#sessions)).
- **A lagging replica granting stale access** — credentials and access judged
  on fresh system state (a read index).
- **A node on an unapproved release** — every internal route judges the
  identified calling node's release, a Raft message's sender must be the node
  that sent it and a member of the group, sessions are signed by the node that
  issued them and accepted only from an approved one
  ([Networking](/protocol/networking/#between-nodes), [Sessions](/protocol/identities/#sessions)).
- **Forged authority in the log** — decisions carry their maker's passkey
  consent or the operator's signature, checked at apply on every node and used
  once ([system group](/protocol/system-group/#decisions-carry-their-proof));
  other commands are built by nodes from verified credentials, and authority
  is checked again at apply.
- **A malicious app frontend** — its own origin and a package-bound session.
- **An app's page driving an approval** — approvals are refused to
  package-bound sessions; an app asks the node, whose own consent page shows
  node-side facts and takes the passkey, and the consent binds the target
  manifest's hash or the release's measurements digest
  ([The consent page](/protocol/consent-page/)).
- **A malicious app** — the WASM component sandbox and its limits (fuel,
  memory, wall clock, writes); it reaches only its own keys, blobs and files;
  outbound HTTPS only through the gate above; xcalls only into entry points
  within its organization.
- **A restored older disk** — the rollback counter: mero-kms and the node's
  sealed store keep the same per-node checkpoint, and a store behind mero-kms
  does not start; a forced start raises the cluster's epoch, which every node
  reports ([Rollback protection](/protocol/encryption/#rollback-protection)).
- **Losing every mero-kms** — the recovery disk: backups sealed to a backup
  key only its holder has, signed and attested by the node that wrote them
  ([The recovery disk](/protocol/encryption/#the-recovery-disk)).
- **Proving all this to a user** — `verify_app_cluster`: every replica's quote,
  receipt keys, and the governance they all attest; receipts on every answer.

## What is not protected yet

- **The system state on unapproved nodes.** Every node of the cluster, whatever
  its release, holds the whole system state: accounts, passkeys' public keys,
  memberships, approvals, app records, refresh-token and API-key hashes, invites.
  Its log and snapshots are sealed at rest under K_c, which every release holds
  ([The system group](/protocol/system-group/)).
- **Commands without a proof.** Housekeeping commands (creating or deleting an
  app, changing its access or metadata, creating an organization or a team,
  uploading a bundle, installing a package, labels, aliases, session
  revocations) still name an actor any node of the cluster can claim; the
  decisions, credentials, memberships, invites and operator commands above
  carry proofs ([system group](/protocol/system-group/#decisions-carry-their-proof)).
- **Which node a client talks to.** A client checks that a node is attested,
  not that the user's approver approved its release, so it sends credentials and
  passkey assertions to any attested node. A sign-in's challenge is not bound to
  the node that issued it: any registered node can take it from its issuer
  (`internal/challenge/take`), so a modified image a person signs in through
  can finish a ceremony another node began.

- **Rollback, partly.** A rollback shorter than one checkpoint (1 s) looks like
  a crash; a store spliced from rows of different ages is not caught; an
  operator can force a rollback (`--accept-rollback`), which is visible in
  `/health` and `/ops/status` but not in the attested KMS evidence; and an
  older mero-kms without counters starts nodes unprotected. Forcing one needs no
  consent from the app's owner.
- **The recovery disk's holder.** Whoever holds an app's upgrades holds the key
  to its recovery-disk files: where governance gives app upgrades to the
  operator, the operator's backup key opens every app's state and the whole
  system state on that disk. That is the same party that could already move
  the app to new code.
- **Keys per app.** One K_c covers every app on a cluster; keys per app from
  mero-kms are not done.
- **Availability.** The host and operator can stop nodes. Raft tolerates the
  loss of a minority of an app's replicas, and a session outlives the node that
  issued it: every node holds every peer's attested signing key
  ([Failover](/protocol/identities/#failover)). A new app's replicas are spread
  across the zones the operator registered ([placement](/protocol/context-lifecycle/#create));
  moving existing apps between zones is the operator's (`ops placement`, `ops move`).
- **Side channels** on the TD and timing of requests are outside this model.
- **The consent page under TLS.** The node's consent page and its model travel
  as plain HTTPS, not in the sealed channel: whoever terminates TLS in front of
  a node can read what a person is asked to approve, or serve another page. It
  cannot change what is approved nor approve without the passkey
  ([The consent page](/protocol/consent-page/#what-it-does-not-protect)).
- **An app's frontend.** The page decrypts and shows what the signed-in
  person reads, and its own JavaScript checks the node's attestation, so the
  person trusts whoever served that page: a page served from a static host
  (Vercel, a branch build: for demos and debugging) trusts that host and its
  build; a page the node serves from the release's signed `.mpk` trusts
  whoever can obtain a WebPKI certificate for its name. Script on the page can
  use the session while it runs and read the 15-minute session token; the
  holder key keeps the refresh token from working anywhere else. A browser
  extension that checks every file against the publisher-signed manifest is
  the way past TLS (proposed in [mero-tee's frontend-verification
  issue](https://github.com/calimero-network/mero-tee/issues/666)).
- **A debug image.** A debug TD exposes its memory to the host. Clients refuse
  debug profiles unless told otherwise, and nodes trust debug peers only when
  they are debug themselves; a cluster on a debug image protects nothing.
