This reference explains how a Calimero cluster works and why it is built that
way. It follows one **call** from the client that makes it to the log entry
that records it, rather than touring the crates. The crates are
[`merod`](/operate/merod/) (the node binary), `calimero-node` (everything
the node does), `calimero-log` (the replicated log), `calimero-sealed` (the
encrypted transport), `calimero-identity` (passkeys, sessions, API keys) and
`calimero-client` (the Rust client, whose attestation check every client
and peer shares). Apps run on `calimero-app-host` over
`calimero-app-engine-wasmtime`; the node fetches its storage key with
`calimero-kms-client` and makes its quotes with `calimero-tee-attestation`.

[Concepts](/protocol/concepts/) → [The system group](/protocol/system-group/) →
[Replication](/protocol/replication/) → [Application execution](/protocol/execution/).
Everything else builds on those four.
:::

## The one idea everything hangs on

A Calimero app is a `calimero:app` WASM component whose state lives on a
**cluster** of attested Intel TDX nodes. Each app instance has **its own Raft log**, replicated on several
nodes (three by default). The log's **leader** runs every call against the app's current
state and appends the call together with what it produced: the result, the
exact storage writes (the **diff**) and the events. Every replica applies the
diff in log order. Nobody runs the call a second time.

A second Raft log, the **system group**, is shared by the whole cluster. It
holds who exists and who may do what: nodes, accounts and their passkeys,
sessions and API keys, organizations and teams, installed packages and the
directory of app instances. Every command in it names the actor it acts for,
and the state machine checks that actor's authority when the command applies,
so the log alone decides every outcome.

Nothing a node holds leaves it in the clear. Clients and peers verify a node's
TDX quote before they send it anything, then speak to it only through a
**sealed channel** bound to the key that quote attests. Everything a node
writes to disk is sealed under the cluster's key, which it keeps wrapped under
a storage key it receives from mero-kms only after proving its own image; the
same key release carries a counter that refuses a disk restored from an older
copy.

> Hold onto that: _one log per app, one log for the cluster, the leader runs
> and everyone applies, and nothing crosses a trust boundary unsealed_. Every
> chapter is a detail of it.

## Why it is built this way

A cluster of attested nodes can afford coordination. With one leader per app
and a log every replica applies in the same order:

- **Calls are linearized.** Two writes to one instance never race; the second
  runs against the state the first left. The SDK's collections are plain
  data structures with nothing to merge (only `Text` stays a sequence CRDT,
  for edits typed against a stale view).
- **Authorization is one verdict.** A command is checked against the state it
  applies to, which is the same state on every replica.
- **Execution need not be deterministic for convergence.** Followers apply the
  leader's diff, so `time_now` and `random_bytes` are read once, on the leader.
- **Confidentiality comes from the hardware and the channel,** not from a key
  per scope delivered to each member. A member's client never holds app state;
  it reads through the node.

## One node, layer by layer

Every request, a client's or a peer's, enters through the same listener and
crosses the same layers. Only the outer layers answer in the clear; everything
below the sealed envelope sees the inner request, as if it had come directly.

## Status

:::caution[Release candidate]
This describes the system as the code stands (1.0.0-rc.20). It is not a
frozen wire specification: requests and entries are JSON, though what a node
keeps already names its format ([Format versions](/protocol/storage/#format-versions)).
Some parts are not done yet and are named where they matter: keys per app from
mero-kms, the rollback epoch in the attested KMS evidence (a node reports it in
`/health` today), and search indexes that survive a restart.
:::

Apps are built with `calimero-sdk` into `calimero:app` components, which run on
`calimero-app-engine-wasmtime`. What they do inside a run is described only as
far as the node depends on it.
