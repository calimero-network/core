An **upgrade** moves an app instance to another bundle, usually another release
of its package, and keeps its state: the new code reads what the old code
stored ([Upgrades & state](/build/migrations/)). This page is about what the
cluster does with it. How a release is parsed, verified and trusted when it is installed is
in [Packages & frontends](/protocol/applications/#installing-a-release).

## Who may upgrade

New code reads the app's data, so an upgrade is one of the three decisions
[deployment governance](/protocol/governance/) assigns:

- **Owner side** (default): the **owner and admins of the app's organization**
  (`OrgRole::Admin` or above), whatever its package's signed manifest declares
  (`upgrades: owner | publisher`, [App upgrades](/protocol/governance/#app-upgrades)),
  and nobody else: not the member who created the app, a team's lead, a holder of
  `MANAGE_APPLICATION`, or the publisher, for an instance of another
  organization. Anyone else is refused `403` before the passkey, and `apply`
  refuses the entry (`ownerApprovedUpgrades`, below). Until every node runs
  1.0.0-rc.33 the rule before holds, and entries logged before it replay as they
  applied: for `owner` the app's owner or whoever holds `MANAGE_APPLICATION` on
  its team or organization-wide; for `publisher` the publisher organization's
  `MANAGE_APPLICATION` holders, for every instance, and nobody until its key is
  bound.

  An app's frontend asks `GET /apps/{app}/update` whether there is a release to
  move to (`available`: a deployment's offer, else the newest newer release the
  caller sees that the upgrade would take), whether the person may approve it
  (`mayApprove`) and who does (`approvers`), and sends the person to the
  [consent page](/protocol/consent-page/)'s upgrade sheet. An instance from a
  deployment moves only to the release its deployment offers, which the sheet
  resolves for a person who never installed it; asking for it names no version.

  Each upgrades with a passkey session and a step-up over the exact upgrade
  (`POST /apps/{app}/upgrade { version | bundle }`, then the `412`
  challenge; a `migrate` is refused, below). The assertion is recorded as `consent` on the directory's
  `UpgradeApp` command. A package may move from `publisher` to `owner` in a
  later release, never back, and an app is never upgraded from an `owner`
  release to a `publisher` one.
- **Operator**: only the operator (`POST /ops/apps/{app}/upgrade`), to a release
  it installed itself.

**An instance from a deployment** moves only to the release its
[deployment](/protocol/governance/#deployments) offers for its package: the
deployment's managers choose the release (`OfferApp`), and whoever holds the
instance's upgrades only accepts it or not. Another version, another package
or a raw bundle is refused `409 OUTSIDE_DEPLOYMENT` before the step-up, an
organization's, publisher's or unit's run notes such an instance as failed,
and `UpgradeApp` refuses it again where it applies.

The developer decides the target, the organization's owner and admins decide
whether to take it, and
nothing else is reachable; with `upgrades: publisher` the publisher's run
takes the owner's place, held to the same offer. An app the instance created
(a unit's member) carries the same deployment and moves only with its unit, in
a unit upgrade to the release the deployment offers (`POST
/apps/{app}/upgrade-unit`): alone, or in a unit run to any other release, it is
refused `409 OUTSIDE_DEPLOYMENT`, before any passkey is asked for.

An owner or admin of the app's organization may hand one app's upgrades to CI
with an [upgrade key](/protocol/identities/#upgrade-keys): made once with a
passkey (`403` for anyone else), it signs
each upgrade of that app to a signed release of its package in place of the
step-up, and the node refuses it everything else. Who may upgrade and the
deadline below are judged for it exactly as for a passkey, on its account, at
each upgrade: once that account is no longer an owner or admin there, the key
upgrades nothing.

Past a [release deadline](/protocol/governance/#release-deadlines) its
approver has not met, an upgrade is refused `409 RELEASE_DEADLINE` before
anything runs.

A version alone means the app's own package and service.

**An instance runs a release, not only a WASM.** A release's frontend ships in
its signed `.mpk` and works with that release's backend only, so approving a
release approves its frontend. The directory records the release each instance
runs (`AppRecord::release`: package, version, service), set when it is created
(the version named, or the release its deployment offers) and by every upgrade.
Releases may share a WASM: one that changes only the frontend is still an
upgrade, approved by whoever holds the app's upgrades exactly as above, and
afterwards the instance runs, is reported at, and is served the frontend of the
new release. An instance recorded before releases were kept (or running a raw
development bundle) is taken to run the release its bundle ships in, if that
release was installed by the time the instance took the bundle.

**Who may upgrade follows the release it runs.** Its `upgrades`, its publisher
and so its approved releases are those of `AppRecord::release`
(`SystemState::governing_release`), not of whichever release first shipped the
same WASM: an instance of an `owner` release stays its owners' even where a
`publisher` release of the package ships the same WASM, and a release installed
after an instance took a raw upload of the same WASM takes nothing from its
owner. A WASM belongs to one signer: a release of another signer's package that
ships it is refused at install. One signer may ship it in several of its
packages, and each instance is judged by the release it runs. A cluster begun before this rule replays what it
logged then as it applied it: the first system leader on a release that judges
by the release writes `AttributeByRelease` (the `attributeByRelease` feature,
so only once the [cluster version](#the-cluster-version) brings it), and the
rule holds from that entry on.

**What the passkey signs.** The challenge's arguments are
`{ bundle, migrate, manifest }`: the target WASM's hash and the target
release's signed-manifest hash, so another manifest installed under the same
version (other outbound prefixes or frontend origins, the same WASM) is not
the upgrade that was approved. The node computes both; a target that changes
between the challenge and the assertion no longer matches it, and the upgrade
is refused. A raw development bundle has no manifest, and `manifest` is
`null`.

**From the app itself.** An app's frontend cannot upgrade its instance (its
session is bound to its package). It asks the node for a consent request
(`{ kind: "upgrade", subject: { app, toVersion } }`); the node's own page shows
the capability sheet (outbound, frontend origins, interfaces, methods,
events, timers, the state version each side declares, build) and takes the owner's passkey there
([The consent page](/protocol/consent-page/)).

## What an upgrade runs

An upgrade is **code only**: the app's state stays as the old code wrote it,
and the new code must read it ([Upgrades & state](/build/migrations/)).
`calimero-sdk` has no migration export yet, so nothing is planned from the
two ABIs and nothing reshapes the state; a named `migrate` is refused
`MigrationsNotSupported`. The state version each side declares
(`#[app::state(version = N)]`) does not decide whether an upgrade runs: the
consent page shows it, and flags a change, since the new code reads the old
data as it is.

So an app moves to **any newer release** of its package in one upgrade,
however many releases or state versions that skips: nothing has to be
applied one release at a time, and an app several releases behind is
offered the newest one it can reach (below).

## The runtime a release needs

A release's signed manifest names the oldest runtime it runs on
(`minRuntimeVersion`): the merod release a node was built as. The node that
installs a release checks it against its own runtime
([Installing a release](/protocol/applications/#installing-a-release)), and
records it with the release (`PackageVersion::min_runtime_version`). The
other nodes take the release's WASM without verifying the `.mpk`, and a
cluster runs several releases while its nodes move to a new one, so the
cluster judges the requirement against the runtime of every node that would
run the app:

- **Upgrades.** An upgrade is refused `409 RUNTIME_TOO_OLD` when any of the
  app's replicas is on a node whose runtime is older than the target release
  needs; `details` names the requirement and each such node
  (`{ minRuntimeVersion, nodes: [{ node, runtime }] }`). It is asked before
  the passkey step-up and on the consent page, and again where every
  upgrade path goes through (`run_upgrade`), which records the refusal as
  the app's last upgrade. Nothing runs on the app's group.
- **New apps.** Placement leaves out the nodes whose runtime is older than
  the release the app is created from; when none is left, the create is
  refused `409 RUNTIME_TOO_OLD`.
- **Replica moves.** `POST /ops/apps/{app}/replicas` refuses `409
  RUNTIME_TOO_OLD` a node the app is not on yet whose runtime is older than
  the release the app runs. A node it is on already is not judged, so an app
  can always be moved off one.

Each node names its runtime over the sealed peer channel (`POST
/internal/runtime`, an attested node's own answer), kept for 30 s. A node on
a release from before this answers `404`: it is older than the asking
node, and judged so. A node that does not answer, or whose release is not a
version (a development build), is not judged, as before.

## Which release an app can reach

Each app's entry in `GET /auth/apps` and `GET /orgs/{org}/apps` names the
newer releases of its package its reader may see and move it to:

- `availableVersions`: the newest 16, oldest first;
- `latestReachable`: the newest of all of them the upgrade would take now,
  or `null`. It may be older than every release in `availableVersions`;
- `latestBlocked`, only when the newest release is not `latestReachable`:
  its `version`, the `reason` and a `message`. `runtime`: a replica's node
  runs an older runtime than it needs, with `minRuntimeVersion` and `nodes`
  as the `409` names them; `authority`: the app's owner upgrades it and the
  release would give its upgrades to the publisher.

Who may upgrade and [release deadlines](/protocol/governance/#release-deadlines)
are the same for every release of a package, so they decide whether to
upgrade, not which release to: the report leaves them to the app's
`upgradesHeldBy` and approvals. A release recorded before releases kept
their runtime requirement is not judged by it here; the upgrade reads it
from the release's `.mpk` and still refuses it.

## Where an update may send data

An app's **unit** is the app and every app it created with it (`uses` in mode
`create`, transitively; never an app attached to it). Its **egress** is every
destination the releases of the unit may send a request to: each release's
`outbound` prefixes, and the host of a declared secret no prefix names. Only
those destinations are reported; an empty list means no data leaves Calimero.
Any destination outside Calimero is just a destination, whatever runs there: the
platform keeps no list of trusted endpoints and never vouches for an external
one, a TEE (a private-inference service, say) included. An app that wants to
trust an external TEE verifies its attestation in its own code; the destination
is still listed.

`GET /packages/{package}/{version}/capabilities` answers a release's unit
destinations before any instance exists (`destinations`, `members`), `GET
/apps/{app}/egress` an instance's as it runs now, and `GET /apps/{app}/update`
classifies the available update over the unit (as `upgrade-unit` would move its
members when it has any, else the app alone). The consent page's upgrade sheets
carry the same verdict (`unit`) and say it in plain words: "This update can send
data to a new place:" and the new hosts when it adds any (red), else "Your data
stays in Calimero" or "This app can send data to:" and the hosts.

The classifier (`calimero_bundle::update`, the same code `meroctl` uses) calls
an update **red** when any of these holds, and **green** otherwise:

| Rule | Why |
| --- | --- |
| The app or a member that stays is signed by another key (`signerChanged`) | The code is no longer from whoever was trusted with it |
| A destination after is covered by none before, members counted (`egressAdded`) | Data may go somewhere it could not |
| The app or a member declares another state version (`stateVersionChanged`) | No migration runs, so the new code reads data in a shape it may not expect |
| A member with egress joins or leaves the unit (`memberAdded`, `memberRemoved`) | A joining member brings its own destinations; one that leaves is no longer upgraded under this consent |
| A release newly calls a method of another app as the person (`delegatedMethodsAdded`) | A new way to act as the user |

New and removed methods are reported (`newMethods`, `removedMethods`) but do not
make an update red. Nothing applies an update by its class yet: every update
still waits for an owner's or admin's approval.

### The class at apply

From cluster version 1.0.0-rc.34 (`Feature::UpgradeClasses`) every `UpgradeApp`
carries the class the proposing node computed for that app's move (the app and
the members it has, as they run when it moves; in a unit's run the instance
carries the whole unit's class, its members moving to the run's targets, and
each member its own). Apply cannot read a release's ABI (it is in the `.mpk`), but the
log holds each release's pinned signer, its `outbound` prefixes, its secrets'
hosts. Apply classifies the move again from
those (`SystemState::check_class`) and refuses, `409 UPGRADE_CLASS_MISMATCH`, a
class that leaves out a reason the log shows (a new signer, a destination no
release before reached), or that the classifier could never answer (red without
a reason, green with one). So no node can log a red update as green. What the
log cannot show (a state version, a method called as the person) is the
proposer's to say. A move the log cannot rebuild (a release the app or a member
runs, or a target, no longer installed, which is allowed while another release
ships the same WASM) is never green: the log cannot confirm it, so apply refuses
a green class for it and takes a red one, gated as red. The API classifies such a
move red with an `unclassified` reason for each part the log lacks (`{ code:
"unclassified", member, package, version }`, `SystemState::unclassified`), and
shows it the same way wherever it shows the class (`GET /apps/{app}/update`, the
consent page's sheets and approval step; what compares the two sides, its
destinations, signer, state version and methods, is unknown: `null` in the API,
"Unknown" on the page), and
apply refuses an `unclassified` reason that names anything else, or one on a
move the log rebuilds. An entry carrying that reason needs cluster version
1.0.0-rc.35 (`Feature::UnclassifiedUpdates`), as rc.34 cannot decode it: below
it, under a `secondApprover` policy, the first approval, the upgrade and the
consent page of such a move are refused `409 FEATURE_NOT_ACTIVE` before the
passkey (every node must run 1.0.0-rc.35 first), and without that policy the
upgrade is logged without a class, as rc.34 logs it; the update still shows red.
The class and its reasons are kept on the app's last upgrade
(`lastUpgrade.class`, `reasons`). An entry without a class (an earlier
release's, a raw bundle's, or a release the classifier could not read) is taken
as red by every rule below; one logged before the feature replays as it applied.

## Update policies

How an app's updates apply is its organization's owner's and admins' to decide,
with a passkey (`Feature::UpgradePolicies`, 1.0.0-rc.34): `SetUpgradePolicy
{ org, app?, policy }`, consent `org:<org> / __set_upgrade_policy / { app,
policy }`, through `POST /orgs/{org}/upgrade-policy` (every app of the
organization that has none of its own) or `POST /apps/{app}/upgrade-policy` (one
app); `policy: null` drops it. An app follows its own policy, else its
organization's, else the defaults (`GET` on either route answers the one in
force and its `source`). Moving an app to another organization drops its own.

| Field | Default | Effect |
| --- | --- | --- |
| `secondApprover` | off | A red (or unclassified) update needs two distinct owners or admins |
| `autoApply` | `never` | `noDestinations`: a green update of an app whose unit has no destinations before or after it (no data leaves Calimero) applies on its own after the hold ([Updates that apply on their own](#updates-that-apply-on-their-own)) |
| `holdHours` | 24 | How long a green update waits before applying on its own: 24 to 168 (`400 BAD_UPGRADE_POLICY`) |

Nothing updates on its own by default.

### A second approver

Where the policy asks for one, a red update waits for two owners or admins. The
first approves with `POST /apps/{app}/upgrade-approvals { version, unit? }`, its
own consent (`<app> / __approve_upgrade / { package, version, targets, class }`,
`ApproveUpgrade`), logged as a pending approval on the organization
(`Org::pending_upgrades`, one per app; with `unit` the members the unit's
upgrade moves, by app). Another owner or admin then upgrades as usual
(`/upgrade`, `/upgrade-unit`, the consent page, an organization's or a
publisher's run); `UpgradeApp` applies only with a live first approval of that
move by someone else (`SystemState::update_gate`), and records its approver
(`lastUpgrade.approvedBy`). Without one the API answers `409
SECOND_APPROVAL_REQUIRED` before any passkey, and apply refuses the same. A
first approval lapses after a week (`MAX_APPROVAL_AGE_SECS`, judged at the
upgrade's own time), once its approver is no longer an owner or admin, and once
every app it covers runs its target. A green update needs one approval whatever
the policy (`409 ONE_APPROVAL` for a first approval of it), and so does every
update without the policy. The operator's upgrades (where it holds app upgrades)
are not judged by policies. A raw bundle carries no class, so under a second
approver it never applies. An update the log cannot classify (the release the app
runs uninstalled while another ships its WASM) is approved first like any red
one: the approval and the upgrade carry the `unclassified` class above.

A unit's upgrade (`/upgrade-unit`, the consent page's `upgradeUnit`) is judged
once, as a whole, under its instance's policy, so it moves whole or not at all:
the unit's class decides (a unit red only through a member waits too; its
page asks for the first of two approvals), a second approver's first approval must be of
that very unit (`unit`, the same targets; a parent unit's approval that covers the
instance too never stands in for it), and the instance's `UpgradeApp`
carries the unit's class. Each member the run then moves takes the instance's
judgement in that run (`SystemState::run_update_gate`; its own class is still
checked against the log), so a member's own policy never stops a unit half way.
A member's own policy governs its upgrades alone. Only a unit's consent
(`__upgrade_unit`) states member targets: an organization's or a publisher's run
keeps none, whatever its entry lists, so each app it moves is judged on its own.

`GET /apps/{app}/update` adds the policy in force (`policy`), the first
approvals waiting that cover the app (`pendingApprovals`), and on `available`
how many approvals it needs (`approvalsNeeded`) and who approved first
(`approvedBy`). `GET /orgs/{org}/updates` lists, for the organization's owner
and admins, its apps with an update available or a first approval waiting, each
as `GET /apps/{app}/update` answers it, 50 apps a page (`?after=`): what the
node's updates page shows.

## Updates that apply on their own

Under a `noDestinations` policy, a green update applies without anyone's
approval once its hold has passed (`Feature::AutoUpdates`, 1.0.0-rc.34). The
system leader looks every `AUTO_UPDATE_EVERY` (5 s; `node::auto_updates`,
from `reconcile`) for apps it would move and the releases each could move to,
newest first (`SystemState::auto_update_candidates`), classifies each move as
any upgrade does, and runs the first green one of each app through the usual
path, restore point first (`api::upgrades::auto_upgrade`), at most
`MAX_AUTO_UPDATES_PER_PASS` (16) apps a pass; an app it skips does not count.
A pass classifies at most `MAX_AUTO_UPDATE_CLASSES_PER_PASS` (64) moves, and
passes on a node take turns, so two never move the same app together. Only the
system leader's pass moves anything: a pass on a node that no longer leads the
system group (a failover while it ran) stops before its next upgrade.
The entry is `UpgradeApp { auto: true }` with `actor: "policy:auto-update"`
(`system::AUTO_UPDATE`, never an account) and no consent: the policy is its
authority, and apply judges it again from the log alone
(`SystemState::auto_update_gate`):

- the app's policy says `noDestinations`, and the class is green (and agrees
  with the log, as [The class at apply](#the-class-at-apply) says);
- it moves the app along its package to a newer release; never back;
- the app is no unit's member (a member moves with its unit) and its unit, as
  the log holds it, has no destination before or after the move;
- its hold has passed: the upgrade's own `at` is at least `holdHours` after the
  release was logged, its install (`installedAt`) or, for an instance of a
  deployment, its deployment's offer of exactly that release (`addedAt`).
  Judged on logged times, never a node's clock, so every replica agrees;
- a restore point was taken where the upgrade runs on the app's group.

Refusals: `409 AUTO_UPDATE_REFUSED`, `HOLD_NOT_OVER`,
`RESTORE_POINT_REQUIRED`. The leader takes the newest release that may apply:
a newer red one, whether the log shows it (its destinations or signer) or only
the leader's classification does (a state version that changed, a new way to
act as the person), waits for an owner or admin and does not hold back a quiet
one below it. So does a green one that drops a method (`removedMethods`): another
app may call it, and nothing records which, so a person decides on it. It never
takes one an update to failed or an undo left: an owner or admin decides on those.
Only the release's own failure counts: the app's
group ran the upgrade and it failed or refused it (`lastUpgrade.ok: false`),
and not when another move of the app won meanwhile: an update on its own names
the release it began from (`UpgradeFailed { fromRelease }`), and apply notes
nothing when the app runs the target already or no longer runs that release.
A failure before anything ran (a replica down, no restore point, a runtime not
ready yet, no leader) leaves no record; the leader tries that move again after
a backoff it keeps in memory (`AUTO_UPDATE_RETRY_FIRST_SECS`, 60 s, doubling to
`AUTO_UPDATE_RETRY_MAX_SECS`, 1 hour), and remembers a move it found not green
for `NOT_GREEN_KEPT_SECS` (1 hour), so the next pass reaches the apps after
it. Neither is replicated: a new leader starts without them, which only means
the work is done again. The record says `lastUpgrade.auto: true`. Only the app moves:
an update that would move its members (an `upgrade-unit`) waits for an owner or
admin.

### Restore points and undo

Every upgrade that runs on an app's group takes a restore point first
(`Feature::RestorePoints`, 1.0.0-rc.34): the group's sealed snapshot, brought up
to what the replica applied, copied with its manifest into that replica's
`<data>/restore-points/<app>/` exactly as a backup is written
(`node::restore_points`; on this node when it hosts the app, else the first
replica that answers `internal/restore-point`). `UpgradeApp { restore_point }`
names it in the log and the app keeps it as its one undo
(`AppRecord::restore_point`, `types::RestorePoint`): the release and bundle it
ran before, the upgrade's time and run, and the file (its node, group, name,
SHA-256 and log index). A move that runs nothing on the group (the bundle it
runs already, a compute-only app) records one without a file; an upgrade that
took none leaves the app with none. A manual upgrade whose restore point
could not be taken still runs (and logs a warning); an update on its own does
not.

For `UNDO_WINDOW_SECS` (7 days, judged on the upgrade's and the undo's logged
times) an owner or admin may undo it: `POST /apps/{app}/undo` with a passkey
over `<app> / __undo_upgrade / { apps: { <app>: { to, bundle, from,
restorePoint } } }` (`SystemCmd::UndoUpgrade`, `SystemState::undo_args`). The
app goes back to the release it ran and, where the upgrade ran on its group, to
the restore point's state, in a new group the restore point's node seeds as an
operator's restore does (`Node::seed_restore`; calls answer `409
APP_RESTORING` meanwhile). It is the one move to an older release. The
restore point is the state just before the upgrade, so whatever the app wrote
since is lost: `GET /apps/{app}/undo` says what would be undone and lost
before anyone decides (`lostWrites`: the group's entries since the restore
point, its last write, and whether it wrote after the restore point was
taken), and the `POST` answers the same. When the restore point's node no
longer hosts the app (a replica move took it off), those are read from the
replicas the app is on now: all are asked, a majority must answer, and the
furthest of them counts (every committed entry is on a majority). Only an
applied index at or past the restore point's counts entries or says nothing is
lost; below it, from a release that does not say, or with no majority
answering, each is `null` (`any: null`, unless a write after the restore point
was seen: `true`), never `0` or `false`: the undo does not say it loses no
writes it cannot see. A unit undoes together: an undo of
the instance reverts each member its unit's upgrade moved in the same run
(`SystemState::undo_set`); a member that run moved is not undone alone (`409
UNDO_NOT_AS_NAMED`). Once the restore finishes (`FinishRestore`) the restore
point is spent; until then the undo may be sent again, which seeds it again.
Refusals, all before the passkey: `409 NO_RESTORE_POINT`,
`UNDO_WINDOW_PASSED`, `UNDO_STALE` (the app no longer runs what the upgrade
moved it to), `RESTORE_POINT_UNAVAILABLE` (its node does not answer or lost
it). The record says `lastUpgrade.undo: true`.

Storage stays bounded: a node keeps, per app, the file the app's record names
and those taken in the last hour (an upgrade not logged yet), and sweeps the
rest every 10 minutes (`RESTORE_POINT_SWEEP_EVERY`), and a file past the undo
window. A restore point is a copy of the app's state on one replica, counted as
the app's storage and billed with the rest of its unit (to the developer, for an
instance of a deployment). If the node that holds it is gone, so is the undo.

### Staged rollouts are not part of core

Core applies a green update on its own to every eligible instance once each one's
hold has passed; it does not pace a release across customers in waves. Staging a
release across a fleet (a few instances first, then more, paused on failures) is
fleet orchestration, outside core: the operator's tooling may do it by choosing
when to install or offer a release. An instance's own policy (`holdHours`), its
restore point and the week's undo are what core keeps for each one.

## Running it

The upgrade is an entry in the app's own log, so it is ordered against the
app's calls: every call before it ran on the old code, every call after it runs
on the new.

An app's frontend asks for the same upgrade through the
[consent page](/protocol/consent-page/) (`kind: "upgrade"`), which runs this
route as the person once they approve there.

1. The app group's leader prepares the target bundle, and refuses the
   upgrade while an active compute run will call a result method the target
   does not declare.
2. It appends `Upgrade { bundle, computeBundle, base_index }`. Every replica
   switches to the new bundle at that entry; no replica switches on its own,
   so there is no window in which replicas run different code.
3. Only then does the node record the new bundle and release in the system
   directory (`UpgradeApp`, which checks the upgrader's authority again, checks
   the release ships the bundle, and notes `lastUpgrade`). An upgrade to a
   release with the same bundle runs nothing on the app's group in an
   organization-wide run; it is recorded the same way.

## Failure

A refused upgrade leaves the app on its bundle with its state untouched.
Refused before anything runs: `409 RUNTIME_TOO_OLD` (above) and `409
RELEASE_DEADLINE`; refused by the app's group: `422 UPGRADE_FAILED` with the
reason. Either is recorded on the instance (`UpgradeFailed` sets the app's
`lastUpgrade` with `ok: false` and the error), so a client can see why. The
app's members read the last upgrade, with the release it went from and to
and the kind of actor, in `GET /orgs/{org}/apps` or `GET /auth/apps`; the
operator reads it without the account or the error in `GET /ops/apps`
([Deployment governance](/protocol/governance/#reading-the-approvals)).

## Upgrade runs

An **upgrade run** moves many instances of one package to one version with a
single decision: one passkey step-up (or one operator signature) for the whole
run, then each app upgraded in turn. There are three kinds, by who starts it:

| Run | Route | Who | Apps it covers | Consent |
| --- | --- | --- | --- | --- |
| An organization's | `POST /orgs/{org}/upgrade { package, version, team?, cascade? }` | Its owner or an admin, where owners hold app upgrades (before 1.0.0-rc.33: a holder of `MANAGE_APPLICATION` there, on `team` or organization-wide) | The organization's apps that run a release of `package`; with `team`, only those with `team` access to it, and with `cascade` to the teams below it too | `org:<org> / __upgrade_org / { package, version, team, cascade, migrate }` |
| A publisher's | `POST /orgs/{org}/packages/{package}/upgrade { version }` | An owner or admin of the [publisher](/protocol/governance/#publishers) of `package` (before 1.0.0-rc.33: an organization-wide `MANAGE_APPLICATION` holder there) | Every instance of `package` that the starter may upgrade: those of the organizations they are an owner or admin of, never another's (before 1.0.0-rc.33: every instance, chiefly those whose release declares `upgrades: publisher`) | `org:<org> / __upgrade_published / { package, version, migrate }` |
| The operator's | `POST /ops/orgs/{org}/upgrade { package, version, team?, cascade? }` | The operator, where governance gives it app upgrades | As an organization's run | The operator key's signature over `org:<org> / __upgrade_org / …` ([The operator](/protocol/operator/#the-credential)) |

`meroctl group upgrade trigger <org> --package P --version V [--group T
[--cascade]]` starts an organization's run, `meroctl group upgrade status
<org> <run>` follows it and `meroctl group upgrade retry <org> <run>` retries
it; `meroctl ops upgrade-org` starts the operator's. A publisher's run
has no command yet: `meroctl raw post /orgs/<org>/packages/<package>/upgrade
'{"version":"V"}'`.

A run is kept by the organization that started it: the apps' own for an
organization's or the operator's run, the publisher for a publisher's run (so
its customers' organizations never see it). Each keeps its newest 20
(`UPGRADE_RUNS_KEPT`).

1. **Checks before the passkey.** The route checks who may start the run (an
   owner or admin of the organization, `403` else, which `StartUpgradeRun`'s
   `apply` refuses again) and that owners (not the operator) hold app upgrades. If the cluster lacks the
   release, the node installs it from the registry first, as the starter
   (where deployments are `granted`, that install needs a
   [deployer grant](/protocol/governance/#deployers)).
2. **The one consent.** The step-up states the package, the version and the
   scope (`team`, `cascade`), never the list of apps. That is what the passkey
   approves, and what `StartUpgradeRun` carries.
3. **What `apply` derives.** Where it applies, on every node,
   `StartUpgradeRun` verifies and spends the consent, then sets the run's apps
   from the state and the method the consent names
   (`SystemState::upgrade_run_apps`), whatever list the proposing node sent:
   - `__upgrade_org`: the organization's apps of `package` in the scope
     (`org_run_apps`);
   - `__upgrade_published`: every instance that runs a release of `package`
     (the release it runs, `app_release`, as an organization's run and each
     app's `UpgradeApp { run }` judge it) and that the starter may upgrade
     (`published_run_apps`: under `ownerApprovedUpgrades`, the instances of the
     organizations the starter is an owner or admin of). An entry logged by a release before 1.0.0-rc.24
     (no `by_release`) replays judging each app by the package its bundle was
     first recorded from, which left out an instance whose component another
     package's release shipped first; the `publishedRunByRelease` feature
     keeps publisher runs refused until every node reads the field;
   - `__upgrade_org_retry`: the apps the retried run failed on, still in the
     directory.

   It clears `done` and `failed`, and refuses a run id that any organization
   already holds. So a node cannot widen a run past what the passkey approved,
   and the answer to the request is the run as it applied. (Entries logged
   before the cluster's `RequireCurrentRules` mark replay as they were
   logged; [The system group](/protocol/system-group/).)
4. **App by app.** A background task on the node that started the run takes
   each app in turn and asks `SystemState::run_may_move` first. An app is
   noted failed, with `{ code: "NOT_IN_RUN", message }` and without running
   anything, when the run does not name it, has already moved or failed it,
   the app no longer runs a release of the run's package, or the run's version
   is older than the release the app runs (a run never downgrades). Otherwise
   the app is upgraded as a single upgrade is ([Running it](#running-it)),
   to the release of `version` with the app's own service. An app whose
   current WASM is already the target's is only recorded (`UpgradeApp`, nothing
   runs on its group). A release the starter cannot see, or one that ships
   nothing for the app's service, is noted `NOT_INSTALLED`.
5. **Judged again per app.** Each app's `UpgradeApp { run }` names the run,
   and `apply` finds the run in whichever organization keeps it and checks:
   the same starter, the run not finished, the app one the run names, and a
   release of the run's package and version that ships the bundle. The
   starter's authority over that app (`may_upgrade`), deadlines and the
   runtime of every replica are judged as for any upgrade. A refusal at any
   point is `UpgradeFailed`, noted on the run's `failed` and on the app's
   `lastUpgrade`, and the run goes on with the next app.
6. **The end.** `FinishUpgradeRun` marks it finished.

### Status and retry

`GET /orgs/{org}/upgrades/{run}` (any member of the organization that keeps
it) answers the run:

```json
{
  "runId": "k3J…", "package": "chat", "version": "1.4.0",
  "team": "t_support", "cascade": true,
  "by": "<account id, or operator>", "startedAt": 1762992000,
  "apps": ["a1", "a2", "a3"],
  "done": ["a1"],
  "failed": { "a3": { "code": "RUNTIME_TOO_OLD", "message": "…" } },
  "finished": true
}
```

`POST /orgs/{org}/upgrades/{run}/retry` starts a **new** run over the old
run's failed apps, under its terms (package, version, team, cascade), with a
fresh step-up over `org:<org> / __upgrade_org_retry / { run }` (the operator
signs the same statement for its own run). The usual reason to retry is a
failure that has since cleared: a replica on a runtime older than the release
needs (`RUNTIME_TOO_OLD`) once that node runs a newer one, or a release
deadline once the release is approved.

The task lives in the memory of the node that started the run: if that node
stops mid-run, the run stays unfinished and the remaining apps are not
upgraded until a retry or a new run.

## Upgrading the cluster itself

Moving nodes to a new mero-tee release is not an app upgrade: it is a new node
image. Nodes on the new release join the cluster, but receive an app's data
only once that app's approver has approved the release
([Release approvals](/protocol/governance/#release-approvals)). App frontends
follow the package: `{label}.{apps-domain}/` serves the newest installed
release.

## The cluster version

During a rollout, nodes on the old and the new release replicate one system
log together, for as long as an app's approver keeps old nodes in use. An
entry only the new release understands (a new command, or a new field that
changes what an old one does) would change the state of the new nodes alone:
an old node cannot apply it, and stops its group on it (below), so a cluster
that proposed one too early would lose its old nodes. Earlier releases
skipped such an entry instead, and kept answering reads and judging access
from the state before it (a revoked API key still working there).

So each such shape is a **feature** with the first core release that applies
it (`system::cluster_version::FEATURES`), and the cluster has an **active
cluster version**: the newest version every node supports.

- **What a node supports.** `GET /health` answers `clusterVersion`: the newest
  of the node's core release and the features it knows (a build between two
  releases supports the coming one). A node from before this release answers
  only its core `release`, which counts in its place. A peer asks over the
  node's sealed channel, so the answer comes from the attested image.
- **Raising it.** The system leader asks every registered node (and every
  member of the system group) at most every 10 seconds while the logged
  version is below its own, and logs `SetClusterVersion { version, nodes }`
  once every one of them answers and the oldest is newer than the logged
  version. Apply checks that `nodes` names every registered node and only
  those, that none is below `version`, and that `version` is newer than the
  logged one: it only moves forward. It is raised automatically, never by
  hand: raising it is safe only once every node supports it, which is what
  the leader checks, so an operator finishes a rollout (removes the old nodes,
  `DELETE /ops/nodes/{id}`) to raise it. A registered node that does not
  answer holds it where it is. `GET /ops/placement` shows the logged version
  (`clusterVersion`, `null` until the first).
- **The gate.** Every proposal goes through `Node::sys_write`, which refuses a
  command using a feature above the active version with `409
  FEATURE_NOT_ACTIVE`, naming the feature and the version it needs (`details:
  { feature, needs, active }`), before anything is logged. It judges on the
  logged version. When that is below but every node supports the feature now,
  the proposing node first has the version every node supports logged
  (`SetClusterVersion`, `system::cluster_version::admit`), then judges again on
  the logged one, so a cluster rolling between two releases keeps every
  feature both have, and no entry is in the log before the version that keeps
  older nodes out. Only `SetClusterVersion` itself, and a cluster whose nodes
  are all below 1.0.0-rc.16 (which cannot decode it), are judged on what the
  nodes support alone. Routes that ask for a passkey step-up check before
  asking.
- **Older nodes stay out.** Once a version is logged, the leader admits no
  node below it to the system group: a rollback means a new cluster, not an
  older node in this one. As every gated entry follows the version that brings
  it, the logged version is the one in effect.
- **Apply never reads it.** An entry applies as it did, so replaying a log is
  unchanged; the gate only decides what is proposed.

A node that still meets an entry it cannot decode (it runs an older release
than the log, or an app entry of a later [entry format](/protocol/storage/#format-versions))
never skips it: its batch fails, which stops that group's Raft core on the
entry, and the node applies nothing after it until it restarts on a release
that reads it. The group's state there stays as it was before the entry; it
never moves on without it. It logs an error and counts the entry in
`calimero_log_undecodable_entries_total{log}` (system or app log): with every
feature gated it stays at zero. A stopped system group takes the node out of
the cluster's system log; the other nodes go on.
