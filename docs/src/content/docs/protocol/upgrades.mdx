An **upgrade** moves an app instance to another bundle, usually another release
of its package, and keeps its state: the new code reads what the old code
stored ([Upgrades & state](/build/migrations/)). This page is about what the
cluster does with it. How a release is parsed, verified and trusted when it is installed is
in [Packages & frontends](/protocol/applications/#installing-a-release).

## Who may upgrade

New code reads the app's data, so an upgrade is one of the three decisions
[deployment governance](/protocol/governance/) assigns:

- **Owner side** (default): each app's package declares who, in its signed
  manifest (`upgrades`, [App upgrades](/protocol/governance/#app-upgrades)):
  - `owner` (the default): the app's owner, or, for an organization's app,
    whoever holds `MANAGE_APPLICATION` on its team or organization-wide;
  - `publisher`: whoever holds `MANAGE_APPLICATION` in the organization the
    package's signing key is bound to, for every instance; nobody until the
    key is bound.

  Each upgrades with a passkey session and a step-up over the exact upgrade
  (`POST /apps/{app}/upgrade { version | bundle, migrate? }`, then the `412`
  challenge). The assertion is recorded as `consent` on the directory's
  `UpgradeApp` command. A package may move from `publisher` to `owner` in a
  later release, never back, and an app is never upgraded from an `owner`
  release to a `publisher` one.
- **Operator**: only the operator (`POST /ops/apps/{app}/upgrade`), to a release
  it installed itself.

An owner-side upgrader may hand one app's upgrades to CI with an [upgrade
key](/protocol/identities/#upgrade-keys): made once with a passkey, it signs
each upgrade of that app to a signed release of its package in place of the
step-up, and the node refuses it everything else. Who may upgrade and the
deadline below are judged for it exactly as for a passkey.

Past a [release deadline](/protocol/governance/#release-deadlines) its
approver has not met, an upgrade is refused `409 RELEASE_DEADLINE` before
anything runs.

A version alone means the app's own package and service.

**An instance runs a release, not only a WASM.** A release's frontend ships in
its signed `.mpk` and works with that release's backend only, so approving a
release approves its frontend. The directory records the release each instance
runs (`AppRecord::release`: package, version, service), set when it is created
(the version named, or the release its deployment offers) and by every upgrade.
Releases may share a WASM: one that changes only the frontend is still an
upgrade, approved by whoever holds the app's upgrades exactly as above, and
afterwards the instance runs, is reported at, and is served the frontend of the
new release. An instance recorded before releases were kept (or running a raw
development bundle) is taken to run the release its bundle ships in.

**What the passkey signs.** The challenge's arguments are
`{ bundle, migrate, manifest }`: the target WASM's hash and the target
release's signed-manifest hash, so another manifest installed under the same
version (other outbound prefixes or frontend origins, the same WASM) is not
the upgrade that was approved. The node computes both; a target that changes
between the challenge and the assertion no longer matches it, and the upgrade
is refused. A raw development bundle has no manifest, and `manifest` is
`null`.

**From the app itself.** An app's frontend cannot upgrade its instance (its
session is bound to its package). It asks the node for a consent request
(`{ kind: "upgrade", subject: { app, toVersion } }`); the node's own page shows
the capability sheet (outbound, frontend origins, interfaces, methods,
events, timers, migration, build) and takes the owner's passkey there
([The consent page](/protocol/consent-page/)).

## What an upgrade runs

An upgrade is **code only**: the app's state stays as the old code wrote it,
and the new code must read it ([Upgrades & state](/build/migrations/)).
`calimero-sdk` has no migration export yet, so nothing is planned from the
two ABIs and nothing reshapes the state; a named `migrate` is refused
`MigrationsNotSupported`. The state version each side declares
(`#[app::state(version = N)]`) does not decide whether an upgrade runs: the
consent page shows it, and flags a change, since the new code reads the old
data as it is.

So an app moves to **any newer release** of its package in one upgrade,
however many releases or state versions that skips: nothing has to be
applied one release at a time, and an app several releases behind is
offered the newest one it can reach (below).

## The runtime a release needs

A release's signed manifest names the oldest runtime it runs on
(`minRuntimeVersion`): the merod release a node was built as. The node that
installs a release checks it against its own runtime
([Installing a release](/protocol/applications/#installing-a-release)), and
records it with the release (`PackageVersion::min_runtime_version`). The
other nodes take the release's WASM without verifying the `.mpk`, and a
cluster runs several releases while its nodes move to a new one, so the
cluster judges the requirement against the runtime of every node that would
run the app:

- **Upgrades.** An upgrade is refused `409 RUNTIME_TOO_OLD` when any of the
  app's replicas is on a node whose runtime is older than the target release
  needs; `details` names the requirement and each such node
  (`{ minRuntimeVersion, nodes: [{ node, runtime }] }`). It is asked before
  the passkey step-up and on the consent page, and again where every
  upgrade path goes through (`run_upgrade`), which records the refusal as
  the app's last upgrade. Nothing runs on the app's group.
- **New apps.** Placement leaves out the nodes whose runtime is older than
  the release the app is created from; when none is left, the create is
  refused `409 RUNTIME_TOO_OLD`.
- **Replica moves.** `POST /ops/apps/{app}/replicas` refuses `409
  RUNTIME_TOO_OLD` a node the app is not on yet whose runtime is older than
  the release the app runs. A node it is on already is not judged, so an app
  can always be moved off one.

Each node names its runtime over the sealed peer channel (`POST
/internal/runtime`, an attested node's own answer), kept for 30 s. A node on
a release from before this answers `404`: it is older than the asking
node, and judged so. A node that does not answer, or whose release is not a
version (a development build), is not judged, as before.

## Which release an app can reach

Each app's entry in `GET /auth/apps` and `GET /orgs/{org}/apps` names the
newer releases of its package its reader may see and move it to:

- `availableVersions`: the newest 16, oldest first;
- `latestReachable`: the newest of all of them the upgrade would take now,
  or `null`. It may be older than every release in `availableVersions`;
- `latestBlocked`, only when the newest release is not `latestReachable`:
  its `version`, the `reason` and a `message`. `runtime`: a replica's node
  runs an older runtime than it needs, with `minRuntimeVersion` and `nodes`
  as the `409` names them; `authority`: the app's owner upgrades it and the
  release would give its upgrades to the publisher.

Who may upgrade and [release deadlines](/protocol/governance/#release-deadlines)
are the same for every release of a package, so they decide whether to
upgrade, not which release to: the report leaves them to the app's
`upgradesHeldBy` and approvals. A release recorded before releases kept
their runtime requirement is not judged by it here; the upgrade reads it
from the release's `.mpk` and still refuses it.

## Running it

The upgrade is an entry in the app's own log, so it is ordered against the
app's calls: every call before it ran on the old code, every call after it runs
on the new.

1. The app group's leader prepares the target bundle, and refuses the
   upgrade while an active compute run will call a result method the target
   does not declare.
2. It appends `Upgrade { bundle, computeBundle, base_index }`. Every replica
   switches to the new bundle at that entry; no replica switches on its own,
   so there is no window in which replicas run different code.
3. Only then does the node record the new bundle and release in the system
   directory (`UpgradeApp`, which checks the upgrader's authority again, checks
   the release ships the bundle, and notes `lastUpgrade`). An upgrade to a
   release with the same bundle runs nothing on the app's group in an
   organization-wide run; it is recorded the same way.

## Failure

A refused upgrade leaves the app on its bundle with its state untouched.
Refused before anything runs: `409 RUNTIME_TOO_OLD` (above) and `409
RELEASE_DEADLINE`; refused by the app's group: `422 UPGRADE_FAILED` with the
reason. Either is recorded on the instance (`UpgradeFailed` sets the app's
`lastUpgrade` with `ok: false` and the error), so a client can see why. The
app's members read the last upgrade, with the release it went from and to
and the kind of actor, in `GET /orgs/{org}/apps` or `GET /auth/apps`; the
operator reads it without the account or the error in `GET /ops/apps`
([Deployment governance](/protocol/governance/#reading-the-approvals)).

## Organization-wide upgrade runs

An **upgrade run** moves every app of an
organization that runs `package` — or only a team's apps, and with `cascade`
the apps of the teams below it — to `version`.

- **Start.** `POST /orgs/{org}/upgrade { package, version, team?, cascade?, migrate? }`
  by a `MANAGE_APPLICATION` holder there, with one passkey step-up for the
  whole run; `POST /orgs/{org}/packages/{package}/upgrade { version, migrate? }`
  by a publisher's `MANAGE_APPLICATION` holder, over every instance of a
  `publisher` package, its customers' included (the run is kept on the
  publisher); or `POST /ops/orgs/{org}/upgrade` where the operator holds app
  upgrades. An app the starter may not upgrade is recorded as failed without
  running anything. A
  release missing from the cluster is installed from the registry first (owner
  runs).
- **Record.** `StartUpgradeRun` stores an `UpgradeRun` on the organization (run id,
  package, version, team, cascade, who started it, its apps, which are done and
  which failed, and whether it finished); the organization keeps its newest 20
  runs.
- **Progress.** A background task on the node that started it upgrades the apps
  one by one; each `UpgradeApp` or `UpgradeFailed` notes the app on the run and
  on the instance. An app already on the target bundle is recorded as done.
  Each app is judged on its own: one with a replica on a node older than the
  release's runtime is recorded as failed (`RUNTIME_TOO_OLD`) and the rest
  move; a retry once those nodes run a newer runtime moves it.
  `FinishUpgradeRun` marks the end.
- **Follow and retry.** `GET /orgs/{org}/upgrades/{run}` shows the run;
  `POST …/retry` starts a new run over the apps that failed.

The task lives in the memory of the node that started it: if that node stops
mid-run, the run stays unfinished and the remaining apps are not upgraded until
a retry or a new run.

## Upgrading the cluster itself

Moving nodes to a new mero-tee release is not an app upgrade: it is a new node
image. Nodes on the new release join the cluster, but receive an app's data
only once that app's approver has approved the release
([Release approvals](/protocol/governance/#release-approvals)). App frontends
follow the package: `{label}.{apps-domain}/` serves the newest installed
release.
