An **upgrade** moves an app instance to another bundle, usually another release
of its package, and keeps its state: the new code reads what the old code
stored ([Upgrades & state](/build/migrations/)). This page is about what the
cluster does with it. How a release is parsed, verified and trusted when it is installed is
in [Packages & frontends](/protocol/applications/#installing-a-release).

## Who may upgrade

New code reads the app's data, so an upgrade is one of the three decisions
[deployment governance](/protocol/governance/) assigns:

- **Owner side** (default): each app's package declares who, in its signed
  manifest (`upgrades`, [App upgrades](/protocol/governance/#app-upgrades)):
  - `owner` (the default): the app's owner, or, for an organization's app,
    whoever holds `MANAGE_APPLICATION` on its team or organization-wide;
  - `publisher`: whoever holds `MANAGE_APPLICATION` in the organization the
    package's signing key is bound to, for every instance; nobody until the
    key is bound.

  Each upgrades with a passkey session and a step-up over the exact upgrade
  (`POST /apps/{app}/upgrade { version | bundle }`, then the `412`
  challenge; a `migrate` is refused, below). The assertion is recorded as `consent` on the directory's
  `UpgradeApp` command. A package may move from `publisher` to `owner` in a
  later release, never back, and an app is never upgraded from an `owner`
  release to a `publisher` one.
- **Operator**: only the operator (`POST /ops/apps/{app}/upgrade`), to a release
  it installed itself.

An owner-side upgrader may hand one app's upgrades to CI with an [upgrade
key](/protocol/identities/#upgrade-keys): made once with a passkey, it signs
each upgrade of that app to a signed release of its package in place of the
step-up, and the node refuses it everything else. Who may upgrade and the
deadline below are judged for it exactly as for a passkey.

Past a [release deadline](/protocol/governance/#release-deadlines) its
approver has not met, an upgrade is refused `409 RELEASE_DEADLINE` before
anything runs.

A version alone means the app's own package and service.

**An instance runs a release, not only a WASM.** A release's frontend ships in
its signed `.mpk` and works with that release's backend only, so approving a
release approves its frontend. The directory records the release each instance
runs (`AppRecord::release`: package, version, service), set when it is created
(the version named, or the release its deployment offers) and by every upgrade.
Releases may share a WASM: one that changes only the frontend is still an
upgrade, approved by whoever holds the app's upgrades exactly as above, and
afterwards the instance runs, is reported at, and is served the frontend of the
new release. An instance recorded before releases were kept (or running a raw
development bundle) is taken to run the release its bundle ships in, if that
release was installed by the time the instance took the bundle.

**Who may upgrade follows the release it runs.** Its `upgrades`, its publisher
and so its approved releases are those of `AppRecord::release`
(`SystemState::governing_release`), not of whichever release first shipped the
same WASM: an instance of an `owner` release stays its owners' even where a
`publisher` release of the package ships the same WASM, and a release installed
after an instance took a raw upload of the same WASM takes nothing from its
owner. A WASM belongs to one signer: a release of another signer's package that
ships it is refused at install. One signer may ship it in several of its
packages, and each instance is judged by the release it runs. A cluster begun before this rule replays what it
logged then as it applied it: the first system leader on a release that judges
by the release writes `AttributeByRelease` (the `attributeByRelease` feature,
so only once the [cluster version](#the-cluster-version) brings it), and the
rule holds from that entry on.

**What the passkey signs.** The challenge's arguments are
`{ bundle, migrate, manifest }`: the target WASM's hash and the target
release's signed-manifest hash, so another manifest installed under the same
version (other outbound prefixes or frontend origins, the same WASM) is not
the upgrade that was approved. The node computes both; a target that changes
between the challenge and the assertion no longer matches it, and the upgrade
is refused. A raw development bundle has no manifest, and `manifest` is
`null`.

**From the app itself.** An app's frontend cannot upgrade its instance (its
session is bound to its package). It asks the node for a consent request
(`{ kind: "upgrade", subject: { app, toVersion } }`); the node's own page shows
the capability sheet (outbound, frontend origins, interfaces, methods,
events, timers, the state version each side declares, build) and takes the owner's passkey there
([The consent page](/protocol/consent-page/)).

## What an upgrade runs

An upgrade is **code only**: the app's state stays as the old code wrote it,
and the new code must read it ([Upgrades & state](/build/migrations/)).
`calimero-sdk` has no migration export yet, so nothing is planned from the
two ABIs and nothing reshapes the state; a named `migrate` is refused
`MigrationsNotSupported`. The state version each side declares
(`#[app::state(version = N)]`) does not decide whether an upgrade runs: the
consent page shows it, and flags a change, since the new code reads the old
data as it is.

So an app moves to **any newer release** of its package in one upgrade,
however many releases or state versions that skips: nothing has to be
applied one release at a time, and an app several releases behind is
offered the newest one it can reach (below).

## The runtime a release needs

A release's signed manifest names the oldest runtime it runs on
(`minRuntimeVersion`): the merod release a node was built as. The node that
installs a release checks it against its own runtime
([Installing a release](/protocol/applications/#installing-a-release)), and
records it with the release (`PackageVersion::min_runtime_version`). The
other nodes take the release's WASM without verifying the `.mpk`, and a
cluster runs several releases while its nodes move to a new one, so the
cluster judges the requirement against the runtime of every node that would
run the app:

- **Upgrades.** An upgrade is refused `409 RUNTIME_TOO_OLD` when any of the
  app's replicas is on a node whose runtime is older than the target release
  needs; `details` names the requirement and each such node
  (`{ minRuntimeVersion, nodes: [{ node, runtime }] }`). It is asked before
  the passkey step-up and on the consent page, and again where every
  upgrade path goes through (`run_upgrade`), which records the refusal as
  the app's last upgrade. Nothing runs on the app's group.
- **New apps.** Placement leaves out the nodes whose runtime is older than
  the release the app is created from; when none is left, the create is
  refused `409 RUNTIME_TOO_OLD`.
- **Replica moves.** `POST /ops/apps/{app}/replicas` refuses `409
  RUNTIME_TOO_OLD` a node the app is not on yet whose runtime is older than
  the release the app runs. A node it is on already is not judged, so an app
  can always be moved off one.

Each node names its runtime over the sealed peer channel (`POST
/internal/runtime`, an attested node's own answer), kept for 30 s. A node on
a release from before this answers `404`: it is older than the asking
node, and judged so. A node that does not answer, or whose release is not a
version (a development build), is not judged, as before.

## Which release an app can reach

Each app's entry in `GET /auth/apps` and `GET /orgs/{org}/apps` names the
newer releases of its package its reader may see and move it to:

- `availableVersions`: the newest 16, oldest first;
- `latestReachable`: the newest of all of them the upgrade would take now,
  or `null`. It may be older than every release in `availableVersions`;
- `latestBlocked`, only when the newest release is not `latestReachable`:
  its `version`, the `reason` and a `message`. `runtime`: a replica's node
  runs an older runtime than it needs, with `minRuntimeVersion` and `nodes`
  as the `409` names them; `authority`: the app's owner upgrades it and the
  release would give its upgrades to the publisher.

Who may upgrade and [release deadlines](/protocol/governance/#release-deadlines)
are the same for every release of a package, so they decide whether to
upgrade, not which release to: the report leaves them to the app's
`upgradesHeldBy` and approvals. A release recorded before releases kept
their runtime requirement is not judged by it here; the upgrade reads it
from the release's `.mpk` and still refuses it.

## Running it

The upgrade is an entry in the app's own log, so it is ordered against the
app's calls: every call before it ran on the old code, every call after it runs
on the new.

An app's frontend asks for the same upgrade through the
[consent page](/protocol/consent-page/) (`kind: "upgrade"`), which runs this
route as the person once they approve there.

1. The app group's leader prepares the target bundle, and refuses the
   upgrade while an active compute run will call a result method the target
   does not declare.
2. It appends `Upgrade { bundle, computeBundle, base_index }`. Every replica
   switches to the new bundle at that entry; no replica switches on its own,
   so there is no window in which replicas run different code.
3. Only then does the node record the new bundle and release in the system
   directory (`UpgradeApp`, which checks the upgrader's authority again, checks
   the release ships the bundle, and notes `lastUpgrade`). An upgrade to a
   release with the same bundle runs nothing on the app's group in an
   organization-wide run; it is recorded the same way.

## Failure

A refused upgrade leaves the app on its bundle with its state untouched.
Refused before anything runs: `409 RUNTIME_TOO_OLD` (above) and `409
RELEASE_DEADLINE`; refused by the app's group: `422 UPGRADE_FAILED` with the
reason. Either is recorded on the instance (`UpgradeFailed` sets the app's
`lastUpgrade` with `ok: false` and the error), so a client can see why. The
app's members read the last upgrade, with the release it went from and to
and the kind of actor, in `GET /orgs/{org}/apps` or `GET /auth/apps`; the
operator reads it without the account or the error in `GET /ops/apps`
([Deployment governance](/protocol/governance/#reading-the-approvals)).

## Upgrade runs

An **upgrade run** moves many instances of one package to one version with a
single decision: one passkey step-up (or one operator signature) for the whole
run, then each app upgraded in turn. There are three kinds, by who starts it:

| Run | Route | Who | Apps it covers | Consent |
| --- | --- | --- | --- | --- |
| An organization's | `POST /orgs/{org}/upgrade { package, version, team?, cascade? }` | A holder of `MANAGE_APPLICATION` there (on `team`, or organization-wide), where owners hold app upgrades | The organization's apps that run a release of `package`; with `team`, only those with `team` access to it, and with `cascade` to the teams below it too | `org:<org> / __upgrade_org / { package, version, team, cascade, migrate }` |
| A publisher's | `POST /orgs/{org}/packages/{package}/upgrade { version }` | An organization-wide `MANAGE_APPLICATION` holder of the [publisher](/protocol/governance/#publishers) of `package` | Every instance of `package`, in any organization, that the starter may upgrade (chiefly those whose release declares `upgrades: publisher`) | `org:<org> / __upgrade_published / { package, version, migrate }` |
| The operator's | `POST /ops/orgs/{org}/upgrade { package, version, team?, cascade? }` | The operator, where governance gives it app upgrades | As an organization's run | The operator key's signature over `org:<org> / __upgrade_org / …` ([The operator](/protocol/operator/#the-credential)) |

`meroctl group upgrade trigger <org> --package P --version V [--group T
[--cascade]]` starts an organization's run, `meroctl group upgrade status
<org> <run>` follows it and `meroctl group upgrade retry <org> <run>` retries
it; `meroctl ops upgrade-namespace` starts the operator's. A publisher's run
has no command yet: `meroctl raw post /orgs/<org>/packages/<package>/upgrade
'{"version":"V"}'`.

A run is kept by the organization that started it: the apps' own for an
organization's or the operator's run, the publisher for a publisher's run (so
its customers' organizations never see it). Each keeps its newest 20
(`UPGRADE_RUNS_KEPT`).

1. **Checks before the passkey.** The route checks who may start the run and
   that owners (not the operator) hold app upgrades. If the cluster lacks the
   release, the node installs it from the registry first, as the starter
   (where deployments are `granted`, that install needs a
   [deployer grant](/protocol/governance/#deployers)).
2. **The one consent.** The step-up states the package, the version and the
   scope (`team`, `cascade`), never the list of apps. That is what the passkey
   approves, and what `StartUpgradeRun` carries.
3. **What `apply` derives.** Where it applies, on every node,
   `StartUpgradeRun` verifies and spends the consent, then sets the run's apps
   from the state and the method the consent names
   (`SystemState::upgrade_run_apps`), whatever list the proposing node sent:
   - `__upgrade_org`: the organization's apps of `package` in the scope
     (`org_run_apps`);
   - `__upgrade_published`: every instance of `package` the starter may
     upgrade (`published_run_apps`);
   - `__upgrade_org_retry`: the apps the retried run failed on, still in the
     directory.

   It clears `done` and `failed`, and refuses a run id that any organization
   already holds. So a node cannot widen a run past what the passkey approved,
   and the answer to the request is the run as it applied. (Entries logged
   before the cluster's `RequireCurrentRules` mark replay as they were
   logged; [The system group](/protocol/system-group/).)
4. **App by app.** A background task on the node that started the run takes
   each app in turn and asks `SystemState::run_may_move` first. An app is
   noted failed, with `{ code: "NOT_IN_RUN", message }` and without running
   anything, when the run does not name it, has already moved or failed it,
   the app no longer runs a release of the run's package, or the run's version
   is older than the release the app runs (a run never downgrades). Otherwise
   the app is upgraded as a single upgrade is ([Running it](#running-it)),
   to the release of `version` with the app's own service. An app whose
   current WASM is already the target's is only recorded (`UpgradeApp`, nothing
   runs on its group). A release the starter cannot see, or one that ships
   nothing for the app's service, is noted `NOT_INSTALLED`.
5. **Judged again per app.** Each app's `UpgradeApp { run }` names the run,
   and `apply` finds the run in whichever organization keeps it and checks:
   the same starter, the run not finished, the app one the run names, and a
   release of the run's package and version that ships the bundle. The
   starter's authority over that app (`may_upgrade`), deadlines and the
   runtime of every replica are judged as for any upgrade. A refusal at any
   point is `UpgradeFailed`, noted on the run's `failed` and on the app's
   `lastUpgrade`, and the run goes on with the next app.
6. **The end.** `FinishUpgradeRun` marks it finished.

### Status and retry

`GET /orgs/{org}/upgrades/{run}` (any member of the organization that keeps
it) answers the run:

```json
{
  "runId": "k3J…", "package": "chat", "version": "1.4.0",
  "team": "t_support", "cascade": true,
  "by": "<account id, or operator>", "startedAt": 1762992000,
  "apps": ["a1", "a2", "a3"],
  "done": ["a1"],
  "failed": { "a3": { "code": "RUNTIME_TOO_OLD", "message": "…" } },
  "finished": true
}
```

`POST /orgs/{org}/upgrades/{run}/retry` starts a **new** run over the old
run's failed apps, under its terms (package, version, team, cascade), with a
fresh step-up over `org:<org> / __upgrade_org_retry / { run }` (the operator
signs the same statement for its own run). The usual reason to retry is a
failure that has since cleared: a replica on a runtime older than the release
needs (`RUNTIME_TOO_OLD`) once that node runs a newer one, or a release
deadline once the release is approved.

The task lives in the memory of the node that started the run: if that node
stops mid-run, the run stays unfinished and the remaining apps are not
upgraded until a retry or a new run.

## Upgrading the cluster itself

Moving nodes to a new mero-tee release is not an app upgrade: it is a new node
image. Nodes on the new release join the cluster, but receive an app's data
only once that app's approver has approved the release
([Release approvals](/protocol/governance/#release-approvals)). App frontends
follow the package: `{label}.{apps-domain}/` serves the newest installed
release.

## The cluster version

During a rollout, nodes on the old and the new release replicate one system
log together, for as long as an app's approver keeps old nodes in use. A node
applies an entry it cannot decode as `malformed command` and skips it, so an
entry only the new release understands (a new command, or a new field that
changes what an old one does) would change the state of the new nodes alone:
the old ones would keep answering reads and judging access from the state
before it, and if the system leader were old, the caller would be refused an
entry the new nodes applied.

So each such shape is a **feature** with the first core release that applies
it (`system::cluster_version::FEATURES`), and the cluster has an **active
cluster version**: the newest version every node supports.

- **What a node supports.** `GET /health` answers `clusterVersion`: the newest
  of the node's core release and the features it knows (a build between two
  releases supports the coming one). A node from before this release answers
  only its core `release`, which counts in its place. A peer asks over the
  node's sealed channel, so the answer comes from the attested image.
- **Raising it.** The system leader asks every registered node (and every
  member of the system group) at most every 10 seconds while the logged
  version is below its own, and logs `SetClusterVersion { version, nodes }`
  once every one of them answers and the oldest is newer than the logged
  version. Apply checks that `nodes` names every registered node and only
  those, that none is below `version`, and that `version` is newer than the
  logged one: it only moves forward. It is raised automatically, never by
  hand: raising it is safe only once every node supports it, which is what
  the leader checks, so an operator finishes a rollout (removes the old nodes,
  `DELETE /ops/nodes/{id}`) to raise it. A registered node that does not
  answer holds it where it is. `GET /ops/placement` shows the logged version
  (`clusterVersion`, `null` until the first).
- **The gate.** Every proposal goes through `Node::sys_write`, which refuses a
  command using a feature above the active version with `409
  FEATURE_NOT_ACTIVE`, naming the feature and the version it needs (`details:
  { feature, needs, active }`), before anything is logged. Until the logged
  version reaches it, the proposing node judges by what every node supports
  now, so a cluster rolling between two releases keeps every feature both
  have. Routes that ask for a passkey step-up check before asking.
- **Older nodes stay out.** Once a version is logged, the leader admits no
  node below it to the system group: a rollback means a new cluster, not an
  older node in this one.
- **Apply never reads it.** An entry applies as it did, so replaying a log is
  unchanged; the gate only decides what is proposed.

A node that still meets an entry it cannot decode logs an error and counts it
in `calimero_log_undecodable_entries_total{log}` (system or app log): with
every feature gated it stays at zero.
