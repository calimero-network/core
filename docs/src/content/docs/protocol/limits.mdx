Every figure here comes from a named constant; when the code and this page
disagree, the code wins.

## Execution limits

One run of a `calimero:app` component is bounded by the host core
(`crates/app-host`) and the engine (`crates/app-engine-wasmtime`). A limit
that stops the run traps it, which leaves an empty diff; a soft limit is an
error the guest's host call returns.

| Limit | Value | Constant |
| --- | --- | --- |
| Fuel per call or view | 200 000 000 | `DEFAULT_FUEL` |
| Memory | 1024 pages = 64 MiB, one memory | `DEFAULT_MEMORY_PAGES`, `MAX_MEMORIES` |
| Wall clock | 2 s for a call, view, timer or delivery; 10 s for an action | `CALL_WALL_CLOCK`, `ACTION_WALL_CLOCK` |
| Stack | 200 KiB | `MAX_WASM_STACK` |
| Table elements, instances, tables, resources | 100 000, 20, 2, 4096 | `MAX_TABLE_ELEMENTS`, `MAX_INSTANCES`, `MAX_TABLES`, `MAX_RESOURCES` |
| Storage key | 1 KiB | `MAX_KEY_BYTES` |
| Bytes one run writes (keys, values, event names and data; every overwrite counts) | 1 MiB (`HostDenied("entry too large")`) | `MAX_RUN_BYTES` |
| Writes per run | 10 000 | `MAX_WRITES` |
| Range reads | 1000 entries per batch; 1024 open cursors | `MAX_RANGE_BATCH`, `MAX_OPEN_CURSORS` |
| Events | 1000 per run; name 100 bytes; data 16 KiB; 1000 accounts in an audience | `MAX_EVENTS`, `MAX_EVENT_NAME_BYTES`, `MAX_EVENT_DATA_BYTES`, `MAX_AUDIENCE_ACCOUNTS` |
| App log | 64 KiB per run; later lines dropped | `MAX_LOG_BYTES` |
| Xcalls (outbox) | 100 per run; app id or method 128 bytes | `MAX_XCALLS`, `MAX_XCALL_NAME_BYTES` |
| Synchronous xcalls | 16 per run; arguments 512 KiB; result 1 MiB | `MAX_SYNC_XCALLS`, `MAX_SYNC_XCALL_ARGS_BYTES`, `MAX_SYNC_XCALL_RESULT_BYTES` |
| Actions | 100 started per call or timer; 1000 `ctx.view` and `ctx.call` per action run | `MAX_STARTED_ACTIONS`, `MAX_ACTION_SUBCALLS` |
| Outbound HTTP | 8 requests per action, one per call; bodies 1 MiB; 64 KiB recorded in a call's entry; 100 headers | `MAX_HTTP_REQUESTS`, `MAX_HTTP_BODY_BYTES`, `MAX_RECORDED_BODY_BYTES`, `MAX_HEADERS` |
| Search | 100 hits at most; query 256 bytes | `MAX_SEARCH_LIMIT`, `MAX_SEARCH_QUERY_BYTES` |
| Files | 16 open; 2 GiB each; 64 MiB written per run; 1 MiB per read | `MAX_OPEN_FILES`, `MAX_FILE_BYTES`, `MAX_RUN_FILE_BYTES`, `MAX_READ_CHUNK` |
| Blob download grant | 1 day at most | `MAX_GRANT_TTL_SECS` |
| Compute runs started | 16 per run; 64 active per app; 64 inputs, 64 KiB of arguments | `MAX_STARTS_PER_RUN`, `MAX_ACTIVE_RUNS`, `MAX_RUN_INPUTS`, `MAX_COMPUTE_ARGS_BYTES` |
| Call arguments | 512 KiB (`413 ARGS_TOO_LARGE`, before anything runs) | `MAX_ARGS_BYTES` |

A run's result also has to fit the log: its whole entry — arguments, diff,
events — must stay under **1 MiB** (`calimero_log::MAX_ENTRY_BYTES`); a run
past it is logged trapped. Compute runs on job nodes have their own caps
(`MAX_COMPUTE_FUEL` 10^12, `MAX_COMPUTE_MEMORY_MIB` 4096,
`MAX_COMPUTE_WALL_SECS` 900; [Compute actions](/protocol/compute-actions/#limits)).

| Compute runs, files and job nodes | See [Compute actions](/protocol/compute-actions/#limits) | `MAX_COMPUTE_WALL_SECS`, `MAX_COMPUTE_MEMORY_MIB`, `MAX_COMPUTE_FUEL` |
| Replicas per app | `--replicas`, 3 by default; moves keep at least 3 | |

A body past a limit is answered `413`, error code `TOO_LARGE`, with the limit
in the message. Under 64 MiB the node's own check answers, sealed like any
answer. Past 64 MiB the sealed envelope is refused before it can be opened, so
its `413` (`{"error":{"code":"too_large",...}}`, which `calimero-client`
reports as `TOO_LARGE`) comes back in the clear: sealing it would mean spending
the request id on bytes nobody has authenticated, letting a relay make the node
vouch for a refusal of a request the client never sent. The node reads and drops
the rest of such a body before it answers, up to 1 GiB and 120 s
(`MAX_DISCARDED_BYTES`, `SEALED_READ_TIME`), because a client that sends its
whole body before reading would otherwise meet a reset, not the answer; past
that, or for a declared length past 1 GiB or a client waiting on
`Expect: 100-continue`, it answers at once and closes.

## Quotas

Per account or per organization (the payer), set by the operator
(`POST /ops/quotas`, with `org` for one payer's compute and file overrides),
checked at apply ([The system group](/protocol/system-group/#quotas)); a
refusal is `429 QUOTA_EXCEEDED`.

| Quota | Default |
| --- | --- |
| Apps owned | 100 |
| Bundle and package bytes uploaded | 1 GiB |
| API keys | 50 |
| Organizations owned (the personal one not counted) | 20 |
| Accounts on the cluster | 100 000 |
| Stored file bytes per organization (`maxFileBytesPerOrg`) | 50 GB |
| Concurrent compute runs per organization (`maxConcurrentRunsPerOrg`) | 4 |
| Reserved compute fuel per organization (`computeFuelPerOrg`) | 10 times `MAX_COMPUTE_FUEL` |
| Fuel per developer per UTC day (`maxFuelPerDeveloperPerDay`; the developer usage is billed to: a deployment's owner for its instances, else the app's org or owner, D78) | 0 (no limit); checked before a client's call or an xcall to any of its apps runs, not at apply: `init`, timer ticks and event handlers still run and count (D76) |

The fuel cap is approximate by at most one refresh interval (5 s). A call never
asks a peer: the node reads the apps it replicates from its own replicas, and the
others from what every peer answered at its last refresh, which asks all peers at
once every 5 s while a cap is set. A developer can so run past its cap for up to one
interval. A peer that stops answering keeps the figures it last reported. An app no
peer has reported yet counts as nothing, so the cap fails open rather than closed:
refusing every call to all of a developer's apps whenever one replica of one of them
is unreachable would be worse than a developer briefly exceeding a daily cap. The cap is a
decimal string in JSON (D20); a node writes a non-zero cap only once every node runs
its release or newer (`409 UPGRADE_PENDING`).
