## Execution limits

One run of a `calimero:app` component is bounded by the host core
(`crates/app-host`) and the engine (`crates/app-engine-wasmtime`). A limit
that stops the run traps it, which leaves an empty diff; a soft limit is an
error the guest's host call returns.

| Limit | Value | Constant |
| --- | --- | --- |
| Fuel per call or view | 200 000 000 | `DEFAULT_FUEL` |
| Memory | 1024 pages = 64 MiB, one memory | `DEFAULT_MEMORY_PAGES`, `MAX_MEMORIES` |
| Wall clock | 2 s for a call, view, timer or delivery; 10 s for an action | `CALL_WALL_CLOCK`, `ACTION_WALL_CLOCK` |
| Stack | 200 KiB | `MAX_WASM_STACK` |
| Table elements, instances, tables, resources | 100 000, 20, 2, 4096 | `MAX_TABLE_ELEMENTS`, `MAX_INSTANCES`, `MAX_TABLES`, `MAX_RESOURCES` |
| Storage key | 1 KiB | `MAX_KEY_BYTES` |
| Bytes one run writes (keys, values, event names and data; every overwrite counts) | 1 MiB (soft: the SDK's typed `RunLimit` error with the bytes the run would reach, WIT `storage.put-checked` 0.5.7; a component built before traps `HostDenied("entry too large")`) | `MAX_RUN_BYTES` |
| Writes per run | 10 000 (soft: `RunLimit` with the write's number; before 0.5.7 a trap) | `MAX_WRITES` |
| Range reads | 1000 entries and 4 MiB (past the first entry) per batch; 1024 open cursors | `MAX_RANGE_BATCH`, `MAX_RANGE_BATCH_BYTES`, `MAX_OPEN_CURSORS` |
| Events | 1000 per run; name 100 bytes; data 16 KiB; 1000 accounts in an audience | `MAX_EVENTS`, `MAX_EVENT_NAME_BYTES`, `MAX_EVENT_DATA_BYTES`, `MAX_AUDIENCE_ACCOUNTS` |
| App log | 64 KiB per run; later lines dropped; never kept by the node | `MAX_LOG_BYTES` |
| Xcalls (outbox) | 100 per run; app id or method 128 bytes | `MAX_XCALLS`, `MAX_XCALL_NAME_BYTES` |
| Synchronous xcalls | 16 per run; arguments 512 KiB; result 1 MiB | `MAX_SYNC_XCALLS`, `MAX_SYNC_XCALL_ARGS_BYTES`, `MAX_SYNC_XCALL_RESULT_BYTES` |
| Actions | 100 started per call or timer; 1000 `ctx.view` and `ctx.call` per action run | `MAX_STARTED_ACTIONS`, `MAX_ACTION_SUBCALLS` |
| Outbound HTTP | 8 requests per run (an action, call, timer or delivery); bodies 1 MiB; 64 KiB of each body recorded in a logged run's entry; 100 headers; 1.5 s wait for a logged run's response (`CALL_FETCH_TIMEOUT`) | `MAX_HTTP_REQUESTS`, `MAX_HTTP_BODY_BYTES`, `MAX_RECORDED_BODY_BYTES`, `MAX_HEADERS` |
| Connector calls | input 64 KiB; 64 values in one limit (metadata keys, models); each call counts as an outbound request | `MAX_CONNECTOR_INPUT`, `MAX_LIMIT_VALUES` |
| Outbound secrets and their redaction | 32 distinct secret values per request (more is refused); each redacted from the response as sent and in 19 common encodings (hex, base64, percent, JSON), 20 patterns a secret, 640 a request; encodings only for a secret of 8 to 4096 bytes, as sent otherwise | `MAX_SECRETS_PER_REQUEST`, `PATTERNS_PER_SECRET`, `MAX_REDACTION_PATTERNS`, `MIN_ENCODED_SECRET_BYTES`, `MAX_ENCODED_SECRET_BYTES` |
| Declared secrets (credential bindings) | 16 per release; name 64 bytes; description 256 bytes; one host, 1 to 8 path prefixes of 256 bytes each, and one place each (a header, or a body field); header name or body field 64 bytes; header `format` 64 bytes with `{}` once; no two on one host's same place on a shared path | `MAX_SECRETS`, `MAX_SECRET_NAME_BYTES`, `MAX_SECRET_DESCRIPTION_BYTES`, `MAX_SECRET_PATHS`, `MAX_SECRET_PATH_BYTES`, `MAX_SECRET_FIELD_BYTES`, `MAX_SECRET_FORMAT_BYTES` |
| Search | 100 hits at most; query 256 bytes; 32 searches per request, its sync xcall views included (`"too many searches in one run"`) | `MAX_SEARCH_LIMIT`, `MAX_SEARCH_QUERY_BYTES`, `MAX_SEARCHES_PER_RUN` |
| Files | 16 open; 2 GiB each; 64 MiB written per run (2 GiB in a compute run); 1,000 new files per run; 1 MiB per read | `MAX_OPEN_FILES`, `MAX_FILE_BYTES`, `MAX_RUN_FILE_BYTES`, `MAX_COMPUTE_FILE_BYTES`, `MAX_NEW_FILES`, `MAX_READ_CHUNK` |
| Blob download grant | 1 day at most | `MAX_GRANT_TTL_SECS` |
| Compute runs started | 16 per run; 64 active per app; 64 inputs, 64 KiB of arguments | `MAX_STARTS_PER_RUN`, `MAX_ACTIVE_RUNS`, `MAX_RUN_INPUTS`, `MAX_COMPUTE_ARGS_BYTES` |
| Call arguments | 512 KiB (`413 ARGS_TOO_LARGE`, before anything runs) | `MAX_ARGS_BYTES` |

A soft limit answers a fixed string, which depends only on the run's own calls,
so every node gives the same answer. `events.emit` answers `too many events`,
`event name too long`, `event data too large`, `too many audience accounts`,
`malformed audience` (an empty account list, account, team or org id),
`unknown team`, or `audience names another org`; `xcall.send` answers
`too many xcalls` or `malformed xcall target`; `emit`, `xcall.send` and
`start-action` past the run's bytes answer
`entry too large: the run would write <n> bytes, over 1048576`. A refused
call records nothing. The caps on keys, events, cursors and logs sit low on
purpose: raising one later breaks no app, lowering one does.

### What host work costs

A run's fuel pays for the guest's own instructions and for the work its host
calls make the node do (`crates/app-host/src/fuel.rs`), on every call, view,
timer, delivery, action and compute run. One fuel is about one nanosecond of
host time; the search figures are the least-squares fit of a query's host time
in `crates/search/bench`.

| Host call | Fuel | Constants |
| --- | --- | --- |
| Every `calimero:app` call, `wasi:random`, a stream write or read, `wasi:http`'s `handle`, and dropping a cursor, file reader or writer | 1000 | `FUEL_HOST_CALL` |
| The bytes a call is handed (keys, values, query text, event name, data and audience, xcall and action targets and arguments, HTTP URL, headers and body, compute run arguments and inputs, file and blob ids), paid before any check | 1 per byte | `FUEL_PER_BYTE` |
| The bytes a call hands back or moves (values read, range batches, xcall, action and HTTP answers, file reads and writes, random bytes, a published file, stream writes and reads, also to stdout once the log is full) | 1 per byte | `FUEL_PER_BYTE` |
| `storage.get`, `put`, `delete`, `add`, opening a range, each `range.next` batch | 1000 more; a batch also 200 per entry | `FUEL_STATE_ACCESS`, `FUEL_PER_RANGE_ENTRY` |
| A `search.query` that runs | 4000 more, plus 14 per matched document, 10 500 per hit and 70 per byte of the hits | `FUEL_SEARCH_QUERY`, `FUEL_PER_SEARCH_MATCH`, `FUEL_PER_SEARCH_HIT`, `FUEL_PER_SEARCH_BYTE` |

The engine takes the base out of the run's fuel as a call starts and the rest
as it returns, so the guest never runs on fuel its host calls already owe, and
a refused or denied call still pays for what it was handed. A run whose fuel
cannot pay ends out of fuel (`422 TRAP`, kind `OutOfFuel`) at that call, as if
the guest had run out; a denied call that could pay is `HostDenied`. A
synchronous xcall's target runs on its own fuel budget, but shares its caller's
search budget: one request makes at most `MAX_SEARCHES_PER_RUN` (32) searches
across its run and every view its xcalls reach (a view forwarded to another
node takes the request's remaining searches with it).

A run's result also has to fit the log: its whole entry — arguments, diff,
events — must stay under **1 MiB** (`calimero_log::MAX_ENTRY_BYTES`); a run
past it is logged trapped (`HostDenied`, `entry too large`). The test harness
measures the same entry (`calimero_app_host::entry_bytes`) and refuses the run
the same way. Compute runs on job nodes have their own caps
(`MAX_COMPUTE_FUEL` 10^12, `MAX_COMPUTE_MEMORY_MIB` 4096,
`MAX_COMPUTE_WALL_SECS` 900; [Compute actions](/protocol/compute-actions/#limits)).

A body past a limit is answered `413`, error code `TOO_LARGE`, with the limit
in the message. Under 64 MiB the node's own check answers, sealed like any
answer. Past 64 MiB the sealed envelope is refused before it can be opened, so
its `413` (`{"error":{"code":"too_large",...}}`, which `calimero-client`
reports as `TOO_LARGE`) comes back in the clear: sealing it would mean spending
the request id on bytes nobody has authenticated, letting a relay make the node
vouch for a refusal of a request the client never sent. The node reads and drops
the rest of such a body before it answers, up to 1 GiB and 120 s
(`MAX_DISCARDED_BYTES`, `SEALED_READ_TIME`), because a client that sends its
whole body before reading would otherwise meet a reset, not the answer; past
that, or for a declared length past 1 GiB or a client waiting on
`Expect: 100-continue`, it answers at once and closes.

## Quotas

Per account or per organization (the payer), set by the operator
(`POST /ops/quotas`, with `org` for one payer's compute and file overrides),
checked at apply ([The system group](/protocol/system-group/#quotas)); a
refusal is `429 QUOTA_EXCEEDED`.

| Quota | Default |
| --- | --- |
| Apps owned | 100 |
| Bundle and package bytes uploaded | 1 GiB |
| API keys | 50 |
| Organizations owned (every one from cluster version 1.0.0-rc.32; before, the personal one not counted) | 20 |
| Accounts on the cluster | 100 000 |
| Stored file bytes per organization (`maxFileBytesPerOrg`) | 50 GB |
| Concurrent compute runs per organization (`maxConcurrentRunsPerOrg`) | 4 |
| Reserved compute fuel per organization (`computeFuelPerOrg`) | 10 times `MAX_COMPUTE_FUEL` |
| Fuel per developer per UTC day (`maxFuelPerDeveloperPerDay`; the developer usage is billed to: a deployment's owner for its instances, else the app's org or owner) | 0 (no limit); checked before a client's call or an xcall to any of its apps runs, not at apply: `init`, timer ticks and event handlers still run and count |

The fuel cap is approximate by at most one refresh interval (5 s). A call never
asks a peer: the node reads the apps it replicates from its own replicas, and the
others from what every peer answered at its last refresh, which asks all peers at
once every 5 s while a cap is set. A developer can so run past its cap for up to one
interval. A peer that stops answering keeps the figures it last reported. An app no
peer has reported yet counts as nothing, so the cap fails open rather than closed:
refusing every call to all of a developer's apps whenever one replica of one of them
is unreachable would be worse than a developer briefly exceeding a daily cap. The cap is a
decimal string in JSON, as every 64-bit integer is
([Types](/build/app-abi/#types)); a node writes a non-zero cap only once every node runs
its release or newer (`409 UPGRADE_PENDING`).

## In `calimero-node`

Where the node implements this chapter, by the names in its code: paths are under `crates/node/src`
unless another crate is named. The design and its reasons are above; a module's own detail is in its
`//!` doc, and the node's mental model is [`crates/node/AGENTS.md`](https://github.com/calimero-network/core/blob/master/crates/node/AGENTS.md).

### Quotas

Code: `system::Quotas`, set with `POST /ops/quotas`.

Live in the system state and are checked at apply, so every node enforces the same limits; refusals
are `429 QUOTA_EXCEEDED`.
`maxFileBytesPerOrg` counts the plaintext bytes of a component's files.
`SystemState::app_file_bytes` holds them per app, and `payer_file_bytes` is its sum per payer
(`usage::payer`), kept in step by `set_app_file_bytes`.
`SystemCmd::ChargeFileBytes { app_id, delta }` refuses a charge past the quota and floors a release
at 0.
`DeleteApp`, `DeleteOrg` and `DeleteTeam` free an app's files through `remove_app`.
`TransferApp` of an app leaving a personal organization (to the new owner's) is refused when that
organization's quota would not hold its files.
The exception is `maxFuelPerDeveloperPerDay` (Q20, D76, D78; `"0"`, the default, is no limit; a
decimal string in JSON, a number refused, `system::decimal_u64`).
It is charged to the app's developer, `usage::developer` (#4839), the same identity usage is billed
to: the owner of the deployment an app was created from, else the app's organization or owner.
So two payers' instances of one developer's deployment share one cap.
The fuel lives in the app groups' usage books, so it is checked where a client's call, a delivered
xcall or a synchronous xcall runs (`Node::fuel_quota_refusal`, from `call_local_component`, after
the idempotent replay and the delivered-xcall check, before the run); an action's own calls are not
refused, as its start was.
The check asks no peer (`Node::developer_fuel_cached`): apps this node replicates are read from the
replica, the others from `Node::refresh_usage`, which every `USAGE_REFRESH` (5 s) while a cap is set
asks all peers at once (`internal/usage/today`) and keeps a silent peer's last figures; so the cap
is approximate by one interval and an app no peer ever reported counts as nothing (fails open).
A refused delivered xcall is the target's final answer (D29, `deliver_one`), not a dead letter.
The refusal is not logged, so the key is not spent; `init`, timer ticks and event handlers are never
refused, and they still count toward the developer's day.
The quota is fuel; wall time is information only (D76).
A non-zero cap is written only once every registered node's attested release is this node's or newer
(`Node::nodes_behind_release`, as D71 gates `base_seq`), else `409 UPGRADE_PENDING`
(`api::UPGRADE_PENDING`, one code for every such release gate), judged before the operator is asked
to sign (`__set_quotas`, #4791): an older node would drop the field and its snapshots would reset
the cap.
Accepted gap (#4809): an older node added after the cap is set, then sent a quota change itself,
writes the quotas without the cap; the runbook says not to add nodes older than `1.0.0-rc.12` then,
and the W19 minimum-release gate closes it.
Usage reads (`app_usage`, `internal/usage`, `replicas_usage_on`) use `replica_group`, never a group
the node keeps after the app moved away.
