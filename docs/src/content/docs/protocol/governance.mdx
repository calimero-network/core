Attestation proves a node runs a trusted image *today*. Three later decisions
could still put an app's data in front of something new:

| Decision | Flag | What it lets in |
| --- | --- | --- |
| **Release approvals** | `--release-approvals` | A new mero-tee release (a new node image) holding the app's data |
| **App upgrades** | `--app-upgrades` | New app code reading the app's state |
| **Outbound approvals** | `--outbound-approvals` | A new destination the app may send data to over HTTPS |

Each is held by exactly one party, chosen when the cluster is deployed
(`system::Governance`, `Authority`):

- **`owner`** (the default): each app's owner decides for that app — for an
  organization's apps, the organization's owner — with a fresh passkey
  assertion that is logged as consent. The operator cannot.
- **`operator`**: the operator decides for every app, through the
  [Ops API](/protocol/operator/). Owners cannot. This suits a managed
  deployment whose users trust its operator with that decision.

Whichever party does not hold a decision is refused by the API (`403`) and,
should a command get that far, by `apply`.

## Fixed at genesis, attested with every receipt key

The first system leader writes the configured governance into the system state
with `SystemCmd::Genesis`, before any account can exist
([The system group](/protocol/system-group/#genesis-fixes-the-rules)). After
that it cannot change: a second genesis is refused, and a node restarted with
other flags reads the state's answer, not its own.

Every node's receipt-key attestation binds the governance its system state
holds (`receipt_key_binding(key, governance)`). `verify_app_cluster` requires
every replica of an app to attest the same governance and returns it, so a user
can prove, from hardware quotes, who may move their app to new code before they
trust it with data ([Attestation & receipts](/protocol/tee-attestation/#verifying-the-whole-app-cluster)).

## Release approvals

A mero-tee release is a node image: kernel, firmware, `merod` build. Upgrading
the cluster means starting nodes on a new release, and those nodes would then
receive app data. So the replicas that hold an app's data decide, per app,
which releases may receive it:

- **Approved set.** Where owners decide, an organization's set lives on the
  organization (`Org::approved_releases`) and covers its apps; an account's own
  set covers the apps it owns outside any organization. The release of the node
  an organization was created through, or an account signed up through, is
  approved from the start. Where the operator decides, one set covers every app
  (`operator_releases`), seeded with the founding node's release.
- **Changing it.** `POST /orgs/{org}/releases` or `/auth/releases`
  `{ version, approved }` by the owner with a passkey step-up, or
  `POST /ops/releases` by the operator. The last approved release cannot be
  withdrawn. An app or console asks the owner for either through the node's
  [consent page](/protocol/consent-page/) (`kind: "release"`, with
  `"withdraw": true` to withdraw). A withdrawal stops new data reaching nodes
  on that release; it deletes and moves nothing: a replica already there keeps
  what it holds (and, if it leads the app, keeps leading it) until the
  operator moves it.
- **Enforcement** is by the nodes that already hold the data:
  - `Node::may_send` refuses every Raft entry and snapshot of an app group to a
    peer whose verified attestation names a release outside the app's set (a
    peer not yet attested is attested first; the system group goes to every
    attested peer);
  - placement of a new app considers only nodes on an approved release;
  - a replica move onto a node whose release is not approved is refused.

So a node on an unapproved image can join the cluster and replicate the system
group, but receives no app's data until that app's approver approves its
release.

## App upgrades

An upgrade switches an app to another bundle and runs its migration over the
existing state ([Upgrades & migrations](/protocol/upgrades/)). Where owners
decide, the app's owner may upgrade it, and so may, for an organization's
app, whoever holds `MANAGE_APPLICATION` on its team or across the
organization: its owner, an admin, the team's leads, or a member granted the
capability ([Organizations](/protocol/organizations/#capabilities)). Each
does so with their own passkey step-up over the exact upgrade (`consent` on
`UpgradeApp`). A personal app stays its owner's alone. Where the
operator decides, `POST /ops/apps/{app}/upgrade` and organization-wide runs
through `/ops/orgs/{org}/upgrade` upgrade to a release the operator installed
itself (`/ops/packages`, recorded as installed by `operator`).

## Outbound approvals

An app's signed manifest declares the URL prefixes it may call. A declared
prefix is usable only once it is approved for the app's **publisher** (the
package's pinned signer): for an organization, by whoever holds
`MANAGE_APPLICATION` across it (`POST /orgs/{org}/outbound`; a grant on one
team is not enough, since the approval covers every app of the organization),
or by the account (`/auth/outbound`), with a passkey
step-up, or by the operator (`POST /ops/outbound`). The approval records both
the prefixes approved and every prefix the approver was shown, so a prefix a
later release adds reads as *awaiting approval* rather than approved. The
operator additionally bounds which hosts any app may reach and holds the
secrets requests may carry ([Application execution](/protocol/execution/#outbound-https)).

## Reading the approvals

Before approving, the approver needs to see what is waiting. Read-only reports
show it, each paged (`?after=ID&limit=N`, at most 100 per page):

- **An organization's members:** `GET /orgs/{org}/apps` (any member; `404`
  to anyone else, as `GET /orgs/{org}`).
- **An account, for its own apps:** `GET /auth/apps`. An app's frontend (a
  session bound to its package) reads only that package's apps, so a
  developer's app can tell its users that a release waits for their approval.
- **The operator:** `GET /ops/apps` and `GET /ops/orgs`, without names or
  accounts ([The operator](/protocol/operator/#what-runs-where)).

Each answers the governance, the scope's approved releases (`null`: none ever
recorded, which leaves the apps unrestricted), the releases the cluster's
nodes run with whether each is approved (so "2.3.131 runs here, not approved
yet" is one read), and per app its release and publisher (the package's pinned signer), newer
releases it could upgrade to, its last upgrade with the actor's kind (`owner`, `member`, `operator`),
and each replica's release and whether it is approved.

Approving and upgrading stay passkey decisions on the cluster's own origin: a
session bound to an app's frontend is refused the approval routes (`403`), so
an app sends its user to the node's consent page, below.

## Asking from an app: the consent page

Where owners decide, an app often needs its user to make one of these
decisions: a new version of the app is out, a feature needs an outbound host,
the operator rolled a new image. The app cannot run the passkey ceremony
itself: an assertion is blind, so the page that asks for it decides what the
person thinks they approve, and an app's page is the publisher's code. A
session opened on an app's frontend is refused every approval route.

Instead the app asks the node (`POST /consent/requests`), and the node serves
a **consent page** of its own, on its own origin, that shows what is being
approved from node-side data only (for an upgrade, a capability sheet diffed
from the two signed manifests), asks for the passkey there, and sends the
person back to the app with the result. The consent then binds the release's
measurements digest or the target's signed-manifest hash, not just a version.
See [The consent page](/protocol/consent-page/).

## Choosing

Giving the operator a decision is giving it the power to put new code, a new
image or a new destination in front of user data. The choice is the
deployment's, made once, and visible to every user who verifies the cluster.
