An app's state is built from the collection types in
`calimero_storage::collections` (`UnorderedMap`, `Vector`, `LwwRegister`,
`Counter`, the text types, `SharedStorage`, …), the SDK and storage crate v1
apps were built with (components built with `calimero-app-sdk` have their own
collections). On a cluster they remain the **storage format** and the **API** apps
program against. What changed is what makes replicas agree: not a merge, but a
log. [Collections](/build/collections/) is the guide to choosing one; this page
explains what is underneath.

## The format: one entity per value

The unit of storage is not the app's struct but the **entity**. Each map entry,
vector element, register or counter slot is its own entity, with its own id and
metadata, stored under keys the storage crate computes. A `Map` with 1 000 keys
is 1 000 entities plus a small container; changing one entry writes that entry
and the index rows above it, not the whole map.

Ids are **derived, not assigned**: an entry's id is a domain-separated hash of
its parent's id and its key, and a nested collection's id a hash of its parent
and field name, so the same logical position has the same id in any run. Each
entity also carries a Merkle hash rolled up from its children, so editing one
leaf rehashes only its ancestor chain, and the root entity's hash summarizes the
whole state.

When a run writes a collection, the storage crate turns that into ordinary key
writes through the host (`storage_write`, `storage_remove`). Those writes are
exactly what the run's overlay records and what becomes the entry's **diff**
([Application execution](/protocol/execution/)). The node never interprets
them: a follower copies the keys and values; it does not know they form a map.

## What the cluster no longer relies on

In v1, two members could write the same entity concurrently on different
nodes, and every replica had to resolve the collision the same way. The
collections were designed for that: per-type merge rules (last-writer-wins
registers, max-per-writer counters, add-wins maps and sets, union of immutable
characters for text), a content-hash tiebreak for equal timestamps, a merge mode
that zeroed timestamps so merged bytes hashed identically, and hybrid logical
clocks to order writes across nodes.

On a cluster, an app's calls run one at a time on its group's leader, each
against the state the previous one left, and followers apply the result.
Nobody re-executes and nothing is merged on the replication path, so:

- **The merge rules do not run between replicas.** Two calls that write the
  same register do not conflict: the second runs after the first and simply
  overwrites it. A plain value would converge just as well as a CRDT.
- **The root hash is not a convergence signal.** Replicas agree because they
  applied the same entries, not because their hashes match. Nothing compares
  them.
- **Timestamps order nothing across nodes.** Registers and entities still carry
  the timestamps the storage crate gives them during the run, on the leader, but
  the log index is what orders calls.

The mechanisms are still in the storage crate and still shape the bytes an app
writes; they are simply not what the cluster's correctness depends on. Choosing
a collection is now about the data structure and its cost — point lookups,
ordering, text editing, per-writer access — rather than its merge semantics.

## What still matters

- **Access-controlled collections** (`SharedStorage` writer sets, `TeeOnly`,
  `Frozen`, per-entity write masks) are checked when the run writes, on the
  leader. A shared cell's writer set lives beside the cell in the app's state,
  written by the node in the same entry as the run's other writes
  ([Who a run acts as](/protocol/authorship/#writers-of-shared-cells)).
- **The ordered index** (`storage_index_*`, used by sorted collections) is not
  provided by the node: index writes report "not persisted" and the
  collections fall back to reading without it.
- **Migrations** rewrite the root entity through the storage crate
  (`write_root_state`), stamped after the entry it replaces
  ([Upgrades & migrations](/protocol/upgrades/)).
- **Search** re-indexes the entities a run touched, which the node reads from
  the run's commit artifact ([Reads](/protocol/reads/#search)).

:::note[What happened to the HLC page]
v1's reference had a chapter on the hybrid logical clock that stamped every
operation and ordered last-writer-wins across nodes. On a cluster the log
orders writes; the storage crate's timestamps are internal to the format.
:::
