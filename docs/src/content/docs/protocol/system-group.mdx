The **system group** is Raft group `1`, hosted by every node of the cluster
(`crates/node/src/system.rs`). Its state machine holds everything that is
not one app's own data:

| Field of `SystemState` | What it is |
| --- | --- |
| `nodes` | Every registered node: id, base URL, zone, role (`replica`, or `job` for a node that only runs compute) |
| `apps` | The app directory: each instance's bundle, owner, organization, access rule, confirm methods, replicas, group, metadata, last upgrade |
| `next_group` | The next app group number |
| `bundles` | Bundle hash → size, uploader, and the release it ships in (the WASM itself is in the blob store) |
| `packages` | Installed packages: pinned signer, owner, and every release (`.mpk` hash and size, source, services, metadata, declared outbound prefixes) |
| `accounts`, `credentials` | Accounts with their passkeys, labels, aliases and approvals; credential id → account |
| `api_keys`, `refresh`, `rotated_refresh` | API-key hashes, live refresh tokens, and refresh tokens already exchanged |
| `revoked_sessions`, `revoked_at` | Sessions that no longer verify, and when they were revoked |
| `used_proofs`, `operator_key` | The consents and operator signatures already used; the operator's verify key and the cluster its signatures name |
| `orgs`, `invites` | Organizations (members, roles, capabilities, teams, approvals, metadata, upgrade runs) and invite-token hashes |
| `quotas` | Per-account limits and the account cap |
| `governance` | Who holds which decision, fixed at genesis ([Deployment governance](/protocol/governance/)) |
| `operator_releases`, `operator_outbound` | The operator's approvals, where governance gives it those decisions |
| `release_deadlines` | The operator's end-of-new-work deadline per mero-tee release ([Release deadlines](/protocol/governance/#release-deadlines)) |
| `publishers` | Package signing key → the organization it is bound to, and its binding generation ([Publishers](/protocol/governance/#publishers)) |

## Commands carry their actor

A change is a `SystemCmd`, serialized as JSON and appended through the system
leader. Every command that acts for someone names them: `actor`, `account`,
`installed_by`, or a credential id. Clients never send commands: a node builds
each one and fills the actor in from the request's verified credential. `apply`
checks the actor's authority against the state the command applies to and
answers `{ "ok": … }` or `{ "err": … }`:

```text
DeleteApp { app_id, actor }
  → refused unless actor is the app's owner, or an admin of its organization
UpgradeApp { app_id, bundle, by_operator, actor, at, consent, … }
  → refused unless governance gives app upgrades to whoever this is, and
    (an `owner` package) actor is the app's owner, or, for an org app, holds
    MANAGE_APPLICATION on its team or org-wide (owner, admin, lead, granted),
    or (a `publisher` package) holds MANAGE_APPLICATION in the publisher org;
    and refused past a release deadline its approver has not met (at `at`)
SetReleaseApproval { scope, version, actor, … }
  → refused unless actor holds APPROVE_RELEASES in the org
BindPublisher { signer_id, org, cluster, proof, actor, … }
  → refused unless actor holds APPROVE_RELEASES in org and proof is the
    key's signature over (cluster, org, key, the key's generation)
InstallPackage { package, signer_id, release }
  → refused if the package is pinned to another signer, or the same
    version is installed with other contents, or the uploader's quota is spent
```

Because the log orders every command and every replica applies the same
commands to the same state, there is one verdict. A refused command is still
committed, as a no-op with its reason, and the node that proposed it turns the
reason into the HTTP answer (`400 REJECTED`, or `429 QUOTA_EXCEEDED` for a
reason that starts with "quota exceeded").

## Decisions carry their proof

`actor` alone is a claim any node of the cluster could make, say
`SetReleaseApproval { actor: <the org's owner>, version: <its own release> }`.
So `apply` first runs `system::authorize`:

| Command | Must carry |
| --- | --- |
| `SetReleaseApproval`, `TransferApp`, `DeleteOrg`, `UpgradeApp` (an owner's), `SetOutboundApproval` (an org's or account's), `StartUpgradeRun` (an account's) | The actor's passkey **consent**: `{ subject, method, args, nonce, assertion }`, where the assertion signs `confirm_challenge(subject, method, args, nonce)` with user verification, under a passkey the actor's account holds in the state |
| `SetOperatorRelease`, `UpgradeApp { by_operator }`, `SetOutboundApproval` (cluster scope), `StartUpgradeRun` (the operator's) | The **operator's signature** (Ed25519, under `operator_key`) over `"calimero.operator.v1\0" ‖ cluster ‖ 0 ‖ subject ‖ 0 ‖ method ‖ 0 ‖ args ‖ 0 ‖ nonce ‖ 0` ([Operator](/protocol/operator/)) |
| `UpgradeApp { run }` | Nothing of its own: the run it names must exist in the app's organization, be started by the same party, not be finished, name the app, and the bundle must be a service of the run's release |

The statement must say what the command does (the subject, `__approve_release`
or `__withdraw_release` as `approved` says, the version, and so on), and each
proof is accepted once (`used_proofs`), so a consent cannot be logged again
after its maker reversed the decision. Every replica reaches the same verdict
from the same state, so a forged decision is refused on every node whoever
proposed it, the system leader included. Origins, the RP id and the signature
counter stay with the node that took the assertion (`verify_assertion`): they
are each node's configuration, not replicated state.

Commands that name an actor but carry no proof yet (memberships, API keys,
passkeys, invites) are still trusted from any node of the cluster; making them
carry the user's proof is the next phase of the design
(`docs/specs/gate-system-group.md`, section 5.6).

The API checks most rules before it proposes, too, so a request that would be
refused usually fails fast and records nothing. The check at apply is the one
that counts: two requests that each passed the API's check against slightly
older state cannot both win.


## Genesis fixes the rules

The first node to lead the system group writes `SystemCmd::Genesis` with the
[governance](/protocol/governance/) it was configured with and its own mero-tee
release. `CreateAccount` is refused until genesis has applied, and `Genesis` is
refused once it has, or once any account exists. A node restarted with other
`--release-approvals`, `--app-upgrades` or `--outbound-approvals` flags
therefore changes nothing: the state already holds the answer, and it is the
state every receipt key attests.

The same leader registers the configured `--peers` as nodes. Genesis also
records the operator's verify key (`--operator-key`) when one is configured.

## Job nodes in the directory

`POST /ops/nodes` takes an optional `role`: `replica` (the default) or `job`.
A job node runs compute for the cluster's apps and never holds the cluster key, so it is never a Raft member, not even a learner: a member keeps its log sealed under that key.
It is also never placed an app, never a target or a majority member of a blob or bundle push, and never sent the cluster key.
`/ops/placement` lists it with its role and an app count of zero, and `/ops/apps/{app}/replicas` refuses a request that names one.
`DELETE /ops/nodes/{id}` removes it at any time and changes no voter.
A node's role is fixed until it is removed, an address belongs to one node in any spelling, and `--peers` must list only replica nodes.
Registering a job node is refused (`409 CLUSTER_NOT_UPGRADED`) until every replica node, voter and learner runs at least the registering node's release, so no older node ever reads a job record.

## The leader's housekeeping

Every node runs a reconcile loop (on each applied system entry, on a follow-up
kick, and every 500 ms). On the system leader it also:

- writes `Genesis` if nothing has;
- registers configured peers that are not yet in `nodes`;
- adds every registered replica node that is not in the system group as a **learner**
  ([Replication](/protocol/replication/#joining-nodes)), once it attests its transport key as a cluster node (a job node registered as a replica never does, so it is never admitted);
- promotes caught-up learners to voters while there are fewer than three.

On every node it starts the app groups this node is a replica of, stops the
ones it no longer is, runs a newly created app's `init` where this node leads
its group, and drives the follow-ups and timers of the groups it leads.

## Reading the system state

The system group's machine keeps its whole state in memory
(`Machine::IN_MEMORY`) and is checkpointed with each snapshot. Reads come in
three strengths:

- **Local** (`Node::sys`): what this replica has applied. Used for lookups that
  can tolerate a moment's lag.
- **Until found** (`Node::sys_until`): wait up to 2 seconds for a lookup to
  find something. A passkey registered through node 1 and used through node 2 a
  moment later is found instead of answering "unknown passkey".
- **Fresh** (`Node::sys_fresh`): a read index. The node asks the system leader
  for its applied index (`internal/system/index`, or locally if it leads) and
  waits up to 2 seconds to apply it. Every request that carries a credential,
  every gated request without one, and every client call on the app's leader
  read the state this way, so a revocation or removal committed through any
  node holds before the next request anywhere.

## Writes

`Node::sys_write` appends through the system leader: locally if this node
leads, else by posting the command to the leader's `internal/system` route over
the [peer sealed channel](/protocol/networking/#between-nodes). It retries for
about 8 seconds to ride out an election. A follower that receives
`internal/system` refuses rather than forwarding again.

Some system commands are not idempotent yet, so a forwarded system write keeps
the long HTTP timeout instead of the short bounded forward app calls use.

## Quotas

`Quotas` live in the system state and are set by the operator
(`POST /ops/quotas`). They are checked inside `apply`, so every node refuses the
same command for the same reason:

| Quota | Default | Checked by |
| --- | --- | --- |
| `maxAppsPerAccount` | 100 | `CreateApp` |
| `maxBundleBytesPerAccount` | 1 GiB | `PutBundle`, `InstallPackage` (operator installs count against no account) |
| `maxApiKeysPerAccount` | 50 | `CreateApiKey` |
| `maxOrgsPerAccount` | 20 (organizations owned) | `CreateOrg` |
| `maxAccounts` | 100 000 | `CreateAccount` (sign-up is open, so this bounds the cluster) |
| `maxFileBytesPerOrg` | 50 000 000 000 | `ChargeFileBytes` (plaintext bytes of the files of an organization's apps, or of a personal account's) |

`GET /auth/usage` shows an account what it uses against them.
