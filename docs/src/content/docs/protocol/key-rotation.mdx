A cluster has few long-lived secrets, and most of its keys die with the
process that made them. This page lists them all, shortest-lived first.

| Key | Made by | Lives | Replaced |
| --- | --- | --- | --- |
| Sealed-session keys | Noise NK handshake (a node to a peer: IK), both sides' ephemeral keys | 1 hour at most; 10 minutes idle | The client opens a new session |
| Transport key (X25519) | Each node, in memory, at start | Until the process stops | On restart; clients get `stale_transport_key` and attest again |
| Receipt key (Ed25519) | Each node, on its first start; kept in its data directory wrapped under K_r; signs receipts and the sessions the node issues | As long as the node's data directory | When a node is replaced (a new data directory): `verify_app_cluster` returns the new key, and the node's sessions refresh |
| Session token | The node that signs someone in, with its receipt key | 15 minutes | Exchanged with a refresh token |
| Refresh token (`rt_…`) | The same node; only its hash is stored | 30 days | The first refresh once it is an hour old returns a new one; younger, it is kept and nothing is logged |
| Operator key (Ed25519) | The operator (mdma); only the public half is in the system state | The cluster's lifetime | Not rotated yet |
| API key (`cal_…`) | Generated for an account; only its hash is stored | Up to 1 year (`ttlSecs`) | Revoked by the account, or expires |
| Passkey | The person's authenticator | Until removed from the account | Added and removed by the account (at least one stays) |
| Account recovery code | Made for an account (`POST /auth/recovery`); the log keeps only its Ed25519 public key | Until used or removed | Set again; a start spends it |
| Organization recovery key (Ed25519) | The organization's owner; only the public half is logged | Until replaced | `SetRecoveryKey` (a new key or `null` ends a recovery under way) |
| Job key (Ed25519) | A job node, in memory, at start; attested with its transport key | Until the process stops | On restart; the leader attests the job node again |
| A sealed file's data key | Random per file; kept wrapped under the app's file key | As long as the file | Never; an export re-wraps it to the requester's key |
| Storage key K_r | HKDF of the KMS key and the cluster name | One mero-tee release (each has its own mero-kms) | Replaced with the release; it only wraps K_c and the receipt key |
| Rollback session key | mero-kms, per key release; only in the TD's memory | Until the process stops | At the next start |
| Cluster key K_c | The founding node's K_r; handed to new nodes by attestation | The cluster's lifetime | Not rotated; a cluster recovered from its recovery disk gets a new one |
| Cluster identity (Ed25519) | Derived from K_c | As K_c | With K_c |
| Backup key (X25519) | The holder (operator, organization or account) on its own machine; only the public half is logged | Until the holder sets another | `SetBackupKey`; files already written stay sealed to the old key |

## Sessions are signed by the node that issued them

Each node signs the sessions it issues with its own receipt key
([Sessions](/protocol/identities/#sessions)); no session-signing key is shared
or replicated. Every node attests each peer's receipt key at its registered
address ahead of time and verifies tokens from that, so a node's sessions
survive its restart (same key) and outlive it while it is down or frozen.
They stop verifying when the node is removed, or replaced on a new data
directory (a new key): clients refresh ([Failover](/protocol/identities/#failover)).

## Revocation

Revocations are system commands, so they hold on every node once applied, and
because a credential is judged on fresh system state, they hold before the next
request anywhere.

| Event | What ends |
| --- | --- |
| `POST /auth/logout` | This session: its refresh tokens go, its tokens stop verifying |
| `POST /auth/logout-all` | Every session of the account |
| Removing a passkey | Every session opened with that passkey; tokens of a session whose passkey is gone are also refused directly |
| A refresh token presented again after it was exchanged | Its session (`RefreshReused`): someone else holds a copy |
| Revoking an API key | That key, at once |

A revoked session id is remembered for an hour (`REVOKED_SESSION_KEEP_SECS`),
past the life of any token it could have minted, and then forgotten; exchanged
refresh tokens are forgotten once they would have expired.

## Signature counters

A passkey assertion reports a signature counter. `SetSignCount` accepts only a
counter that moves forward, whatever order sign-ins committed in, so a cloned
authenticator replaying an old counter is refused; an authenticator that
reports zero every time records nothing. It carries the assertion that
reached the counter and is checked at apply, so no node can set a counter
the authenticator never reached.

## What does not rotate yet

- **K_c** is fixed for the cluster. K_r changes with every release, but it
  only wraps K_c ([The cluster key](/protocol/encryption/#the-cluster-key-k_c)).
  Rotating K_c would mean re-sealing every value and snapshot; nothing does
  that in place. The one way to a new K_c is a cluster brought back from its
  [recovery disk](/protocol/encryption/#the-recovery-disk), which seals every
  row again under the new cluster's key. Keys per app are not done.
- **The operator key** is recorded at genesis and not rotated.

## The rollback counter

Not a key, but it lives with them: mero-kms and the node's store each keep the
node's `(generation, mark)`, raised every second, and a store behind mero-kms
does not start. `merod run --accept-rollback` forces such a start and raises
the cluster's epoch, which every node reports
([Rollback protection](/protocol/encryption/#rollback-protection)).
