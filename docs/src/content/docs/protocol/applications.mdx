An app instance runs one **bundle**: a `calimero:app` WebAssembly component
named by `hex(SHA-256(wasm))`. A core module (an SDK 0.12 app, which ran on
wasmer) is refused at upload, create and install (`400 UNSUPPORTED_BUNDLE`),
and an instance the node left behind answers `410 UNSUPPORTED_ENGINE`. In production a bundle always comes out of a **package
release**: a signed `.mpk` (`calimero-bundle`) holding a `calimero:app`
component built with `meroctl app build`, its manifest signed by its publisher
with `meroctl app pack` (or `meroctl app sign`). See
[Packaging & signing](/build/packaging-signing/) for building one.

## What a release carries

The `.mpk` manifest names the package, its version, its services (each a
`calimero:app` component, `wasm`, and optionally a compute component,
`compute`; a single-service package has one unnamed service), a frontend,
display metadata, who upgrades its instances (`upgrades: owner | publisher`),
the `minRuntimeVersion` it needs, the outbound URL prefixes it declares and
any pipelines it registers (`pipelines`). The manifest is signed by the
publisher's key, and every artifact in the archive is listed with its digest.

- **A compute component** runs only on job nodes, never on a replica. Install
  prepares it on the compute engine alone and refuses the release unless its
  ABI lists exactly the app component's compute methods with the same caps
  (`400 COMPUTE_ABI_MISMATCH`) and it imports nothing outside the compute world
  (`400 BAD_BUNDLE`). A release without one installs and runs calls; it cannot
  run compute ([Compute actions](/protocol/compute-actions/#two-components)).
- **A compute-only package** ships the compute component alone (one service,
  no `wasm`). It needs at least one compute method (`400 NO_COMPUTE_METHODS`)
  and installs only once every node runs a release that knows it (`409
  CLUSTER_NOT_UPGRADED`). Its instances have no app state: a call, view or
  init is `422 NO_APP_COMPONENT`; they hold files and run pipelines.
- **Pipelines** (`pipelines/*.yaml`) are compiled and checked at install
  against the release's compute methods and the modules of other packages a
  step names (`module: <package>[@<version>]`, pinned to the release resolved
  then: one the installer may use that is public or the operator's, its own
  signer's, or private to every organization a private release is for); any error is `400 BAD_PIPELINE` with every problem listed. `GET
  /packages/{package}/{version}/pipelines` answers them ([Pipeline
  runs](/protocol/compute-actions/#pipeline-runs)).

A release travels from its publisher to a registry, and from there to every
node that runs it, never from node to node: the node that installs it verifies
it before the system log records its hash, and each replica fetches and
verifies the same bytes again before running them. The installer is an
account (or an app's creator, since `POST /apps` installs a missing release
first) or the operator. On a development cluster (`--dev`) an uploaded `.mpk`
(`POST /packages`) skips the registry and is spread to a majority of nodes
instead; a production node refuses uploads (`403 UPLOADS_DISABLED`).

There are two ways in:

- `POST /packages/install { package, version, org? }` fetches `package@version` from
  the operator's registry (`--registry-url`, `calimero-app-downloader`'s
  `HttpRegistry`).
- `POST /packages?org=` takes an uploaded `.mpk`, on a development cluster only.

Before the system log records anything (`InstallPackage`), the node that took
the request verifies the release (`Node::verify_release`):

1. The publisher's signature over the manifest and every artifact's digest
   (`calimero_bundle::VerifiedBundle`), and that it ships WASM at all.
2. `minRuntimeVersion` is not newer than this node's release
   (`CALIMERO_RELEASE_VERSION`). The other nodes do not verify the `.mpk`:
   placement, replica moves and upgrades judge the requirement against each
   node that would run the app ([The runtime a release
   needs](/protocol/upgrades/#the-runtime-a-release-needs)).
3. The package's **pinned signer**: the first release of a package pins its
   publisher key (`did:key`); a release signed by any other key is refused.
4. Each service's WASM compiles, imports nothing outside the `calimero:app`
   world ([What the host offers](/protocol/execution/#what-the-host-offers-a-cloud-run)),
   and carries an ABI of a supported `abiVersion`; otherwise `400 BAD_BUNDLE`.
5. A registry install got the package and version it asked for.
6. No WASM it ships (a service or a compute component) ships in a release of
   another package signed by another key (`409`): a WASM belongs to one
   signer, whose packages alone may name it (each instance is judged by the
   release it runs).

`apply` checks the signer pin and the one-signer rule again, refuses a version already installed with
other contents (the same release again changes nothing but who installed it:
the new installer is added to the release's `installers`), and charges each of its parts (every service's
component and compute component) at its own size to the installer's bundle quota (the operator's installs count against no
account). The log keeps, per release, the `.mpk`'s hash and size, where it came
from (`registry` or `upload`), each service's bundle hash, the metadata, and the
declared outbound prefixes.

:::note[Why a pinned signer]
A package's name is the identity apps, approvals and frontends refer to. Pinning
the first release's key means nobody but that publisher can ship a later
"version" of it into the cluster, and it is what outbound approvals are granted
to: `(package, signer)`.
:::

## Where the bytes live

- A **registry** release is never passed between nodes. Each node that needs
  to run it fetches it from the registry itself (`Node::release_wasm`), refuses
  bytes whose hash differs from the one the log recorded, and verifies the
  release again before using its WASM. That is the one-source rule: the
  registry is the only place a registry release comes from.
- An **uploaded** release (development clusters only) has no registry. The
  `.mpk` is stored on a majority of nodes before the log records it; a node
  that lacks it fetches it from a peer, checks the recorded hash and verifies
  it again. Production takes no uploads: an upload's only copies are on the
  nodes it reached, and a cluster that grows from one node and retires it would
  lose the release, while a registry release can always be fetched again.
- Each service's WASM is also kept in the installing node's blob store under
  its bundle hash; other nodes extract it from the `.mpk` on first use.

## Creating, upgrading and removing

- `POST /apps { package, version?, service?, … }` creates an instance from a
  release; without a version, the newest installed one. If the release is not
  installed yet, it is installed from the registry first. A package with
  several services needs `service`. With `deployment`, the instance runs the
  release that [deployment](/protocol/governance/#deployments) offers for
  `package`, and records it.
- `POST /apps/{app}/upgrade { version }` moves an instance to another release
  of its package ([Upgrades](/protocol/upgrades/)).
- `DELETE /packages/{p}[/{v}]` removes a release, or all of them, and is
  refused while any app still runs one of its bundles. A bundle another
  release also ships stays, recorded under that release. Only whoever installed
  the package's first release (an account, or the operator) may uninstall, and
  never a release a deployment offers.
  It takes only the releases it may use: one it may not answers as a missing
  version, and with none named, the others stay.
  The same holds for registering the package's origins: a first installer does it
  only while a release of the package is theirs to use.

## Who sees a release

Many organizations may share one cluster, and what one of them installed is
not another's to list or run.
An account installs a release for an organization it is a member of: the one it names (`org`), else its only one; an account in several must name one.
Below the cluster version that brings `Feature::PrivateReleases` an install names no organization, as before, so a rolling upgrade breaks no install.
The release is public when the registry serves it to anyone (fetched without the cluster's registry credential), and private otherwise: a private registry package (fetched with the credential and the installing account, `x-calimero-install-account`), or an upload.
A release is visible, which is the right to use it (`SystemState::sees_release`), to:

- every account, for a release the operator installed (`/ops/packages`): the
  cluster's own catalog, which the operator upgrades apps to;
- every account, for a public release;
- a member of an organization a private release was installed for (an installer
  only while such a member), each install for another organization adding it;
- the accounts that installed a private release installed for no organization
  (an account in none installs for none), until an install for an organization
  adds one; an account in none installing again a release already private to some
  organization is refused `404` before anything is recorded, as the registry
  answers an account it does not serve;
- the operator, for the releases it installed; it sees no account's releases.

A session opened on the package's own frontend sees what its account sees, the display name and author of the package's newest release included; a sign-up there names the package by its id unless that release is public, the operator's, or recorded before `visibility`.
A release recorded before releases were public or private keeps the earlier rule: whoever installed it, an account sharing an organization with an installer, an account that reaches an app running it, and a session on the package's frontend.
Reaching an instance reads the release it runs (its name and version, `SystemState::reads_release`), never uses it, nor reads another release that shares its WASM.
An instance whose record names no release (made by its WASM's hash) is told, to one who only reaches it, a release that reader may use, else a public or catalog one that ships its WASM, never a private one.

For anyone else the release is not installed. `GET /packages` and
`GET /packages/{p}` list only the releases the caller sees (a package with
none answers `404`), and `GET /ops/packages` only the operator's. Creating or
upgrading an app from it resolves as for a missing release: without a version,
the newest release the caller sees; with one, the release is installed from
the registry first, which makes a registry release the caller's too, and
answers what a missing release answers when the registry lacks it (an upload).
Naming its WASM by hash answers as an unknown bundle. Approving outbound hosts
takes the prefixes of the newest release the caller reads (a newer private
release of another organization neither blocks it nor shows), and answers `404`
when it reads none, on the API and the consent page; the page's requesting app
name and author and the frontend origins it may return to come from that release
too. An
upgrade run, whoever starts it, moves an app only to a release the app's owner
sees, or that the app's deployment still offers; the operator's run also to one
it installed. From the cluster version that brings `Feature::PrivateReleases`,
applying the move judges it again (`RELEASE_NOT_USABLE`), so no node moves an
app onto a release its owner may not use.

Records from before `installers` existed read with none; every release has
always recorded `installedBy`, so each is visible by the rules above from the
first start of this version.

:::caution[What stays shared]
Package names are shared by the whole cluster: installing a release of a name
another publisher's key pinned is refused with that key named, so the name's
existence shows. A frontend is served to anyone who asks for its origin (a
page loads before anyone signs in), so a package's frontend, its releases'
versions and `/.well-known/calimero.json` are public to whoever knows the
package's name. `owner` (whoever installed the first release) is shown with
any release one sees.
:::

**Rolling upgrade (no version gate).** A node on the previous release applies
an install of an already installed release as a no-op. While both releases
run, a repeated install is recorded only on the upgraded nodes (and a node
upgraded later keeps the record its old snapshot had). Repeat the install once
every node runs this version, and it is recorded everywhere. Nodes on the
previous release still list every package to everyone.

## Development bundles

`POST /bundles` takes raw WASM (at most 16 MiB) with no publisher signature. It
is refused unless the node allows unsigned bundles (`--dev`, or
`allow_unsigned_bundles`). The node checks the WASM compiles, stores it on a
majority of nodes, then records `PutBundle { hash, size }`. Raw bundles have no
package, so they cannot be served as a frontend, cannot declare outbound
prefixes, and have no pinned signer.

## ABI facts

The node reads the ABI a component embeds (its `calimero:abi` section) for what
it acts on: which methods are views and confirm methods, whom each method admits
(accounts, API keys, other apps, the system), its timers, and the tables search
indexes. A method the ABI does not name is refused (default-deny). These facts
are trusted because they are part of the component's bytes, which a release's
publisher signs, so an operator cannot mark a method public or a view a
write ([App interface](/build/app-abi/)).

## Frontends

With `--apps-domain D`, each package's frontend is served at its own origin,
`{label}.D`, where the label is 52 lowercase base32 characters of
`SHA-256("calimero.app-host.v1\0" ‖ package)` (`app_host::label`). `merod local`
uses `localhost`.

- The files are the release's own `.mpk` frontend, fetched like its WASM and
  verified against the publisher's signature before a byte is served.
- `GET /` redirects to the newest release's entry; `/{version}/{path}` serves a
  file, falling back to the entry for client-side routes. `/.well-known/calimero.json`
  names the package, the cluster serving it (merod's `--cluster`), its releases,
  the deployments offering it (`id`, `name`, `app`, `version`) and the cluster's
  API URLs, so one frontend build finds its cluster wherever it is served.
- `GET /app/{app}/{path}` redirects to `/{version}/{path}` of the release that
  instance runs (the one it was created at or last upgraded to, never simply
  the newest shipping its WASM: releases may share one and differ only in
  their frontend), so a link handed to a customer opens the frontend matching
  their instance after a newer release is installed. `GET /d/{deployment}/{path}`
  redirects to `/{version}/{path}?deployment={id}`, the release that deployment
  offers for this package (the newest, if it offers several), so the page
  knows which deployment to create instances from. Neither names anything
  but a version; an instance of another package, or a deployment that does
  not offer this one, is a `404`.
- Only `GET` and `HEAD` of files. An unknown label under D is a `404`, never a
  node route. Responses carry a fixed content security policy with the cluster's
  API origins and the attestation mirror (`https://cloud.calimero.network`, where
  the page's client gets the release's signed measurements and Intel's
  collateral; both are signed, so the mirror is trusted with nothing) added to
  `connect-src`.

A session signed in on a frontend is bound to its package; what it may call,
and how it asks for the rest, is in [Sessions & authority](/protocol/sessions-and-authority/).

### Cluster hosts

A package may be deployed on several clusters while each customer's account and
organization live on one, and a front that routes by hostname alone (Calimero
Cloud's resolver) cannot tell them apart by the package's host. So on each
cluster the package also has the host `{cluster_label}.D`, where the label is 52
lowercase base32 characters (unpadded, alphabet `a`–`z`, `2`–`7`) of
`SHA-256("calimero.app-host.cluster.v1\0" ‖ cluster ‖ "\0" ‖ package)`,
`cluster` being the node's `--cluster` (`app_host::cluster_label`). For example,
`com.calimero.kv` on cluster `eu-shared-1` is at
`zqcnu7vlgoxqnu6ar6awxsbcclqru6ry4ygt3bou7tqpimvx25va.D`.

On its cluster the host is the package's site exactly as `{label}.D` is (every
path above, `/d/{deployment}/` included), and an origin of the package: CORS
admits it, and a passkey ceremony from it opens a session bound to the package.
A cluster label made for another cluster answers `404`.

### Deployment hosts

Every deployment has a host of its own too, `{dlabel}.D`, where the dlabel is
52 lowercase base32 characters (unpadded, alphabet `a`–`z`, `2`–`7`) of
`SHA-256("calimero.app-host.deployment.v1\0" ‖ id)` and `id` is the
deployment's id (32 lowercase hex characters; `app_host::deployment_label`).
For example, deployment `0123456789abcdef0123456789abcdef` is served at
`lprfchrsznkwfwiu7gfovvcywyujxdza3rentyjkivnw6cxescca.D`. Its own prefix keeps a
dlabel apart from every package label.

The deployment's host names the deployment, and with it the cluster that holds
it.

- It serves the frontend of the one package the deployment offers, exactly as
  `/d/{deployment}/` does on the package's host: `GET /` redirects to
  `/{version}/?deployment={id}` of the release it offers; files, client routes
  and `/app/{app}/` as above; `/d/{deployment}/` only for its own deployment.
- `/.well-known/calimero.json` carries `"deployment": id` and lists that
  deployment first (`null` on the package's host).
- A deployment that offers nothing yet, or apps of several packages, has no
  frontend: its host answers `404`.
- It is an origin of its own, of the same package: CORS admits it, and a
  passkey ceremony from it opens a session bound to that package, like one from
  the package's host.
- `POST /deployments` answers the new deployment's `host` beside its `id`, and
  `GET /deployments` and `GET /deployments/{id}` carry it (`null` without
  `--apps-domain`).

### Custom domains

A package's manager may have the cluster serve its frontend on a domain of
their own (`https://kv.example.com`) by registering it as a **served origin**
(`POST /package-origins/{package} { origin, served: true }`, with their
passkey; [Registered origins](/protocol/identities/#registered-origins)). A
request whose `Host` is that name gets the package's site exactly as `{label}.D`
serves it (every path above, the same content security policy, `/.well-known/calimero.json`),
before any node route. Unlike the package's host, it is a registered origin: a
passkey ceremony there runs under the domain's own rp-id, never the
cluster's, and opens a session bound to the package that names the origin;
removing it ends the site and those sessions together, as does uninstalling
the package's last release.

- **Which requests.** A `Host` of the name alone, or with port 443, names
  `https://{name}`; on a `--dev` node a `localhost` name with its port names
  `http://{name}:{port}` (`app_host::served_origin_of`). Another port, a name
  under D, or a node's own API host is never a served site, so the request
  reaches the node's routes.
- **What is refused.** Only on a node with `--apps-domain` (`400 NOT_SERVING`);
  never a name under D or under the cluster's rp-id; 4 per package and 64 per
  cluster (`MAX_SERVED_ORIGINS_PER_PACKAGE`, `MAX_SERVED_ORIGINS`). Adding one
  needs every replica, voter and learner on a release that reads the flag
  (`409 CLUSTER_NOT_UPGRADED`): an older node would drop `served` and hold the
  origin unserved, not serving the site but still admitting its ceremonies. The
  API and `SystemState::add_package_origin` judge the same rules, so a command
  any node proposes is judged alike on every node. The full list is in
  [Registered origins](/protocol/identities/#registered-origins).
- **Certificates.** merod holds none: TLS for the name ends in front of it, as
  for D. `GET /ops/served-origins` lists every served origin's host by its
  package's label, never the package's name, for whatever orders the
  certificates and routes the name ([The operator](/protocol/operator/)).
- **One cluster's record.** Each cluster's log holds its own origins, so the
  same origin may be registered on another cluster; which cluster a browser
  reaches is decided by the name's DNS and the front, not by either log.

**Why a flag on a registered origin.** Everything a custom domain needs once
the bytes arrive (who may add and remove it, ceremonies under its rp-id, CORS,
binding sessions to the package and ending them on removal) is a registered
origin's already. A separate record would duplicate all of it, and the same
name could then be held twice, by two packages or under two rp-ids. One map
keyed by origin gives one answer to who holds `https://kv.example.com`, so a
held origin keeps its `served` and its rp-id: changing either is refused
(`409 ORIGIN_TAKEN` for `served`; remove it first). The consent names `served: true` so that a
consent to the plain origin, signed by a client that never knew the flag,
cannot be replayed to make the name served.

A custom domain's sessions are only as safe as its DNS: whoever controls the
name can serve their own page there and use its passkeys, though only for
that package. On the package's host, that trust rests on the apps domain's
DNS alone.

**Why its own origin.** An app's page is third-party code. Served from the
cluster's own origin, it could reach anything the signed-in account can. On its
own origin it is a separate site to the browser, and a passkey ceremony from it
opens a session **bound to its package**: that session reaches only instances
of that package, creates only instances of it, and is refused credentials, API
keys, approvals, upgrades, uninstalls and uploads, and every organization
change but its own package's channels ([Package-bound
sessions](/protocol/identities/#package-bound-sessions)). Its step-ups come
only from its own origin. What it may not do itself, such as approving an
upgrade or creating an organization, it asks the node's
[consent page](/protocol/consent-page/) for.

## In `calimero-node`

Where the node implements this chapter, by the names in its code: paths are under `crates/node/src` unless another crate is named.
The design and its reasons are above; a module's own detail is in its `//!` doc, and the node's mental model is [`crates/node/AGENTS.md`](https://github.com/calimero-network/core/blob/master/crates/node/AGENTS.md).

### Packages

Code: `packages.rs`, `system::PackageRecord`.

- `POST /packages` (uploads) needs `Config::allow_package_uploads`, on with `--dev`.
- `minRuntimeVersion` is compared with `CALIMERO_RELEASE_VERSION`, set by `build.rs`.
- `Node::release_wasm` fetches a release this node does not hold: from the registry for a registry release, never a peer; from a peer for an upload.
- `POST /packages/install { package, version, org? }` and `POST /packages?org=` pick the organization with `Node::install_org` and `api::apps::only_org` (`404` for a non-member's, `400 ORG_REQUIRED`).
  `PackageVersion::orgs` gains it, and `InstallPackage` refuses a non-member's (`NOT_AN_ORG_MEMBER`); below `Feature::PrivateReleases`, `record_release` drops it.
- Uninstall answers a release the actor may not use as missing (`api::packages::refuse_unusable`; `UninstallPackage` from `Feature::PrivateReleases`), and `manages_package` holds origins to the same rule.

#### Public and private releases

`PackageVersion::visibility` (`Feature::PrivateReleases`) comes from `Node::fetch_for_install`:

1. Without the registry URL's credential (userinfo): served is public; `401` or `403` (`RegistryStatus`) goes on to step 2; any other failure is `503`.
2. With the credential and `INSTALL_ACCOUNT_HEADER` (none for the operator): private.
   A `403` with `error: account_not_linked` is `403 ACCOUNT_NOT_LINKED`, which says to link the account in Calimero Cloud (`refused_as_not_linked`).

- An account in no organization records none (`orgs` empty; `installed_by_any`); an install again its installer could not then use is `404` (`not_for_this_account`) and records nothing.
- A reinstall the registry serves to anyone makes a release public, never private again.
- `release_mpk` fetches a public release without the credential, then once more with it on `404`, `401` or `403`; the recorded hash pins what comes back.

#### Compiling

Every compile (each service's component and compute component, and a raw `POST /bundles`) goes through the node's one `compile::Compiler` (`Node::compile`) on the blocking pool.

| Limit | Value | On breach |
| --- | --- | --- |
| `MAX_CONCURRENT_COMPILES` | 1 at a time | — |
| `MAX_QUEUED_COMPILES`, `COMPILE_WAIT` | 4 waiting, 10 s each | `503 BUSY` |
| `COMPILE_TIMEOUT` | 60 s | `422 COMPILE_TIMEOUT`, the service in `details`; the slot is held until the thread returns |
| `MAX_COMPONENT_BYTES` | 47 MiB unpacked (a blob) | `413 TOO_LARGE` before compiling, since it could not reach another node |

A component app's first-use prepare (`Node::prepare_bytes`) stays outside the compiler, off the workers through `spawn_blocking`.

#### Compute components and compute-only packages

- A compute component is prepared on `Node::compute_engine` only.
- A compute-only release has `PackageVersion::components = ComputeOnly`, empty `services`, and `compute[""]` holding the hash.
- It needs `require_upgraded_nodes` (`409 CLUSTER_NOT_UPGRADED`): an older node drops `components` and would apply it as an app's release.
- App-level lookups read `PackageVersion::app_parts`, so a compute-only app's `bundle` and `compute_bundle` are both the compute hash.
- Its app has `AppRecord::components = ComputeOnly`; `AppRecord::require_app_component` refuses a call, view, intent, init or tick (`422 NO_APP_COMPONENT`).
- An upgrade between compute-only releases only moves the directory record; one that adds or drops the app component is `409 COMPONENTS_CHANGED`.
- `PackageVersion::compute` maps service to hash; its `BundleRecord` has `PackageRef::compute = true`, so `resolve_release`, `CreateApp` and `UpgradeApp` never treat it as a service.
- `release_facts` reads a compute-only release's ABI from its compute component, as `GET /apps/{app}/abi` does.

#### Pipelines

Code: `packages/pipelines.rs`.

Install compiles each pipeline (`calimero_pipeline::compile`) against an `Env`:

- `self`: the package's compute methods and caps, the default module for a step;
- one module per other package a step names, resolved by `Node::resolve_modules` (newest when unversioned) to a release that ships one compute component, else `UNKNOWN_MODULE`;
  the release must be one `SystemState::may_pin` allows;
- the cluster's pool memory ceilings.

Errors are `400 BAD_PIPELINE` with `details: [{file, path, code, message}]`, including `NO_COMPUTE` and `DUPLICATE_NAME`.
A named service declaring pipelines is `422 PIPELINES_NEED_ONE_SERVICE`.
`PackageVersion::pipelines` maps name to `PipelineRef { hash, worstCaseFuel, modules }`, each module a `ModulePin { package, version, compute }`.
`InstallPackage` applies only while every pinned release is installed, and uninstalling a pinned one is `409 MODULE_IN_USE` (`SystemState::module_pinned`).
The canonical JSON is a blob under its hash; `Node::pipeline_json(hash)` reads it, else recompiles from the `.mpk`.
A release with pipelines also needs `409 CLUSTER_NOT_UPGRADED` cleared.
`may_pin` judges the release as the install leaves it, and an install again resolves its existing pins; `InstallPackage` judges `may_pin_all` again from `Feature::PrivateReleases`.

#### Release reads

- `GET /packages/{package}/{version}/pipelines` answers `{ name: { hash, worstCaseFuel, modules, pipeline } }` (`meroctl package pipelines`).
- `GET /packages/{package}/{version}/capabilities` answers the release's card before any app of it exists, to whoever sees the release.
  A session bound to the package sees what its account does, and every release only for a record from before `visibility` (`SystemState::sees_release_from`).
  It is read through `consent_page::release_capabilities`; its first eight keys match `consent_page::diff::side`, and `abi` is the embedded `calimero:abi` verbatim.
  `?service=` picks the service; an unknown name, or none on a multi-service release, is `400 NO_SUCH_SERVICE` (`packages::no_such_service`).
  A name over `MAX_SERVICE_QUERY_BYTES` is `400 BAD_REQUEST`, checked first.

### An instance's release

Code: `AppRecord::release`, a `system::PackageRef`.

`AppRecord::release` is set at create and by every `UpgradeApp`, which checks that the release ships the bundle (`SystemState::release_ships`).
Releases may share a WASM, so `bundle` alone does not say which release runs, and moving to a release with the same WASM is an ordinary upgrade.
An org run writes such an `UpgradeApp` without running anything on the app's group.

- `Node::release_of_app` and `report::release_of_app` read it, as does `GET /apps`.
- A record without it (older, or a raw upload) falls back to the only release shipping its bundle (`SystemState::running_release`), and to none when several do.
- The apply-side `SystemState::governing` still takes the bundle's first recorded release for such a record.
- `UpgradeRecord::from_release` and `to_release` name both ends of an upgrade.
- Create and upgrade carry the compute hash of the release they name (`resolve_release_parts`); apply checks the pair with `SystemState::ships_compute`.
- By bundle hash alone, `SystemState::compute_of` resolves the compute part; `400 AMBIGUOUS_COMPUTE` when releases differ, `compute: false` when none ships one.
- `ComponentCmd::Init` and `Upgrade` carry `compute_bundle` into `ComponentHead::compute_bundle`, so a run pins what the group runs, not the system record.
- A release's parts are charged at their own sizes (`PackageVersion::part_sizes`); an older release counts the whole `.mpk` per part.

#### Who sees a release

`SystemState::sees_release` is the rule above; a release recorded before `visibility` keeps the earlier one (`sees_release_from`).

- Reading an instance's release (`report::release_of_app`) is `SystemState::reads_release`, by the package and version the app's record names.
- A route (`src/api`, `src/consent_page`) reads a release a client names only through `release_used`, `releases_used`, `package_used`, `newest_used`, `newest_read` and `release_offered_to`.
  The gate `crates/node/tests/it/release_lookups.rs` fails on any other read of `packages`, `versions` or `bundles` there, unless `READS_ALLOWED` names the line and why.
- `GET /packages[/{p}]` shows each release's kind (`PackageVersion::visibility_shown`; a catalog release is public) and, of a private one's `orgs`, only the reader's (`SystemState::release_orgs_of`).
- For anyone else, `resolve_release` treats the release as missing and upgrade runs skip it (`api::upgrades::upgrade_release`).
- `sees_bundle` hides its WASM; a raw bundle's uploader still names it, and a release's first installer counts only beside a release recorded before `visibility`.
- Outbound approval picks the newest release the caller reads with `PackageRecord::latest_where`; `SetOutboundApproval` judges it again at apply from `Feature::PrivateReleases`.
- An app team (`ScopeApps`, `MoveApp`, `createOrg`'s) is named after the newest release its maker may use (`latest_where`), else `no such package`, and `createOrg` offers no app team.
- A sign-up's package name is `passkeys::app_name`.

### Deployments

Code: `SystemState::deployments`, `system::Deployment`, `Offer`, `api/deployments.rs`.

- Managers are whoever `acts_for` the owner (a `Deployer`); create and offer also need `may_deploy` where deployments are granted.
- `CreateDeployment`'s id is `system::deployment_id` of the consent's nonce.
- Bounds: `MAX_DEPLOYMENTS_PER_OWNER`, `MAX_DEPLOYMENTS`, `MAX_APPS_PER_DEPLOYMENT`; names `deployment_name_fits`, app names and ids `deployment_segment_fits`.
- `POST /apps { deployment, ... }` resolves through `api::offered_bundle`; `CreateApp` checks the offer again (`offers_bundle`).
- An offer serves a create or an upgrade only while someone who `acts_for` the owner may use its release (`SystemState::offer_serves`), else `400 NOT_OFFERED`; instances made before keep running.
- `upgrade_app` resolves a deployment instance's target with `api::apps::offered_bundle`; `node::outside_deployment` answers `409 OUTSIDE_DEPLOYMENT`.
- At apply, `SystemState::within_deployment` judges `UpgradeApp` when its `in_deployment` flag is set (`Feature::UpgradeInDeployment`, `in_deployment_rule`) or `SystemState::cluster_brings` the rule.
  Organization, publisher, operator and unit runs judge the same; from `Feature::PrivateReleases` only an offer that still serves counts, as in an automatic update (`auto_update_allows`).
- The consent page's `upgrade` and `upgradeUnit` take `toVersion` as optional (`UpgradeSubject::to_version`) and resolve it in `consent_page::requested_release`.
  Another instance still names it (`400 VERSION_REQUIRED`).
- `UninstallPackage` refuses an offered release (`offered`).
- An organization owner holds a recovery key (`system::RECOVERY_KEY_REQUIRED`, `Feature::DeploymentNeedsRecovery`), judged in `api/deployments.rs` and `api/recovery.rs` before the passkey and again in `system/deployments.rs`.
- A transfer is `OfferDeployment`, `AcceptDeployment` and `CancelDeploymentTransfer` (`Feature::DeploymentTransfer`), keeping one `PendingTransfer` on `Deployment::transfer`.
  `hands_over` decides who may offer (`NOT_HANDING_OVER`); an acceptance past `TRANSFER_TTL_SECS` is `TRANSFER_LAPSED`, and `Deployment::transferred` records the hand-over.
- Until a person approves an update of an instance after the hand-over (`AppRecord::owner_seen_at`), `SystemState::handed_over_unseen` keeps updates from applying on their own.

### Deployment secrets

Code: `SystemState::deployment_secrets` (deployment id → name → `component::InstanceSecret`); `api/deployments.rs`: `deployment_secrets`, `deployment_secret_set`, `deployment_secret_clear`.

- `SetDeploymentSecret` and `ClearDeploymentSecret`; `authorize` recomputes the fingerprint from the value the entry carries, so no node swaps it.
- Refused: `system::UNDECLARED_SECRET`.
- Bounds: `component::MAX_SECRET_VALUE_BYTES` (shared with instance secrets), `MAX_SECRETS_PER_DEPLOYMENT`, `MAX_DEPLOYMENT_SECRETS`.
- Gates: `Feature::DeploymentSecrets` and, for names reached through `uses`, `Feature::DeploymentUsedSecrets`.
- The API sets `SetDeploymentSecret { used: true }` only when no offered release declares the name; apply then checks `SystemState::deployment_uses_declare` over `used_releases`.
  From `Feature::PrivateReleases`, a used release counts only if someone acting for the owner may use it (`offer_serves`) or the offered package's signer signs it (`same_signer`).
- `InstallPackage` records `uses` (`system::ReleaseUse`) only once the feature is active (`record_release` drops it before); reinstalling the same `.mpk` fills it in.
- `GET` adds `declaredBy` (`deployment_declarers`).
- Lookup at run time: `Node::outbound_for` → `component::run_secrets`.
  The deployment's value comes from `SystemState::deployment_secrets_of` on this node's system state, not the app's log, and only where `SystemState::deployment_covers`.
- The gate attaches a value where `PackageVersion::secrets` binds it: one host and one header or body field each (a hard cutover in 1.0.0-rc.37).
- `SecretValue`'s `Debug` hides the value, and `apply`'s answers never carry it.

### Instance secrets

Code: `api/apps.rs`: `app_secrets`, `app_secret_set`, `app_secret_clear`; `component.rs`: `ComponentCmd::SecretSet`/`SecretClear`, `InstanceSecret`, `rows::CSECRET`.

- The owner, or whoever manages the organization's apps, sets a value with a step-up over `{ name, fingerprint }`.
- The host commands `__secret_set` and `__secret_clear` write one hidden row on the replicas (`AppMachine::instance_secrets`) that no host function reads.
- A call's or tick's run reads it with the state it sees (`RunExtras::secrets`); an action reads it on the leader.
- `outbound_for` hands it to the gate as `calimero_outbound::OwnSecrets`.
- `GET` answers through the leader's reserved view `__secrets`: fingerprints, never values.
- Set and clear need `require_upgraded_nodes`.

### Units

Code: `api/apps.rs`: `create_instance`, `unit_members`; `api/upgrades.rs`: `app_upgrade_unit`.

#### Creating and deleting

- `create_instance` creates each `mode: create` reference first, at most `MAX_UNIT_DEPTH` deep.
- `unit_members` picks the newest installed release in range that the creator may use (`sees_release`), that the instance's own signer published, or, for a deployment instance, that `offer_serves` allows.
  Otherwise it is `409 USES_NOT_INSTALLED`, answered as for a package not installed.
- The member's create runs exactly that release (`CreateAppBody::unit_release`, `serde(skip)`); a unit's preview (`egress::release_unit`) and upgrade (`unit_plan`, `egress::update`) pick by the same rule.
- It records them in `AppRecord::links` (`Feature::AppLinks`) and passes their ids as `links` in `initArgs` when `init` takes them; a client's own `links` there is refused.
- A failure after a member was made leaves it in place.
- With `Feature::WholeUnits`, members of a deployment instance carry its deployment, and their `CreateApp` names `unit_offer`, checked at apply in place of the member's own release.
  `CreateAppBody::unit_offer` is `serde(skip)`: only the node sets it.
- `DELETE /apps/{app}` of an instance deletes its unit (`SystemState::unit_of`, over `links` transitively) and answers it in `members`.
  `DeleteApp { members }` must match at apply (`UNIT_NOT_AS_NAMED`), and the actor must be allowed to delete each one.
- A member (`unit_parent`) deleted alone is `409 UNIT_MEMBER` at the API and `UNIT_MEMBER` at apply.
- The API sends `members` once the cluster version brings the feature, or for an instance with members (else `409 FEATURE_NOT_ACTIVE`).
- A member finds its instance with `env::unit_of` (WIT `context.unit-of`; `SysDirectory::unit_of`), derived from the system state, so nothing new is stored.

#### Upgrading a unit

- `POST /apps/{app}/upgrade-unit` starts a run whose consent (`org:<org> / __upgrade_unit / { app, package, version, targets }`) names each member's release (`UpgradeRun::targets`, `RunTarget`, `Feature::UnitUpgrade`).
- Apply derives the apps from `links` (`upgrade_run_apps`); `run_may_move` and `UpgradeApp { run }` judge each by `UpgradeRun::target_of`.
- A member upgraded alone outside its instance's range is `409 OUTSIDE_UNIT_RANGE` (`refuse_off_unit_range`).
- `unit_plan` reads nothing of a target its account may not use: before any member, target or passkey it answers as `resolve_release` answers a missing release.
  For a deployment instance, anything but its offer that still serves is `409 OUTSIDE_DEPLOYMENT`.
- The consent page's `upgradeUnit` (`unit_upgrade_request`) builds one model from `api::unit_plan` and each app's sheet; members skip the bound session's `within`.
  `Action::UpgradeUnit` is stale when a bundle or the targets moved, and `act` runs `api::upgrade_unit`.

#### Attached apps

- An `attach` reference is held in `AppRecord::attached`, apart from `links`, so unit upgrades and deletes never touch it.
- `SystemCmd::LinkApp { app_id, name, target }` (`Feature::AttachApp`; consent `<app> / __link / { name, target }`, `system::link_app_args`) sets it; `target: null` detaches.
- Apply requires: whoever manages both apps, the same organization, a name (`calimero_bundle::is_use_name`) that is not a unit member's, and at most `MAX_ATTACHED`.
- `PUT|DELETE /apps/{app}/links/{name}` (`app_link`, `app_unlink`) also need an `attach` reference of the running release (`release_uses`; `409 NOT_AN_ATTACH_REFERENCE`) and an app of that package (`409 WRONG_PACKAGE`).
  An app outside the range is attached and answered `inRange: false`.
- `GET /apps/{app}/links` lists each reference (`link_row`).
- `remove_app` detaches a deleted app everywhere.
- The upgrade sheet's `attachedOutOfRange` comes from `attached_outside`.
- Runs read links with `env::linked` (`SysDirectory::linked`: `links`, then `attached`).

### App frontends

Code: `app_host.rs`.

- Files come from `Node::release_mpk`, verified before a byte is served; opened ones are cached, and so is a release shipping none.
- `FrontendCache::get_or_load` runs one load per release and at most `FRONTEND_LOADS` at once.
- `/app/{app}/` of a record without `AppRecord::release` goes to the newest release shipping its WASM, by `compare_versions`.
- `/d/{deployment}/` is looked up again on fresh state when nothing matches.
- Every redirect keeps the request's query, after any `deployment` it adds, so `/?invite=...` reaches the page.
- The mirror in `connect-src` is `ATTESTATION_MIRROR`.
- Cluster hosts are `cluster_label(config.cluster, package)`; deployment hosts are `deployment_label(id)`, served as an `app_host::Site`.

#### Package-bound sessions

- The session's package is `SessionClaims::app`, carried by refresh.
- `Principal::within` keeps it to that package's apps: gate, app reads and writes, listings.
- `unbound` and `holder` refuse it everything the design lists, plus redeeming invites, an app's delete and its access.
- The exception is its own package's teams (`Principal::within_team`, `OwnTeam`, `Org::package_of_team`):
  - `team_create` under one;
  - `team_update` of a team below the app team, never the app team itself, with a move only within;
  - `team_set_member` and `team_remove_member` on any of them;
  - `team_delete` below the app team when every app in its subtree is the package's;
  - `app_access` of a package app between two such teams.
- Step-ups are over one of the package's apps, or `org:{org}` for `BOUND_TEAM_STEP_UPS` (`__set_team_member`, `__remove_team_member`, `__delete_team`); `step_up` judges `within_team` again.

### Smaller rules

- **Init**: `initArgs` is kept on the `AppRecord`; a failed init answers `422 INIT_FAILED` (`AppState::init_error`).
- **Typed ids** (accounts, apps, organizations, teams, upgrade runs, API keys) are base64url that never starts with `-` (`api::typed_id`), which meroctl would read as a flag.
- **Context ids**: an app answers to `hex(SHA-256(app_id))` wherever the API takes an app id (`Node::canonical_app_id`); a component reads its id with `env::app_id`.
- **Inspection**: `GET /apps/{app}/storage`, `GET /apps/{app}/abi`, `GET /auth/usage` (with `developerFuelToday` and `developerWritesToday`), `GET /orgs/{org}/usage` (admins) and `GET /apps/{app}/usage` (owner and org admins; see [Execution](/protocol/execution/)).
