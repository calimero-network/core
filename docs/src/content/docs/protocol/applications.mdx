An app instance runs one **bundle**: a `calimero:app` WebAssembly component
named by `hex(SHA-256(wasm))`. A core module (an SDK 0.12 app, which ran on
wasmer) is refused at upload, create and install (`400 UNSUPPORTED_BUNDLE`),
and an instance the node left behind answers `410 UNSUPPORTED_ENGINE`. In production a bundle always comes out of a **package
release**: a signed `.mpk` (`calimero-bundle`) holding a `calimero:app`
component built with `meroctl app build`, its manifest signed by its publisher
with `meroctl app pack` (or `meroctl app sign`). See
[Packaging & signing](/build/packaging-signing/) for building one.

## What a release carries

The `.mpk` manifest names the package, its version, its services (each a
`calimero:app` component, `wasm`, and optionally a compute component,
`compute`; a single-service package has one unnamed service), a frontend,
display metadata, who upgrades its instances (`upgrades: owner | publisher`),
the `minRuntimeVersion` it needs, the outbound URL prefixes it declares and
any pipelines it registers (`pipelines`). The manifest is signed by the
publisher's key, and every artifact in the archive is listed with its digest.

- **A compute component** runs only on job nodes, never on a replica. Install
  prepares it on the compute engine alone and refuses the release unless its
  ABI lists exactly the app component's compute methods with the same caps
  (`400 COMPUTE_ABI_MISMATCH`) and it imports nothing outside the compute world
  (`400 BAD_BUNDLE`). A release without one installs and runs calls; it cannot
  run compute ([Compute actions](/protocol/compute-actions/#two-components)).
- **A compute-only package** ships the compute component alone (one service,
  no `wasm`). It needs at least one compute method (`400 NO_COMPUTE_METHODS`)
  and installs only once every node runs a release that knows it (`409
  CLUSTER_NOT_UPGRADED`). Its instances have no app state: a call, view or
  init is `422 NO_APP_COMPONENT`; they hold files and run pipelines.
- **Pipelines** (`pipelines/*.yaml`) are compiled and checked at install
  against the release's compute methods and the modules of other packages a
  step names (`module: <package>[@<version>]`, pinned to the release resolved
  then: one the installer may use that is public or the operator's, its own
  signer's, or private to every organization a private release is for); any error is `400 BAD_PIPELINE` with every problem listed. `GET
  /packages/{package}/{version}/pipelines` answers them ([Pipeline
  runs](/protocol/compute-actions/#pipeline-runs)).

A release travels from its publisher to a registry, and from there to every
node that runs it, never from node to node: the node that installs it verifies
it before the system log records its hash, and each replica fetches and
verifies the same bytes again before running them. The installer is an
account (or an app's creator, since `POST /apps` installs a missing release
first) or the operator. On a development cluster (`--dev`) an uploaded `.mpk`
(`POST /packages`) skips the registry and is spread to a majority of nodes
instead; a production node refuses uploads (`403 UPLOADS_DISABLED`).

There are two ways in:

- `POST /packages/install { package, version, org? }` fetches `package@version` from
  the operator's registry (`--registry-url`, `calimero-app-downloader`'s
  `HttpRegistry`).
- `POST /packages?org=` takes an uploaded `.mpk`, on a development cluster only.

Before the system log records anything (`InstallPackage`), the node that took
the request verifies the release (`Node::verify_release`):

1. The publisher's signature over the manifest and every artifact's digest
   (`calimero_bundle::VerifiedBundle`), and that it ships WASM at all.
2. `minRuntimeVersion` is not newer than this node's release
   (`CALIMERO_RELEASE_VERSION`). The other nodes do not verify the `.mpk`:
   placement, replica moves and upgrades judge the requirement against each
   node that would run the app ([The runtime a release
   needs](/protocol/upgrades/#the-runtime-a-release-needs)).
3. The package's **pinned signer**: the first release of a package pins its
   publisher key (`did:key`); a release signed by any other key is refused.
4. Each service's WASM compiles.
5. A registry install got the package and version it asked for.
6. No WASM it ships (a service or a compute component) ships in a release of
   another package signed by another key (`409`): a WASM belongs to one
   signer, whose packages alone may name it (each instance is judged by the
   release it runs).

`apply` checks the signer pin and the one-signer rule again, refuses a version already installed with
other contents (the same release again changes nothing but who installed it:
the new installer is added to the release's `installers`), and charges each of its parts (every service's
component and compute component) at its own size to the installer's bundle quota (the operator's installs count against no
account). The log keeps, per release, the `.mpk`'s hash and size, where it came
from (`registry` or `upload`), each service's bundle hash, the metadata, and the
declared outbound prefixes.

:::note[Why a pinned signer]
A package's name is the identity apps, approvals and frontends refer to. Pinning
the first release's key means nobody but that publisher can ship a later
"version" of it into the cluster, and it is what outbound approvals are granted
to: `(package, signer)`.
:::

## Where the bytes live

- A **registry** release is never passed between nodes. Each node that needs
  to run it fetches it from the registry itself (`Node::release_wasm`), refuses
  bytes whose hash differs from the one the log recorded, and verifies the
  release again before using its WASM. That is the one-source rule: the
  registry is the only place a registry release comes from.
- An **uploaded** release (development clusters only) has no registry. The
  `.mpk` is stored on a majority of nodes before the log records it; a node
  that lacks it fetches it from a peer, checks the recorded hash and verifies
  it again. Production takes no uploads: an upload's only copies are on the
  nodes it reached, and a cluster that grows from one node and retires it would
  lose the release, while a registry release can always be fetched again.
- Each service's WASM is also kept in the installing node's blob store under
  its bundle hash; other nodes extract it from the `.mpk` on first use.

## Creating, upgrading and removing

- `POST /apps { package, version?, service?, … }` creates an instance from a
  release; without a version, the newest installed one. If the release is not
  installed yet, it is installed from the registry first. A package with
  several services needs `service`. With `deployment`, the instance runs the
  release that [deployment](/protocol/governance/#deployments) offers for
  `package`, and records it.
- `POST /apps/{app}/upgrade { version }` moves an instance to another release
  of its package ([Upgrades](/protocol/upgrades/)).
- `DELETE /packages/{p}[/{v}]` removes a release, or all of them, and is
  refused while any app still runs one of its bundles. A bundle another
  release also ships stays, recorded under that release. Only whoever installed
  the package's first release (an account, or the operator) may uninstall, and
  never a release a deployment offers.
  It takes only the releases it may use: one it may not answers as a missing
  version, and with none named, the others stay.
  The same holds for registering the package's origins: a first installer does it
  only while a release of the package is theirs to use.

## Who sees a release

Many organizations may share one cluster, and what one of them installed is
not another's to list or run.
An account installs a release for an organization it is a member of: the one it names (`org`), else its only one.
The release is public when the registry serves it to anyone (fetched without the cluster's registry credential), and private otherwise: a private registry package (fetched with the credential and the installing account, `x-calimero-install-account`), or an upload.
A release is visible, which is the right to use it (`SystemState::sees_release`), to:

- every account, for a release the operator installed (`/ops/packages`): the
  cluster's own catalog, which the operator upgrades apps to;
- every account, for a public release;
- a member of an organization a private release was installed for (an installer
  only while such a member), each install for another organization adding it;
- the accounts that installed a private release installed for no organization
  (an account in none installs for none), until an install for an organization
  adds one; an account in none installing again a release already private to some
  organization is refused `404` before anything is recorded, as the registry
  answers an account it does not serve;
- the operator, for the releases it installed; it sees no account's releases.

A session opened on the package's own frontend sees what its account sees, the display name and author of the package's newest release included; a sign-up there names the package by its id unless that release is public or the operator's.
A release recorded before releases were public or private keeps the earlier rule: whoever installed it, an account sharing an organization with an installer, an account that reaches an app running it, and a session on the package's frontend.
Reaching an instance reads the release it runs (its name and version, `SystemState::reads_release`), never uses it, nor reads another release that shares its WASM.
An instance whose record names no release (made by its WASM's hash) is told, to one who only reaches it, a release that reader may use, else a public or catalog one that ships its WASM, never a private one.

For anyone else the release is not installed. `GET /packages` and
`GET /packages/{p}` list only the releases the caller sees (a package with
none answers `404`), and `GET /ops/packages` only the operator's. Creating or
upgrading an app from it resolves as for a missing release: without a version,
the newest release the caller sees; with one, the release is installed from
the registry first, which makes a registry release the caller's too, and
answers what a missing release answers when the registry lacks it (an upload).
Naming its WASM by hash answers as an unknown bundle. Approving outbound hosts
takes the prefixes of the newest release the caller reads (a newer private
release of another organization neither blocks it nor shows), and answers `404`
when it reads none, on the API and the consent page; the page's requesting app
name and author and the frontend origins it may return to come from that release
too. An
organization's upgrade run moves an app only to a release its upgrader sees;
the operator's, to one it installed or the app's owner sees.

Records from before `installers` existed read with none; every release has
always recorded `installedBy`, so each is visible by the rules above from the
first start of this version.

:::caution[What stays shared]
Package names are one namespace per cluster: installing a release of a name
another publisher's key pinned is refused with that key named, so the name's
existence shows. A frontend is served to anyone who asks for its origin (a
page loads before anyone signs in), so a package's frontend, its releases'
versions and `/.well-known/calimero.json` are public to whoever knows the
package's name. `owner` (whoever installed the first release) is shown with
any release one sees.
:::

**Rolling upgrade (no version gate).** A node on the previous release applies
an install of an already installed release as a no-op. While both releases
run, a repeated install is recorded only on the upgraded nodes (and a node
upgraded later keeps the record its old snapshot had). Repeat the install once
every node runs this version, and it is recorded everywhere. Nodes on the
previous release still list every package to everyone.

## Development bundles

`POST /bundles` takes raw WASM (at most 16 MiB) with no publisher signature. It
is refused unless the node allows unsigned bundles (`--dev`, or
`allow_unsigned_bundles`). The node checks the WASM compiles, stores it on a
majority of nodes, then records `PutBundle { hash, size }`. Raw bundles have no
package, so they cannot be served as a frontend, cannot declare outbound
prefixes, and have no pinned signer.

## ABI facts

The node reads the ABI a component embeds (its `calimero:abi` section) for what
it acts on: which methods are views and confirm methods, whom each method admits
(accounts, API keys, other apps, the system), its timers, and the tables search
indexes. A method the ABI does not name is refused (default-deny).

## Frontends

With `--apps-domain D`, each package's frontend is served at its own origin,
`{label}.D`, where the label is 52 lowercase base32 characters of
`SHA-256("calimero.app-host.v1\0" ‖ package)` (`app_host::label`). `merod local`
uses `localhost`.

- The files are the release's own `.mpk` frontend, fetched like its WASM and
  verified against the publisher's signature before a byte is served.
- `GET /` redirects to the newest release's entry; `/{version}/{path}` serves a
  file, falling back to the entry for client-side routes. `/.well-known/calimero.json`
  names the package, the cluster serving it (merod's `--cluster`), its releases,
  the deployments offering it (`id`, `name`, `app`, `version`) and the cluster's
  API URLs, so one frontend build finds its cluster wherever it is served.
- `GET /app/{app}/{path}` redirects to `/{version}/{path}` of the release that
  instance runs (the one it was created at or last upgraded to, never simply
  the newest shipping its WASM: releases may share one and differ only in
  their frontend), so a link handed to a customer opens the frontend matching
  their instance after a newer release is installed. `GET /d/{deployment}/{path}`
  redirects to `/{version}/{path}?deployment={id}`, the release that deployment
  offers for this package (the newest, if it offers several), so the page
  knows which deployment to create instances from. Neither names anything
  but a version; an instance of another package, or a deployment that does
  not offer this one, is a `404`.
- Only `GET` and `HEAD` of files. An unknown label under D is a `404`, never a
  node route. Responses carry a fixed content security policy with the cluster's
  API origins and the attestation mirror (`https://cloud.calimero.network`, where
  the page's client gets the release's signed measurements and Intel's
  collateral; both are signed, so the mirror is trusted with nothing) added to
  `connect-src`.

A session signed in on a frontend is bound to its package; what it may call,
and how it asks for the rest, is in [Sessions & authority](/protocol/sessions-and-authority/).

### Cluster hosts

A package may be deployed on several clusters while each customer's account and
organization live on one, and a front that routes by hostname alone (Calimero
Cloud's resolver) cannot tell them apart by the package's host. So on each
cluster the package also has the host `{cluster_label}.D`, where the label is 52
lowercase base32 characters (unpadded, alphabet `a`–`z`, `2`–`7`) of
`SHA-256("calimero.app-host.cluster.v1\0" ‖ cluster ‖ "\0" ‖ package)`,
`cluster` being the node's `--cluster` (`app_host::cluster_label`). For example,
`com.calimero.kv` on cluster `eu-shared-1` is at
`zqcnu7vlgoxqnu6ar6awxsbcclqru6ry4ygt3bou7tqpimvx25va.D`.

On its cluster the host is the package's site exactly as `{label}.D` is (every
path above, `/d/{deployment}/` included), and an origin of the package: CORS
admits it, and a passkey ceremony from it opens a session bound to the package.
A cluster label made for another cluster answers `404`.

### Deployment hosts

The front does not route these yet; cluster hosts are what it routes.

Every deployment has a host of its own too, `{dlabel}.D`, where the dlabel is
52 lowercase base32 characters (unpadded, alphabet `a`–`z`, `2`–`7`) of
`SHA-256("calimero.app-host.deployment.v1\0" ‖ id)` and `id` is the
deployment's id (32 lowercase hex characters; `app_host::deployment_label`).
For example, deployment `0123456789abcdef0123456789abcdef` is served at
`lprfchrsznkwfwiu7gfovvcywyujxdza3rentyjkivnw6cxescca.D`. Its own prefix keeps a
dlabel apart from every package label.

The deployment's host names the deployment, and with it the cluster that holds
it.

- It serves the frontend of the one package the deployment offers, exactly as
  `/d/{deployment}/` does on the package's host: `GET /` redirects to
  `/{version}/?deployment={id}` of the release it offers; files, client routes
  and `/app/{app}/` as above; `/d/{deployment}/` only for its own deployment.
- `/.well-known/calimero.json` carries `"deployment": id` and lists that
  deployment first (`null` on the package's host).
- A deployment that offers nothing yet, or apps of several packages, has no
  frontend: its host answers `404`.
- It is an origin of its own, of the same package: CORS admits it, and a
  passkey ceremony from it opens a session bound to that package, like one from
  the package's host.
- `POST /deployments` answers the new deployment's `host` beside its `id`, and
  `GET /deployments` and `GET /deployments/{id}` carry it (`null` without
  `--apps-domain`).

### Custom domains

A package's manager may have the cluster serve its frontend on a domain of
their own (`https://kv.example.com`) by registering it as a **served origin**
(`POST /package-origins/{package} { origin, served: true }`, with their
passkey; [Registered origins](/protocol/identities/#registered-origins)). A
request whose `Host` is that name gets the package's site exactly as `{label}.D`
serves it (every path above, the same content security policy, `/.well-known/calimero.json`),
before any node route. Unlike the package's host, it is a registered origin: a
passkey ceremony there runs under the domain's own rp-id, never the
cluster's, and opens a session bound to the package that names the origin;
removing it ends the site and those sessions together. TLS for the name ends
inside the TD with a certificate Calimero Cloud orders for the node's attested
key; the end-to-end design is `docs/specs/custom-domains.md`.

**Why its own origin.** An app's page is third-party code. Served from the
cluster's own origin, it could reach anything the signed-in account can. On its
own origin it is a separate site to the browser, and a passkey ceremony from it
opens a session **bound to its package**: that session reaches only instances
of that package, creates only instances of it, and is refused credentials, API
keys, approvals, upgrades, uninstalls and uploads, and every organization
change but its own package's channels ([Package-bound
sessions](/protocol/identities/#package-bound-sessions)). Its step-ups come
only from its own origin. What it may not do itself, such as approving an
upgrade or creating an organization, it asks the node's
[consent page](/protocol/consent-page/) for.

## In `calimero-node`

Where the node implements this chapter, by the names in its code: paths are under `crates/node/src`
unless another crate is named. The design and its reasons are above; a module's own detail is in its
`//!` doc, and the node's mental model is [`crates/node/AGENTS.md`](https://github.com/calimero-network/core/blob/master/crates/node/AGENTS.md).

### Packages

Code: `packages.rs`, `system::PackageRecord`.

Signed `.mpk` releases.
`POST /packages/install { package, version, org? }` fetches from the operator's registry
(`--registry-url`, `calimero-app-downloader`'s `HttpRegistry`); `POST /packages?org=` takes an uploaded
file, only with `Config::allow_package_uploads` (`--dev`; else `403 UPLOADS_DISABLED`: a production
release comes from the registry, which any node can fetch it from again).
An account installs for an organization (`Node::install_org`): `org`, which it must be a member of (else `404`), else its only one (`api::apps::only_org`; several `400 ORG_REQUIRED`).
Below the logged cluster version that brings `Feature::PrivateReleases` an install names no organization at all (`record_release` drops it), so a multi-org account is never asked for `org`.
Public or private (`PackageVersion::visibility`, `Feature::PrivateReleases`, rc.38; `Node::fetch_for_install`): the registry URL's credential (userinfo) is left out first, and a release served so is public (a `401` or `403` to that fetch, `RegistryStatus`, counts as not public; any other failure is `503`); else it is fetched with the credential and `x-calimero-install-account: <account>` (`INSTALL_ACCOUNT_HEADER`; none for the operator) and is private.
An upload is private.
An account in no organization installs for none (`orgs` empty): such a private release is its installing accounts' alone (`sees_release`, `installed_by_any`) until an install for an organization adds one, and then the organization rule holds (regressions `a_private_release_for_no_organization_is_its_installers_alone`, `system::tests` and `tests/cluster.rs`).
`PackageVersion::orgs` gains the organization of each install; `InstallPackage` refuses one the actor is not a member of (`NOT_AN_ORG_MEMBER`).
An install again that would leave the release one its installer may not use (an account in no organization, of a release private to some) is refused before it is logged, `404` as the registry answers an account it does not serve (`not_for_this_account`), and records nothing (regression `an_install_its_installer_could_not_use_is_refused_and_records_nothing`).
A reinstall the registry serves to anyone makes a release public, never private again.
`release_mpk` fetches a public release without the credential and, when the registry no longer serves it so (`404`, `401`, `403`: the publisher made it private since), once more with it; any other release with it from the start, naming no account; the recorded hash pins what comes back.
Before `InstallPackage` is logged the node checks the publisher signature and every artifact digest
(`calimero_bundle::VerifiedBundle`), `minRuntimeVersion` (build.rs's `CALIMERO_RELEASE_VERSION`),
the package's pinned signer (first release wins, `apply` re-checks) and that each service's WASM
compiles.
Each compile (every service's component and compute component, and a raw `POST /bundles`) goes
through the node's one `compile::Compiler` (`Node::compile`): on the blocking pool,
`MAX_CONCURRENT_COMPILES` (1) at a time, `MAX_QUEUED_COMPILES` (4) more waiting at most
`COMPILE_WAIT` (10 s), past that `503 BUSY`; one that runs past `COMPILE_TIMEOUT` (60 s) is `422
COMPILE_TIMEOUT` (with the service in `details`) and keeps the slot until its thread returns.
A component over `MAX_COMPONENT_BYTES` (a blob, 47 MiB, unpacked) is `413 TOO_LARGE` before it
compiles: it could not reach another node as a blob.
A component app's first-use prepare at run time (`Node::prepare_bytes`) stays outside the compiler,
off the workers through `spawn_blocking`.
The log keeps the `.mpk`'s hash; a node that runs a release it does not hold fetches it itself
(`Node::release_wasm`: the registry for a registry release, never a peer; a peer for an upload),
refuses bytes whose hash differs, and verifies them again.
A service may also ship a compute component (`compute` in the manifest): it is prepared on
`Node::compute_engine` only (never the replica engine), and the release is refused `400
COMPUTE_ABI_MISMATCH` unless its ABI lists exactly the main ABI's compute methods, each with the
same caps, and `400 BAD_BUNDLE` when it imports outside the compute world or its ABI is not the
compute world's.
A release without one installs and its app runs calls; it cannot run compute.
A single-service package may ship the compute component alone (no `wasm`):
`PackageVersion::components` is `ComputeOnly`, `services` is empty and `compute[""]` holds the hash.
Install skips the ABI agreement and instead needs at least one compute method (`400
NO_COMPUTE_METHODS`).
It is installed only once every node runs this release (`409 CLUSTER_NOT_UPGRADED`,
`require_upgraded_nodes`): an older node drops `components` and would apply it as an app's release.
Every app-level lookup reads `PackageVersion::app_parts` (the services, or the compute map when
compute-only), so a compute-only app's `bundle` and `compute_bundle` are both the compute hash.
Such an app has `AppRecord::components = ComputeOnly`: it has no app group state, and a call, view,
intent, init or tick is `422 NO_APP_COMPONENT` (`AppRecord::require_app_component`).
An upgrade between compute-only releases only moves the directory record; one that adds or drops the
app component is `409 COMPONENTS_CHANGED`.
A release may ship pipelines (`pipelines` in the manifest or a service; `packages/pipelines.rs`).
Install compiles each (`calimero_pipeline::compile`) and checks it against an `Env` with the module
`self` (the package's compute methods and caps; the default for a step that names none), one module
per other package a step names (`module: <package>[@<version>]`, resolved by `Node::resolve_modules`
to a release `SystemState::may_pin` allows (the installer may use it, and it is not recorded private, the operator's, of the same signer, or private to every organization the installing private release is for, judged on the release as the install leaves it; an install again of a release resolves its existing pins), newest when no version, that ships one compute component, else
`UNKNOWN_MODULE`; `InstallPackage` judges `may_pin_all` again once the logged cluster version brings `Feature::PrivateReleases`; regressions `a_private_module_is_pinned_only_into_a_release_private_to_its_organizations`, `system::tests` and `tests/component_packages.rs`), and the cluster's pool memory ceilings; anything else is `400 BAD_PIPELINE` with
`details: [{file, path, code, message}]` for every error, a package with pipelines but no compute
component included (`NO_COMPUTE`) and a repeated name (`DUPLICATE_NAME`); a named service declaring
pipelines is `422 PIPELINES_NEED_ONE_SERVICE`, as start refuses it.
`PackageVersion::pipelines` maps name to `PipelineRef { hash, worstCaseFuel }` (hash of the
canonical JSON, fuel a decimal string, `modules`: reference as written to `ModulePin { package,
version, compute }`, pinned at install so a newer module release moves nothing until the pipeline's
package is released again; `InstallPackage` applies only while every pinned release is still
installed, and `UninstallPackage` of a pinned release is `409 MODULE_IN_USE`,
`SystemState::module_pinned`); the canonical JSON is stored as a blob by its hash beside the wasm
parts, and `Node::pipeline_json(hash)` reads it, else recompiles it from the release's `.mpk`.
Such a release is installed only once every node runs this release (`409 CLUSTER_NOT_UPGRADED`).
`GET /packages/{package}/{version}/pipelines` (who sees the release) answers `{ name: { hash,
worstCaseFuel, modules, pipeline } }`; `meroctl app pipelines`.
`GET /packages/{package}/{version}/capabilities` (the same access: who sees the release; a
session bound to the package sees what its account does, every release only for a record from before `visibility`, `SystemState::sees_release_from`) answers the release's capability card before any app of it exists: `{
package, version, service, bundle, mpk, manifestHash, signer, name, author, outbound, abi }`, the
first eight keys as `consent_page::diff::side` shows each side of an upgrade's sheet, `outbound` the
manifest's sorted prefixes and `abi` the service component's embedded `calimero:abi` verbatim
(`null` when it embeds none), read from the verified `.mpk` through
`consent_page::release_capabilities` (cached with the consent page's release facts).
The card is of one service: `?service=<name>`, else the release's only one (named or not; the card's
`service` says which), and an unknown name, or no name on a release with several, is `400
NO_SUCH_SERVICE` listing the release's services (`packages::no_such_service`, as
`resolve_release_parts` answers).
A name over `MAX_SERVICE_QUERY_BYTES` is `400 BAD_REQUEST`, checked before the release is read.
`release_facts` reads a compute-only release's ABI from its compute component, as `GET
/apps/{app}/abi` does from the running bundle.
`PackageVersion::compute` maps service to that hash, whose `BundleRecord` has `PackageRef::compute =
true`: never a service (`resolve_release`, `CreateApp` and `UpgradeApp` refuse it), and fetched by
`release_wasm` like a service.
`AppRecord::compute_bundle` carries the running release's compute hash next to `bundle`.

### An instance's release

Code: `AppRecord::release`, a `system::PackageRef`.

The package release it runs, set at create (the version named, the newest visible one, or the
deployment's offer) and by every `UpgradeApp` (one app, an org or publisher run, the operator's, the
consent page's), which also checks that the release ships the bundle (`SystemState::release_ships`).
A frontend ships in its release's `.mpk` and works with that release's backend only, and releases
may share a WASM, so `bundle` alone does not say which release runs: approving a release approves
its frontend, and moving to a release with the same WASM is an upgrade like any other (same
authority, consent and record; an org run writes `UpgradeApp` without running anything on the app's
group, and notes a refusal as failed).
`Node::release_of_app` and `report::release_of_app` read it; a record without it (from before, or a
raw upload) falls back to the only release shipping its bundle (`SystemState::running_release`), and
to none when several share the WASM, never to the first recorded.
`GET /apps` reads it too.
The apply-side `SystemState::governing` still takes the bundle's first recorded release for such a
record.
`UpgradeRecord::from_release` / `to_release` name both ends of an upgrade.
Releases may share an app component and differ in compute, so create and upgrade carry the compute
hash of the release they name (`resolve_release_parts`), and apply only checks that a release ships
that pair (`SystemState::ships_compute`).
A create or upgrade by bundle hash alone resolves the compute part of the releases that ship that
app component (`SystemState::compute_of`), `400 AMBIGUOUS_COMPUTE` when they differ, and answers
`compute: false` when none ships one.
The app's log carries the pair too: `ComponentCmd::Init` and `Upgrade` name `compute_bundle` beside
`bundle`, and apply keeps it in `ComponentHead::compute_bundle`, so a run pins the pair the group
runs and never the system record's, which a delayed or failed system write may leave behind.
A release's parts count against the bundle quota each at its own size (`PackageVersion::part_sizes`;
a release from before counts the whole `.mpk` per part).
`POST /apps { package, version?, service? }` creates from a release (installing it from the registry
first); upgrade takes `{ version }`; `DELETE /apps/{app}`; `DELETE /packages/{p}[/{v}]` is refused
while an app runs the release (a WASM another release ships stays).
It takes only releases the actor may use, one it may not answering as missing (`api::packages::refuse_unusable`, before anything is logged, a missing package too, and `UninstallPackage` at apply once the logged cluster version brings `Feature::PrivateReleases`, so earlier entries replay as they applied; `manages_package` keeps a first installer to the origins of a package with a release it may use, the same way; regressions `an_uninstall_takes_only_the_releases_its_actor_may_use`, `a_first_installer_uninstalls_only_the_releases_it_may_use`, `an_uninstall_of_a_release_its_actor_may_not_use_logs_nothing`, `a_first_installer_manages_origins_only_while_it_may_use_a_release`).
Raw `POST /bundles` is development only (`allow_unsigned_bundles`, on with `--dev`).

**Who sees a release** (`SystemState::sees_release`, the right to use it): everyone for a release the operator installed (the catalog), and the operator for its own installs only; a public release (`visibility: public`): everyone; a private one: the members of an organization in `PackageVersion::orgs` (an installer only while such a member), or with `orgs` empty, its installing accounts.
A release recorded before `visibility` keeps the earlier rule: its installers (`installed_by`, `PackageVersion::installers`), accounts sharing an organization with an installing account, accounts that reach an app running it, and a session bound to the package's frontend (`sees_release_from`).
Reading the release an instance runs (`report::release_of_app`) is `SystemState::reads_release`: who sees it, or reaches an app running it (the package and version the app's record names, so a release sharing its WASM, in that package or another, is not read; for a record naming none, only a release not recorded private, so `GET /apps/{app}/update`'s `running`, `GET /apps`' `package` and `version` and the reports never name a private sibling to one who only reaches it: regressions `reaching_an_app_by_its_bundle_never_names_a_private_sibling`, `the_app_list_never_names_a_private_sibling_sharing_the_wasm`, `an_outbound_approval_never_reads_another_packages_release_of_the_same_wasm`, `the_app_list_filters_by_the_package_an_instance_runs`, `system::tests::reaching_an_instance_never_reads_another_packages_release_of_its_wasm`, `report::tests` and `tests/cluster.rs`).
A route (`src/api`, `src/consent_page`) reads a release a client names only through `SystemState`'s lookups: `release_used`, `releases_used` (with a bound session's `frontend`), `package_used`, `newest_used` (use), `newest_read` (read) and `release_offered_to` (a deployment's offer that still serves).
The gate `tests/it/release_lookups.rs` (`routes_read_releases_through_the_rule`) fails on any other read of `packages` or `versions` there, or of a bundle record's release (`bundles`, which names the release its WASM was first recorded from; filter by `report::release_of_app`), unless its `READS_ALLOWED` names the line and why no client names that release.
For anyone else it is not installed: `GET /packages[/{p}]` and `GET /ops/packages` leave it out (`404` by name), `resolve_release` treats it as missing (a registry install makes it theirs; an upload answers as a missing release), a bundle hash it ships is an unknown bundle (`sees_bundle`; its uploader, which a release's first installer is too, counts only beside a release recorded before `visibility`), outbound approval (`POST /orgs/{org}/outbound`, the consent page's `outbound`) approves and shows the prefixes of the newest release the caller reads (the operator's cluster-wide one, the newest of all; `PackageRecord::latest_where`; `SetOutboundApproval` at apply once the logged cluster version brings `Feature::PrivateReleases`), `404` with none; the page's `requestedBy` and its `returnTo` origins read that release too (regression `an_outbound_approval_takes_the_newest_release_its_approver_reads`), and upgrade runs skip it (`api::upgrade_sees`; the operator's: its own or the app owner's).
Frontends stay public by name; the newest release's display name and author reach a session bound to the package (the consent page's `requestedBy`) only when its account reads that release, an app team (`ScopeApps`, `MoveApp`, `createOrg`'s) is named after the newest release its maker may use (`PackageRecord::latest_where`), and a package named for one with no such release answers `no such package` (API, and apply once the logged cluster version brings `Feature::PrivateReleases`; `createOrg` then offers no app team; regressions `an_app_team_reads_only_the_releases_its_actor_may_use`, `an_app_team_of_a_private_package_answers_as_a_missing_package`), and a sign-up on the package's origin (`passkeys::app_name`) names the newest release that is public or the operator's; else they answer as for a release without them (`a_strangers_bound_session_never_shows_a_private_releases_name`, `a_sign_up_names_the_newest_release_open_to_anyone`).
Regressions: `a_private_package_is_listed_only_to_accounts_that_may_use_it`, `a_release_from_before_installers_reads_and_records_who_installs_it_again`, `a_private_release_is_used_only_in_the_organizations_it_was_installed_for` (both `system::tests` and `tests/cluster.rs`), `a_release_recorded_before_visibility_keeps_the_rule_from_before`, `reaching_an_instance_reads_its_release_but_does_not_use_it`, `a_bound_session_does_not_open_a_package_its_account_cannot_see`, `another_orgs_account_cannot_install_a_private_package_from_the_registry`, `a_release_is_fetched_again_with_the_credential_only_while_it_is_private`, `an_anonymous_fetch_refused_as_unauthorized_goes_on_with_the_credential`, `an_outbound_approval_never_reads_a_release_its_approver_cannot_read`, `an_outbound_sheet_never_shows_a_release_its_asker_cannot_read`.

### Deployments

Code: `SystemState::deployments`, `system::Deployment`, `Offer`.

An owner's (`Deployer`: account or org) list of offered apps, app name -> one installed
`package@version`.
Managed by whoever `acts_for` the owner (the account; org-wide `MANAGE_APPLICATION`), each change
with that actor's passkey consent judged at apply: `CreateDeployment` (`POST /deployments { name,
owner }`, `cluster / __create_deployment / { name, owner }`; the id is `system::deployment_id` of
the consent's nonce), `OfferApp` (`POST /deployments/{id}/apps`, `deployment:{id} / __offer_app / {
app, package, version }`; the release installed and seen by the actor; an entry keeps its package),
`WithdrawApp` (`DELETE /deployments/{id}/apps/{app}`; refused while an instance from it runs that
package; the release stays installed), `DeleteDeployment` (`DELETE /deployments/{id}`; nothing
offered, no instance from it).
Create and offer need `may_deploy` for the actor where deployments are granted.
Bounds: `MAX_DEPLOYMENTS_PER_OWNER`, `MAX_DEPLOYMENTS`, `MAX_APPS_PER_DEPLOYMENT`; names
`deployment_name_fits`, app names and ids `deployment_segment_fits`.
`POST /apps { deployment, package, version? }` creates from the offer (`api::offered_bundle`, no
install, no grant, no `sees_release` for the creator; an offer serves, for a create or an upgrade, only while someone who `acts_for` the owner may use its release, `SystemState::offer_serves`, else `400 NOT_OFFERED`; apply is unchanged and instances made before keep running; regression `an_offer_outlives_no_offerer_who_may_no_longer_use_its_release`) and records `AppRecord::deployment`; `CreateApp` checks the
offer again (`offers_bundle`).
The managers decide which release its instances run; an owner only accepts it: `upgrade_app`
resolves an instance's target from the offer (`api::apps::offered_bundle`, the package it runs;
naming no version accepts the offer), and another version, another package or a raw bundle is `409
OUTSIDE_DEPLOYMENT` (`node::outside_deployment`) before the step-up; `run_upgrade` and an org,
publisher, operator's or unit run judge the same (`SystemState::within_deployment`: once the logged cluster version brings `Feature::PrivateReleases`, only an offer that still serves, `offer_serves`, as an automatic update's deployment branch, `auto_update_allows`; regressions `an_offer_that_no_longer_serves_moves_no_instance`, `the_operators_run_follows_no_offer_that_no_longer_serves`, `an_update_never_applies_on_its_own_from_an_offer_that_no_longer_serves`, `system::tests::an_offer_that_no_longer_serves_moves_no_instance_from_the_version_that_brings_the_rule`, `system::tests::a_deployment_instance_updates_on_its_own_only_from_an_offer_that_serves`), and `UpgradeApp` refuses it
at apply when its `in_deployment` flag is set (`Feature::UpgradeInDeployment`, rc.32,
`in_deployment_rule`) or the logged cluster version brings it (`SystemState::cluster_brings`);
earlier entries replay as they applied.
The customer accepts the offer from inside the app: the consent page's `upgrade` (and `upgradeUnit`)
of a deployment instance takes `toVersion` as optional (`UpgradeSubject::to_version`) and resolves
the target from the offer (`consent_page::requested_release` over `api::apps::offered_bundle`; no
`sees_release`), any other version `409 OUTSIDE_DEPLOYMENT`; a unit's member takes the target its
instance's plan gave it, from the state.
Another instance still names it (`400 VERSION_REQUIRED`).
The frontend learns of it from `GET /apps/{app}/update` ([upgrades](/protocol/upgrades/)).
`UninstallPackage` refuses an offered release (`offered`); `DeleteOrg` refuses an org that owns a
deployment.
Reads: `GET /deployments` (what the caller manages), `GET /deployments/{id}` (public, on fresh
state: name, owner kind and name, offers), `GET /deployments/{id}/orgs` (managers, `sys_fresh`:
customer orgs' id, name, instance count, apps and versions, first created).

### Deployment secrets

Code: `SystemState::deployment_secrets`, deployment id -> name -> `component::InstanceSecret`;
`api/deployments.rs`: `deployment_secrets`, `deployment_secret_set`, `deployment_secret_clear`.

A manager sets a value of a secret a release the deployment offers declares (`SetDeploymentSecret`,
`PUT /deployments/{id}/secrets/{name} { value }`, `deployment:{id} / __set_secret / { name,
fingerprint }`; `authorize` works the fingerprint out again from the value the entry carries, so no
node swaps it; refused `404 UNDECLARED_SECRET` otherwise, `system::UNDECLARED_SECRET`) or clears it
(`ClearDeploymentSecret`, `__clear_secret / { name }`).
Bounds: `component::MAX_SECRET_VALUE_BYTES` (shared with instance secrets),
`MAX_SECRETS_PER_DEPLOYMENT`, `MAX_DEPLOYMENT_SECRETS` (the system state is one checkpoint).
`DeleteDeployment` drops them.
A value whose name no offer declares any more stays, unused, until cleared.
`Feature::DeploymentSecrets` (rc.32).
A name a release an offered one references declares is taken too (`SetDeploymentSecret { used: true
}`, which the API sets only when no offered release declares it; `Feature::DeploymentUsedSecrets`,
rc.32; an entry without it is judged by the offers alone, as before):
`SystemState::deployment_uses_declare` over `used_releases` (every installed release of each
`PackageVersion::uses` package inside its range that someone acting for the deployment's owner may use, `offer_serves`, or that the offered package's signer signs, `same_signer`, as `unit_members` admits a member, once the logged cluster version brings `Feature::PrivateReleases`; regressions `a_deployments_secrets_never_name_a_used_release_its_owner_may_not_use`, `system::tests::a_used_release_its_owner_may_not_use_declares_no_deployment_secret`, `system::tests::a_member_of_its_offers_signer_reads_the_deployments_secret`).
`uses` (`system::ReleaseUse`: package, range, version) is recorded by `InstallPackage` only once the
feature is active (`record_release` drops it before; `SystemCmd::features` names it), and installing
the same `.mpk` again fills it into a record that has none.
`GET` adds `declaredBy` (`deployment_declarers`) and lists the offered apps that reach a name
through `uses` in `apps`.
Lookup: `Node::outbound_for` -> `component::run_secrets`: the instance's own value, else its
deployment's (`SystemState::deployment_secrets_of`, this node's system state at run time, not the
app's log), else the operator's in the gate; each only for a name the release declares, and attached
by the gate where its binding says (`PackageVersion::secrets`, one host and one header or body field
each; the shape since 1.0.0-rc.37, a hard cutover).
The deployment's only for a run of a release of a package it offers or an offered release references
(`SystemState::deployment_covers`, over `used_releases`; any version: its signer is pinned): its
managers set values for the code they ship, and a record that somehow runs other code (a customer's
own package declaring the name for its own host) gets none.
Upgrades keep instances on the offer (Deployments above).
Never answered: `GET /deployments/{id}/secrets` gives fingerprints, `setBy`, `setAt`; an instance's
`GET /apps/{app}/secrets` only `source: deployment`; `SecretValue`'s `Debug` hides it; `apply`'s
answers and refusals never carry it.

### Instance secrets

Code: `api/apps.rs`: `app_secrets`, `app_secret_set`, `app_secret_clear`; `component.rs`:
`ComponentCmd::SecretSet`/`SecretClear`, `InstanceSecret`, `rows::CSECRET`.

An app's owner (or whoever manages its organization's apps) sets its own value of a secret its
release declares (`PackageVersion::secrets`), with a step-up over `{ name, fingerprint }`.
The host command `__secret_set` / `__secret_clear` writes one hidden row on the app's replicas
(`AppMachine::instance_secrets`), which no host function reads; a call's or tick's run reads it with
the state it sees (`RunExtras::secrets`), an action reads it on the leader, and `outbound_for` hands
it to the gate (`calimero_outbound::OwnSecrets`, which wins over the operator's for a declared name,
only to its declared hosts; with the instance's deployment's values below its own,
`component::run_secrets`, Deployment secrets above).
`GET` answers through the leader's reserved view `__secrets`: fingerprints, never values.
Set or clear only once every node runs this release (`require_upgraded_nodes`).

### Units

Code: `api/apps.rs`: `create_instance`, `unit_members`; docs: build packaging-signing, `uses`.

Creating an instance of a release whose signed manifest has `uses` with `mode: create` first creates
each referenced app (same organization and owner, the release its lock pinned or the newest
installed one in range that the creator may use (`sees_release`), the instance's own signer published, or, for an instance from a deployment, that deployment offers; else `409 USES_NOT_INSTALLED`, answered as for a package not installed; the member's create runs exactly that release (`CreateAppBody::unit_release`, `serde(skip)`); a unit's preview (`egress::release_unit`) and upgrade (`unit_plan`, `egress::update`) pick by the same rule for the instance's owner and deployment; at most `MAX_UNIT_DEPTH` deep), then records
them on the instance (`AppRecord::links`, `Feature::AppLinks`, rc.31) and, when the release's `init`
takes `links`, passes their ids in `initArgs` (a client's own `links` there is refused).
A failure after a member was made leaves it in place.
Regressions: `creating_an_instance_creates_the_apps_its_release_uses`, `a_unit_never_creates_a_member_from_a_private_release_its_creator_cannot_use`, `a_deployments_unit_never_creates_a_member_from_a_private_release_it_does_not_offer`, `a_deployments_unit_creates_a_member_from_a_release_the_deployment_offers`, `a_deployments_unit_takes_no_member_from_an_offer_that_no_longer_serves`.
A unit is one (`Feature::WholeUnits`, rc.32): members of an instance from a deployment carry its
deployment (billed to its developer, its secret values), their `CreateApp` naming the offer of the
instance's release that covers them (`unit_offer`, checked at apply in place of the member's own
release; set by the node, `CreateAppBody::unit_offer` is `serde(skip)`; the member's release is the one `unit_members` chose, above).
`DELETE /apps/{app}` of an instance deletes its whole unit (`SystemState::unit_of`: its `links`,
transitively, as they exist; `DeleteApp { members }` names them and apply refuses a list that
differs, `UNIT_NOT_AS_NAMED`, or an actor who may not delete each one) and answers them in
`members`; a member (`unit_parent`: an app whose `links` hold it) is refused alone, `409
UNIT_MEMBER` at the API and `UNIT_MEMBER` at apply.
The API sends `members` once the logged cluster version brings the feature, or for an instance with
members (then `409 FEATURE_NOT_ACTIVE` below it); entries without either field replay as before.
A member names its instance with `env::unit_of` (WIT `context.unit-of`, 0.5.5;
`SysDirectory::unit_of`: the app whose `links` hold it, derived from the system state, so nothing
new is stored and it is `None` once the instance is gone); Confidential KV and Private Inference
releases take `app:<unit_of>` as their admin.
A unit upgrades in one consent (`api/upgrades.rs`: `app_upgrade_unit`, `POST
/apps/{app}/upgrade-unit`): a run whose consent (`org:<org> / __upgrade_unit / { app, package,
version, targets }`) names each member's own release (`UpgradeRun::targets`, `RunTarget`,
`Feature::UnitUpgrade`); apply derives its apps from the instance's `links` (`upgrade_run_apps`),
and `run_may_move` and `UpgradeApp { run }` judge a member by its target (`UpgradeRun::target_of`).
A member upgraded alone off its instance's range is refused at the API (`refuse_off_unit_range`,
`409 OUTSIDE_UNIT_RANGE`).
`unit_plan` reads nothing of a target its account may not use: it answers as `resolve_release` answers a missing release (for an instance from a deployment, anything but its offer that still serves is `409 OUTSIDE_DEPLOYMENT`), before any member, target or passkey (regression `a_unit_upgrade_answers_a_release_its_owner_may_not_use_as_a_missing_one`).
The consent page's `upgradeUnit { app, toVersion }` (`unit_upgrade_request`) builds one model from
`api::unit_plan` and each app's `upgrade_request` sheet (members skip the package-bound session's
`within`: the instance created them), `Action::UpgradeUnit` is stale when a bundle or the targets
moved, and `act` runs `api::upgrade_unit`.
An `attach` reference holds an app its owner already runs (`AppRecord::attached`, apart from
`links`, so a unit's upgrade, `upgrade_run_apps` and `refuse_off_unit_range` never touch it):
`SystemCmd::LinkApp { app_id, name, target }` (`Feature::AttachApp`, rc.31; consent `<app> / __link
/ { name, target }`, `system::link_app_args`; `target: null` detaches), judged at apply: whoever
manages both apps, another app of the same organization, a reference name
(`calimero_bundle::is_use_name`) that is not a unit member's, at most `MAX_ATTACHED`.
`PUT|DELETE /apps/{app}/links/{name}` (`api::apps`: `app_link`, `app_unlink`) also check the name is
an `attach` reference of the release the app runs (`release_uses`; `409 NOT_AN_ATTACH_REFERENCE`)
and the app runs its package (`409 WRONG_PACKAGE`); one outside the range is attached and answered
`inRange: false`.
`GET /apps/{app}/links` lists each reference with what is linked, its release and `inRange`
(`link_row`).
Deleting an app detaches it everywhere (`remove_app`); an attached app is no unit member and is
never deleted with the instance.
The consent page's upgrade sheet adds `attachedOutOfRange` and the `attachedOutOfRange` attention
when the target release takes an attached app in another range (`attached_outside`).
Runs read links with `env::linked` (`SysDirectory::linked`: `links`, then `attached`).

### App frontends

Code: `app_host.rs`.

With `--apps-domain D` (`merod local`: `localhost`), each package's frontend is at `{label}.D`
(`app_host::label`, 52 base32 characters), from its release's `.mpk` (`Node::release_mpk`, verified
before a byte is served, opened ones cached, and so is a release shipping none;
`FrontendCache::get_or_load` runs one load per release and `FRONTEND_LOADS` at once).
Outermost layer: only `GET`/`HEAD` of files, `/` → newest release, `/app/{app}/` → the release that
instance runs (`AppRecord::release`; for a record from before, the newest release, by
`compare_versions`, shipping its WASM), `/d/{deployment}/` → `/{version}/?deployment={id}` of the
release it offers (looked up again on fresh state when nothing matches); every redirect keeps the
request's query (after the `deployment` it adds), so `/?invite=...` reaches the page with its token,
client routes and relative tails served as the bundle's, its CSP plus the cluster's API origins and
the attestation mirror (`ATTESTATION_MIRROR`, where clients get the release's measurements and
Intel's collateral) in `connect-src`, `/.well-known/calimero.json` (the node's `cluster` and the
deployments offering the package); an unknown label under D is a 404, never a node route.
Each package is also at `{cluster_label(config.cluster, package)}.D` on its cluster, the same site
and origin (for mdma's hostname resolver; another cluster's label 404s).
Each deployment has its own host too, `{deployment_label(id)}.D` (`app_host::Site`): the one package
it offers (404 while it offers none or several), `/` → what `/d/{deployment}/` gives, `/d/` only for
itself, well-known `deployment` set and listed first; the deployment API answers its `host`.
App origins (both kinds) pass CORS, and a passkey ceremony from one opens a session bound to its
package (`SessionClaims::app`, carried by refresh): `Principal::within` keeps it to that package's
apps (gate, app reads and writes, listings), `unbound`/`holder` refuse it credentials, API keys,
approvals, upgrades, uninstalls and uploads, organization, team, member and invite changes
(redeeming included), and an app's delete and access, and it creates instances of its own package
only.
The exception is its own package's teams (`Principal::within_team`, `OwnTeam`;
`Org::package_of_team`: the org's app team for the package or a team below it), so a chat app runs
its channels: `team_create` under one, `team_update` of a team below the app team (never the app
team: name, mark, openness; a move only within), `team_set_member`/`team_remove_member` on any of
them, `team_delete` below the app team when every app in its subtree is the package's, and
`app_access` of its package's app from one such team to another.
Authority is the person's, judged at apply as for any session.
Its step-ups come from its own origin only, over one of its package's apps, or `org:{org}` for
`BOUND_TEAM_STEP_UPS` (`__set_team_member`, `__remove_team_member`, `__delete_team`) over its own
package's team (`step_up` judges `within_team` again and refuses any other subject).

### Inspection

`GET /apps/{app}/storage` (keys, bytes, blobs, `lastWriteAt`), `GET /apps/{app}/abi` (the bundle's
embedded ABI), `GET /auth/usage` (the account's apps, bundle bytes, API keys, owned orgs, the
quotas, and `developerFuelToday`/`developerWritesToday`: today's runs of the apps the account is the
developer of), `GET /orgs/{org}/usage` (the same figures for the apps an organization is the
developer of, its admins only, D78), `GET /apps/{app}/usage` (a component's runs, owner and org
admins only; see [the usage book](/protocol/execution/)).
