An app instance runs one **bundle**: a WASM module named by
`hex(SHA-256(wasm))`. In production a bundle always comes out of a **package
release**: a signed `.mpk` (`calimero-bundle`) built with `cargo mero build`
and signed by its publisher with `mero-sign`. See
[Packaging & signing](/build/packaging-signing/) for building one.

## What a release carries

The `.mpk` manifest names the package, its version, its services (each a WASM
module; a single-service package has one unnamed service), a frontend, display
metadata, the `minRuntimeVersion` it needs, and the outbound URL prefixes it
declares. The manifest is signed by the publisher's key, and every artifact in
the archive is listed with its digest.

A release travels from its publisher to a registry, and from there to every
node that runs it, never from node to node: the node that installs it verifies
it before the system log records its hash, and each replica fetches and
verifies the same bytes again before running them. The installer is an
account (or an app's creator, since `POST /apps` installs a missing release
first) or the operator. An uploaded `.mpk` (`POST /packages`) skips the
registry and is spread to a majority of nodes instead.

There are two ways in:

- `POST /packages/install { package, version }` fetches `package@version` from
  the operator's registry (`--registry-url`, `calimero-app-downloader`'s
  `HttpRegistry`).
- `POST /packages` takes an uploaded `.mpk`.

Before the system log records anything (`InstallPackage`), the node that took
the request verifies the release (`Node::verify_release`):

1. The publisher's signature over the manifest and every artifact's digest
   (`calimero_bundle::VerifiedBundle`), and that it ships WASM at all.
2. `minRuntimeVersion` is not newer than this node's release
   (`CALIMERO_RELEASE_VERSION`).
3. The package's **pinned signer**: the first release of a package pins its
   publisher key (`did:key`); a release signed by any other key is refused.
4. Each service's WASM compiles.
5. A registry install got the package and version it asked for.

`apply` checks the signer pin again, refuses a version already installed with
other contents (the same release again is a no-op), and charges the `.mpk`'s
size to the installer's bundle quota (the operator's installs count against no
account). The log keeps, per release, the `.mpk`'s hash and size, where it came
from (`registry` or `upload`), each service's bundle hash, the metadata, and the
declared outbound prefixes.

:::note[Why a pinned signer]
A package's name is the identity apps, approvals and frontends refer to. Pinning
the first release's key means nobody but that publisher can ship a later
"version" of it into the cluster, and it is what outbound approvals are granted
to: `(package, signer)`.
:::

## Where the bytes live

- A **registry** release is never passed between nodes. Each node that needs
  to run it fetches it from the registry itself (`Node::release_wasm`), refuses
  bytes whose hash differs from the one the log recorded, and verifies the
  release again before using its WASM. That is the one-source rule: the
  registry is the only place a registry release comes from.
- An **uploaded** release has no registry. The `.mpk` is stored on a majority
  of nodes before the log records it; a node that lacks it fetches it from a
  peer, checks the recorded hash and verifies it again.
- Each service's WASM is also kept in the installing node's blob store under
  its bundle hash; other nodes extract it from the `.mpk` on first use.

## Creating, upgrading and removing

- `POST /apps { package, version?, service?, … }` creates an instance from a
  release; without a version, the newest installed one. If the release is not
  installed yet, it is installed from the registry first. A package with
  several services needs `service`.
- `POST /apps/{app}/upgrade { version }` moves an instance to another release
  of its package ([Upgrades](/protocol/upgrades/)).
- `DELETE /packages/{p}[/{v}]` removes a release, or all of them, and is
  refused while any app still runs one of its bundles. A bundle another
  release also ships stays, recorded under that release. Only whoever installed
  the package's first release (an account, or the operator) may uninstall.

## Development bundles

`POST /bundles` takes raw WASM (at most 16 MiB) with no publisher signature. It
is refused unless the node allows unsigned bundles (`--dev`, or
`allow_unsigned_bundles`). The node checks the WASM compiles, stores it on a
majority of nodes, then records `PutBundle { hash, size }`. Raw bundles have no
package, so they cannot be served as a frontend, cannot declare outbound
prefixes, and have no pinned signer.

## ABI facts

The node reads a bundle's embedded ABI (`services::BundleFacts`) for what it
acts on: which methods are `#[app::view]`, `#[app::handler]` and
`#[app::xcall]` entry points (and whom an entry point admits), which
`#[app::tee(every)]` timers to fire, and the state version and migrations an
upgrade plans from. Bundles built without `cargo mero build` embed no ABI and
get none of these.

## Frontends

With `--apps-domain D`, each package's frontend is served at its own origin,
`{label}.D`, where the label is 52 lowercase base32 characters of
`SHA-256("calimero.app-host.v1\0" ‖ package)` (`app_host::label`). `merod local`
uses `localhost`.

- The files are the release's own `.mpk` frontend, fetched like its WASM and
  verified against the publisher's signature before a byte is served.
- `GET /` redirects to the newest release's entry; `/{version}/{path}` serves a
  file, falling back to the entry for client-side routes. `/.well-known/calimero.json`
  names the package, its releases and the cluster's API URLs.
- Only `GET` and `HEAD` of files. An unknown label under D is a `404`, never a
  node route. Responses carry a fixed content security policy with the cluster's
  API origins added to `connect-src`.

**Why its own origin.** An app's page is third-party code. Served from the
cluster's own origin, it could reach anything the signed-in account can. On its
own origin it is a separate site to the browser, and a passkey ceremony from it
opens a session **bound to its package**: that session reaches only instances
of that package, creates only instances of it, and is refused credentials, API
keys, approvals, upgrades, uninstalls and uploads ([Accounts, passkeys &
sessions](/protocol/identities/#which-credential-may-do-what)). Its step-ups
come only from its own origin.
