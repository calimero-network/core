This page is the practical loop: build, run, test, and the conventions your PR
has to satisfy before it merges. Commands here are the same ones CI runs (see
`.github/workflows/ci-checks.yml`).

## Prerequisites

The toolchain is pinned in `rust-toolchain.toml` (stable Rust). To build and run
example apps you also need the WASM target:

```sh
rustup target add wasm32-unknown-unknown
```

## Build

```sh
# Build the whole workspace (debug)
cargo build

# Release build
cargo build --release

# Typecheck without producing artifacts
cargo check --workspace
```

Building the example WASM apps is a separate step (apps compile to
`wasm32-unknown-unknown`):

```sh
# Build one app; `cargo mero` embeds the ABI a bare `cargo build` leaves out
PATH="$(scripts/setup-cargo-mero.sh):$PATH"
cargo mero build --manifest-path apps/kv-store/Cargo.toml

# Build all example apps
./scripts/build-all-apps.sh
```

<Aside type="note">
  CI's build step runs both: `./scripts/build-all-apps.sh` followed by
  `cargo build --workspace --all-targets --tests`. Building the apps first is
  expected — several workspace tests load the compiled WASM artifacts.
</Aside>

## Run local nodes

`merod` is the node daemon; each node is initialized once, then run. To bring up
two nodes that talk to each other:

<Steps>

1. Initialize and run the first node:

   ```sh
   merod --node node1 init --auth-mode proxy --server-port 2428 --swarm-port 2528 --mdns
   merod --node node1 run
   ```

   `--auth-mode proxy` keeps these local nodes free of a login.
   It authenticates no caller, so any page served from localhost can reach the admin API: use it only on a development machine.
   Without it, `init` defaults to embedded auth and needs admin credentials or `--no-admin`.

2. Initialize the second node so it can find the first:

   ```sh
   merod --node node2 init --auth-mode proxy --server-port 2429 --swarm-port 2529 --mdns
   merod --node node2 run
   ```

   `--mdns` is on both, and it is load-bearing rather than tidy-up. mDNS is off by
   default, and two nodes with no bootstrap peer and no rendezvous have no other
   way to find each other. Leaving it off does not fail cleanly: the nodes start,
   the join is accepted locally, and it then times out waiting for a group key —
   so it reads as a broken join rather than as two nodes that never met.

   To point the second node at the first explicitly instead, you need node1's
   **peer id** — a bare `/ip4/…/tcp/…` is rejected at startup with "Failed to
   parse peer id from addr":

   ```sh
   # with node1 running
   curl -s localhost:2428/admin-api/network/status | jq -r .localPeerId

   merod --node node2 init --auth-mode proxy --server-port 2429 --swarm-port 2529 \
     --boot-nodes /ip4/127.0.0.1/tcp/2528/p2p/<node1-peer-id>
   merod --node node2 run
   ```

3. Drive nodes from the CLI with `meroctl`, or turn up logging with `RUST_LOG`:

   ```sh
   RUST_LOG=debug merod --node node1 run
   ```

</Steps>

<Aside type="note">
  Node state and config live under `~/.calimero/<node>/` (e.g.
  `~/.calimero/node/config.toml`), outside the repository.
</Aside>

## Test

```sh
# Run the full workspace test suite
cargo test

# CI runs with output shown
cargo test -- --nocapture
```

<Aside type="caution">
  Some networking tests bind to real interfaces. CI sets a `TEST_HOSTS`
  environment variable (a comma-separated list including `127.0.0.1`, `0.0.0.0`,
  and the machine's primary interface IP). If host-dependent tests fail locally,
  set it yourself, e.g. `TEST_HOSTS=127.0.0.1,0.0.0.0`.
</Aside>

## The pre-PR gate

Run every check CI's required `Rust` status waits on, read straight from
`.github/workflows/ci-checks.yml` so the list cannot drift:

```sh
./scripts/check-like-ci.py                 # all of it
./scripts/check-like-ci.py --list          # what it runs, in order
./scripts/check-like-ci.py --only clippy   # a subset, by name
```

The rest of the Definition of Done (proof for a bug fix, docs, review) is in
the root [`AGENTS.md`](https://github.com/calimero-network/core/blob/master/AGENTS.md#definition-of-done).

<Aside type="note">
  A pre-commit hook runs `cargo fmt --check` on staged Rust files. It installs
  itself during any `cargo build` / `cargo test` via the `calimero-git-hooks`
  build script — no husky or pnpm required, and it works from linked git
  worktrees. The hook sources live in `.githooks/`. To format manually, run
  `cargo fmt`.

  Migrating from the old husky setup: if `git config --get core.hooksPath`
  prints `.husky`, clear it once with `git config --unset core.hooksPath`.
</Aside>

## Commit & PR conventions

Commit subjects and PR titles follow the [commit rule](https://github.com/calimero-network/core/blob/master/CODING_STANDARDS.md#commits)
in the coding standards.

For pull requests:

- The project uses a **fork-and-pull** workflow; base your PR on the `master`
  branch.
- A PR should focus on **either functionality or style, not both**.
- PRs must follow the template, with **Description**, **Test plan**, and
  **Documentation update** sections, and link any related issue.
- Maintainers **squash-and-merge** approved PRs; resolve each review
  conversation as you address it.
