release-v2 is tested in layers that trade scope for speed. Most of the node is
covered by real clusters in one process: three nodes, sealed channels, real
WASM, driven only through the client. Multi-process behaviour (crashes,
freezes, restarts, upgrades) is covered by merobox scenarios.

| Layer | Where | What it proves | Speed |
| --- | --- | --- | --- |
| Unit tests | `#[cfg(test)]` in each crate | One module's logic: config merging, key sources, quotas, presence rules, outbound gates | Milliseconds |
| Raft engine | `crates/log` | Replication, failover, restart from disk, learner catch-up, snapshot streaming, no plaintext on disk, the `log.redb` migration | Seconds |
| Cluster | `crates/cloud-node/tests/cluster.rs` | The node end to end in one process: sign-up, installs, calls, views, events, orgs and teams, upgrades and migrations, blobs, follow-ups, governance, replica moves | Seconds to minutes |
| CLI | `crates/merod/tests/cli.rs`, `crates/meroctl/tests/cli.rs` | `merod init/config/run/inspect` through the binary; every `meroctl` command group against a local cluster | Seconds to minutes |
| App logic | `TestHost` in `crates/sdk/src/testing.rs`, `converge` in `crates/storage/src/testing.rs` | An app's methods, events and migrations; that a state type converges | Milliseconds |
| Scenarios | merobox `cloud-v2` backend | Separate `merod` processes: crash, freeze, restart and upgrade under load | Slow |

Use both ends. A green cluster test does not prove a process restart or a
frozen leader behaves, and a green scenario does not localize a logic bug.

## Fixtures

The cluster and CLI tests load compiled apps from
`target/wasm32-unknown-unknown/app-release/`. Build them first:

```bash
cargo build -p kv-store -p org-gated -p outbound-probe \
  --target wasm32-unknown-unknown --profile app-release
PATH="$(scripts/setup-cargo-mero.sh):$PATH"
for a in blobs kv-store-with-handlers search-chat xcall-example tee-cards tee-dice \
  migrations/migration-suite-v1 migrations/migration-suite-v2-add-field \
  migrations/scenario-migration-check-fail-v1 migrations/scenario-migration-check-fail-v2; do
  cargo mero build --manifest-path "apps/$a/Cargo.toml"
done
```

The `cargo mero` builds carry the embedded ABI the node reads for handlers,
timers, xcalls, search and migrations. `KV_STORE_WASM` points the tests at
another `kv_store.wasm`.

## Running the tests

```bash
cargo test -p calimero-cloud-node                 # the cluster tests
cargo test -p calimero-cloud-node --test cluster teams_work_like_v1_subgroups -- --nocapture
cargo test -p merod -p meroctl                    # the CLI tests
cargo test -p calimero-log
cargo test -p calimero-cloud-client -p calimero-identity -p calimero-sealed
cargo test -p calimero-outbound --features outbound-testing
cargo test -p calimero-kms-client --features mock-attestation
cargo test -p calimero-tee-attestation --features mock-attestation
cargo test --workspace                            # everything
```

[cargo-nextest](https://nexte.st/) runs the workspace faster
(`cargo nextest run --workspace`, then `cargo test --workspace --doc` for the
doctests it skips).

<Aside type="caution">
  Cluster tests start several nodes on free local ports and use real WASM; run
  them on Linux. A test that fails with "build kv-store for wasm32 first" is
  missing a fixture, not broken.
</Aside>

### Writing a cluster test

`crates/cloud-node/tests/cluster.rs` builds clusters with the real `run`,
mock attestation and a soft authenticator, and drives them only through
`calimero-cloud-client`, as an SDK user would. Write a new test there when the
behaviour crosses the API: start the cluster, sign up, do the thing, assert on
what the client sees. Name it for the behaviour
(`teams_work_like_v1_subgroups`,
`a_node_added_to_a_running_cluster_hosts_replicas`).

## App logic: `TestHost` and `converge`

Unchanged from v1. [`TestHost`](https://github.com/calimero-network/core/blob/master/crates/sdk/src/testing.rs)
runs an `#[app::state]` type as plain Rust: `call`, `view`, `events()`,
`logs()`, `migrate`, `set_caller_org`. It does not run xcalls, networked blobs
or event-handler dispatch. `converge` / `converge_app` in
[`crates/storage/src/testing.rs`](https://github.com/calimero-network/core/blob/master/crates/storage/src/testing.rs)
asserts that a state type reaches the same root on N in-memory replicas under
reordered operations. The app-author guide is [Testing your app](/build/testing/).

<Aside type="note">
  On release-v2 an app instance's calls are applied in one order by its Raft
  log, so convergence under concurrent writes matters less for the node than it
  did for v1; it still matters for code that also targets v1.
</Aside>

## Scenario tests with merobox

[merobox](https://github.com/calimero-network/merobox)'s `cloud-v2` backend
(its `release-v2` branch) starts one `merod` process per node and runs YAML
scenarios: deploy, call and read as several accounts, then crash, freeze,
restart or upgrade nodes and check the app keeps its data and answers within a
time budget.

```bash
MEROD_V2_BINARY=target/debug/merod \
KV_STORE_WASM=target/wasm32-unknown-unknown/app-release/kv_store.wasm \
merobox cloud run workflow-examples/cloud-v2/frozen-leader.yml
```

The scenarios and their step reference are in merobox's
`workflow-examples/cloud-v2/`. A node behaviour that only shows across
processes (the bounded forward to a frozen leader is the example) gets its
regression scenario there.

<Aside type="caution" title="Older scenario files">
  The YAML files under `apps/*/workflows/` and `workflows/` in this repository
  were written for v1's node and merobox's Docker backend (`merobox bootstrap
  run`). They exercise v1 concepts (gossip sync, key delivery, namespace
  governance) that release-v2 does not have; do not take them as release-v2
  coverage.
</Aside>

## What scenario tests cannot catch

Every node in a merobox run is the same build on fresh state, so it never
tests data written by an older version. A change to an on-disk or wire format
needs its own migration test, as `calimero-log`'s `migration_tests.rs` does for
the `log.redb` store.

## Proving a fix

<Steps>

1. **Reproduce first, at the layer a user hits it.** A cluster test for API
   behaviour, a unit test for a rule, a merobox scenario for a multi-process
   flow. Watch it fail for the reason the bug describes.

2. **Fix it and rerun the same test.** Keep it as the regression test; the
   before and after output goes in the PR description.

3. **Reason about old data.** For anything touching the store, snapshots, the
   sealed wire format or signed formats, work through existing data and
   mixed-version clusters explicitly.

</Steps>
