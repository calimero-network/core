Calimero Core is tested in layers that trade scope for speed. Most of the node is
covered by real clusters in one process: three nodes, sealed channels, real
WASM, driven only through the client. Multi-process behaviour (crashes,
freezes, restarts, upgrades) is covered by merobox scenarios.

| Layer | Where | What it proves | Speed |
| --- | --- | --- | --- |
| Unit tests | `#[cfg(test)]` in each crate | One module's logic: config merging, key sources, quotas, presence rules, outbound gates | Milliseconds |
| Raft engine | `crates/log` | Replication, failover, restart from disk, learner catch-up, snapshot streaming, no plaintext on disk, the `log.redb` migration | Seconds |
| Cluster | `crates/node/tests/cluster.rs` | The node end to end in one process: sign-up, installs, calls, views, events, orgs and teams, upgrades and migrations, blobs, follow-ups, governance, replica moves | Seconds to minutes |
| CLI | `crates/merod/tests/cli.rs`, `crates/meroctl/tests/cli.rs` | `merod init/config/run/inspect` through the binary; every `meroctl` command group against a local cluster | Seconds to minutes |
| App logic | `TestHost` in `crates/sdk/src/testing.rs`, `converge` in `crates/storage/src/testing.rs` | An app's methods, events and migrations; that a state type converges | Milliseconds |
| Scenarios | merobox `cloud-v2` backend | Separate `merod` processes: crash, freeze, restart and upgrade under load | Slow |

Use both ends. A green cluster test does not prove a process restart or a
frozen leader behaves, and a green scenario does not localize a logic bug.

## Fixtures

The cluster and CLI tests load compiled apps from
`target/wasm32-unknown-unknown/app-release/`. Build them first:

```bash
cargo build -p kv-store -p org-gated -p outbound-probe \
  --target wasm32-unknown-unknown --profile app-release
PATH="$(scripts/setup-cargo-mero.sh):$PATH"
for a in blobs kv-store-with-handlers kv-store-with-shared-storage search-chat xcall-example tee-cards tee-dice \
  migrations/migration-suite-v1 migrations/migration-suite-v2-add-field \
  migrations/scenario-migration-check-fail-v1 migrations/scenario-migration-check-fail-v2 \
  migrations/scenario-identity-downgrade-v1 migrations/scenario-identity-downgrade-v2; do
  cargo mero build --manifest-path "apps/$a/Cargo.toml"
done
```

The `cargo mero` builds carry the embedded ABI the node reads for handlers,
timers, xcalls, search and migrations. `KV_STORE_WASM` points the tests at
another `kv_store.wasm`.

## Running the tests

```bash
cargo test -p calimero-node                 # the cluster tests
cargo test -p calimero-node --test cluster teams_work_like_v1_subgroups -- --nocapture
cargo test -p merod -p meroctl                    # the CLI tests
cargo test -p calimero-log
cargo test -p calimero-client -p calimero-identity -p calimero-sealed
cargo test -p calimero-outbound --features outbound-testing
cargo test -p calimero-kms-client --features mock-attestation
cargo test -p calimero-tee-attestation --features mock-attestation
cargo test --workspace                            # everything
```

[cargo-nextest](https://nexte.st/) runs the workspace faster
(`cargo nextest run --workspace`, then `cargo test --workspace --doc` for the
doctests it skips).

<Aside type="caution">
  Cluster tests start several nodes on free local ports and use real WASM; run
  them on Linux. A test that fails with "build kv-store for wasm32 first" is
  missing a fixture, not broken.
</Aside>

### Writing a cluster test

`crates/node/tests/cluster.rs` builds clusters with the real `run`,
mock attestation and a soft authenticator, and drives them only through
`calimero-client`, as an SDK user would. Write a new test there when the
behaviour crosses the API: start the cluster, sign up, do the thing, assert on
what the client sees. Name it for the behaviour
(`teams_work_like_v1_subgroups`,
`a_node_added_to_a_running_cluster_hosts_replicas`).

## App logic: `TestHost` and `converge`

[`TestHost`](https://github.com/calimero-network/core/blob/master/crates/sdk/src/testing.rs)
runs an `#[app::state]` type as plain Rust: `call`, `view`, `events()`,
`logs()`, `migrate`, `set_caller_org`. It does not run xcalls, networked blobs
or event-handler dispatch. `converge` / `converge_app` in
[`crates/storage/src/testing.rs`](https://github.com/calimero-network/core/blob/master/crates/storage/src/testing.rs)
asserts that a state type reaches the same root on N in-memory replicas under
reordered operations. The app-author guide is [Testing your app](/build/testing/).

<Aside type="note">
  An app instance's calls are applied in one order by its Raft log, so the
  node never merges concurrent writes; `converge` checks the storage format's
  own merge rules.
</Aside>

## Scenario tests with merobox

[merobox](https://github.com/calimero-network/merobox)'s `cloud-v2` backend
(CI pins it with `MEROBOX_REF`) starts one `merod` process per node and runs YAML
scenarios: deploy, call and read as several accounts, then crash, freeze,
restart or upgrade nodes and check the app keeps its data and answers within a
time budget.

```bash
MEROD_BINARY=target/debug/merod \
KV_STORE_WASM=target/wasm32-unknown-unknown/app-release/kv_store.wasm \
merobox cloud run workflow-examples/cloud-v2/frozen-leader.yml
```

The scenarios and their step reference are in merobox's
`workflow-examples/cloud-v2/`. A node behaviour that only shows across
processes (the bounded forward to a frozen leader is the example) gets its
regression scenario there.

### Core and app workflows

Core's workflows (`workflows/`: app migrations, `sync-tests` (replication), fuzzy loads) and
every app's (`apps/*/workflows/`) are merobox workflows for the `cloud-v2`
backend; every deployable app has at least one. Some files' headers still
record how they were ported from the earlier release's workflows. Run them
against a build:

```bash
python3 scripts/build-workflow-fixtures.py      # the releases and WASM they install
MEROD_BINARY=target/debug/merod python3 scripts/run-workflows.py [FILE...]
python3 scripts/run-workflows.py --shard 2/4 --list   # what CI's shard 2 runs
```

Every workflow names its own `cluster.base_port` and no two overlap, so the four
shards of one checkout can run side by side, each with its own `--json`. To run
the same workflows from two checkouts at once, give each a band of its own with
`--port-offset N` (or `WORKFLOW_PORT_OFFSET`), e.g. 10000 and 20000.

`scripts/workflows-baseline.json` lists the workflows that pass; one
of them failing fails CI. Add a workflow to it once it passes, and its measured
duration to `scripts/workflows-durations.json` (the shards are packed
by it). A workflow not on the baseline still runs and is reported, so a fix
shows up as a pass.

### In CI

`.github/workflows/e2e.yml` runs on every PR that touches code:

- job `merobox fixtures`: builds `merod`, the fixtures and merobox's
  example inputs once, for the jobs below;
- job `merobox workflows (K/4)`: every workflow, core's and the
  apps', in four shards of about equal length (merobox at `MEROBOX_REF`);
  nightly, the fuzzy loads run 15 minutes each. Each shard's fuzzy load
  reports its latency and throughput (below) in the job summary and as the
  artifact `soak-metrics-K`;
- job `merobox examples`: merobox's own examples;
- job `clients against merod`: mero-js's `test:cloud-v2` and
  calimero-client-py's cluster tests against this tree's `merod`. A change that
  breaks a client goes green with the client's fix: a same-named branch there,
  or `sdk-ref: <ref>` (mero-js) / `py-ref: <ref>` (Python) in the PR body.

Those test a debug `cargo build`. Two jobs test the `merod` that ships, the
binary inside the Docker image (merobox starts processes, so it is copied out
with `docker create` and `docker cp`):

- **A PR's own image** (`.github/workflows/release.yml`, job
  `E2E on the merod image`, on PRs and the merge queue whenever the PR builds
  the image). `Release Merod container` builds the amd64 image as it does for
  master, loads it instead of pushing it, and hands it on as the artifact
  `merod-image`; the job runs the smoke list,
  `scripts/run-workflows.py --smoke` (one workflow per area, listed with
  the fixtures they need in `scripts/workflows-smoke.json`, every one
  on the baseline; `check-scenario-coverage.py` checks), and merobox's
  `kv-store-failover` and `frozen-leader` examples against it, about four
  minutes after the image. `Image E2E fixtures` builds only the smoke list's
  fixtures, alongside the binaries.
- **The latest release's image, nightly** (`e2e.yml`, jobs
  `Latest release image`, `merobox fixtures (release V)` and
  `merobox workflows on release V (K/4)`; on demand with the `release_image`
  input: `latest`, a tag of `ghcr.io/<owner>/merod` such as `release-v2-edge`,
  or an image reference). It pulls
  `ghcr.io/calimero-network/merod:<version>` for the newest published release
  (a prerelease included) and runs the four shards, soak included, on the
  workflows, fixtures and baseline of the commit the image was built from
  (its `org.opencontainers.image.revision`), so a workflow added after the
  release does not fail it. A release older than 1.0 runs the earlier node,
  which merobox does not run: the job says so in its summary and the shards
  are skipped. On the release branch the nightly tests `release-v2-edge`
  instead, the image of the branch's latest merge
  ([Release branch](#release-branch)).

To run the smoke list against a binary taken out of an image locally:

```bash
docker create --name m ghcr.io/calimero-network/merod:release-v2-edge && docker cp m:/usr/local/bin/merod /tmp/merod && docker rm m
python3 scripts/build-workflow-fixtures.py $(jq -r '.fixtures[]' scripts/workflows-smoke.json)
MEROD_BINARY=/tmp/merod python3 scripts/run-workflows.py --smoke
```

### Soak latency and throughput

A `fuzzy_test` step times every step it sends to the cluster (one round trip
each). With `MEROBOX_SOAK_REPORT=file.json` it appends a report to that file:
per operation, how many ran and failed, operations and calls per second over
the run, and the p50/p95/p99 (and mean, max) latency of its calls in
milliseconds, the same per step kind (`call set`, `call get`), and the whole
run's. `merobox cloud soak-report file.json` (or `scripts/soak-summary.sh`,
which CI runs) prints it as a table:

```bash
MEROD_BINARY=target/debug/merod MEROBOX_FUZZY_SECONDS=30 MEROBOX_SOAK_REPORT=soak.json \
  python3 scripts/run-workflows.py workflows/fuzzy-tests/kv-store/fuzzy-test.yml
merobox cloud soak-report soak.json
```

A 30-second kv-store run against a debug `merod` on a shared 4-vCPU Linux
container (the shape of the nightly table, not a reference):

| Operation | Ops | Pass % | Ops/s | Calls | Calls/s | p50 ms | p95 ms | p99 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| cross_node_write_read | 7 | 100.0 | 0.23 | 14 | 0.46 | 19.5 | 21.8 | 21.8 |
| list_entries | 29 | 100.0 | 0.96 | 29 | 0.96 | 43.3 | 74.1 | 85.3 |
| random_read | 28 | 100.0 | 0.93 | 28 | 0.93 | 11.6 | 16.2 | 20.0 |
| set_and_verify | 96 | 100.0 | 3.18 | 192 | 6.36 | 17.8 | 29.3 | 31.9 |
| write_burst | 56 | 100.0 | 1.86 | 672 | 22.28 | 25.1 | 30.9 | 33.5 |
| **all** (30s) | 216 | 100.0 | 7.16 | 935 | 31.00 | 22.1 | 31.8 | 51.1 |

The calls run one at a time, so a call's latency is what one caller sees and
calls/s is one caller's rate, not the cluster's capacity; the cluster bench
([below](#cluster-throughput)) measures that. Numbers from a debug build
(the PR shards) are for comparing runs of the same job, not the release's
speed; the release image's shards measure that. The pass rate and
`success_threshold` gate as before; latency gates nothing.

### Flamegraphs

Nightly (or with the `flamegraph` input), job `merod flamegraph (kv-store
soak)` builds `merod` with the `profiling` profile (optimized, with symbols)
and `-C force-frame-pointers=yes`, runs the kv-store fuzzy load for five
minutes, and records node 1 with `perf record -g` for most of it
(`scripts/soak-flamegraph.sh`; the runner sets `kernel.perf_event_paranoid=-1`).
inferno renders the samples; the artifact `merod-flamegraph` holds
`merod-flamegraph.svg`, the folded stacks `merod.folded` (compare two nights
with `inferno-diff-folded old.folded new.folded | inferno-flamegraph > diff.svg`)
and the profiled run's soak report. Locally, on Linux:

```bash
cargo install inferno --version 0.12.8 --locked
RUSTFLAGS="-C force-frame-pointers=yes" cargo build -p merod --profile profiling
sudo sysctl -w kernel.perf_event_paranoid=-1
MEROD_BINARY=target/profiling/merod MEROBOX_FUZZY_SECONDS=120 scripts/soak-flamegraph.sh /tmp/flame
```

`PERF=/usr/lib/linux-tools/<version>/perf` points it at a perf whose wrapper
does not match the running kernel; `PROFILE_DELAY`, `PROFILE_SECONDS` and
`PROFILE_HZ` set when and how it samples, and a second argument names another
fuzzy workflow (a third, another node).

## Release branch

Calimero 1.0 was developed on `release-v2-parity`, which has since been merged
into master (`1.0.0-rc.1`). CI still treats that branch as a release branch,
with its own image tags:

| When | What runs | What publishes |
| --- | --- | --- |
| PR into the branch | Every check a PR into master runs (no check's `pull_request` trigger leaves the branch out; `abi-guard.yml` and `platforms.yml` name it) | Nothing; `Release Merod container` builds the PR's image and `E2E on the merod image` tests it |
| Merge (push) into the branch | `ci-checks.yml`, `e2e.yml`, `release.yml`, `benchmarks.yml`, `docs-ci.yml`, `crypto-vectors.yml`, `abi-contract.yml`, `abi-guard.yml`, `workflow-lint.yml`, `codeql.yml`; ci-checks and E2E runs are never cancelled, and the ci-checks, wasm-apps and storage-cost caches save, as on master | The multi-arch `merod` image as `ghcr.io/calimero-network/merod:release-v2-edge` and `:release-v2-<short sha>`, labelled with the commit (`org.opencontainers.image.revision`); the release binaries as the run's `artifacts-<target>` artifacts, kept 14 days; the criterion, search and cluster benchmark reports as the base the branch's PRs compare against |
| Nightly | `e2e.yml` with `nightly: true` (the 15-minute soak, the shards on `release-v2-edge`, the flamegraph), `fuzz.yml` (30 minutes per target) and `platforms.yml` with `nightly: true` (macOS; a failure opens "Nightly platform build is failing on release-v2-parity") | Nothing |

The branch never publishes a version: no `edge`, `latest`, `prerelease` or
version tag, no GitHub Release, crates, App Bundle, Homebrew tap update or SDK
bump PRs. `release.yml` gates each of those on master. The clients job tests
the clients' own `release-v2-parity` branches when nothing is paired
(`sdk-ref:`, `py-ref:` or a same-named branch), since their master has no
cluster tests.

GitHub runs `schedule` only from the default branch, so the branch's nightly
runs only when dispatched. To run one by hand:

```bash
gh workflow run e2e.yml --ref release-v2-parity -f nightly=true
gh workflow run e2e.yml --ref release-v2-parity -f release_image=release-v2-edge   # the 30 s soak, plus the image's shards
```

`docs-site.yml` stays master's: it deploys the public documentation site to
GitHub Pages, which has one site per repository, so the branch's docs are
built and link-checked (`docs-ci.yml`) but not deployed.

## What scenario tests cannot catch

Every node in a scenario run is the same build on fresh state, so it never
tests data written by an older version. A change to an on-disk or wire format
needs its own migration test, as `calimero-log`'s `migration_tests.rs` does for
the `log.redb` store.

## Proving a fix

<Steps>

1. **Reproduce first, at the layer a user hits it.** A cluster test for API
   behaviour, a unit test for a rule, a merobox scenario for a multi-process
   flow. Watch it fail for the reason the bug describes.

2. **Fix it and rerun the same test.** Keep it as the regression test; the
   before and after output goes in the PR description.

3. **Reason about old data.** For anything touching the store, snapshots, the
   sealed wire format or signed formats, work through existing data and
   mixed-version clusters explicitly.

</Steps>

## Benchmarks and cost gates

Storage cost gates, scaling guards and criterion benches are described in
[`docs/benchmarking.md`](https://github.com/calimero-network/core/blob/master/docs/benchmarking.md).
`.github/workflows/benchmarks.yml` runs them on every push to master or the
release branch and on a PR labelled `run-benchmarks`: the criterion benches per
crate (`calimero-log`'s append and commit, `calimero-sealed`'s request round
trip, the storage and runtime benches), compared with `critcmp` against the
base commit's push run on the PR's base branch, plus two
reports that are not criterion: `tools/search-bench` (the search engine) and
the cluster throughput bench, whose JSON the comparison also diffs.

### Cluster throughput

`crates/node/benches/cluster_throughput.rs` drives a 3-node cluster in
one process (the harness of `tests/cluster.rs`, in `tests/harness/cluster.rs`,
with merod's Raft timing) through the sealed client, calling the kv-store
fixture's `set` on the app's leader:

```bash
cargo build -p kv-store --target wasm32-unknown-unknown --profile app-release
cargo bench -p calimero-node --bench cluster_throughput -- --secs 15 --out cluster.json
```

Two runs on a 4-vCPU Linux container (bench profile with LTO off; the machine
was shared with other work, so treat rows as ±25%):

| Scenario | Calls/s | Per app | p50 | p99 |
| --- | --- | --- | --- | --- |
| (a) 1 app, 1 in flight | 148 / 185 | | 6.3 / 5.2 ms | 15 / 8 ms |
| (b) 1 app, 64 in flight | 205 / 250 | | 285 / 253 ms | 519 / 317 ms |
| (c) 2 apps, 64 each, one leader node | 322 / 349 | 160 + 162 / 176 + 173 | 348 / 340 ms | 780 / 495 ms |
| (c') 2 apps, 64 each, two leader nodes | 264 / 298 | 119 + 146 / 139 + 159 | 436 / 423 ms | 2963 / 3671 ms |

One synced RocksDB write (`rocksdb_write/synced` in `calimero-log`'s bench, and
timed again by this bench) took 0.16 to 0.19 ms on this disk; unsynced, 2 µs.

**Appends without a leadership round.** `Group::propose` used to confirm
leadership with a majority (`ensure_linearizable`) before every build; it now
does so only for a proposal that answers without appending, and concurrent
`sys_fresh` callers share one read-index round. Before and after on the same
machine, two runs each, `--secs 10` (other work shared the machine, so ±25%
still holds):

| Scenario | Calls/s before → after | p50 before → after | p99 before → after |
| --- | --- | --- | --- |
| (a) 1 app, 1 in flight | 219 / 191 → 205 / 233 | 4.5 / 5.1 → 4.8 / 4.2 ms | 6.6 / 7.2 → 7.9 / 6.3 ms |
| (b) 1 app, 64 in flight | 238 / 233 → 293 / 298 | 270 / 273 → 216 / 212 ms | 337 / 301 → 259 / 247 ms |
| (c) 2 apps, 64 each, one leader node | 368 / 415 → 497 / 465 | 343 / 305 → 252 / 277 ms | 453 / 382 → 327 / 365 ms |
| (c') 2 apps, 64 each, two leader nodes | 452 / 460 → 481 / 471 | 286 / 274 → 259 / 259 ms | 2273 / 2322 → 368 / 362 ms |

`calimero-log`'s bench on a 3-node group: one proposal in flight 689 / 633 →
573 / 528 µs, 64 in flight 36.8 / 38.1 → 33.4 / 31.8 ms (1 node: unchanged, it
had no round to save). A single caller (a) gains nothing measurable; the
queue behind the propose lock (b, c) moves about a fifth faster, and the
seconds-long p99 with two leader nodes (c') is gone.

- **The limit is per app, not per node.** A group proposes one call at a time
  (`propose_lock` in `Group::propose` is held while the leader runs the WASM
  and until the entry commits), so 64 calls in flight on one app only queue:
  (b) is 1.35x (a), and its p50 is about 50 times (a)'s. A second app on the same
  leader node adds its own stream: (c) is 1.4 to 1.6x (b) (2x in an earlier
  run), and the two apps share it evenly; a per-node limit would hold (c)
  at about 1x. Two leader nodes did no better than one here, and their p99
  was seconds: 4 cores ran all three nodes and 128 callers.
- **The disk is not the limit.** A call needs the leader's synced append and a
  follower's (in parallel), so about 2 syncs: 1 ÷ (2 × 0.17 ms) is about 3,000
  calls/s per app, against the 150 to 300 measured. A call's 4 to 7 ms is the
  sealed HTTP round trip, the fresh system read, the WASM run and the Raft
  round trip of its append, the last two inside the propose lock. On a disk whose sync takes 10 to
  25 ms (macOS, where Rust's `sync_data` is `F_FULLFSYNC`, which redb ran on
  every commit), the same formula gives 20 to 50 writes/s per app, the range
  of the ~38/s a macOS build on redb reported.

<Aside type="note" title="Fuzzing">
  `fuzz/` fuzzes what a node reads from untrusted bytes (`sealed_request`,
  `passkey_verify`, `session_token`, `quote_parse`, `bundle_open`,
  `crdt_sync`). `fuzz.yml` runs a changed target for a minute on a PR and
  every target for 30 minutes nightly; `scripts/fuzz.sh <target> [seconds]`
  runs one locally.
</Aside>
