## 1. A local cluster

```bash
# in core
cargo install --locked --path crates/meroctl
cargo install --locked --path crates/merod
meroctl app build apps/kv-store --out kv_store.wasm
meroctl local up
```

`meroctl local up` starts `merod local` in the background: three nodes on
`http://127.0.0.1:2501-2503/` in one process, with mock attestation and a
development storage key, keeping state in `.merod-local/` (`--fresh` starts
over). It saves the cluster as the node `local`, trusting its mock attestation
for this node only, so it cannot carry over to a real cluster; `meroctl local
status` shows it and `meroctl local down` stops it. Browser apps
on `http://localhost:3000` and `http://localhost:5173` may call it (`--origins`).
On macOS, run the same cluster in Docker instead
([Install](/operate/install/#first-run-on-macos-a-cluster-in-docker)) and use its
URL below.

## 2. Sign up, deploy and call from the terminal

```bash
# A new passkey file signs up: an account and its personal organization.
meroctl login --dev-passkey ./dev-passkey.json --name ada
meroctl whoami            # orgs: [{ "name": "Personal", "personal": true, ... }]

# Install the bundle and create an instance; naming no organization puts it in
# your personal one.
meroctl context create --path kv_store.wasm --name kv --alias kv
meroctl call --context kv set --args '{"key":"a","value":"1"}'
meroctl call --context kv get --args '{"key":"a"}' --view
meroctl context watch kv --limit 1        # the committed events, as JSON lines

# A read-only API key for a script, approved with your passkey.
meroctl account api-key create --context kv --read-only --dev-passkey ./dev-passkey.json
```

To share an app, create it in an organization of its own and invite people:

```bash
meroctl namespace create Acme                          # answers { "orgId": ... }
meroctl context create --path kv_store.wasm --name team-kv --namespace <org-id>
meroctl namespace invite <org-id> --role member --uses 1 --dev-passkey ./dev-passkey.json
# the invitee, signed in on their own: meroctl namespace join <token>
```

In `meroctl`, an `app` is a signed package, a `context` an app instance, a
`namespace` an organization, a `group` one of its teams, `account` you (each
passkey is one of your devices) and `ops` the operator
([glossary](/protocol/glossary/)). Every app instance is in an organization:
the personal one each account gets at sign-up, or one it created or joined.
`--dev-passkey` keeps a passkey in a file, which only a development cluster
accepts. Against a real cluster, use an API key made in the console
(`CALIMERO_API_KEY`) and name the images you trust:
`--tee-profiles <profile> [--min-release <version>]`. The release floor defaults
to the client's `DEFAULT_MIN_RELEASE`, and debug profiles are refused unless you
pass `--allow-debug-profiles`. Install apps there as signed packages
(`meroctl app install PACKAGE@VERSION`, then `meroctl context create --package
PACKAGE --name NAME`); raw bundles are for development clusters.

## 3. From code

### JavaScript (mero-js)

In a page served from `http://localhost:3000` or `http://localhost:5173` (the
origins `merod local` allows for passkeys), with the bundle's bytes in `wasm`:

```ts
import { CalimeroClient, browserPasskey } from '@calimero-network/mero-js';

// merod local sends mock quotes: allow them explicitly, for this client only.
const client = new CalimeroClient({ baseUrl: 'http://127.0.0.1:2501', policy: { allowMock: true } });

await client.signUp(browserPasskey(), 'ada'); // or client.signIn(browserPasskey())
const { hash: bundle } = await client.packages.bundlePut({ body: wasm, contentType: 'application/wasm' });
const { appId: app } = await client.apps.create({ name: 'kv', bundle }); // your personal organization

await client.apps.call({ app, method: 'set', args: { key: 'a', value: '1' } });
const { result } = await client.apps.view({ app, method: 'get', args: { key: 'a' } });
for await (const ev of client.events(app)) console.log(ev);
```

On Calimero Cloud, reach a cluster by name and install a signed release from
its registry instead of uploading a bundle; every node the directory names is
attested under your policy first:

```ts
const cloud = await CalimeroClient.connect({
  cluster: 'eu-shared-1',
  policy: { release: { minReleaseVersion: '2.3.109' } },
});
await cloud.signIn(browserPasskey());
await cloud.packages.install({ package: 'com.example.kv', version: '1.0.0' });
const { appId } = await cloud.apps.create({ name: 'kv', package: 'com.example.kv', version: '1.0.0' });
```

A script uses an API key (`client.useApiKey('cal_...')`) instead of a passkey.
The [mero-js docs](https://calimero-network.github.io/mero-js/) cover the rest.

### Python (calimero-client-py)

```python
from calimero_client_py import Client

client = Client("http://127.0.0.1:2501", allow_mock=True)
client.use_api_key("cal_...")   # the key `meroctl account api-key create` printed
print(client.apps.view(app=app_id, method="get", args={"key": "a"}).to_dict()["result"])
```

For a complete browser frontend (passkey sign-in, live events), see the
`apps` repository's `apps/kv-store/app`, built on mero-js.

## 4. Scenario tests and the process suite

An app's scenarios (`apps/<app>/scenarios/*.json`) and core's
(`workflows/**/scenarios/`) run on an in-process 3-node cluster: deploy, call
and read as several accounts, in orgs and teams, with packages and upgrades.
The process suite starts one `merod run --dev` process per node and crashes,
freezes, restarts or upgrades them, checking the app keeps its data and answers
within a time budget.

```bash
cargo test -p calimero-node --test scenarios -- apps/kv-store/   # kv-store's scenarios
cargo build --release -p merod -p meroctl
meroctl app build apps/v2-fixtures/kv --out target/app-components/kv.wasm
python3 -I crates/node/tests/fault/suite.py --only frozen-leader
```

See [Testing strategy](/contribute/testing/#scenarios) for the file format and
every step.
