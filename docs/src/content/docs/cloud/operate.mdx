## Starting a TDX node

```bash
merod --node n1 init --node-id 1 --listen 0.0.0.0:2501 --public-url https://n1.eu1.example/ \
  --cluster eu1 \
  --peers 1=https://n1.eu1.example/,2=https://n2.eu1.example/,3=https://n3.eu1.example/ \
  --kms-url https://kms.internal/ --kms-identity /data/disk-identity \
  --rp-id example.com --origins https://app.example.com \
  --ops-token-sha256 "$OPS_TOKEN_SHA256" --backup-dir /backups
MERO_TEE_VERSION=<mero-tee release> MERO_TEE_PROFILE=<profile> merod --node n1 run
```

`init` writes `~/.calimero/n1/config.toml` (`--home` or `CALIMERO_HOME` moves
it; data goes to `n1/data` unless `--data-dir` says otherwise); `merod --node
n1 config --flag value` changes it; flags and `MEROD_*` variables given to
`run` override it for that run, so a container can also run with flags alone.
The configuration's `[outbound]` table is the outbound policy below.

- **Storage key.** merod runs its KMS client (`merod kms disk-key` is the same, for a boot script: the KMS
  is verified against the signed release policy and the key is sealed to the TD)
  and derives its storage key as `HKDF(KMS key, cluster)`. The cluster's nodes
  share the disk identity, so they share the key. A boot script that already
  fetched the key passes `--storage-key-file` instead.
- **Peers.** A peer's quote must match a profile of the signed mero-tee release it
  names: `--peer-profiles` (default: this node's `MERO_TEE_PROFILE`) and an
  optional floor `--peer-min-release`. A TDX node refuses to start without them.
- **Sessions.** The session-signing key rotates every
  `--session-key-rotation-secs` (default 6 h, at least 30 min); the previous key
  keeps verifying.
- **Browsers.** `--origins` are both the passkey origins and the CORS origins.
- **Governance.** Three decisions, each given at deployment to either each
  app's `owner` (the default; an organization's owner for its apps, with a
  passkey) or the `operator` (for every app, through the Ops API):
  `--release-approvals` (which mero-tee releases may hold the data:
  `POST /ops/releases { version }`), `--app-upgrades`
  (`POST /ops/apps/{app}/upgrade { version | bundle }`, an installed release)
  and `--outbound-approvals` (`POST /ops/outbound { package, prefixes }`). The
  party not chosen cannot make that decision. They are fixed the first time the
  cluster starts and attested with every node's receipt key, so users check
  them (`verify_app_cluster`). Give the operator a decision only where users
  trust it with code, or destinations, that read their data.
- **App frontends.** `--apps-domain apps.example.com` (with a wildcard DNS name
  for it pointing at the cluster) serves each package's frontend, from its
  signed release, at its own origin `{label}.apps.example.com` (the label is in
  `calimero_cloud_node::app_host::label`; `merod local` uses `localhost`).
  Signing in there opens a session that reaches that package's apps only.
- **Outbound HTTPS.** Off unless the configuration (or `--settings FILE`) has an `[outbound]` table
  (`enabled`, `hosts`, and `env_secrets` or a loopback `sidecar`), v1's
  `[context.outbound]`. The operator bounds the hosts and holds the secrets;
  which prefixes an app may reach is approved by whoever `--outbound-approvals`
  names.

## The Ops API

`--ops-token-sha256 HEX` instead of `--ops-token` gives a node only the token's
hash. `GET /ops/metrics` answers Prometheus text. A node started without
`--bootstrap` joins the running cluster once `POST /ops/nodes` registers it.

Bearer `--ops-token`, inside the sealed channel. mdma's `OpsClient` and
`meroctl --ops-token TOKEN ops ...` use it: `status`, `metrics`, `add-node`,
`move`, `backup`, `quotas`/`set-quotas`, and where the deployment gave the
operator the decision, `release`, `outbound`, `install`/`uninstall`/`packages`
(the releases it upgrades to), `upgrade` and `upgrade-namespace`.

| Route | What |
| --- | --- |
| `GET /ops/status` | This node, the system group's and hosted groups' Raft status, fleet, counts |
| `POST /ops/nodes` | Register a node |
| `POST /ops/apps/{app}/replicas` | Move an app to a replica set (on a follower: `421 NOT_LEADER` with `leaderUrl`) |
| `GET/POST /ops/quotas` | Per-account limits |
| `POST /ops/backup` | Encrypted snapshots of the apps this node leads |

Placement (zone-spread, least-loaded, deterministic) and drain plans are in mdma's
`mdma_common.cloud_v2`.
