A `merod` node serves one HTTP API on its `--listen` address. The route table is
`router` in `crates/node/src/api.rs` with the area routers it merges
(`crates/node/src/api/<area>.rs`); this page lists every route in it.
Calls, reads, events (server-sent events) and administration are all routes of
this one API.

Each route's request and response schemas and error codes are in the
[Node API reference (OpenAPI)](/core/operate/api-reference/), rendered from
[`openapi.json`](/core/openapi.json), an OpenAPI 3.1 document generated from the
code and checked against the router on every CI run. Its requests are sealed
like every other client's, so a tool built from it needs a sealing client
underneath (see [Transport](#transport)).

## Transport

- **In the clear:** `GET /health`, `GET /attestation` and the consent page
  (`GET /consent/{id}`, `GET /consent/{id}/model`, `POST /consent/{id}/approve`,
  `POST /consent/{id}/decline`), which a person opens in a browser on the
  node's own origin; app frontends under `--apps-domain` (below) and a job
  node's `/job/*` routes are served by their own layers.
- **Sealed:** everything else travels inside the sealed channel
  (`calimero-sealed`, wire format v2, Noise NK). A client fetches
  `/attestation`, checks the quote binds the node's transport key and that the
  quote's measurements match a signed mero-tee release it trusts, and only then
  seals requests to that key. The sealed envelope wraps the router from
  outside, so an opened request meets the same handlers as a direct one.
- A node started with `--dev` also accepts plain requests; a TDX node refuses
  them.
- Requests are limited to 64 MiB.
- The path carries no version: the API changes additively, and a route on its
  way out answers with a `Deprecation` header (RFC 9745, the day it was
  deprecated) and a `Link` (`rel="deprecation"`) to
  [Compatibility](/operate/compatibility/), which says how long it stays
  (`crates/node/api-deprecations.toml` lists them).

Use a client that does this: `meroctl`, `calimero-client` (Rust), mero-js
`CalimeroClient`, or calimero-client-py `CloudClient`. A hand-written `curl`
reaches only `/health` and `/attestation` on a TDX node.

## Credentials

The `Authorization: Bearer` header carries one of:

| Credential | Form | Obtained from |
| --- | --- | --- |
| Session token | `v2.<claims>.<signature>` by the issuing node, 15 minutes | a passkey ceremony, or `/auth/refresh` |
| API key | `cal_…` | `POST /auth/apikeys` |
| Ops token | the configured token | `--ops-token` / `--ops-token-sha256` |

Cluster peers add an `x-cluster-auth` header on `/internal/*`. See
[Authentication](/operate/auth/) for lifetimes, scopes and revocation.

The **Who** column below uses these terms:

| Who | Means |
| --- | --- |
| anyone | no credential needed |
| signed in | a session or an API key |
| session | a passkey session; an API key is refused (`403`) |
| account holder | a passkey session not bound to an app's frontend |
| installer | an account holder, or an API key scoped to no app and no method and not read-only |
| app access | whoever the app's access setting admits (`public` admits anyone); an API key's app, method and read-only scope apply |
| ops | the ops token |
| peer | another node of the cluster |

Authority beyond the credential (an org admin, the app's owner, the holder of a
governance decision) is checked when the command applies to the system log,
so every node reaches the same verdict; a refusal there answers
`400 REJECTED`.

## Errors

An error answer has an HTTP status and a JSON body:

```json
{ "status": 403, "error": "FORBIDDEN", "message": "this needs a passkey session, not an API key" }
```

with `details` when there is more to say (for example `leaderUrl` with
`421 NOT_LEADER`). The codes an operator meets most:

| Status | `error` | Means |
| --- | --- | --- |
| 400 | `BAD_REQUEST`, `BAD_NONCE`, `BAD_PACKAGE`, `BAD_BUNDLE`, `UNKNOWN_CHALLENGE`, `EXPIRED_CHALLENGE`, `TOO_FEW`, `NO_REGISTRY` | The request is malformed, refers to nothing valid, or needs a registry the node lacks. |
| 400 | `REJECTED` | The system log refused the command when it applied; `message` says why (for example the caller is not an admin of the organization). |
| 403 | `BAD_OPERATOR_SIGNATURE` | The `operatorProof` does not verify under the operator key recorded at genesis. |
| 401 | `UNAUTHENTICATED` | No, unknown, expired or revoked credential. |
| 401 | `PASSKEY_UNKNOWN_HERE` | A sign-in or step-up with a passkey no account of this cluster has: one from another cluster under the same rp-id, or a removed one. |
| 403 | `FORBIDDEN` | The credential may not do this (scope, role, governance, read-only). |
| 404 | `NOT_FOUND` | No such object, or one the caller may not see. |
| 409 | `CONFLICT`, `UPGRADE_PENDING`, `FEATURE_NOT_ACTIVE` | The state does not allow it now; a fuel cap waits for every node to run this release; a command or field waits for every node to support its [cluster version](/protocol/upgrades/#the-cluster-version) (`details: { feature, needs, active }`). |
| 409 | `APP_RESTORING` | The app is being restored from a backup; retry once the restore answers. |
| 410 | `UNSUPPORTED_ENGINE` | The app is an SDK 0.12 (wasmer) app: listed and deletable, nothing runs. |
| 412 | `CONFIRM_REQUIRED` | A passkey assertion is needed; `details` carries the challenge. |
| 428 | `OPERATOR_SIGNATURE_REQUIRED` | An operator decision: `details` names the statement and a nonce; send the request again with `operatorProof`, the operator key's signature over them. |
| 413 | `TOO_LARGE` | Over a size limit (a bundle over 16 MiB, a log entry over 1 MiB). |
| 421 | `NOT_LEADER` | Send it to the leader named in `details.leaderUrl`. |
| 422 | `INIT_FAILED`, `APP_ERROR`, `UPGRADE_FAILED` | The app's code refused. |
| 429 | `QUOTA_EXCEEDED`, `RATE_LIMITED` | An account quota, or a node's limit on open streams or ceremonies. |
| 503 | `UNAVAILABLE`, `NOT_CAUGHT_UP` | The cluster cannot answer now, or a replica is behind `minIndex`. |

## Public

| Route | Who | What | meroctl |
| --- | --- | --- | --- |
| `GET /health` | anyone | `{ ok, node, systemLeader, release, clusterVersion, rollbackEpoch }` (`clusterVersion`: the newest [cluster version](/protocol/upgrades/#the-cluster-version) this node supports; `rollbackEpoch`: the cluster's [rollback](/operate/security/#rollback) epoch, `null` without a rollback counter). | `GET /releases` | anyone | `{ governance, deadlines: [{ version, after, afterSecs }] }`: the cluster's governance and the deadlines the operator set on mero-tee releases | |

| `GET /auth/backup-key`, `POST /auth/backup-key` | account holder | The account's [recovery-disk](/operate/deployment/#backups-and-the-recovery-disk) backup key `{ holder, key, apps }`, or set it (`{ publicKey, confirm? }`, 64 hex, an X25519 public key; `412` first; `409 FEATURE_NOT_ACTIVE` below 1.0.0-rc.20). Every app is in an organization, so a person's own apps are backed up under their personal organization's key (`/orgs/{org}/backup-key`) | |

| `DELETE /packages/{package}` | account holder | Uninstall every version; refused while an app runs one | `app uninstall` |
| `DELETE /packages/{package}/{version}` | account holder | Uninstall one version | `app uninstall --version` |
| `GET /packages/{package}/{version}/pipelines` | signed in | The pipelines the release registers: per name `hash`, `worstCaseFuel`, the `modules` they pin and the canonical `pipeline`; `404` for a release the caller may not see | `app pipelines` |

| `POST /package-origins/{package}` | account holder | `{ origin, rpId?, served?, confirm? }`: register an origin whose pages sign people in to the package (`served: true`: the cluster also serves its frontend there, a custom domain); the package's manager, `412` first ([Registered origins](/protocol/identities/#registered-origins)) | `app origins add` |
| `DELETE /package-origins/{package}` | account holder | `{ origin, confirm? }`: remove one; the sessions opened there end. `412` first | `app origins remove` |
| `POST /orgs/{org}/publishers` | account holder | `{ signerId, publicKey, signature, confirm? }`: bind a package signing key to the organization (the key's signature over the binding, an `APPROVE_RELEASES` holder's passkey, `412` first), so its `MANAGE_APPLICATION` holders upgrade the apps of packages that declare `upgrades: publisher` | |
| `GET /publishers/{signer}` | signed in | `{ bound, generation }`: whether a signing key (`did:key`) is bound on this cluster, never to which organization, and the generation the next binding signs | |

Before an install is logged the node checks the publisher signature and every
artifact digest, `minRuntimeVersion`, the package's pinned signer (the first
release's wins) and that each service's WASM compiles. A node that later runs
the release fetches and verifies it again.

## Consent requests

How an app's frontend asks the person to approve what its own session may
not do ([The consent page](/protocol/consent-page/)): the request is sealed,
the approval happens on the node's own page in the clear, with the person's
passkey.

| Route | Who | What | meroctl |
| --- | --- | --- | --- |
| `POST /consent/requests` | session (an app's frontend included) | `{ kind, scope?, subject, returnTo }` → `{ requestId, url, expiresAt, code }`. `kind`: `release`, `upgrade`, `outbound`, `createOrg`, `createInvite`, `acceptInvite`, `leaveOrg`, `removeMember`, `setMemberRole`, `setMemberTeams`, `removeMemberTeams`, `revokeInvite`, `renameOrg`, `deleteOrg`, `setCapabilities`, `setAllApps`. One undecided request per account per node: a new one replaces the older, whose page then answers `404` | |
| `GET /consent/{request}/result` | session (the asking account) | `{ decidedAt, ... , outcome? }`: `decidedAt` `null` while pending; `outcome` what the approval made (`{ orgId }`, `{ token }`, `{ org }`, `{ orgId, name }`, `{ apps }`) | |
| `GET /consent/{id}`, `GET /consent/{id}/model` | anyone, in the clear | The page (static HTML, hash-only CSP, no framing) and the frozen model it shows; with `--attestation-verifier-url`, `verifier` links to the independent verifier | |
| `POST /consent/{id}/approve`, `POST /consent/{id}/decline` | the page, same origin | Approve with the person's passkey (`412` first, over the frozen arguments; `409 CONSENT_STALE` when the facts changed), or decline | |

## Ops

Every route needs the ops token. The Ops API returns counts, Raft status,
placement and per-app usage by id, never app state, names or credentials.
A node started with `--metrics-listen ADDR` also serves the `/ops/metrics`
text as plain-HTTP `GET /metrics` on that separate address, and nothing else
there.

## Internal

`/internal/raft`, `/internal/system`, `/internal/system/index`,
`/internal/call`, `/internal/view`, `/internal/challenge/take`,
`/internal/consent/result`, `/internal/runtime`, `/internal/blob`,
`/internal/blob/get`, `/internal/blob/held`, `/internal/blob/pin`,
`/internal/blob/delete`, `/internal/segment/{hash}` (`GET`, `PUT`),
`/internal/upload-begin/...` and `/internal/upload/...` (a resumable file
upload forwarded to the app's leader), `/internal/storage`,
`/internal/last-write`, `/internal/xcalls`, `/internal/usage`,
`/internal/usage/today`, `/internal/presence`, `/internal/app-ready` and
`/internal/events` are for the cluster's own nodes: they need the cluster secret (an HMAC of the cluster key
and the cluster name) inside a sealed channel whose key was attested like any
client's. Nothing outside the cluster calls them.

`/internal/cluster-key` is the one internal route without the cluster secret:
a new node, often of the next mero-tee release, asks it for the cluster key
K_c (`{ cluster, node, token }`). It is never answered with the key: the peer
delivers K_c (`POST /internal/cluster-key/deliver` on the waiting node) to the address the cluster has for that node id, inside a sealed
channel to the key the TD there attests (`403` for another cluster, an
unknown or removed node, or a delivery that fails; `429 BUSY` past four at
once). See [The cluster key](/protocol/encryption/#the-cluster-key-k_c).

A job node (`merod run --job-node`) serves only `/health`,
`/attestation?purpose=jobs`, `GET /job/load`, `PUT /job/bundles/{hash}` and
`/job/runs/...`, each judged by the cluster identity's signature or the run's
token, never by a session or the ops token.

<Aside type="note" title="App frontends">
  With `--apps-domain`, requests whose `Host` is `{label}.{domain}` (or a
  deployment's `{dlabel}.{domain}`) are served
  before any of these routes: `GET`/`HEAD` of a package's frontend files and
  `/.well-known/calimero.json`. See [Networking](/operate/networking/#app-frontends).
</Aside>
