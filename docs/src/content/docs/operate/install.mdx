Both binaries live in this repository: `merod` (the node) and `meroctl` (the
command line).

| Platform | `merod` | `meroctl` |
| --- | --- | --- |
| Linux (x86_64, aarch64) | native | native |
| macOS | in Docker | native |
| Windows | not supported | not supported |

Production nodes run in Intel TDX VMs, which are Linux only; on a laptop you
run nodes in development mode (`--dev`, or `merod local`), with mock
attestation.

## Build

<Tabs>
  <TabItem label="From source">

The toolchain is pinned in `rust-toolchain.toml` (Rust `1.98.0`); `rustup`
selects it. The build needs `clang`, `libclang-dev`, `make`, `pkg-config` and
`libssl-dev` (Debian/Ubuntu names).

```bash
git clone https://github.com/calimero-network/core
cd core
cargo build --locked --release -p merod -p meroctl
# or put them on PATH:
cargo install --locked --path crates/merod
cargo install --locked --path crates/meroctl
```

The binaries land in `target/release/`. On macOS, install only `meroctl` and
run `merod` in Docker.

  </TabItem>
  <TabItem label="Docker">

Every release publishes a `merod` image, for Linux amd64 and arm64:
`ghcr.io/calimero-network/merod:<version>`, plus `latest` (the newest stable
release) and `prerelease` (the newest release candidate). Its entrypoint is
`merod`, running as an unprivileged user, with `CALIMERO_HOME=/data` and
`/data` a volume. It holds `merod` only; install `meroctl` on the host.

```bash
docker pull ghcr.io/calimero-network/merod:prerelease
docker run --rm ghcr.io/calimero-network/merod:prerelease --help
```

Arguments after the image name go to `merod`. To run a node built from your
own checkout, the root `Dockerfile` builds the same kind of image:
`docker build -t merod .`.

  </TabItem>
</Tabs>

## First run on Linux: a local cluster

<Steps>

1. **Start three nodes in one process:**

   ```bash
   merod local
   ```

   They listen on `http://127.0.0.1:2501/` to `2503`, with mock attestation and
   a development storage key, and keep state in `.merod-local/` (`--fresh`
   starts over). It prints the ops token and the `meroctl` commands to connect.

2. **Save the node and sign up** with a file passkey (development clusters
   only):

   ```bash
   meroctl node add local http://127.0.0.1:2501/ --allow-mock
   meroctl login --dev-passkey ./dev-passkey.json --name ada
   ```

3. **Check it:**

   ```bash
   meroctl network status      # node, release, system leader
   meroctl whoami
   meroctl --ops-token <printed token> ops status
   ```

</Steps>

Then deploy an app: [Quickstart](/cloud/quickstart/).

## First run on macOS: a cluster in Docker

The same `merod local` cluster runs in the published image. `--bind 0.0.0.0`
makes its nodes listen on every interface of the container, so the published
ports reach them, at the same URLs as on Linux:

```bash
docker run --rm -p 2501-2503:2501-2503 -v merod-local:/data \
  ghcr.io/calimero-network/merod:prerelease \
  local --bind 0.0.0.0 --ops-token devtoken
```

- Mock attestation, a development storage key and raw WASM uploads, as
  `merod local` on Linux; each app gets three replicas.
- State is in the `merod-local` volume, under `/data/.merod-local`
  (`--fresh` starts over).
- Use `:latest` for the newest stable release, or `:<version>` to pin one;
  match `meroctl`'s release to it.

Then, from the host:

```bash
meroctl node add local http://127.0.0.1:2501/ --allow-mock
meroctl login --dev-passkey ./dev-passkey.json --name ada
meroctl network status
```

<Aside type="note">
  If the node cannot write `/data` (a bind mount owned by another user), mount
  a directory writable by uid `10001`, the image's user.
</Aside>
