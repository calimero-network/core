Commands below assume `meroctl` can reach the cluster and trusts it:

```bash
export CALIMERO_API=https://n1.eu1.example.com/
export CALIMERO_TEE_PROFILES=<profile>
export CALIMERO_OPS_TOKEN=<ops token>
```

## Add a node

A node that is not one of the founding `--peers` joins a running cluster as a
learner of the system group once it is registered.

<Steps>

1. Start it with the cluster's settings (`--cluster`, KMS identity, governance
   flags, `--rp-id`, `--origins`), its own `--node-id` and `--public-url`, and
   **without** `--bootstrap`. It waits.

2. Register it:

   ```bash
   meroctl ops add-node 4 https://n4.eu1.example.com/ [--zone eu1-b]
   ```

3. The system leader adds it as a learner; the log shows `a registered node
   joined the system group`. `meroctl ops status` lists it under the system
   group's learners and in `nodes`.

4. New apps may now be placed on it (spread across zones, least-loaded first
   within that; see [placement](/protocol/context-lifecycle/#create)), and you
   can move existing ones onto it.

</Steps>

A learner holds the directory and can serve and host apps, but does not vote
in the system group. It becomes a voter when a voter is removed (below) and
fewer than 3 would be left.

## Remove a node

<Steps>

1. Move every app off it: for each app whose `replicas` name the node, `meroctl
   ops move APP --replicas ...` with a set that leaves it out (run against the
   app's leader). The node refuses to be removed while an app keeps a replica on it.

2. Remove it, against the system leader (another node answers `421 NOT_LEADER`
   with `details.leaderUrl`): `meroctl --ops-token T ops remove-node ID`
   (`DELETE /ops/nodes/{id}`). It leaves the directory and the system group; a
   registered learner takes its vote while fewer than 3 voters are left.

3. Stop the process and retire its data disk. The other nodes do not register it
   again from their `--peers`; only `ops add-node` brings it back.

</Steps>

## Move an app's replicas

<Steps>

1. Find the app's group and its leader: `meroctl ops status` (the `groups`
   entry for the app on a node that hosts it).

2. Move it:

   ```bash
   meroctl ops move <app-or-context-id> --replicas 2,3,4
   ```

   meroctl sends it to the node you named; a follower answers
   `421 NOT_LEADER` and meroctl retries at the leader's URL.

3. The leader adds the new nodes as learners, waits, switches the voters to the
   new set, and records it. The answer is the group's new status.

</Steps>

Refusals: `TOO_FEW` (fewer than `min(3, nodes in the cluster)` replicas),
`403` naming a node whose release the app's owner has not approved, or
`NOT_HOSTED` when the node asked does not hold the app.

## Back up app state

With `--backup-dir` set, every node writes, every 60 seconds, a snapshot of
each app group it leads that has moved since its last one:
`{backup-dir}/{app-id}/{index:020}.{group}.{snapshot-id}.snap`. Force one now
on a node with `meroctl ops backup` (it answers `{ written }`).

- Snapshots are the Raft snapshot files as written, sealed frame by frame under
  K_r; only a node of the same cluster (or a tool holding K_r) opens them.
- Only leaders write, so collect `--backup-dir` from every node; the newest
  file per app is the newest backup.
- Copy them off the machine; the directory stands in for object storage.

<Aside type="caution" title="Restore is not implemented">
  There is no route or command that restores a snapshot into a running
  cluster (the node's notes list it as not done). `calimero_node::backup::latest`
  opens the newest snapshot of an app with K_r, which is what a restore tool
  would build on. The system group (accounts, organizations, the directory) is
  not in these backups; it lives in memory on every node and in their Raft
  snapshots.
</Aside>

## Set quotas

```bash
meroctl ops quotas
meroctl ops set-quotas '{"maxAppsPerAccount":100,"maxBundleBytesPerAccount":1073741824,"maxApiKeysPerAccount":50,"maxOrgsPerAccount":20,"maxAccounts":100000}'
```

`set-quotas` replaces all of them (a field left out takes its default). They
live in the system state, so every node enforces the same limits when commands
apply; refusals are `429 QUOTA_EXCEEDED`. Sign-up is open, so `maxAccounts` is
what bounds the cluster's growth.

## Upgrade the cluster's release

A new `merod` reaches production as a new mero-tee release (a new image). An
app's data moves only to nodes on a release approved for it.

<Steps>

1. **Get the release approved.** Where the operator holds release approvals:

   ```bash
   meroctl ops release <version>
   ```

   Where owners hold them (the default), each organization's owner approves it
   with a passkey (`POST /orgs/{org}/releases`; `meroctl namespace
   approve-release` on development clusters), and each account for its own
   apps. Until then, nodes on the new release get none of that owner's data.

2. **Raise the peers' floor** only after every node runs the new release:
   `--peer-min-release` on nodes, `--min-release` on clients.

3. **Start nodes on the new image** and [add them](#add-a-node).

4. **Move each app** onto nodes on the new release with
   [`ops move`](#move-an-apps-replicas). A move onto a node whose release the
   app's owner has not approved is refused.

5. **Retire the old nodes** once they host no app: stop them. They stay in the
   directory and the system group's membership (see [Add a node](#add-a-node)).

</Steps>

<Aside type="caution" title="Not confirmed here">
  Restarting an existing node on a new image with its old data directory
  depends on mero-kms releasing the same key to the new image, which is
  mero-kms's policy, not core's. A data directory from an earlier `merod`
  storage format (`log.redb`) is migrated at start.
</Aside>

## Upgrade apps

Who upgrades depends on `--app-upgrades`.

- **Owner (default).** The app's owner, or for an org app anyone holding
  `MANAGE_APPLICATION` there (the org owner, an admin, a team lead, or a member
  granted it), approves each upgrade with their own passkey: `POST /apps/{app}/upgrade { version }`, or an
  organization-wide run `POST /orgs/{org}/upgrade { package, version, team?,
  cascade? }` approved once. Development clusters: `meroctl context update`,
  `meroctl group upgrade trigger`.
- **Operator.** Install the release the operator upgrades to, then upgrade:

  ```bash
  meroctl ops install com.example.kv@1.3.0
  meroctl ops upgrade <app-id> --version 1.3.0
  meroctl ops upgrade-namespace <org> --package com.example.kv --version 1.3.0 [--group <team> --cascade]
  meroctl group upgrade status <org> <run>
  ```

An upgrade plans its migration from the two bundles' embedded ABIs: one state
version up runs the target's `#[app::migrate]` edge (or the export named with
`--migrate`), the app's migration check must pass, and a downgrade, a jump or a
missing edge is refused. A run upgrades its apps one at a time and records
each failure; `POST /orgs/{org}/upgrades/{run}/retry` runs the failed ones
again as a new run.

## Rotate the ops token

The token is per node configuration, not cluster state.

<Steps>

1. Make a new token and its hash (`openssl rand -hex 32`, then `sha256sum`).
2. On each node: `merod --node nX config --ops-token-sha256 <new hash>` (or the
   variable), then restart it.
3. Switch your tools to the new token; the old one fails with `403` on each
   node as it restarts.

</Steps>

Session-signing keys rotate by themselves every `--session-key-rotation-secs`.

## A node is lost

- **App groups** on it keep serving while a majority of each group's replicas
  answers; leaders move within seconds and forwarded calls retry at the new
  leader. Move the lost node's apps to healthy nodes with `ops move` to restore
  their margin.
- **The system group** keeps working while a majority of its voters answers.
  If a majority of the founding voters is lost, sign-ins, installs and
  organization changes stop; there is no route to change the system group's
  voters.
- **Restarting** a node with the same data directory and configuration resumes
  it: it catches up from the leaders.

## Inspect a stopped node

```bash
merod --node n1 inspect                              # the raw layout, sealed sizes
merod --node n1 inspect --storage-key-file k_r.hex   # plus each group's vote, applied index, membership
```

Stop the node first: `inspect` opens the store for writing. The key file holds
K_r as 64 hex characters, which only a development node gives you directly.

## Clean up a development cluster

```bash
merod local --fresh        # start over
rm -rf .merod-local        # or delete its state
```
